# E2-QA1: доказательный отчёт установленного приложения

Дата: 02.10.2026. Исполнитель: Кодекс (Джарвис).

Область: E2 — снятие десятиминутного запрета повторной погрузки после разгрузки, сохранность очереди и однократность эффекта после восстановления связи.

## 1. Итог

На отдельном физически установленном диагностическом APK и изолированном backend точного candidate SHA функциональная часть E2-QA1 прошла:

- обычный самосвал повторно погружен значительно раньше 10 минут после завершения предыдущего рейса;
- офлайн-погрузка пережила принудительное закрытие и повторный запуск того же приложения, затем дошла с прежними `event_id` и `occurred_at`;
- при потере ответа уже после серверного commit повтор той же записи завершился как `deduplicated` с прежними receipt/trip ID;
- во всех трёх основных сценариях остался ровно один `OfflineFieldEvent`, один `TripClientAction` и один `Trip` для Y;
- в отобранных client/server-доказательствах отсутствует `post_unload_cooldown`.

Вердикт исполнителя: **PASS функциональной цепочки повторной погрузки Y / PARTIAL по полному критерию E2-QA1**. Реальная Driver-unload provenance для X — `NOT_RUN`; отдельный PNG состояния Q3 до повторной отправки — `NOT_CAPTURED`. Это не решение о merge и не приёмка release владельцем. Остальные ограничения перечислены в разделе 8.

## 3. Изолированный стенд и реальный жест

Backend exact SHA работал на `127.0.0.1:18461`; тестовый HTTP fault proxy — на `18460`; TLS bridge — на `18462`. Телефон получал только этот loopback через адресный `adb reverse tcp:18462 tcp:18462`. TLS и hostname проверялись штатно; обход доверия сертификату не применялся.

Для диагностического профиля отдельно разрешён только `https://e2qa.localhost.direct:18462/`. Эта узкая build-time дельта приложена как patch и отсутствует в PR №149.

Погрузка выполнялась жестом установленного приложения: `adb shell input swipe` от центра обычной карточки к видимой зоне `[data-eo-dump-target]`. Прямой вызов `enqueue`, `fetch` или серверного обработчика вместо жеста не использовался.

Использованы обычные QA-самосвалы `QA-T-01` — `QA-T-04`; особый `ТЕСТ-1`, manual/replace и свободный ковш не использовались.

`prepare_excavator_qa` создаёт или повторно использует открытую водительскую смену для каждого обычного QA-самосвала (`trips/qa_simulator.py:416-432` на candidate SHA). Это подтверждено кодом и работой сценариев, но отдельный DB-снимок водительских смен в доказательный пакет не сохранялся.

### Q1

После завершения X та же обычная карточка была доступна. Свайп создал Y; сервер сохранил один receipt/action/trip. Устройство пометило часы как требующие коррекции, поэтому raw `occurred_at` сохранён в квитанции, а `Trip.loaded_at` взят из первого серверного приёма (`load_time_source=server_receipt`).

Дополнительный визуальный цикл Q1-V выполнен на `QA-T-04`, `truck_id=5`:

- X: event `excavator-load-c2d201f2-af47-4e49-a179-eb19e469d275`, trip `7`, затем `completed_at=05:56:16.064303Z`;
- до Y карточка показана обычной `НАЗНАЧЕНА`, без затемнения и отсчёта cooldown;
- Y: event `excavator-load-992717f4-d77b-4a57-b7be-5ab2ba487594`, trip `8`, tap `05:56:43.970Z`;
- между завершением X и tap Y — `27.905697 с`; после жеста карточка показана `НА РАЗГРУЗКУ`;
- для каждого события — по одному receipt/action/trip.

Q1-V — отдельный подтверждающий цикл, а не кадры исходного события Q1.

### Q2

Связь с backend была полностью убрана удалением только адресного reverse `18462`. После жеста на экране появилось `СОХРАНЕНО НА ТЕЛЕФОНЕ`, а в IndexedDB осталась исходная запись. До reconnect сервер не имел ни receipt, ни action, ни trip.

Приложение было принудительно закрыто и снова запущено без возврата связи. Кэш v264 открылся, показал `Ожидает отправки 1`, а очередь сохранила тот же `event_id`, `occurred_at`, sequence и truck. После восстановления reverse сервер принял одну запись, очередь очистилась. Здесь `Trip.loaded_at=05:39:03.846Z` точно совпал с tap, `load_time_source=excavator_device`.

Дополнительный визуальный цикл Q2-V выполнен на том же `QA-T-04` после завершения trip `8`:

- Y: event `excavator-load-4cc54f5a-70b7-4be5-bf02-7e7fbb912194`, tap `05:57:55.568Z`, sequence `9`;
- кадры фиксируют `СОХРАНЕНО НА ТЕЛЕФОНЕ`, сохранение состояния после offline restart и `НА РАЗГРУЗКУ` после reconnect;
- до reconnect сервер: `0/0/0`; после: receipt/action/trip `9/9/9`, `1/1/1`;
- `Trip.loaded_at` равен исходному tap, доставка задержана на `91.651087 с`;
- между завершением X и tap Y — `31.748098 с`.

Точная сохранность одного и того же локального конверта после restart доказана основным Q2 JSON. В Q2-V отдельный CDP JSON после restart не сохранён; его кадр доказывает видимое сохранённое состояние, а DB-файлы — отсутствие/появление единственного серверного эффекта.

### Q3

Одноразовый fault proxy пропустил POST в Django, полностью дочитал upstream `200`, записал SHA-256 ответа и затем уничтожил соединение между proxy и TLS bridge. TLS bridge при этом upstream error формирует клиенту HTTP `502`; следовательно, доказана потеря принятого ответа после server commit, но не «тихий» end-to-end socket drop до телефона. Accepted-подтверждение клиент не получил. К этому моменту в БД уже существовали ровно один receipt, action и trip.

После этого proxy восемь раз намеренно отвечал `503` на тот же envelope. Приложение было принудительно закрыто и перезапущено; в IndexedDB сохранились исходные `event_id`, `occurred_at`, sequence и truck. После release-файла следующий запрос с тем же ID прошёл, клиент получил `deduplicated`, прежние `event_receipt_id=6` и `trip_id=6`, очередь очистилась. DB-снимки до и после имеют одинаковый SHA-256 и по-прежнему `1/1/1`.

## 5. Временные данные

Проверка не подменяет разные временные источники одним правилом:

- `OfflineFieldEvent.occurred_at` во всех сценариях сохраняет время жеста телефона;
- Q1/Q3 были отправлены live, но сервер отметил коррекцию часов; effective `Trip.loaded_at` и `load_time_source` — `server_receipt`;
- Q2 после offline restart сохранил исходный tap как `Trip.loaded_at`, источник — `excavator_device`;
- повторы Q3 не изменили `occurred_at`, `received_at`, `loaded_at`, receipt ID или trip ID.

## 6. Экран и очередь — отдельные доказательства

- Серверное принятие подтверждено DB-снимками, а не только текстом карточки.
- Сохранность очереди подтверждена IndexedDB-проекцией до/после restart.
- Обновление экрана подтверждено отдельными DOM-снимками и PNG; оно не используется как замена receipt/action/trip.
- Отсутствие дублей подтверждено числом строк по устойчивому `event_id` и `TripClientAction.client_action_id`.

## 8. Границы результата

1. Завершение X выполнял изолированный `run_excavator_qa_tick()`, который вызывает `finalize_trip_unloaded` и создаёт серверное завершение с источником QA-симулятора. Реальная водительская unload-квитанция/action здесь не проверена: `NOT_RUN`.
2. Для Q1/Q2 опубликованы отдельные безопасные визуальные циклы Q1-V/Q2-V. Для Q3 опубликован финальный кадр и DOM-снимок pending-состояния, но отдельного PNG до повторной отправки нет: `NOT_CAPTURED`. Функциональная цепочка Q3 подтверждена proxy/client/DB.
3. Проверка выполнена на одном Infinix, отдельном debug package и синтетической PostgreSQL БД. Общий RuStore QA и production не затрагивались.
4. Q2 доказал запуск кэшированной оболочки при полностью отсутствующем backend в этой конфигурации. Это не закрывает общий дефект OFF-C1 запуска при продолжающем молчать TCP listener и не переносит OFF-C1 в E2.
5. В PR №149, release и production ничего не внесено. Draft PR остаётся без auto-merge. Merge, VERIFY и deploy не выполнялись.

Следующий шаг: Астра проверяет пакет и принимает либо возвращает установленную E2-механику; после этого Координатор повторно сверяет свежий release и выносит владельцу отдельное решение о merge.
