## 2. QA-TRAFFIC-P1-001 — секундный глобальный polling

- для активных рабочих ролей установлен интервал `5 секунд`;
- для наблюдательных ролей установлен интервал `15 секунд`;

  повторы;

- восстановление polling без принудительного reload;

## 3. QA-TRAFFIC-P1-002 — полные HTML GET по широко распространяемым событиям

Статус: **ГОТОВО К ПЕРЕПРОВЕРКЕ**.

Исправление:

- `/realtime/state/` возвращает релевантную событийную дельту в том же
  ответе; клиент больше не выполняет второй GET `/realtime/state/` за
  подробностями тех же событий;
- сервер фильтрует события по роли, сотруднику, доступу, технике и
  связанному производственному комплексу;
- связь техники учитывает действующие смены, `EquipmentAssignment` и
  открытые `HaulAssignment`;
- события изменения сотрудника и доступа получают связанные
  `equipment_ids`;
- для событий с явно заданной областью нерелевантный клиент получает
  продвижение версии без HTML GET;
- узкая same-role область не превращается в глобальную;
- legacy-событие без области обрабатывается консервативно;
- просмотр ограничен первыми 1 000 событиями после клиентского cursor, а
  snapshot ограничен `version <= state_version`, поэтому событие,
  созданное во время ответа, не теряется;
- клиентские Водитель, Машинист, Диспетчер и Горный мастер принимают
  уже отфильтрованные сервером связанные события без повторного
  отбрасывания по более узкому списку.

Адресный фактический proxy-перехват:

| Сценарий Водителя | Короткий state GET | Второй state GET за событиями | Полный HTML GET | Примерный обмен по перехвату |
|---|---:|---:|---:|---:|
| нерелевантное событие другого сотрудника | 1 | 0 | 0 | 1 341 Б |
| релевантное событие своего сотрудника | 1 | 0 | 1 связанный `/driver/` | 42 331 Б |

Состав измерения:

- нерелевантный state: request headers `752 Б`, gzip body `299 Б`,
  response headers `290 Б`;
- релевантный state: `752 + 376 + 290 = 1 418 Б`;
- связанный HTML: `772 + 39 680 + 461 = 40 913 Б`;
- несжатое тело связанного HTML: `225 759 Б`.

Сценарные `5,065 ГиБ` документа 127 здесь не выдаются за фактический
расход. Фактический перехват доказывает ноль HTML GET для нерелевантного
события и ровно один HTML GET только для связанного экрана.

Остаточное ограничение: для релевантного события рабочие PWA пока
получают один полный HTML связанного экрана, а не отдельный малый
серверный фрагмент. Широкое распространение устранено серверной областью
события; дальнейшее выделение фрагментов требует отдельной карточки и
сопоставления всех динамических частей рабочих экранов.

## 6. QA-TRAFFIC-P1-005 — умножение reconcile_due_haul_assignments()

Статус: **ГОТОВО К ПЕРЕПРОВЕРКЕ**.

Исправление:

- дешёвый process-local monotonic gate не допускает повторной проверки
  раньше пяти секунд;
- неблокирующий lock-файл в системной временной папке дедуплицирует
  одновременные worker-процессы одного сервера;
- имя lock содержит безопасный SHA-256 namespace по
  `ENGINE/HOST/PORT/NAME`, поэтому разные QA-базы не используют один
  marker;
- timestamp завершённой попытки хранится в lock-файле и задаёт момент
  следующей разрешённой попытки;
- в базе не создано marker-моделей и не выполняется служебный DML;
- при I/O-сбое lock механизм безопасно деградирует до process-local
  throttle без HTTP 500;
- ошибка самой доменной сверки не маскируется ошибкой финализации lock;
- lock и file handle освобождаются на аварийных путях;
- отдельные транзакции, `Equipment/Employee/Trip` locks и
  идемпотентные повторные проверки существующей доменной логики
  сохранены.

Регрессии подтверждают:

- 100 прогретых realtime GET не выполняют ни одного запроса к
  `assignments_haulassignment` и ни одного DML;
- после интервала выполняется одна read-only due-проверка;
- параллельные потоки не выполняют сверку одновременно;
- настоящий Windows-compatible `spawn` двух Python-процессов выполняет
  фактическую сверку ровно один раз;
- сбой чтения, unlock и записи marker не маскирует исходное доменное
  исключение; handle закрывается также после ошибки чтения или unlock;
- следующий вызов после аварии способен получить lock.

Ограничение: файловый lock координирует процессы одного Windows-хоста.
Для нескольких application-host потребуется отдельный распределённый
scheduler/lock. Такой production-контур в этой задаче не разворачивался.
