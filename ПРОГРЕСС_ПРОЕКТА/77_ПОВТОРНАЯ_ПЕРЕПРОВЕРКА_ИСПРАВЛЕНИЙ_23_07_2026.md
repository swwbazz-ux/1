## 6. Доказательства незакрытых дефектов

### 6.1. `QA-P1-001` — переходящий рейс попадает в KPI после разгрузки

Изолированное воспроизведение выполнено внутри транзакции с последующим rollback:

1. рейс создан за 10 минут до открытия новой смены Диспетчера;
2. пока рейс открыт, KPI новой смены корректно показывает `0`;
3. рейс завершен через 10 минут после открытия новой смены;
4. после завершения KPI новой смены показывает `127 т`.

Фактический результат:

```text
CARRYOVER_CREATED_BEFORE_SHIFT=True
KPI_WHILE_OPEN=0
KPI_AFTER_UNLOAD=127
ROLLED_BACK=True
```

Причина подтверждается в `trips/views.py`: завершенный факт ограничивается `completed_at >= opened_at` новой смены, но не исключает рейсы, созданные или погруженные до нее. Новый тест проверяет только состояние до разгрузки.

Ожидалось: один переходящий ID виден оперативно, но его объем ни до, ни после разгрузки не становится фактом новой смены.

### 6.2. `QA-P1-002-R1` — новый P1-регресс ночного отчета после полуночи

В транзакции время завершения существующего ночного рейса временно перенесено на `01:30 Asia/Vladivostok` следующей календарной даты. Затем вызваны фактические построители транспортного отчета для обеих дат, после чего изменение откатилось.

Фактический результат:

```text
Дата начала ночной смены:
shift_ids=[54,55]
row_trips=1
row_volume=47

Следующая календарная дата:
shift_ids=[]
row_trips=0
row_volume=0

ROLLED_BACK=True
```

Ожидалось для исходного набора: ночная смена производственной даты содержит оба ночных рейса — `2 рейса / 104 м3`.

Причина:

- смены выбираются по `opened_at__date`;
- рейсы выбираются по `completed_at__date`;
- статистика рейса получает ключ ночной смены предыдущей даты;
- строка этой смены на следующей дате отсутствует, и статистика отбрасывается.

Исходное удвоение строк исправлено, но ранее учитываемый завершенный рейс теперь теряется. Поэтому исходный ID получает `REGRESSION`, а конкретное воспроизведение зарегистрировано как дочерний дефект `QA-P1-002-R1`.

## 10. Открытый `QA-RISK-001`

Статус: `NOT RUN / OPEN RISK`.

SQLite и последовательные тесты не доказывают поведение истинно одновременных транзакций. Статический анализ дополнительно показывает непокрытые гонки:

До реального пилота нужны два независимых клиента и штатная тестовая PostgreSQL. Проверить одновременный старт смены, первое назначение, открытие/закрытие простоя, разгрузку и повтор после потери ответа.

## 11. Обязательные исправления до следующей передачи

### 11.1. Переходящий рейс

Сменный KPI должен опираться на доменную принадлежность события к смене, а не только на время завершения рейса. Для погрузки авторитетна `loading_shift`, для разгрузки — `unloading_shift`; временной fallback допустим только для согласованных legacy-записей без этих связей. Отдельно проверить рейс, подготовленный до границы, но фактически погруженный после нее: он должен относиться к фактической смене погрузки.

Обязательный тест:

1. погрузить рейс в старой смене до пересменки и сохранить его `loading_shift`;
2. открыть новую смену;
3. подтвердить KPI `0`;
4. завершить рейс;
5. повторно подтвердить KPI `0`;
6. проверить тот же ID в оперативной истории и правильную сменную атрибуцию.

### 11.2. Ночной транспортный отчет

Смены отбирать по производственной дате `D`, а рейсы относить к строке по фактической `unloading_shift`. Интервал `19:00 D — 07:00 D+1` применять для выбора ночных смен и только как согласованный fallback для legacy-рейсов без `unloading_shift`.

Обязательный тест экрана и Excel:

- ночная смена открыта в `19:00 D`;
- рейс завершен в `01:30 D+1`;
- на производственной дате `D` он присутствует ровно один раз;
- на `D+1` второй копии нет;
- итог ночи совпадает с контрольным оракулом.

### 11.3. Единый временной контракт

В производственных сменных отчетах, планах и соответствующих Excel-выгрузках заменить самостоятельные границы `08/20` и календарное `__date` там, где данные должны относиться к производственным суткам, на единый серверный контракт `Asia/Vladivostok`, `07/19`. Несменные календарные отчеты не изменять без отдельного бизнес-требования.

Обязательные моменты:

- `06:59:59`;
- `07:00:00`;
- `18:59:59`;
- `19:00:00`;
- `23:59:59`;
- `00:00:00`.

Один абсолютный момент проверить из UTC, Самары и Владивостока. Результат роли, отчета и Excel должен быть одинаковым.

### 11.4. Сенсорное закрытие смены

Короткий tap должен самостоятельно открывать подтверждение до подавления синтетического `click`. Long-press и короткий tap не должны вызывать двойное серверное действие.

Обязательная проверка:

- `hasTouch` в Browser QA;
- физический Android;
- короткий tap;
- удержание;
- клавиатурные `Enter` и `Space`;
- ровно одна операция на сервере для каждого подтвержденного действия.

### 11.5. Конкуренция и идемпотентность

Нужны серверные и DB-гарантии для глобальной активной смены, первого назначения и единственного открытого простоя. `client_action_id` должен реально участвовать в идемпотентности.

Обязательный результат параллельного теста: одна запись, один управляемый повтор или конфликт, отсутствие дублей и HTTP 500.
