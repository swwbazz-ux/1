## 1. Итог

Единственный дефект E2-R2-C1 закрыт отдельным code commit поверх принятого в ограниченных границах E2-R1.

- Сервер сохраняет доказанное происхождение снятого отказа через промежуточные предметные, конкурентные и общие временные `RETRY`.
- Повторный успех root переносит основание в `conflict_recovery`; повторный успех ребёнка — в `dependency_recovery`, поэтому сохранённый потомок продолжает причинную цепочку после restart.
- Исходные `event_id`, `occurred_at`, `received_at`, `sequence`, `depends_on`, `payload` и fingerprint не переписываются.
- Разрешение нельзя создать клиентским payload или одним `depends_on`: marker создаёт сервер только из уже доказанного `CONFLICT/post_unload_cooldown` либо из заново проверенной цепочки.
- Снятие десятиминутного cooldown повторно не делалось. Production JS, Driver, оболочки, модели и миграции не изменены.
- PR, merge, VERIFY, deploy и production не выполнялись.

## 2. Узкий diff

Commit меняет три файла: `366 insertions, 10 deletions`.

1. `СИСТЕМА_MVP/backend/core/offline_sync.py`
   - `_removed_refusal_retry_provenance` читает только серверный `result_payload.retry_recovery` и валидирует точный тип, роль, причину, исходный код и корни;
   - `_removed_refusal_retry_payload` сохраняет marker до попытки применения;
   - при каждом повторе сервер заново проходит фактические зависимости и требует равенства вычисленных корней сохранённым;
   - marker переносится через `trip_reference_pending`, `concurrent_state_retry` и `temporary_server_error`;
   - при окончательном `ACCEPTED` внутренний marker заменяется публичным `conflict_recovery`/`dependency_recovery`.
2. `СИСТЕМА_MVP/backend/core/test_offline_sync.py`
   - три адресных server regression для корня и ребёнка через реальные processors.
3. `СИСТЕМА_MVP/backend/static/js/tests/excavator-field-outbox.test.js`
   - restart после принятого через RETRY ребёнка поднимает сохранённого внука без изменения ID/времени.

Production JavaScript не менялся: существующий R1-клиент уже обрабатывал окончательный `dependency_recovery`; R2 закрывает утрату серверного происхождения до этого окончательного подтверждения.

## 3. Красное и зелёное доказательство

До server fix три добавленные Django-регрессии завершались ошибкой отсутствующего `retry_recovery`: промежуточный RETRY действительно стирал основание. Сохранённый excerpt: [django-e2-r2-red-before-fix.log](ПАКЕТ_E2_R2_2026_10_02/raw/django-e2-r2-red-before-fix.log). Клиентская регрессия уже проходила, что локализовало дефект на серверной квитанции, а не на restart-проекции очереди.

После исправления:

### Корень через конкурентный RETRY

- прежний root `CONFLICT/post_unload_cooldown` два раза подряд проходит настоящий endpoint/processor и получает `RETRY/concurrent_state_retry` из `TimeoutError`;
- оба receipt содержат тот же серверный `retry_recovery.reason=removed_refusal`, `original_code=post_unload_cooldown` и точный root ID;
- подмена payload и чужой device получают `event_id_reused`, marker сохранённого receipt не повреждается;
- следующий неизменный повтор root принимается, затем принимаются child и grandchild;
- повтор всех трёх возвращает deduplicated без второго эффекта.

### Ребёнок через общий временный RETRY

- root уже принят с доказанным `conflict_recovery`;
- реальный child processor получает `RuntimeError` в доменной операции и сохраняется как `RETRY/temporary_server_error` с `retry_recovery.reason=removed_refusal_chain`;
- следующий неизменный повтор child принимается с `dependency_recovery`, grandchild затем принимается;
- один receipt и один `TripClientAction` на событие.

### Ребёнок через предметный RETRY

- после принятия root его временно недоступная trip-ссылка даёт child два последовательных `RETRY/trip_reference_pending`;
- marker сохраняется в обоих receipt;
- после восстановления ссылки тот же child и затем grandchild принимаются с исходными ID и временем.

Встроенный отрицательный контур R1 сохранён: чужой actor/access/role/device, изменённый immutable envelope, дополнительная неготовая зависимость и посторонний предметный отказ не получают допуск.

Машинно-читаемая граница: [retry-provenance-contract.json](ПАКЕТ_E2_R2_2026_10_02/raw/retry-provenance-contract.json).

## 5. Уточнение браузерной проверки

Формулировка E2-R1 уточнена без переписывания исходных raw.

Доказано:

- настоящий silent TCP listener на уже открытой PWA-странице;
- настоящий жест и сохранение события в очереди;
- очередь пережила закрытие и повторное открытие вкладки;
- после остановки listener и возврата Django доставлен исходный event с одним receipt/action/trip и сохранённым `loaded_at=occurred_at`.

Не доказано:

- что оболочка после restart становится рабочей, пока listener продолжает принимать и удерживать соединения.

В сохранённом JSON `Page.navigate` получил timeout; оболочка появилась после остановки listener. Исправление startup/hung-fetch относится к OFF-C1, не переносилось в E2-R2. Повторный браузерный прогон только ради этого документального уточнения не выполнялся.

Точные команды подготовки QA-БД, запуска, жеста, restart и снимка БД: [BROWSER_QA_BOUNDARY_AND_COMMANDS.md](ПАКЕТ_E2_R2_2026_10_02/BROWSER_QA_BOUNDARY_AND_COMMANDS.md). Исходные browser/DB raw остаются в пакете E2-R1.
