# 201. Архитектура обязательных проверок CI

Дата: 21.09.2026.

Статус: локально проверено и зафиксировано в технической ветке;
GitHub PR-прогон, push, merge и production deploy ещё не выполнялись.

## 1. Зачем меняется CI

Прежний workflow запускал `manage.py check`, два точечных
JavaScript-теста и только модуль `users`. После оздоровления этого
набора он стал зелёным, но по-прежнему не видел большую часть проекта.

Фактическая инвентаризация на каноническом SHA
`0460e59688198a9fff20e0daab97dc021751a686`:

- обычный Django discovery находит `2841` уникальный тест в `11`
  прикладных модулях;
- ещё `18` чистых unittest-контрактов бенчмарка и CI-матрицы лежат в `tools` и
  не входят в обычный discovery;
- минимум `62` конкурентных и транзакционных теста на SQLite
  пропускаются и требуют настоящий PostgreSQL;
- backend JavaScript: `671` тест, из них `670 PASS` и один штатный `SKIP`;
- mobile shell: `42/42 PASS`;
- один монолитный последовательный SQLite-прогон ранее не уложился в
  `20` минут локального лимита; после разбиения все семь изолированных
  групп завершены последовательно и получили итоговый зелёный результат.

## 2. Обязательный PR-gate

Каждый PR получает один стабильный итоговый status
`Required quality gate`. Он зелёный только если прошли все группы:

1. Структурные и контрактные проверки:
   `manage.py check`, migration guard, `18` tools-тестов, весь backend
   JavaScript и все mobile contracts.
2. Семь изолированных SQLite-групп:
   `users`; `core + trips + downtimes`; `shifts + assignments + references`;
   `reports + portal`; `rotations`; две группы `settlement`.
3. Три critical-группы на PostgreSQL 16:
   полевые операции; `users + reports`; `settlement`.

Группы не запускаются параллельно в одной рабочей папке. Локальная
попытка такого запуска подтвердила конфликты общих временных файлов.
В GitHub Actions каждая matrix-группа получает чистую отдельную машину.

Проверка только «изменённого модуля» не применяется: в проекте пока нет
тегов скорости, а домены связаны общими моделями и миграциями.

## 3. Полный nightly

Отдельный workflow выполняет:

- весь Django discovery последовательно на чистом PostgreSQL 16;
- отдельные tools-контракты;
- все JavaScript и mobile contracts;
- Android unit tests и debug-сборку всех профилей на JDK 21;
- загрузку Django-логов, Android-отчётов и debug APK как артефактов.

В начале workflow имя ветки один раз разрешается в полный неизменяемый
commit SHA. Django, JavaScript и Android jobs получают именно этот SHA, поэтому
один зелёный итог не может случайно объединить проверки разных ревизий.
Внешние GitHub Actions закреплены полными проверенными SHA, а не подвижными
major-тегами.

Плановое время — `18:17 UTC`, что соответствует `04:17`
по Владивостоку. Первая полная приёмка запускается в PR только при
изменении CI-файлов. GitHub принимает `schedule` и ручной
`workflow_dispatch` только когда сам workflow существует в default-ветке
репозитория. Поэтому расписание и ручной запуск из GitHub UI начнут
работать только после переноса workflow в `main`. Такой bootstrap-PR делается
после зелёного слияния кандидата в каноническую release-ветку и синхронизации
нужного quality-baseline в `main`: любой PR обязан проверять собственный merge
SHA, подменять его другой веткой нельзя.

## 4. Защита от неполной матрицы

Единый манифест `.github/ci/django-test-matrix.json` хранит группы.
Скрипт `tools/validate_ci_test_matrix.py` сравнивает их с фактическим
`INSTALLED_APPS`, запрещает shell-метасимволы в test labels и проверяет каждый
найденный `test*.py`. Если в проект добавят новое приложение или тестовый
модуль внутри дробимого приложения и забудут включить его в CI, сам test-plan
станет красным. Backend JavaScript-файлы находятся рекурсивно, поэтому тесты
в будущей подпапке также не выпадут из gate.

## 5. Границы изменения

Расширение gate обнаружило не только устаревшие тестовые fixture, но и реальные
дефекты текущего кода. Локально исправлены: пустой `UPDATE` в частом polling,
недостижимый locked recheck активной роли Экскаваторщика, гонка повторной
активации той же роли, пропавшее предупреждение о ненастроенной вместимости
бака и неверный pinned SHA QA replay-артефакта. Ограничения моделей и доменные
защиты не ослаблялись; миграций, базы, APK и PWA-версий нет.

Работа остаётся в отдельном чистом worktree. Production deploy не выполняется,
поэтому текущие полевые приложения не меняются. Параллельные продуктовые правки
Водителя и Экскаваторщика могут продолжаться в своих ветках; перед будущим
слиянием нужен rebase и проверка пересекающихся файлов `trips/views.py`.

## 7. Критерии приёмки

- Локально проходят matrix guard, Django check, migration guard,
  tools-контракты, backend JavaScript и mobile contracts.
- GitHub принимает оба YAML-workflow и все PR-группы проходят на
  чистых Linux runner.
- Полный PostgreSQL nightly и Android debug-сборки проходят при
  ручном контрольном запуске.
- В branch protection как required check выбран стабильный
  `Required quality gate`.
- После переноса workflow в default-ветку подтверждён хотя бы
  один автоматический ночной запуск.

До выполнения этих пунктов этап не считается завершённым.
