задание и не дает разрешения продолжать оставшиеся карточки.

изменения по четырем карточкам этапа A:

четырех уже подготовленных изменений. Он не возобновляет документ 108.

## 2. Решение по подготовленным изменениям

Подготовленные изменения:

- не откатывать целыми файлами;
- не объявлять исправленными или принятыми;
- три правки заморозить в текущем локальном состоянии, а для `P04-009`
  выполнить только узкое уточнение раздела 3;
- довести только до полного отчета и независимой перепроверки.

Решение по каждой карточке:

| Карточка | Решение |
|---|---|
| `QA-CHAOS-P1-008-R1` | Сохранить как защитный серверный запрет; Механик остается вне первой волны и не считается готовым |
| `QA-CHAOS-P1-P02-016` | Оставить кандидатом в действующее ядро Администратора |
| `QA-CHAOS-P2-P04-006` | Оставить кандидатом в действующие контуры Водителя и Машиниста |
| последовательная `QA-CHAOS-P1-P04-009` | Не принимать в текущем виде: сузить обработку `IntegrityError`, затем оставить кандидатом; настоящая PostgreSQL-конкуренция остается непроверенной |

Защитная правка прав Механика не является вводом, проектированием или
приемкой интерфейса Механика.

## 3. Обязательное уточнение по `P04-009`

Независимый read-only аудит выявил, что подготовленная обертка
`open_excavator_shift()` преобразует любой `IntegrityError` внутри
открытия смены в `equipment_shift_already_open`.

Это может скрыть несвязанный сбой базы данных и показать пользователю
ложную причину. Такая реализация не передается на приемку без минимального
уточнения.

Разрешена только узкая корректировка:

- после отката атомарной операции проверить существующее
  `ShiftClientAction`;
- проверить фактически существующую открытую смену сотрудника или техники;
- преобразовывать ошибку в доменный `409` только при подтвержденном
  конфликте;
- если ни действие, ни конфликтующая смена не найдены, повторно выбросить
  исходный `IntegrityError`, не маскируя его;
- добавить регрессию, подтверждающую, что посторонний `IntegrityError` не
  превращается в ложный конфликт техники.

Нельзя откатывать `shifts/services.py` целиком: файл содержит ранее
принятые изменения. Изменяется только адресная обработка `P04-009`.

## 5. Разрешенный объем завершения этапа A

Чату исправлений разрешено только:

1. сохранить подготовленные правки без расширения;
2. выполнить узкое исправление `P04-009` из раздела 3;
3. повторить точные целевые тесты;
4. выполнить полный Django-набор;
5. выполнить `manage.py check`;
6. выполнить `makemigrations --check --dry-run`;
7. выполнить `git diff --check`;
8. провести Browser QA затронутых состояний на desktop и `390×844`:
   архивный и активно заблокированный сотрудник у Администратора,
   занятая и свободная техника у Водителя, конфликт и обычное начало
   смены у Машиниста;
9. проверить PWA ready, консоль и отсутствие горизонтального overflow;
10. для Механика проверить только серверный запрет прямого POST и отсутствие
   изменяющего действия для простоя Самосвала, не принимая весь его
   интерфейс;
11. повторно подтвердить неизменность рабочей базы и `private_media`;
12. составить отдельный отчет со статусом не выше
    `ГОТОВО К ПЕРЕПРОВЕРКЕ`.

Если любая из этих проверок выявит новый дефект, чат исправлений не
расширяет правку автоматически, а останавливается и включает результат в
отчет.

## 6. Обязательный статус конкурентной проверки

Последовательная обработка `IntegrityError` и обычного конфликта может
быть передана на независимую перепроверку.

До запуска двух настоящих параллельных транзакций на отдельной тестовой
PostgreSQL карточка `QA-CHAOS-P1-P04-009` не может получить полный
`PASS`. Обязательная формулировка:

```text
РЕАЛИЗОВАНО / POSTGRESQL НЕ ПРОВЕРЕНО
```

## 7. Требования к отчету

Отчет должен содержать:

- точный перечень измененных файлов;
- назначение каждого изменения;
- SHA-256 всех измененных и новых файлов;
- команды и фактические результаты целевых и полных тестов;
- результаты Browser QA только разрешенных состояний;
- статус каждой из четырех карточек отдельно;
- явный перечень четырех не начатых карточек;
- подтверждение неизменности рабочей базы и `private_media`;
- подтверждение отсутствия миграций;
- границы непроверенной PostgreSQL-конкуренции.

Рекомендуемое имя отчета:

```text
111_ОТЧЕТ_О_ПОДГОТОВЛЕННЫХ_ИСПРАВЛЕНИЯХ_ЭТАПА_A_26_07_2026.md
```

## 8. Запреты

Без отдельного решения владельца нельзя выполнять:

- дополнительные изменения кода вне четырех карточек;
- создание или применение миграций;
- изменение рабочей базы, `.env` и production;
- commit;
- push;
- deploy.

После получения отчета текущий тестовый чат независимо решает, принять,
отклонить или вернуть на доработку каждую карточку. Только принятые
изменения могут войти в целевой повтор R05 производственного ядра.
