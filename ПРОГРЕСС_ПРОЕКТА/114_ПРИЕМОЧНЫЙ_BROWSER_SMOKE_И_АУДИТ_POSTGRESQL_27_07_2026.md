## 1. Границы проверки

Проверялись только готовые контуры:

- Системный администратор `system-admin-shell-v19`;
- Водитель `driver-mobile-shell-v107`;
- Машинист экскаватора `excavator-mobile-shell-v122`;
- общий PWA/realtime-контракт после временной потери сервера.

Рабочая база, production, `.env`, миграции, deploy, nginx, systemd и
collectstatic не использовались и не изменялись.

## 2. Изолированная среда

Browser QA выполнена на временной копии текущей SQLite-базы.

Для неё временно использовались отдельные:

- SQLite;
- `MEDIA_ROOT`;
- `PORTAL_PRIVATE_MEDIA_ROOT`;
- `STATIC_ROOT`;
- settings-модуль.

Тестовые изменения выполнялись только в этой копии. После проверки:

- сервер остановлен штатным `STOP_SERVER_MVP.bat`;
- порт `8000` свободен;
- временная база и каталоги удалены;
- временный settings-модуль и его `pyc` удалены.

## 3. Системный администратор и настоящий рестарт

Исходное состояние `/system-admin/employees/`:

- viewport `1280 × 720`;
- shell `system-admin-shell-v19`;
- `contractReady=true`;
- `roleActive=true`;
- realtime-экран `system-admin`;
- `48` строк сотрудников;
- `48` draggable-строк;
- `180` скрытых DnD-действий;
- горизонтального overflow нет.

Затем при открытом экране выполнен настоящий цикл:

1. `STOP_SERVER_MVP.bat`;
2. подтверждено освобождение порта `8000`;
3. открытая страница осталась на прежнем URL и сохранила авторизацию;
4. появилась заметная надпись
   `Связь с сервером потеряна. Экран может отставать.`;
5. в изолированную базу добавлен один контрольный сотрудник
   `QA_ACCEPT_114_RESTART_MARKER`;
6. `START_SERVER_MVP.bat` запущен с теми же QA-настройками;
7. открытая страница самостоятельно получила новую версию состояния и
   выполнила штатный reload;
8. после восстановления на экране стало `49` строк и появился контрольный
   сотрудник без ручной перезагрузки.

После восстановления:

- URL и сессия сохранены;
- `stale=false`;
- предупреждение скрыто;
- shell остался `system-admin-shell-v19`;
- `contractReady=true`;
- `roleActive=true`;
- горизонтального overflow нет.

Результат `P13-005`: **PASS в настоящем открытом браузере после
`STOP → START`**.

На `/driver/` подтверждены:

- `roleReadonly=false`;
- realtime-экран `driver`;
- открытый рейс № 9;

Скрытый `client_action_id` разгрузки перед reload:

`trip-unloaded-ff96d9ba-8e27-4c74-a9c5-d8a53b289bc7`.

После настоящего reload:

- рейс остался № 9;
- `client_action_id` остался побайтово тем же;
- авторизация и активная роль сохранились.

Затем при открытом PWA Водителя повторён настоящий цикл
`STOP_SERVER_MVP.bat → START_SERVER_MVP.bat`.

Во время остановки:

- страница не ушла на вход;
- `roleActive=true`;
- показано сообщение о потере связи;
- ID разгрузки не изменился.

После запуска:

- связь восстановилась;
- предупреждение скрылось;
- shell остался `driver-mobile-shell-v107`;
- рейс остался № 9;
- ID разгрузки остался тем же;
- горизонтального overflow нет.

Результат browser-части `P09-003`: **PASS для reload и настоящего
серверного рестарта**.

Исполняемые actual-runtime регрессии документа 113 остаются основным
доказательством потерянного ответа, повторного POST с тем же ID и серверной
идемпотентности. В этой Browser QA рабочий рейс не завершался, потому что
целью была проверка сохранения незавершённого действия через reload и
сетевой рестарт.

## 7. Аудит готовности PostgreSQL

Read-only аудит компьютера показал:

- PostgreSQL-сервер не установлен;
- `psql`, `pg_isready`, `postgres`, `initdb`, `createdb` отсутствуют;
- службы, процесса и слушателя `5432` нет;
- Docker и Podman отсутствуют;
- WSL как подсистема и Linux-дистрибутивы не установлены;
- PostgreSQL-переменные окружения не заданы;
- рабочий `.env` отсутствует;
- Python-драйвер `psycopg 3.3.4` уже установлен и импортируется;
- Django settings уже поддерживает PostgreSQL через
  `DJANGO_DB_ENGINE=postgres` и `POSTGRES_*`.

Всего ожидают настоящий PostgreSQL 14 тестов:

- 3 — непрерывный простой и конкурентное завершение;
- 1 — одновременный старт смены Машиниста;
- 2 — активная роль Диспетчера;
- 8 — терминальная идемпотентность рейса.

Это **не новый дефект приложения**. Проверка не может быть честно объявлена
пройденной без отдельного PostgreSQL 16.

Предпочтительный следующий шаг:

1. получить отдельное разрешение владельца;
2. установить PostgreSQL 16 локально;
3. оставить доступ только через `127.0.0.1`;
4. создать отдельного QA-пользователя и QA-базу;
5. выполнить 14 PostgreSQL-only тестов;
6. не использовать production, рабочую БД и рабочий `.env`.

Альтернатива — выданный отдельный тестовый PostgreSQL 16 с разрешением
Django создавать и удалять только тестовую базу.
