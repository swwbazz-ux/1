| Сценарий | Диспетчер | Горный мастер |
|---|---|---|
| свежая команда при сети | прямой POST; перед отправкой записи в `localStorage` нет; HTTP 200 — MOCK | команда сначала записана в `localStorage`, затем реальная `flushDispatcherSyncQueue()` отправила её; HTTP 200 — MOCK |
| ответ потерян после принятия | MOCK-принятие, сетевой отказ, затем в очередь сохранён тот же payload и тот же `client_action_id`; повтор удалил запись | запись уже была в очереди; после MOCK-принятия и сетевого отказа остались тот же ID, payload и запись, `attempts=1`; повтор удалил запись |
| два первых отправления в обратном порядке | два прямых POST не сериализованы; MOCK-завершение выполнено `B → A` | штатный assignment-путь мастера очередь сериализует; вместо второго независимого элемента команды одного самосвала сливаются |
| перезапуск runtime | созданная после сетевого отказа запись прочитана новым экземпляром и отправлена с тем же payload/ID | запись, созданная до первой отправки, прочитана новым экземпляром и отправлена с тем же payload/ID |
| слияние команд одного самосвала | `post()` не задаёт `coalesceKey`; две аварийно сохранённые команды остаются двумя записями | новая команда заменяет ID и payload старой, но наследует её `createdAt`; следовательно, `createdAt` уже не является временем заменившей команды |

## 3. Трасса данных

### Диспетчер

1. Доска вызывает `dispatcherPost()` для `assign/release`:
   `dispatcher-board-dnd-v1.js:123-128,203-223`.
2. `dispatcher-control-v1.js:69-77` связывает это имя с
   `dispatcherTransport.post`.
3. `dispatcher-transport-v1.js:254-275` создаёт
   `client_action_id = mm-<Date.now>-<random>`, немедленно вызывает `send()` и
   лишь при сетевой ошибке вызывает `enqueue()`.
4. `enqueue()` (`:99-120`) создаёт отдельный локальный `id`, `createdAt` и
   `attempts=0`; `flush()` (`:192-241`) увеличивает `attempts` и повторяет
   сохранённый `request.data`.
5. `send()` (`:123-163`) передаёт JSON только из `request.data`. Локальные
   `id`, `createdAt`, `attempts` серверу не отправляются.

### Горный мастер

1. Assignment-жесты вызывают `dispatcherPostQueued()`:
   `dispatcher_control.html:3157-3172,3506-3512`.
2. `dispatcherPostQueued()` (`:996-1020`) создаёт `client_action_id` и до
   отправки вызывает `enqueueDispatcherSyncRequest()` с
   `coalesceKey=haul-truck-<truck_id>`.
3. Очередь (`:808-829`) хранит `id`, `createdAt`, `attempts`, URL и payload в
   `localStorage` под ключом `mining-master-mobile-sync-queue-v3`.
4. `flushDispatcherSyncQueue()` (`:898-960`) отправляет голову очереди
   последовательно. `sendDispatcherSyncRequest()` (`:831-896`) снова передаёт
   только `request.data`.
5. При загрузке страницы, `online`, `focus`, `pageshow`, возвращении видимости
   и realtime-connect вызывается планирование flush (`:1045-1048,5675-5689`).

Запись в `localStorage` выполняется синхронной заменой всего JSON-массива.
Между вкладками нет CAS/lock; между двумя телефонами хранилища вообще разные.
Поэтому тест одного runtime не доказывает отсутствие потерь при параллельной
записи вкладок или согласование двух устройств.

## 4. Фактические временные опоры

| Кандидат | Где | Ограничение |
|---|---|---|
| `createdAt = Date.now()` | обе очереди | локальные настенные часы; у диспетчера появляется только после ошибки; не передаётся серверу; у мастера после coalesce может принадлежать заменённой команде |
| время внутри `client_action_id` | обе роли | часть непрозрачного ключа идемпотентности, не объявлена временем действия и не сопровождается качеством часов |
| таймаут 12 секунд | оба `send` | только локальный AbortController; не сохраняется и не отправляется |
| `performance.now()` | жесты шаблона мастера, `:5197-5205,6580-6595` | монотонен только внутри жизни страницы; не связан с assignment payload и не сохраняется |
| `operational-state-version` | `sessionStorage`, `:1085-1110` | версия состояния, не время команды; исчезает вместе с сессией браузера |
| `dispatcherRealtimeLastSuccessAt` | память страницы, `:5681` | локальное время успешной связи; не связывается с командой и не сохраняется в её записи |
| серверное время доски диспетчера | `dispatcher-control-v1.js:25-45` | применяется только к сроку маркеров «Свободного ковша»; assignment-транспорт его не читает |

Итог: релизный формат передаёт устойчивый `client_action_id`, но не передаёт
доказательство времени нажатия. Ни `createdAt`, ни порядок отправки, ни таймаут
не могут служить таким доказательством.

## 5. Минимальная граница старого и нового формата

Граница должна определяться содержимым самой записи, а не способом доставки.
То есть один новый формат обязателен и для прямого диспетчерского POST, и для
онлайн-очереди мастера.

| Состояние записи | Минимальная классификация | Допустимое действие до отдельного утверждения алгоритма |
|---|---|---|
| нет явного `command_format_version` | `legacy` | принять как старую команду; не выводить время действия из `createdAt`, ID или порядка прихода |
| новая версия и есть проверяемая опора | `versioned/anchored` | хранить неизменяемый ID, payload и саму опору до первой сети; повторять без изменения; применять только утверждённый способ вычисления интервала |
| новая версия, но опоры нет | `versioned/unanchored` | явно сохранить отсутствие опоры; не маскировать его временем получения или локальным `createdAt` |
| новая версия, свидетельства противоречат друг другу | `versioned/contradictory` | сохранить все свидетельства и факт противоречия; не выбирать победителя скрытым правилом транспорта |

Минимальные поля новой записи: явная версия формата, неизменяемый
`client_action_id`, неизменяемый исходный payload и отдельный блок
`time_evidence` со статусом (`anchored/unavailable/contradictory`) и данными
опоры. Счётчик попыток и транспортные timestamps должны оставаться отдельными
от факта действия. До первой отправки такая запись должна быть долговечной у
обеих ролей. Coalesce допустим только как создание новой команды с новой
временной записью, а не как перенос старого `createdAt` на новый payload.

Это предложение границы формата, не реализация и не утверждение механики.

## 6. Что не доказано

- PostgreSQL/Django и реальное серверное idempotency-применение: **NOT_RUN**;
- браузерная DOM-отрисовка и достижимость двух быстрых жестов: **NOT_RUN**;
- установленное приложение диспетчера/мастера: **NOT_RUN**;
- сохранение WebView/localStorage после реального kill, перезагрузки ОС,
  обновления или переустановки: **NOT_RUN**;
- поведение двух телефонов и сбитых часов устройства: **NOT_RUN**.

Проверено только поведение функций JavaScript с управляемыми сетью, временем и
`localStorage`. PR №106, PR №120, release и production не изменялись; merge и
deploy не выполнялись.
