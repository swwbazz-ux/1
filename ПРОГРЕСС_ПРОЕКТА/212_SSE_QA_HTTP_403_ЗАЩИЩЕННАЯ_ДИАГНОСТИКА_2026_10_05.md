# SSE QA: защищённая диагностика HTTP 403 за цикл 05.10.2026

## Причина этапа

Единственный QA-цикл с временным `/32` завершился до сценариев 2–4: настоящие
оболочки Водителя и Машиниста экскаватора получили HTTP 403 от nginx. QA затем
штатно выключен, временный allowlist возвращён в исходное состояние, HTTPS
inspect подтвердил `qa=disabled`, `nginx_limit_fix=applied` и
`allow_cidr_swap=none`.

Повторный подбор адреса через внешний echo-сервис запрещён. Следующий шаг —
установить фактическую причину по уже существующим QA-журналам.

## Фиксированный диагностический контракт

Добавлена одноразовая параметр-free операция `sse_qa_http_403_v1` режима
`diagnose`. Она:

- читает только `/srv/sse-qa/log/nginx-error.log` и
  `/srv/sse-qa/log/nginx-access.log`;
- использует только окно `2026-10-05 09:49:00–10:09:59 UTC`;
- рассматривает только `GET /driver/` и `GET /excavator/work/` со статусом 403;
- сопоставляет client IPv4 из access/error строк, точную nginx-причину
  `access forbidden by rule` и защищённый отпечаток `/32`, фактически
  применённого в этом цикле;
- при неподтверждённом nginx allowlist-denial читает только фиксированный
  `journalctl` сервиса `sse-qa-wsgi.service` за то же окно;
- не запускает QA, nginx, приложение или БД и ничего на сервере не изменяет.

Адреса и защищённые канонические строки попадают только в CMS-артефакт,
зашифрованный отдельным сертификатом этого этапа. В workflow-лог разрешены только
enum-причина, булевы сравнения, ограниченные счётчики и статусы источников.

## Локальная проверка

На точных байтах кандидата пройдены:

- release protocol: `69/69`, один ожидаемый Windows skip;
- HTTPS controller: `67/67`, три ожидаемых platform skip;
- HTTPS release protocol: `25/25`;
- seed-fix: `11/11 + 20/20 + 6/6`;
- Firebase validator: `6/6`;
- `py_compile`, YAML parse и `git diff --check`.

Покрыты оба результата сравнения: один общий адрес обеих ролей и разные адреса.
Проверено, что Basic username, query, referer, user-agent и адреса не появляются
в открытом envelope/workflow-выводе.

## Текущий статус

Локальный кандидат готов. До получения фактических журналов ещё обязательны PR,
CI/CodeQL, слияние в каноническую control-ветку, повторные проверки merged SHA,
`verify_receiver`, `update_receiver` и один read-only `diagnose`.

Если журнал подтвердит один общий IPv4 обеих ролей и точный отказ allowlist,
разрешён один следующий QA-цикл с этим наблюдавшимся адресом. При разных адресах
или другой причине нового enable выполнять нельзя.
