## 3. Как читать боевой телефон по USB (это главный инструмент, без него сегодня ничего бы не нашлось)

- `adb` на машине не установлен; `platform-tools-latest-windows.zip` (~8 МБ, dl.google.com) распаковать в любую папку. Пользователь разрешал скачивание.
- Под Git Bash обязательно `MSYS_NO_PATHCONV=1` перед `adb shell … /sdcard/…`, иначе пути ломаются.
- APK не debuggable: `run-as` и DevTools недоступны. **Но консоль WebView попадает в logcat** как `I/Capacitor/Console(pid): File: … - Msg: …` — любой `console.info` в коде экрана читается так: `adb logcat -v time --pid $(adb shell pidof ru.copperresources.driver)`.
- Нативные HTTP-запросы службы видны как `CapacitorCookies: Getting cookies at: <url>`; JS-`fetch` страницы в logcat НЕ виден.
- Уже включённые строки: `driver-refresh-deferred … busy=…`, `driver-fragment ok/fail … ms=…`, `driver-outbox pending=… review=… […]`.
- Экран: `adb shell screencap -p /sdcard/x.png` + `adb pull`; дерево элементов: `adb shell uiautomator dump /sdcard/ui.xml` (скрытые элементы в дамп не попадают).
- Вибрация: `adb shell dumpsys vibrator_manager` — каждый вызов с длительностью и `scale`; `scale: 0,00` = телефон глушит (системная настройка «Виброотклик при касании» выключена: `settings get system haptic_feedback_enabled`). Уровень в приложении тут бессилен.
- Холодный перезапуск: `adb shell am force-stop ru.copperresources.driver && adb shell monkey -p ru.copperresources.driver -c android.intent.category.LAUNCHER 1`.
- Замеры во время СОБСТВЕННЫХ выкладок не годятся: перезагрузка оболочки искажает время.

## 4. ЗАДАЧА: push-канал (FCM) + нативный виброотклик — одна новая сборка APK

### 4.1. Зачем
Сейчас экран узнаёт о событии опросом (0,3–2 с на переднем плане, до 10 с в фоне). Пользователь хочет, чтобы **сервер сам стучался в приложение**. Одновременно веб не умеет задавать силу вибрации (только длительность) — нужна нативная вибрация с амплитудой. Обе вещи требуют пересборки APK всем водителям, поэтому делаются вместе.

### 4.2. Что должно получиться (критерии приёмки)
1. При событии для водителя (погрузка, назначение, снятие, свободный ковш) сервер отправляет FCM-сообщение на все его активные устройства **в той же транзакционной точке, где сейчас зовётся `notify_employee` (`trips/views.py` ~5099, `assignments/services.py` ~1760, `users/push_views.py`)** — единая функция, которая шлёт и web-push (браузер), и FCM (приложение).
2. Приложение при получении push **немедленно запускает тот же нативный heartbeat** (`ConnectivityForegroundService.scheduleHeartbeat(0L)`) — не отдельную логику: события, озвучка и `native-connection-state` для JS остаются как есть. Так push не дублирует голос и не обходит дедупликацию (`already_announced`).
3. Push — **пустой data-сигнал** (без текста), как у существующего web-push: текст берётся с сервера в ответе `/realtime/state/`. Никаких секретов в payload.
4. Опрос остаётся страховкой: нативный интервал можно поднять с 10 до 30 с ТОЛЬКО после того, как push подтверждён на бою минимум сутки. В первой сборке интервал не трогать.
5. Нативный виброотклик: плагин `Haptics` (собственный, в `BackgroundConnectionPlugin` или отдельный `NativeHapticsPlugin`) с методом `vibrate({pattern, amplitude})` на `VibrationEffect.createWaveform` с амплитудами и **usage не TOUCH** (`VibrationAttributes.USAGE_MEDIA` или `USAGE_HARDWARE_FEEDBACK`), чтобы не зависеть от системной настройки «виброотклик при касании». В JS `driver-haptics-v1.js`: если `window.Capacitor.Plugins.NativeHaptics` есть — звать его (уровень → амплитуда 90/160/255 + те же длительности), иначе — как сейчас `navigator.vibrate`. Уровень и кнопки на вкладке «Смена» остаются.
6. Замер на телефоне пользователя по USB: время `DriverVoicePlayer queued` (или строки push-приёмника в logcat) относительно момента погрузки на экскаваторе и `driver-fragment ok` — цель ≤1 с при свёрнутом приложении и погашенном экране.
7. Все существующие тесты — те же числа (см. п. 0). Новые тесты: серверная отправка FCM (мок HTTP), регистрация/деактивация токена, JS-маршрутизация вибрации в нативный плагин при его наличии.

### 4.2a. Доставщик push должен быть СМЕННЫМ: FCM сегодня, RuStore Push — запасной (решение пользователя 20.09.2026)

Приложение самодельное и не в Google Play; телефоны водителей — российские Xiaomi с сервисами Google (на них FCM работает), но зависимость от Google для России — риск «однажды перестанет». Поэтому канал строится так, чтобы поставщик менялся без переделки сервера и экрана:

- **На сервере** модель `NativePushDevice` получает поле `provider` (`fcm` | `rustore`, позже `hms`), токен уникален в паре с провайдером. Отправка — через одну точку `native_push.notify_employee_devices(employee, kind, version)`, внутри — по провайдеру: `fcm` → FCM HTTP v1; `rustore` → RuStore Push API (`https://vkpns.rustore.ru/v1/projects/<project_id>/messages:send`, авторизация сервисным токеном из кабинета RuStore Console; формат сообщения тот же по смыслу: `data` без текста). Ключи обоих — только в `.env`, в git не класть. Настройки: `NATIVE_PUSH_PROVIDERS` (какие включены), при недоступности одного провайдера второй не страдает.
- **В оболочке** одна точка входа для JS: `notifyListeners("pushToken", {provider, token})` и одна реакция на входящий сигнал — `ConnectivityForegroundService.scheduleHeartbeat(0L)` — независимо от того, кто доставил. Первая сборка: FCM (`@capacitor/push-notifications` или свой `FirebaseMessagingService`). Вторая, по решению пользователя: RuStore Push SDK (`ru.rustore.sdk:pushclient`, документация на русском: https://www.rustore.ru/help/sdk/push-notifications) — он требует, чтобы на телефоне стояло приложение RuStore, и чтобы приложение было опубликовано в RuStore (профили `driver_rustore*` в `mobile/capacitor-shell/profiles/` уже есть). У RuStore есть и «Universal Push» SDK, который сам выбирает FCM/HMS/RuStore — рассмотреть, если не усложняет сборку.
- **Поведение при отказе**: если ни один провайдер не доставил — ничего не ломается, экран живёт на опросе (2 с спереди, нативный пульс сзади). Это и есть страховка, её не убирать.
- **В JS экрана** (`driver-native-push-v1.js`) регистрация токена не знает о провайдере ничего, кроме его имени в payload.

Для пользователя это означает: сначала 15 минут на проект Firebase (у него есть аккаунт Google), а кабинет RuStore — когда/если понадобится второй канал.
