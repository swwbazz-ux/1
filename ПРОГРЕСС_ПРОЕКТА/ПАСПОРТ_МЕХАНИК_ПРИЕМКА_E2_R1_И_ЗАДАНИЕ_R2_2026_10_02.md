Кандидат: f7936b9f83db0160dcc9070c1b2565d82fb6bc57.

## Решение

Снятие cooldown и восстановление обычной цепочки root→child→grandchild сохраняются. Сравнение Driver baseline принято. Кандидат целиком пока не принят: один блокирующий дефект сохранности основания повторной обработки при промежуточном RETRY. Единственное новое поручение — E2-R2 ниже.

Это адресное чтение кода, тестов, отчёта и опубликованных журналов. Астра не повторяла Django/браузер/PostgreSQL/телефон. Указанные PASS — результаты автора; собственный новый runtime PASS не заявляется. Производственные правила не меняются.

## Что закрыто

- Сервер проверяет неизменность конверта до допуска; цепочка ограничена actor/access/role/device/sequence и точным прежним cooldown. Маркеры принятого корня и принятого ребёнка позволяют обычной последовательности продолжиться.
- Клиент использует сохранённые confirmations после удаления принятого root из очереди.
- Добавленные тесты проверяют успешную цепочку, раннего ребёнка, дополнительный посторонний конфликт, изменённый payload и чужое устройство при повторе.
- Raw Django заканчивается Ran 290 / OK; это не проверка всех возможных переходов восстановления.
- Driver baseline: в обоих raw f1b144e8/efb39c9a один и тот же тест, строка 282, TypeError, 15/16. Замечание E2-R1-C3 закрыто в этих границах. Новый Driver UI-ремонт в E2 не нужен.
- Свежая основа уже содержит #145/Driver v375. Изменения Driver относительно старого E2 принадлежат release-основе, а не четырём файлам R1.

## E2-R2-C1 — основание восстановления теряется через RETRY (блокирует)

Код: core/offline_sync.py, process_one_offline_event, _removed_refusal_result_roots, _removed_refusal_lineage.

Минимальная трасса, часы исправны:
1. В БД root R = CONFLICT/post_unload_cooldown, ребёнок C = CONFLICT/dependency_rejected, C.depends_on=[R].
2. Повтор R получает recoverable_removed_refusal=True.
3. В обработчике R происходит временный сбой, например TimeoutError. Внутренняя транзакция откатывает эффект; внешний обработчик сохраняет R=RETRY/concurrent_state_retry. result_payload заменён только server_received_at.
4. Повтор R после устранения сбоя разрешён как RETRY, но recoverable_removed_refusal=False: прежнего кода и маркера уже нет. R успешно ACCEPTED без conflict_recovery.
5. Повтор C: _removed_refusal_lineage на принятом R возвращает valid=True, roots=empty. Собственного clock skew и clock-skewed dependency нет. Допуск C не открыт, возвращается прежний dependency_rejected.

Тот же провал на середине: R уже принят с маркером → C допущен по цепочке → временный RETRY → C принят без dependency_recovery → ранее отклонённый G не восстанавливается. Проверки R1 этого перехода не покрывают.

Требование:
- Сохранить доказанное сервером происхождение восстановления до попытки применения и через все временные результаты RETRY. Повторный успех обязан перенести его в receipt/квитанцию для потомков.
- Обработка обычных успешных событий/ACCEPTED/no_effect не переоткрывается. Клиентский payload или depends_on сами по себе не являются разрешением.
- Не расширять допуск на посторонние предметные отказы. Не переносить чужие object ID/полномочия; сохранить проверки identity и всех зависимостей.
- Не менять исходные event_id, время, sequence, depends_on, payload. Не заменять исправное время ребёнка временем корня или приёма.
- Учитывать повторяемый предметный RETRY (например, временно отсутствующая ссылка), конкурентный RETRY и temporary_server_error. Доказательство происхождения не должно исчезать при перезаписи result_payload. Механизм выбрать узкий; новые модели/миграции не требуются по умолчанию.

Адресные красные/зелёные Django-регрессии:
а) временный сбой R при восстановлении → отдельный следующий запрос R → C → G;
б) R принят → временный сбой C → отдельный следующий запрос C → G;
в) потерян ответ принятия после такой цепочки → dedup без повторного эффекта;
г) исходные отрицательные проверки сохраняются: чужой владелец/устройство, подмена конверта, дополнительная неготовая зависимость, посторонний отказ.
Проверять не только status, но и собственное время, наличие серверного происхождения после RETRY/ACCEPTED, один receipt и один эффект на событие. Добавить клиентский тест: подтверждённый восстановленный предок после RETRY удалён из очереди, restart поднимает сохранённого потомка. Серверный прогон — настоящий processor, не mock send.

## Уточнение браузерной приёмки — без расширения E2 на весь OFF-C1

silent-port-browser-qa.json прямо сообщает:
Page.navigate timed out; оболочка показалась после остановки silent listener.

Принимаются опубликованные наблюдения в узких границах:
- настоящий молчащий TCP listener и жест на уже открытой странице;
- сохранность очереди через закрытие/открытие вкладки;
- после устранения зависшего соединения и возврата Django один receipt/action/рейс;
- loaded_at=occurred_at=00:17:05.756Z, приём позже.

НЕ принимается общий PASS «после перезапуска приложение работает при продолжающейся зависшей сети»: такого результата нет. Начальный отчёт §5 сокращает важное условие из JSON. Исправить формулировки отчёта/прогресса отдельным дополнением, исходные raw не переписывать.

Зависание старта зарегистрировать в существующей приёмке OFF-C1-R1, не чинить service worker внутри E2-R2 и не переносить весь OFF-кандидат. Оно остаётся ограничением общей автономности и требует проверки на итоговом OFF SHA с неостановленным listener. Сам E2 не объявлять решением всей офлайн-механики.

Для воспроизводимости E2 сохранить точные команды подготовки изолированной QA-БД/запуска, способ браузерного жеста, перезапуска и снимка БД. Не нужен повтор всего браузерного прогона только ради нового заголовка отчёта.

Выполнить адресные регрессии и обязательные gates затронутого контура по AGENTS.md; широкий повтор проверок только если появился конкретный риск. PostgreSQL и физический APK остаются NOT_RUN, пока реально не выполнены. Не называть весь suite зелёным при известном Driver baseline fail.

Вернуть SHA кандидата, release-base, узкий diff, команды и raw, результаты отрицательных тестов и границы. Shell-номер самовольно не менять; общий выпуск и совместимость v264 с OFF остаются за координацией.

PR/merge/VERIFY/deploy не выполнять. Production, PR №106/№120/№145 и OFF-C1-R1 не изменять. Эта рецензия не является разрешением выпуска.
