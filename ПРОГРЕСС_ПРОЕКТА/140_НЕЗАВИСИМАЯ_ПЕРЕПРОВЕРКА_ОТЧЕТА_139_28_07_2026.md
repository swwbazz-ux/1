### 5.1. QA-TRAFFIC-P2-002-R1 — потеря приза при truncated delta

Файл:

- `templates/includes/achievement_prize.html`, функция
  `matchingAchievementEventKey()`.

При `context.eventsTruncated=true` завершивший рейс может не попасть в
ограниченный список `context.events`. Текущий код:

1. проверяет только фактически пришедшие события;
2. не находит matching completion;
3. выполняет `0` achievements GET;
4. realtime принимает полную новую версию;
5. усечённая дельта больше не возвращается.

В результате приз может быть пропущен до следующего рейса или перезагрузки.
Текущая JavaScript-регрессия ошибочно закрепляет нулевой GET для этого
сценария.

Требуется:

- при `eventsTruncated=true` выполнять ровно один catch-up achievements
  GET для Водителя или Машиниста с действующей сменой и техникой;
- объединять его с pending initial/relevant check;
- не возвращать периодический polling;
- после принятия новой версии не терять pending catch-up.

### 5.2. QA-TRAFFIC-P2-002-R2 — нет ограниченного восстановления после ошибки

Файл:

- `templates/includes/achievement_prize.html`, функции
  `runPendingAchievementCheck()` и `scheduleAchievementCheck()`.

Если единственный initial или qualifying GET завершился HTTP/network
ошибкой:

- ключ сохраняется в `failedAchievementCheck`;
- повтор того же ключа блокируется;
- восстановление возможно только после `visibilitychange`.

При постоянно видимой вкладке и отсутствии следующего рейса unlock может
не создаться и не показаться.

Требуется:

- добавить ограниченный retry/backoff только после фактической ошибки;
- сохранить single-flight и один pending key;
- поддержать online/connection recovery;
- не возвращать постоянный двадцатисекундный polling;
- при hidden не выполнять GET, а на visible сделать ровно один catch-up;
- тест hidden catch-up должен требовать конкретный ожидаемый счётчик,
  а не проходить при `0` через условие `<= 1`.

## 6. QA-TRAFFIC-P2-003 — три остаточных race-дефекта

Основная трафиковая часть исправлена:

- в production-коде трёх PWA нет `?version_check`;
- стабильная shell-версия не вызывает автоматический full-SW GET;
- `role_shell_version` используется общим guard;
- повтор одной серверной версии не создаёт повторный controlled update;
- fragment rebind Водителя не добавляет повторную регистрацию и
  `controllerchange`;
- версии `v111`, `v124`, `v117` согласованы;
- стабильное proxy-окно подтвердило `?version_check=0`.

Но карточка пока не может получить PASS.

### 6.1. QA-TRAFFIC-P2-003-R1 — auto/manual update не имеют общего single-flight

Файл:

- `templates/base.html`, функции `requestControlledUpdate()` и
  `requestManualUpdate()`.

Автоматический update хранится в `automaticUpdatePromise`, ручной — в
отдельном `manualUpdatePromise`. Если пользователь нажмёт ручную проверку
во время controlled update новой `role_shell_version`, возможны два
одновременных `registration.update()`.

Требуется:

- один общий update-flight на одну регистрацию и target shell;
- ручной путь должен присоединяться к уже выполняющемуся controlled
  update;
- при двойном trigger фактический `registration.update()` должен быть
  ровно один.

### 6.2. QA-TRAFFIC-P2-003-R2 — запоздавший worker может откатить contract-state

Файл:

- `templates/base.html`, функции `requestWorkerVersion()` и
  `acceptServiceWorkerVersion()`.

Ответ `GET_VERSION` принимается без generation/token и без проверки
идентичности актуального worker. После `waiting → active →
controllerchange` запоздавший ответ старого worker способен снова записать
старую версию и оставить экран в contract-lock.

Требуется:

- привязать запрос версии к worker identity и generation;
- игнорировать ответ worker, который больше не является ожидаемым
  controller/active/waiting;
- после controllerchange явно считать версию текущего controller;
- delayed stale response не должен менять готовое состояние.

### 6.3. QA-TRAFFIC-P2-003-R3 — stale waiting race у Машиниста и Горного мастера

Файлы:

- `templates/trips/excavator_work.html`,
  `inspectWaitingWorker()`;
- `templates/trips/dispatcher_control.html`,
  `inspectMiningMasterWaitingWorker()`.

Водитель после асинхронного `GET_VERSION` повторно проверяет, что worker
всё ещё является `registration.waiting` и не был активирован.
Машинист и Горный мастер такой повторной проверки не выполняют.

Запоздавший ответ может:

- повторно показать устаревшие badge/modal;
- сохранить worker, который уже стал controller;
- разрешить повторный `SKIP_WAITING`.

Требуется:

- после каждого await/Promise повторно проверять
  `registration.waiting === inspectedWorker`;
- не принимать controller и уже активированный worker как waiting;
- иметь activation-generation либо identity guard;
- delayed stale ответ должен дать `0` badge/modal и `0` повторных
  `SKIP_WAITING`.

## 7. Обязательные новые регрессии

### 7.1. Достижения

- `eventsTruncated=true`, matching completion отсутствует в доставленном
  списке: ровно один catch-up GET;
- truncated burst + initial: суммарно один GET;
- qualifying GET с HTTP/network ошибкой: ограниченный retry;
- несколько recovery-событий во время retry: один in-flight GET;
- hidden: `0` GET, visible: ровно один pending catch-up;
- successful retry сохраняет unlock/show/close/shown;
- 12 стабильных часов без событий: периодический GET равен `0`.

### 7.2. PWA update

- automatic update в процессе + ручная кнопка: один
  `registration.update()`;
- delayed ответ старого active/waiting worker после controllerchange:
  contract-state не откатывается;
- delayed waiting worker Машиниста: badge/modal `0`;
- delayed waiting worker Горного мастера: badge/modal `0`;
- повторный `SKIP_WAITING` для уже активированного worker: `0`;
- тесты должны исполнять настоящий общий `AppPwaContractGuard` вместе с
  настоящими role-runtime, а не только проверять строки исходника.

Поскольку меняется общий `templates/base.html`, после доработки нужен
минимальный Browser smoke всех восьми готовых PWA, а полный responsive
Browser QA обязателен для Водителя, Машиниста и Горного мастера.
