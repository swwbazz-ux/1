## 7. `QA-P1-002-R1` — исправлен не полностью

### 7.2. Обязательный legacy-fallback не проходит

Созданный транзакционно рейс без `unloading_shift`, завершенный в `01:30 D+1`, попадает в отчет без выбора смены, но исчезает при выборе `Ночь`:

```text
legacy_trip_id=15
all_filter_trips=1
night_filter_trips=0
ROLLED_BACK=True
```

Причина находится в `reports/views.py`: сначала legacy-строка допускается по `completed_at` внутри производственного интервала, но затем общий фильтр

```python
trips.filter(unloading_shift__shift_type=filters['shift_type'])
```

исключает все строки, у которых `unloading_shift IS NULL`.

Это противоречит обязательному правилу документа `77`: производственный интервал должен оставаться согласованным fallback для legacy-рейсов без связи. Поэтому общий статус `QA-P1-002-R1` остается `NOT FIXED`.

### Требуемое исправление

При фильтре `day/night` необходимо:

- для связанных рейсов использовать `unloading_shift__shift_type`;
- для legacy-рейсов без `unloading_shift` определять смену по центральному производственному интервалу;
- сохранить ровно одну строку на дате `D` и ноль строк на `D+1`;
- добавить отдельные тесты страницы и Excel для legacy-рейса в `01:30 D+1` с фильтрами `Все`, `День`, `Ночь`.

```text
downtime_default=2026-07-24
shift_log_default=2026-07-24
group_active_from_default=2026-07-24
shift_plan_date_default=2026-07-24
```

Подтвержденные производственные места, которые продолжают использовать календарный контракт:

- `reports/views.py:361` — дата горных объемов по умолчанию через `timezone.localdate()`;
- `reports/views.py:382` — горные объемы по `completed_at__date`;
- `reports/views.py:914` и `933` — простой по календарной дате;

Не каждое использование календарной даты в проекте является ошибкой. Исправлять нужно только производственные сменные отчеты, планы и их Excel, оставляя несменные календарные отчеты без изменений.

## 11. `QA-RISK-001` — риск остается открытым

Полезные усиления подтверждены:

- глобальный старт смены сериализуется общей строкой производственного состояния;
- первое назначение дополнительно защищается блокировкой строки самосвала;
- часть start/close-операций выполняется атомарно.

Однако статус нельзя объяснять только отсутствием PostgreSQL-стенда. В коде остаются конкретные незакрытые гарантии:

1. `client_action_id` при старте простоев Водителя и Машиниста фактически не используется как ключ идемпотентности.
2. После последовательности `start(A) → close(B) → повтор start(A)` старый идентификатор действия способен создать новый простой.
3. Для `DowntimeEvent` нет action-ledger и условного уникального ограничения единственного открытого простоя техники.
4. Механик выполняет отдельные `проверка → create` без общей транзакции и блокировки техники; два механика либо механик и Машинист могут создать два открытых события.
5. Водитель ищет активный простой одновременно по технике и текущему сотруднику. Незакрытый простой прежнего водителя может быть пропущен.
6. У `HaulAssignment` нет DB-ограничения единственного активного назначения и отдельного журнала идемпотентных действий.

Для закрытия риска нужны:

- исправление перечисленных серверных контрактов;
- тестовая PostgreSQL;
- два независимых соединения;
- параллельные старты глобальной смены, первого назначения и простоя;
- одновременное закрытие смены и старт простоя;
- повтор старого `client_action_id` после промежуточного действия;
- результат: одна запись либо управляемый конфликт, без дублей и HTTP 500.

Текущий статус: `OPEN RISK / NOT VERIFIED`.
