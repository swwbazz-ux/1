## 3. Результат по карточкам

### 3.1. QA-TRAFFIC-P2-002-R1

Статус:

```text
ГОТОВО К ПЕРЕПРОВЕРКЕ
```

В `templates/includes/achievement_prize.html` добавлен catch-up для
усечённой realtime-дельты:

- при `eventsTruncated=true` Водитель или Машинист с действующей техникой
  выполняет ровно один achievements GET;
- отсутствие matching completion в доставленном списке больше не
  приводит к окончательной потере проверки;
- truncated burst объединяется с pending initial/relevant check;
- pending catch-up сохраняется после принятия новой operational-state
  version;
- без активной техники запрос не выполняется;
- периодический polling не добавлен.

Исполняемая интеграционная регрессия пропускает truncated-контекст через
настоящие обработчики fragment apply Водителя и Машиниста.

### 3.2. QA-TRAFFIC-P2-002-R2

Статус:

```text
ГОТОВО К ПЕРЕПРОВЕРКЕ
```

Для фактической HTTP/network ошибки добавлено ограниченное
восстановление:

- backoff `1 с → 3 с → 10 с`;
- не более трёх автоматических retry после исходного запроса;
- один pending key;
- один in-flight GET;
- recovery по `visibilitychange`, `online` и изменению соединения;
- hidden-вкладка выполняет `0` GET;
- после возврата visible выполняется ровно один pending catch-up;
- успешный retry сохраняет полный путь unlock → show → close →
  `achievement_shown`;
- 12 стабильных часов без событий не создают achievements polling.

### 3.3. QA-TRAFFIC-P2-003-R1

Статус:

```text
ГОТОВО К ПЕРЕПРОВЕРКЕ
```

В общем `AppPwaContractGuard` автоматическая и ручная проверка теперь
используют один update-flight по:

- identity регистрации service worker;
- target contract/shell key.

Ручная кнопка во время автоматического controlled update присоединяется к
существующему Promise. Фактический `registration.update()` вызывается
ровно один раз.

### 3.4. QA-TRAFFIC-P2-003-R2

Статус:

```text
ГОТОВО К ПЕРЕПРОВЕРКЕ
```

Запрос версии worker привязан к:

- identity worker;
- generation общего PWA guard;
- актуальному controller/active/waiting/installing.

При `controllerchange` generation увеличивается и версия считывается у
текущего controller. Запоздавшие ответы прежнего active или waiting
worker игнорируются и больше не могут вернуть готовый экран в
contract-lock.

### 3.5. QA-TRAFFIC-P2-003-R3

Статус:

```text
ГОТОВО К ПЕРЕПРОВЕРКЕ
```

В runtime Машиниста и Горного мастера после каждой асинхронной границы
повторно проверяются:

- текущая registration;
- `registration.waiting === inspectedWorker`;
- identity/generation инспекции;
- worker не является controller;
- worker ещё не находится в состоянии `activated`.

Дополнительно закрыт отдельный race после уже показанного окна:

```text
waiting modal показан
→ worker самостоятельно стал active/controller
→ пользователь нажал «Обновить»
→ повторный SKIP_WAITING = 0
```

При отправке `SKIP_WAITING` ссылка на worker атомарно снимается, что также
защищает от двойного trigger.

## 14. Остаточные риски

1. Ручной Browser QA не способен детерминированно создать задержанный
   ответ конкретного прежнего worker. Поэтому acceptance race-путей
   основан на исполняемом production-runtime harness.
2. Машинист и Горный мастер в доступных QA-сессиях были в read-only
   состоянии неактивной роли. Responsive, PWA contract и update UI
   проверены; изменяющие производственные действия не относятся к этим
   пяти карточкам.
3. Proxy warmup содержит клиентские отмены ответов при навигации. Они
   явно отделены от стабильного окна, где ошибок нет.
