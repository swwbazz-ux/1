## 3. QA-TRAFFIC-P1-002-R1

### 3.1. Причина

При публикации `CrewPlan` event payload содержал только сотрудников
нового плана и всю технику опубликованного плана. После закрытия старого
назначения сервер уже не мог восстановить технику снятого сотрудника.
Клиент получал новую глобальную версию, считал событие нерелевантным и
продвигал cursor без обновления экрана.

Дополнительно explicit scope с пустыми `employee_ids`/`equipment_ids`
мог ошибочно перейти к широкому fallback по роли.

### 3.2. Исправление

- `employee_ids` строится как объединение сотрудников реально
  закрываемых и реально создаваемых назначений;
- `equipment_ids` строится только по технике реально изменённых слотов;
- неизменённые сотрудники и техника в payload не добавляются;
- наличие explicit entity scope распознаётся отдельно от его
  непустоты: explicit пустой scope не расширяется fallback-логикой по
  роли.

### 3.3. Регрессии

Исполняемая серверная регрессия через настоящий
`/realtime/state/?after=...&include_events=1` доказывает:

```text
снятый сотрудник:       получает событие
новый сотрудник:        получает событие
неизменённый сотрудник: не получает событие
explicit empty scope:   не расширяется по роли
```

## 4. QA-TRAFFIC-P1-002-R2

### 4.1. Причина

Обработчики Водителя, Машиниста, Диспетчера и Горного мастера после
релевантного события запрашивали полный рабочий HTML. У Горного мастера
дополнительно существовала безусловная загрузка полного HTML каждые
10 секунд из passive reconcile.

### 4.2. Новый fragment-контракт

Добавлен серверный контракт:

```text
operational-fragment-v1
```

Ответ имеет JSON-форму:

```json
{
  "contract": "operational-fragment-v1",
  "screen": "<screen>",
  "version": 123,
  "html": "<только рабочий root>"
}
```

Свойства контракта:

- сервер возвращает только нужный рабочий root;
- `html`, `head`, `script`, `style` и полная страница в fragment не
  попадают;
- ответ имеет `Cache-Control: no-store`;
- версия ответа не может быть ниже запрошенной operational version;
- malformed/неполный fragment отклоняется fail-closed;
- `401` сохраняет утверждённое завершение realtime;
- перед DOM-заменой повторно проверяются формы, holds, drag,
  pending-action, sheet и modal;
- Водитель сохраняет активную вкладку;
- Горный мастер в passive reconcile выполняет только state poll, а
  fragment запрашивает лишь после релевантного события.

Fragment-контракт подключён для:

| Экран | Возвращаемый root |
|---|---|
| Водитель | `[data-driver-shell]` |
| Машинист | `[data-eo-shell]` |
| Диспетчер | `.dispatcher-board` |
| Горный мастер | `.mm-mobile-shell` |

## 5. QA-TRAFFIC-P1-005-R1

### 5.1. Причина

Process-local throttle защищал только решение о запуске, но освобождал
локальную защиту до завершения самой сверки. При недоступном файловом
lock второй поток мог войти в fallback во время ещё работающего первого
вызова.

Изолированное воспроизведение до исправления:

```text
calls:      2
max_active: 2
```

### 5.2. Исправление

Добавлен process-local running guard под существующим gate:

- первый вызов помечает сверку выполняющейся до входа в доменный путь;
- параллельные вызовы завершаются до выполнения callback;
- running-флаг освобождается во внешнем `finally`;
- освобождение выполняется и после исключения;
- таймер, файловый lock и доменная транзакция сохранены.

Регрессия после исправления:

```text
calls:      1
max_active: 1
```

Файловый lock остаётся single-host механизмом. Несколько независимых
application-host требуют отдельного распределённого scheduler/lock и в
этом задании не проверялись.

## 7. QA-TRAFFIC-DOC-P2-002

Корректная граница доказательства:

- Windows spawn-регрессия действительно запускает два отдельных
  процесса;
- оба процесса конкурируют за один файловый lock;
- защищённый callback заменён probe-callback;
- тест доказывает, что в probe одновременно входит только один процесс;
- этот тест не выполняет настоящее доменное применение назначений;
- этот тест не доказывает PostgreSQL row locks
  `Equipment`/`Employee`/`Trip`;
- доменный reconcile и его транзакционные блокировки проверяются
  отдельными Django/PostgreSQL-регрессиями, но не единым настоящим
  multiprocess domain-тестом.

Таким образом, прежняя формулировка о полном multiprocess PostgreSQL
domain-доказательстве не повторяется.
