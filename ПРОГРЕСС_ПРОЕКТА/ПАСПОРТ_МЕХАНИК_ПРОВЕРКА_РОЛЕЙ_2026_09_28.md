## 4. Просмотр нельзя смешивать с редактированием

- Почасовой отчёт машиниста, управленческая витрина руководства и большинство отчётов ничего не меняют сами по себе.
- Пульт показывает планы, CrewPlan и assignments, но редакторы этих сущностей находятся у разных ролей.
- `manager` штатно открывает отчёт, однако это не доказывает отсутствие mutation API.
- Admin видит и меняет справочники/планы; наличие тех же значений на пульте не делает диспетчера редактором `EquipmentPlanGroup`.
- Driver/Excavator видят assignment, но водитель только принимает pending, а поле может применить переход фактом; общий редактор топологии — Dispatcher/Master.

### 5.2. Фактическая утечка прав `manager`

`dispatcher_access_from_request` и `lock_dispatcher_mutation_access` допускают `dispatcher`, `admin`, **`manager`** (`trips/dispatcher_guards.py:84-121`). Для не-dispatcher `get_active_dispatcher_shift` возвращает первую глобальную открытую диспетчерскую смену (`dispatcher_header.py:73-82`). Поэтому при наличии чужой открытой диспетчерской смены `manager` может прямыми JSON-запросами:

- двигать экскаватор;
- назначать/снимать самосвал;
- менять забой;
- закрывать простой.

При этом отдельные guards запрещают `manager` служебное закрытие смены, cancel/complete/manual Trip и report correction. Это **факт кода и приоритетный дефект проверки прав**, а не утверждённая функция руководителя. Браузерный сценарий не запускался.

## 7. Значимые различия PR №106 и release

1. **Спорный старт «Ожидание разгрузки».** В обоих текущих SHA он принимается, даже если сервер считает самосвал пустым:
   - `REL: core/offline_sync.py:2671-2681`;
   - `PR: core/offline_sync.py:3930-3940`.
   Результат — `accepted`, открытый `DowntimeEvent`, пустой `error_code`. Код `loaded_trip_required` существует только в `logger.warning` через `_log_discrepancy` (`REL:36-46; PR:46-56`); отдельной DB-записи расхождения нет. Историческое сравнение `51813506… ↔ fd749e8a…` сохраняет смысл, но не описывает текущие головы.

2. **Погрузка и простои.** Release закрывает выбранные workflow-простои; PR после разных видов load закрывает все интервалы truck+excavator, пересекающие `loaded_at`, включая ремонт/заправку.

3. **Carryover и пятиминутный reconciler.** Release может погасить переносимый рейс закрытой смены через 5 минут; PR исключает `is_carryover=True` (`REL: manual_loading.py:103-120; PR:101-119`).

4. **Гонки рейсов/free-bucket.** PR существенно расширяет `accepted/no_effect`, historical load и восстановление предыдущего Trip/acceptance после отмены. Эти свойства нельзя приписывать release.

5. **Управленческие права/команды.** В проверенных ключевых файлах они между двумя SHA одинаковы; различия PR сосредоточены в полевой/offline логике.

## 9. Конкретный адресный PostgreSQL-прогон

Общий зелёный CI не считается доказательством этого сценария. Нужен отдельный артефакт для каждого exact SHA.

1. Поднять одноразовый `postgres:16` с отдельной сетью и БД `passport_probe`; использовать те же env, что `.github/workflows/django.yml:153-217`:
   `DJANGO_DB_ENGINE=postgres`, `POSTGRES_HOST`, `POSTGRES_PORT=5432`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_CONN_MAX_AGE=0`.
2. Смонтировать каждый clean worktree read-only и внешний временный `pg_downtime_probe.py` через `PYTHONPATH`. Файл не коммитить ни в PR №106, ни в release.
3. Probe наследует fixture `OfflineEventSyncTests`, но дополнительно к существующему тесту обязан проверить:
   - `connection.vendor == 'postgresql'`;
   - result и `OfflineFieldEvent.status == accepted`;
   - `OfflineFieldEvent.error_code == ''`;
   - создан ровно один открытый `DowntimeEvent` нужной причины;
   - `OfflineFieldEventConflict` для event отсутствует;
   - `assertLogs('core.offline_sync', WARNING)` содержит `loaded_trip_required`;
   - в stdout печатается JSON с result, receipt id/status/result_payload, downtime id/timestamps и warning.
4. Запустить отдельно на `5f47d798…` и `1754269…` командой вида:

```powershell
python manage.py test pg_downtime_probe --verbosity 2 --noinput
```

   внутри контейнера Python 3.12 с `requirements.txt`; перед каждым запуском сохранить `git rev-parse HEAD`.
5. Артефакты: полный stdout/stderr, exit code, оба SHA, digest Docker image, JSON probe и header PostgreSQL backend. После прогона удалить контейнер, сеть и test DB.

Этот способ изолирует БД, не меняет приложение и доказывает именно спорный event, а не соседнюю PostgreSQL-группу CI.

## 10. Приоритетные сценарии следующей проверки

1. `manager` штатной ролью вызывает topology/settings/downtime API при чужой открытой диспетчерской смене.

## Итог

R-18 подтверждается только там, где функции уже общие: оперативная расстановка техники. Забой, люди, планы, служебные закрытия и исправление рейсов распределены между другими редакторами и не становятся общими автоматически. При этом фактический backend сейчас шире целевой картины: admin имеет параллельные редакторы тех же данных, а `manager` допущен к четырём диспетчерским mutation-путям. Это зафиксировано как факт кода и предмет проверки, без изменения правил и реализации.

PR №106 не сливался; release и production не менялись; deploy не выполнялся.
