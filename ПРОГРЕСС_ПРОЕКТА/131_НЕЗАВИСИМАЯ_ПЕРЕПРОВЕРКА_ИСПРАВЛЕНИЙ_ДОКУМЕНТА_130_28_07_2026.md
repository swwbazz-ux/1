## 5. Новый дефект QA-TRAFFIC-P1-002-R2-R1

Название: **Водитель теряет несохранённые начальные показания при
realtime-обновлении**.

Статус: **ВОСПРОИЗВЕДЕНО / P1**.

### 5.1. Живое воспроизведение

В изолированной недельной QA-БД Водителю временно назначен свободный
самосвал. Экран без reload получил форму открытия смены.

В поля введено:

```text
топливо:    321
одометр:    654
моточасы:   987
```

После ухода фокуса значения оставались в форме. Затем создано обычное
связанное событие `personnel_assignment_changed`.

Через штатный polling:

```text
operational version: 83518 → 83519
значения до события:  ["321", "654", "987"]
значения после события: ["", "", ""]
```

Ручной reload не выполнялся.

### 5.2. Причина

- форма открытия смены:
  `templates/users/driver_shift.html:3102`;
- guard проверяет dirty/error только формы закрытия смены:
  `templates/users/driver_shift.html:3533`;
- обработчики формы открытия не устанавливают dirty-флаг:
  `templates/users/driver_shift.html:3624`;
- после blur корневой блок заменяется:
  `templates/users/driver_shift.html:3571`.

### 5.3. Требуется

1. учитывать форму открытия смены в
   `isDriverOperationalRefreshUnsafe()`;
2. считать небезопасными:
   - изменённые начальные показания;
   - ошибки формы;
   - незавершённую отправку;
3. пока форма небезопасна, не заменять корень;
4. после сохранения или явного сброса применить отложенную версию;
5. добавить исполняемую JavaScript-регрессию и Browser QA:
   `ввод → blur → событие → значения сохранены`.

## 6. Новый дефект QA-TRAFFIC-P1-002-R2-R2

Название: **Диспетчер после fragment-refresh использует устаревший
признак открытой смены**.

Статус: **ВОСПРОИЗВЕДЕНО ПО PRODUCTION-КОДУ / P1**.

### 6.1. Подтверждённое состояние

Экран Диспетчера был открыт при закрытой смене. В другой серверной
операции смена открыта, после чего штатный realtime заменил
`.dispatcher-board` без reload:

```text
до:    .dispatcher-board.is-readonly
после: .dispatcher-board
version: 83526
```

Визуальный блок стал рабочим, но JavaScript-признак
`dispatcherShiftOpen` вычисляется только один раз из первоначального
HTML.

### 6.2. Причина

- одноразовая инициализация:
  `templates/trips/dispatcher_control.html:807`;
- замена только `.dispatcher-board`:
  `templates/trips/dispatcher_control.html:1468`;
- fragment-ответ не передаёт новый признак смены:
  `trips/views.py:4618`;
- drag-and-drop после повторной привязки по-прежнему проверяет старую
  переменную:
  `templates/trips/dispatcher_control.html:5622` и
  `templates/trips/dispatcher_control.html:5873`.

Следствия:

- после фонового открытия смены визуально рабочий пульт может не
  получить рабочие drag-and-drop handlers;
- после фонового закрытия смены код может продолжать считать смену
  открытой до reload;
- серверные запреты сохраняют защиту данных, но интерфейс не
  соответствует актуальному состоянию.

### 6.3. Требуется

1. передавать `shift_is_open` в JSON fragment-контракт либо брать его из
   нового корня;
2. после каждой замены обновлять runtime-state;
3. повторно связывать действия уже с новым значением;
4. добавить исполняемую регрессию:
   `closed → fragment open → DnD enabled`;
5. добавить обратную регрессию:
   `open → fragment closed → DnD disabled, fetch count = 0`.

## 7. Новый дефект QA-TRAFFIC-P2-002-R1-R1

Название: **Событие расстановки одной роли приходит другой активной
роли того же сотрудника**.

Статус: **ВОСПРОИЗВЕДЕНО / P2 TRAFFIC SCOPE**.

Изолированная проверка production-функции:

```text
event role_code: driver
event employee_id: 42
active access role: excavator_operator
active access employee_id: 42
event_is_relevant: True
```

Причина:

- `_personal_access_event()` считает совпадение `employee_id`
  достаточным до проверки `role_code`:
  `core/realtime.py:132`;
- дальнейшая проверка роли уже не выполняется после раннего `True`.

Это не меняет данные, но создаёт лишний state/fragment-путь для другой
активной роли сотрудника.

Требуется учитывать роль события для
`personnel_assignment_changed/crew_plan_published`, сохранив личные
события доступа, которые по контракту действительно должны приходить
независимо от рабочей роли.

## 8. Новый дефект QA-TRAFFIC-P2-002-R1-R2

Название: **Неизменённый сотрудник противоположной смены на той же
технике получает событие расстановки**.

Статус: **ВОСПРОИЗВЕДЕНО / P2 TRAFFIC SCOPE**.

Проверка production-функции:

```text
изменённые employee_ids: [1, 2]
неизменённый employee_id: 3
общая equipment_id: 501
event_is_relevant: True
```

Причина:

- publisher передаёт `equipment_id`, но не `shift_type`;
- `_worker_equipment_ids()` собирает действующие назначения сотрудника
  без ограничения сменой;
- пересечение по технике делает событие релевантным.

Текущий тест использует для неизменённого сотрудника другую технику и
не покрывает обычный случай `день/ночь на одном самосвале`.

Требуется добавить в область события смену либо сформировать
получателей по изменённым слотам так, чтобы сотрудник другого
неизменённого слота не получал лишний refresh.

## 9. Документальные остатки

### 9.1. Неверный счётчик адресного Django-набора

Документ 130 указывает:

```text
55/55 OK
```

Однако команда раздела 16.2, содержащая четыре перечисленных модуля,
фактически обнаружила и выполнила:

```text
35/35 OK
```

Падений нет, но число `55/55` не воспроизводится указанной командой.

### 9.2. Завышенное описание транзакционных блокировок

Документ 130 честно сообщил, что spawn-проверка использует probe и не
является настоящим multiprocess domain-тестом.

При этом формулировка раздела 7 о том, что доменный reconcile «и его
транзакционные блокировки» проверяются отдельными PostgreSQL-
регрессиями, остаётся сильнее доказательств:

- отдельной конкурентной reconcile-регрессии нет;
- reconcile блокирует строки `HaulAssignment`;
- эффект блокировок в настоящем multiprocess-сценарии не доказан.

Корректная формулировка:

> Доменная функциональность проверяется Django-тестами на PostgreSQL;
> эффект строковых блокировок в конкурентном multiprocess reconcile
> отдельно не доказан.

### 9.3. Документ 128

В документе 128 осталось прежнее завышенное описание spawn-теста и
`Equipment/Employee/Trip locks`. Документ 130 фактически исправляет его,
но документ 128 не помечен как уточнённый более поздним отчётом.
