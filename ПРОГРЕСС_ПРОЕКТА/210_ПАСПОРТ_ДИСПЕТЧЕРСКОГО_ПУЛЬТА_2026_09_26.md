# Паспорт Диспетчерского пульта — 26.09.2026

## Зачем нужен этот документ

Это единая точка входа для дальнейшей разработки пульта. Перед новой функцией или
правкой не нужно перечитывать весь `trips/views.py` и весь шаблон: сначала выбирается
раздел ниже, затем открываются только указанные владельцы кода и их тесты.

Главный порядок работы: сначала локально закончить карту, разделение и стабилизацию;
затем развивать интерфейс и добавлять функции; публикацию на production рассматривать
только отдельным последним этапом после полного локального release-аудита.

## Межролевые границы

- `dispatcher_control_view` также используется как renderer Горного мастера. Нельзя
  менять его общий контекст, не проверив этот контракт.
- `dispatcher_shift_report_for_equipment`, plan payload/card helpers и часть расчётов
  используются экраном Экскаваторщика. Их нельзя переносить в Dispatcher-only модуль
  только из-за удобного имени.
- Общие realtime, connection, active-role и shift-контракты нельзя копировать внутрь
  пульта: у них должен сохраняться один источник истины.

## Закрытая граница холста и упаковки

`dispatcher-canvas-v1.js` и `dispatcher-canvas-v1.css` являются обязательной частью
desktop-оболочки. Оба файла добавлены в `.github/deploy/production-files.txt` и
`CORE_ASSETS` service worker, а shell поднят до `dispatcher-desktop-shell-v144`.
Exact-once release-тест не позволяет снова потерять файлы из точечного payload.

Телефонная landscape-подгонка desktop-пульта больше не живёт inline в шаблоне: ею
владеет тот же canvas-модуль. Атрибут `data-dispatcher-phone-fit` включает этот режим
только для `/dispatcher/control/`, поэтому сменный отчёт с тем же canvas-файлом не
получает трансформацию пульта. Отдельный inline scaler Горного мастера не менялся.
Полная сверка ветки подтвердила `32/32` рабочих production-файла в manifest и отсутствие
дублей.

## Как выполнять каждую следующую задачу

1. Найти строку задачи в таблице владельцев и открыть только эти файлы.
2. Проверить, нет ли межролевого вызова из Горного мастера или Экскаваторщика.
3. Сначала добавить или уточнить тест текущего поведения.
4. Сделать одну структурную или функциональную группу, не смешивая её с редизайном.
5. Запустить профильные Django/JavaScript-тесты, `manage.py check` и Browser QA.
6. Обновить этот паспорт, если появился новый файл, контракт или точка расширения.
7. Зафиксировать отдельный локальный commit. Публикацию не подразумевать.

## Карта большого шаблона

Построчная карта, DOM/data-контракты, внешний desktop runtime, inline runtime
Горного мастера и обязательные rebind-точки записаны в
`211_КАРТА_ШАБЛОНА_ДИСПЕТЧЕРСКОГО_ПУЛЬТА_2026_09_26.md`.

Ключевое ограничение: строки `707–6893` находятся в mobile-ветке Горного мастера и
не должны переноситься в desktop-модули Диспетчера. Desktop runtime уже состоит из
шести внешних модулей. Четыре самостоятельных HTML include выполнены без изменения
DOM, поведения и дизайна; оставшийся крупный HTML принадлежит мобильной оболочке
Горного мастера и требует отдельного межролевого этапа.

Новый include нельзя оставлять только в Git-дереве приложения: защищённая публикация
копирует manifest-scoped payload. Поэтому каждый include должен добавляться в
`.github/deploy/production-files.txt` и release-тест в том же локальном commit. Для
`dispatcher_board.html`, `dispatcher_service_lists.html`,
`dispatcher_equipment_detail.html` и `dispatcher_push_invite.html` это правило уже
выполнено.
Push, PR, `VERIFY` и deploy
этим не разрешаются.

## Закрытие смены после realtime fragment

Экран с необработанным JSON после закрытия смены возникает, если служебный URL
operational fragment попадает в `next` обычной POST-формы. Владельцы защиты:

- `trips/views.py` формирует `dispatcher_shift_return_url` через
  `get_dispatcher_control_url(request)` и сохраняет только пользовательские фильтры;
- `templates/includes/dispatcher_shift_action.html` кладёт этот полноэкранный адрес
  в скрытое поле `next`;
- `trips/dispatcher_guards.py:get_dispatcher_action_redirect_url` повторно удаляет
  `_operational_fragment`, `_operational_version` и другие внутренние refresh-параметры
  из `next` и `Referer` перед redirect;
- регрессия закреплена в `trips/tests.py` и `trips/test_dispatcher_guards.py`.

Минимальный Browser QA для этой границы: открыть смену, получить реальный fragment с
пользовательским фильтром, проверить полноэкранный `next`, затем завершить смену и
убедиться, что браузер остался на HTML-экране `/dispatcher/control/`, а не на JSON.
Этот сценарий пройден локально 26.09.2026 на заполненной временной базе.

## Этапы до начала большой функциональной разработки

1. Считать dispatcher-owned HTML-декомпозицию завершённой; мобильную оболочку Горного
   мастера не переносить в рамках чисто dispatcher-задачи.
2. Вынести оставшийся inline JavaScript в
   существующие или новые узкие модули, сохраняя DOM и поведение.
3. Для каждого владельца закрепить минимальный профиль тестов и Browser QA-сценарий.
4. Провести отдельный аудит упаковки: template assets, service worker, release manifest,
   shell/cache version и полный production payload.
5. Только после этого переходить к новым функциям и заметной переработке интерфейса.
