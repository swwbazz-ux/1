## Правила владельца (выше любых документов)
Утверждены 26.09.2026:
1. Водитель и машинист экскаватора — истина и источник данных. Телефон решает сам и сразу, без ожидания сервера. Сервер только записывает и подсказывает; не отклоняет, не отменяет, не блокирует и сам не закрывает действия работника. Отказ — только на битые данные, работнику при этом ничего не показывается. Нет связи — проблема сервера, не работника.
2. Время действия = время нажатия (с поправкой на сбитые часы). Настройки — как были на экране в момент нажатия. Опоздавшие события — на своё время в свою смену.
3. Погрузку определяет машинист (в ручном режиме — водитель); разгрузку, точку и время разгрузки — водитель. Двойная отметка одной погрузки = один рейс.
4. Незакрытый рейс переходит сменщику и засчитывается тому, кто грузил. Приложение водителя само не даёт вторую ручную погрузку без нажатия «разгрузка». Погрузка МАШИНИСТОМ самосвала, который по системе гружёный, проходит ВСЕГДА: старый рейс → UNCONTROLLED за первым грузившим (выбор владельца «всегда»).
5. Погрузка самосвала, назначенного на другой экскаватор = рейс через «Свободный ковш», основное назначение не меняется (правила свободного ковша — журнал решений 14–17.09).
6. Простои: погрузка закрывает «ожидание погрузки», разгрузка — «ожидание разгрузки», закрытие смены — все; если работник закрыл сам раньше — его время.
7. Никаких пометок/«нужна сверка» ни диспетчеру (1 диспетчер на 80+ машин × ~20 рейсов), ни работнику. Сервер решает сам по правилам, расхождения — во внутренний лог.
8. Опоздавшее событие никогда не закрывает и не меняет рейс, погруженный позже него (раскладка по времени).

Уже согласовано в разборе Codex 27.09 (владелец не возражал, но формально не утверждал — вынести в список решений):
- Погрузка при любом простое проходит; простои, начатые не позже погрузки, закрываются временем погрузки (причина work_resumed_by_load).
- Смена открывается телефоном сразу (в т.ч. офлайн); открытие на занятой технике закрывает прежнюю смену временем нового открытия.
- Принудительное закрытие смены диспетчером: действия до него — в старую смену, после — «техническое продолжение» к следующей смене работника; раннее закрытие работника побеждает.
- Факт рейса: COMPLETED по разгрузке, или UNCONTROLLED с причиной next_load_uncontrolled; отчёты — по времени действий (loaded_at / completed_at / operationally_closed_at), не по created_at.

## Уроки ночи (обязательно учесть в разделе «приёмка»)
1. Два самых тяжёлых бага не проявлялись на стенде: (а) PostgreSQL на бою отвергал `select_for_update()` с `select_related` по nullable-связи — каждый рабочий простой водителя падал с 25.09 (SQLite этого не ловит); (б) стенд в headless-браузере не опрашивает сервер (pageActive), поэтому сбросы таймера от обновлений экрана там не видны. Приёмка: стенд на PostgreSQL + реальный телефон в фокусе + фоновая нагрузка других машин.
2. Боевой журнал телефона — лучший источник правды: приложение Capacitor пишет консоль в logcat (`Capacitor/Console`, строки `driver-outbox pending=… review=…` со статусами и кодами каждого события очереди).
3. Сервер решал за работника в местах, о которых никто не помнил (например, `driver_downtime_start_conflict` — «простой доступен только после погрузки» по серверному, запаздывающему видению рейса). Паспорт должен явно перечислить ВСЕ места, где сервер может отказать, и для каждого — правило без отказа.
4. Каскад `dependency_rejected`: один отклонённый элемент очереди тянет за собой все последующие. Отклонённые события телефон повторно не шлёт — данные теряются.
5. Экран водителя перезаписывает своё состояние запоздавшими снимками сервера (фрагмент core/full каждые ~20 с) — источник сбросов таймера и «воскрешения» простоев. Паспорт должен определить: что на экране главнее — локальная проекция очереди или снимок сервера, и когда.
