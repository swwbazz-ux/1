# Матрица разрывов и трассируемости

Версия: 0.5
Проверенный HEAD перед текущей документационной актуализацией: `8265ab361dc49afc569d5a9f3eca8eed06f09ee1`; локальный принятый resident occupancy transition имеет leaf `settlement.0013_resident_occupancy_subject`

## Правило использования

Каждая реализационная задача Codex должна ссылаться на один или несколько ID этой матрицы. Задача считается принятой только после выполнения указанных проверок. Статус меняется по доказательствам нового HEAD, а не по отчёту «сделано».

### Implementation checkpoint перед текущей документационной актуализацией

В baseline `902e3886` локально реализованы schema `SettlementControlLease/SettlementControlEvent`, migration `0007` с FREE singleton, внутренние acquire/heartbeat/release/expire, административный takeover, fencing/token/HMAC и application-level неизменяемый аудит. Эти primitives проверены на SQLite и PostgreSQL, но не подключены к manual settlement writers, HTTP/session или UI. Поэтому end-to-end требования TR-043–TR-047 не считаются закрытыми: write gate и общий порядок Employee/EmployeeAccess отсутствуют, а TR-048 остаётся полностью `ABSENT`. Migration `0007` не объявляется применённой к production.

После этого historical checkpoint migrations `0008/0009` реализовали M4 calendar binding и M5 authoritative cohort, `0010_settlement_residents` ввела общий `SettlementResident`, а migration `0011_resident_subject_transition` завершила resident subject transition M4/M5. Исторические описания прежних прямых Employee FK относятся к состоянию до `0011`. Минимальное безопасное read-only ядро M6 для MVP завершено: binding → equipment assignment → position → controlled unresolved. Migration `0012_m7_saved_previews` завершила M7 persistence/confirmation. Migration `0013_resident_occupancy_subject` перевела фактическую occupancy на обязательный resident subject и canonical resident writers, включая external resident без Employee/Access/Role/PIN. Apply, AUTO replacement, UI внешних карточек/ручного внешнего заселения, UI preview/confirm/apply, persistent RoomUseProfile/ResolverRule и trainee adapter не считаются реализованными.

## Критерий закрытия разрыва

Для смены статуса на READY обязательны одновременно:

1. реализация в утверждённом HEAD;
2. миграция или доказательство, что она не нужна;
3. позитивный, негативный и граничный тест;
4. для interval/concurrency — PostgreSQL-проверка;
5. обновление `07_ТЕКУЩЕЕ_СОСТОЯНИЕ_HEAD.md` и этой матрицы;
6. независимая проверка агентом, не реализовывавшим изменение.
