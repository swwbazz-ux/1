# План миграции от текущей модели к целевой

Версия: 0.5
Baseline кода: `f7719c7d2e5ed009ca5b61e6ec375341cb62288d`; принятый baseline документов v0.4: `45de5d068f3b8c7f971e6065b974e4857e872f76`; рабочая версия документов v0.5 добавляет control lease до дальнейших writers
Статус: архитектурный план; production-операции запрещены без отдельного решения

## 1. Принципы

1. Миграции выполняются additively: сначала новые таблицы/поля, затем заполнение и сверка, только потом переключение readers/writers.
2. Существующие occupancies, anchors и assignments не преобразуются в постоянные bindings автоматически.
3. Неоднозначная строка попадает в reconciliation report и требует подтверждения.
4. Каждая schema/data migration получает отдельную задачу и отдельную проверку.
5. SQLite может использоваться для быстрой регрессии, но interval/concurrency готовность доказывается на PostgreSQL.
6. Production data migration, commit, push и deploy — разные операции и требуют отдельных разрешений.

## 4. M2 — усиление существующих инвариантов

### Anchor-bed

- добавить DB-level interval guarantee для confirmed rows на PostgreSQL;
- публичные `update/bulk_create/bulk_update` уже закрыты для всех статусов commit `4e88278e`; сохранить этот guard;
- сохранить normal writer как единственную application-команду;
- проверить единый lock order.

### Occupancy

- выбрать и реализовать PostgreSQL-гарантию effective interval с учётом `terminated_at`;
- публичные `update/bulk_create/bulk_update` уже закрыты commit `1e701208`; определить отдельную политику разрешённых create/save/delete и private/raw boundary;
- добавить actor/reason/source/revision links additively;
- единый lock order manual writers реализован commit `f7719c7d` и принят PostgreSQL pairwise-матрицей;
- сохранить controlled 409 contract для доменных конфликтов; retry/нормализацию определить отдельно для иных deadlock/serialization failure.

### Исключительное управление

До расширения ручных writers и до реализации Apply добавить:

- singleton `SettlementControlLease`, который хранит только current state: `scope`, `owner_access` → `EmployeeAccess`, отдельные session hash и непрогнозируемый UUID `lease_token`, сохраняемую монотонную `fencing_revision`, конечные heartbeat/expiry и служебные timestamps;
- атомарные acquire, renew, explicit release и expiry claim под `SELECT FOR UPDATE`;
- общий write-boundary guard, который первым блокирует control row, проверяет access/session/token/revision и только затем переходит к Employee → Beds → Rooms → Occupancies;
- release и expiry с очисткой `owner_access`, session hash, token и timestamps текущего владения, увеличением revision и событиями `RELEASED`/`EXPIRED`;
- административный takeover с подтверждением и обязательной причиной, атомарной заменой текущих owner access/session/token/timestamps, увеличением revision и событием `TAKEN_OVER`;
- `SettlementControlEvent` как единственный неизменяемый history store: enum `ACQUIRED`, `RELEASED`, `EXPIRED`, `TAKEN_OVER`, actor/previous/new owner access, occurred_at, source, revisions, безопасная session metadata и reason; heartbeat отдельного события не создаёт;
- controlled 409 для старой/перехваченной сессии без частичной доменной записи;
- read-only режим для остальных уполномоченных пользователей.
- расширение существующей карты v29 индикатором владельца, acquire/release, read-only banner и административным takeover без переписывания комнат, коек, поиска, счётчиков, DnD и guards.

Точный timeout утверждается эксплуатационно до включения. Миграция создаёт FREE singleton control row с сохранённой `fencing_revision` и отдельную таблицу `SettlementControlEvent`; она не назначает владельца автоматически, не хранит history-поля в lease и не делает кадровый график техническим lock.

До внедрения DB-ограничения обязательна проверка существующих overlaps; иначе migration должна остановиться.

## 5. M3 — два atomic equipment slots

Использовать существующие `AccommodationAnchor.equipment` и `ordinal`.

Добавить:

- type-shape validation для equipment anchors;
- уникальность active `(equipment, ordinal)`;
- допустимые ordinal 1/2 для технической пары;
- сервис подтверждения полноты пары;
- validator `An+Bn`: одна room, одинаковая position, разные A/B.

Существующий единственный anchor не клонируется автоматически. Для каждой Equipment формируется report:

- существующий anchor/bed;
- предлагаемая трактовка ordinal;
- отсутствующий второй slot;
- необходимые ручные решения.

## 6. M4 — calendar slots и permanent binding

Создать additively:

- `EmployeeAccommodationBinding`;
- status/source/revision/approval/history;
- overlap constraints employee и calendar slot;
- команды confirm/close/supersede.

Backfill:

- обычный опубликованный CrewPlan/EquipmentAssignment может быть основанием первого binding только внутри подтверждённого Apply;
- при создании binding сохраняется неизменяемый snapshot плана, назначения и ревизии;

## 7. M5 — authoritative cohort

Создать сохраняемые `SettlementCohort/SettlementCohortMember` как жилищную проекцию существующих upstream-моделей.

Обязательные данные:

- approved version;
- employee;
- `[arrival_at, departure_at)`;
- WatchComposition/rotation group;
- участие/незаезд/продление;
- source revision;
- input fingerprint.

`WatchComposition`, `WatchPeriod` и подтверждённые ротационные решения являются базовыми источниками; продления и ручные подтверждённые поправки версионируются отдельно. Делопроизводитель фиксирует жилищную версию, не меняя кадровое членство.

## 8. M6 — room profiles, явные категории и resolver rules

Additive модели/конфигурация:

- period room use profile;
- gender, early/standard/special;
- staff/contractor;
- reserve/protected/service;
- 2+1 orientation;
- `SettlementCategory` и `EmployeeSettlementCategoryAssignment` с permanent/temporary lifecycle;
- адаптер статуса стажировки и ссылка на подтверждённую будущую вакансию без trainee anchors/pool;

Начальная конфигурация покрывает утверждённые технические и функциональные группы, общий женский фонд, отдельных подрядчиков и protected. Фамилии, количество техники и номера комнат не зашиваются. До настройки категории возвращается `resolver_not_configured`.

## 9. M7 — saved preview

Создать:

- `AutoSettlementRun`;
- immutable `AutoSettlementRunRow`;
- `AutoSettlementRunConflict` для групповой потребности и дефицита;
- отдельный immutable `SettlementConflictDecision` с автором, основанием, сотрудниками и ссылкой на новый run/команду;
- source snapshot;
- input hash;
- rule version;
- `KEEP/SETTLE/SETTLE_NEW_BINDING/CONFLICT`;
- reason codes.

Group-first allocator не применяет частичный скрытый приоритет, если мест не хватает всей группе. Конфликт содержит потребность, доступно, дефицит и затронутых сотрудников и ждёт решения уполномоченного руководителя. Решение не изменяет исходный run и применяется только как вход нового расчёта или отдельной разрешённой команды.

Старый GET preview остаётся временно доступным как диагностический legacy path, но не получает Apply. После parity-проверки UI переключается на saved run.

## 12. Обработка legacy assignment types

| Legacy type | Миграционная политика |
|---|---|
| `PERMANENT` occupancy | Сохранить как historical factual record; не считать binding без подтверждения |
| `TEMPORARY` | Сохранить factual interval; проверить обязательный конец и reason/provenance |
| `PROPOSED` | Проинвентаризировать отдельно; не переносить в run и не считать подтверждённым предложением автоматически |

Удаление legacy fields/types возможно только после полного чтения старых записей новым кодом, reconciliation и отдельного rollback-плана.

## 13. Стоп-условия

Миграция останавливается, если:

- найдены неразрешённые interval overlaps;
- Equipment pair нельзя восстановить однозначно;
- неизвестна календарная группа;
- нет официального источника для binding/cohort;
- отсутствуют обязательные актуальные кадровые или room-profile факты для включаемой resolver-волны;
- фактическое число/тип техники не сверены с реестром;
- dirty worktree пересекается с изменяемыми файлами;
- PostgreSQL-проверка недоступна;
- control lease/takeover допускает двух владельцев, старую revision или необъяснимый административный перехват;
- data migration предполагает постоянное решение за владельца продукта.
