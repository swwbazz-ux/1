# План миграции от текущей модели к целевой

Версия: 0.5
Проверенный HEAD перед текущей документационной актуализацией: `dd0459ee39b00a352ef0da0ff647f1d03ad59389`; локальный migration leaf после принятого M4/M5 resident transition: `settlement.0011_resident_subject_transition`
Статус: архитектурный план; production-операции запрещены без отдельного решения

## 1. Принципы

1. Миграции выполняются additively: сначала новые таблицы/поля, затем заполнение и сверка, только потом переключение readers/writers.
2. Существующие occupancies, anchors и assignments не преобразуются в постоянные bindings автоматически.
3. Неоднозначная строка попадает в reconciliation report и требует подтверждения.
4. Каждая schema/data migration получает отдельную задачу и отдельную проверку.
5. SQLite может использоваться для быстрой регрессии, но interval/concurrency готовность доказывается на PostgreSQL.
6. Production data migration, commit, push и deploy — разные операции и требуют отдельных разрешений.

- сохранить controlled 409 contract для доменных конфликтов; retry/нормализацию определить отдельно для иных deadlock/serialization failure.

### Исключительное управление

В проверенном baseline `902e3886` локально реализованы:

- schema `SettlementControlLease` и `SettlementControlEvent` с current-state lease, отдельными session hash, UUID `lease_token`, сохраняемой монотонной `fencing_revision` и application-level неизменяемым audit;
- migration `0007_settlement_control_lease_and_event` с bootstrap FREE singleton `scope='settlement'` без фиктивного владельца;
- внутренние ensure/acquire/heartbeat/release/expire, HMAC session binding, fencing validation и события `ACQUIRED`, `RELEASED`, `EXPIRED`;
- внутренний административный takeover с обязательной причиной, новым token/revision и событием `TAKEN_OVER`;
- SQLite/PostgreSQL schema, lifecycle, audit и concurrency tests; migration drift отсутствует.

Migration `0007` существует в репозитории и проверена только в изолированных тестовых средах. Её применение к production не выполнялось и этим документом не утверждается.

До расширения ручных writers и до реализации Apply остаётся:

- связать control acquire с единственной открытой бизнес-сменой делопроизводителя (`EmployeeShift` + `WatchPeriod`); expiry lease не должен передавать бизнес-право второму сотруднику до закрытия этой смены;
- привести acquire/takeover и все кадровые writers к единому порядку `Lease, если участвует → все Employee по PK → все EmployeeAccess по PK`, исключив joined-row locks и повторно проверяя предварительно прочитанные данные;
- добавить общий write-boundary guard, который первым блокирует control row, проверяет session/token/revision, неблокирующим чтением строит полный lock plan, затем блокирует все `Employee` по PK, все `EmployeeAccess` по PK с `OF self`, повторно проверяет связи/активность/роли и только после этого переходит к `PhysicalBed` → `PhysicalRoom` → `EmployeeBedOccupancy` по PK;
- подключить gate к `settle`, `relocate`, `release` и будущему Apply;
- добавить control HTTP endpoints/URLs, хранение credentials в пользовательской session и browser heartbeat;
- controlled 409 для старой/перехваченной сессии без частичной доменной записи;
- server-side read-only режим для остальных уполномоченных пользователей;
- расширение существующей карты v29 индикатором владельца, acquire/release, read-only banner и административным takeover без переписывания комнат, коек, поиска, счётчиков, DnD и guards;
- реализовать AutoSettlement Apply только через общий gate после готовности остальных M2–M7.

Точный timeout утверждается эксплуатационно до включения HTTP/browser lifecycle. Существующая migration не назначает владельца автоматически, не хранит history-поля в lease и не делает кадровый график техническим lock.

До первой блокировки `EmployeeAccess` gate обязан знать полный набор `Employee`: владельца lease/оператора, subject employee, отличный `settled_by`/actor и всех участников пакетного Apply. Порядок `Employee(A) → EmployeeAccess(A) → Employee(B)` запрещён; невозможность заранее построить полный набор завершает команду fail-closed. Предварительно прочитанный Access не является авторитетным до повторной проверки под блокировками, joined Employee/Role не расширяют lock set, а отдельный Role-lock при необходимости выполняется только после EmployeeAccess. OUP, login/activation, кадровые переводы и batch writers используют тот же кадровый префикс без Lease.

До внедрения DB-ограничения обязательна проверка существующих overlaps; иначе migration должна остановиться.

## 7A. Authoritative resident subject

Additive migration `settlement.0010_settlement_residents` создаёт `SettlementResident`:

- `EMPLOYEE` — один wrapper на один внутренний Employee с `PROTECT`;
- `CONTRACTOR/BUSINESS_TRIP/EXTERNAL_OTHER` — внешняя карточка без Employee, login и Access;
- обязательные внешние ФИО, профессия, текстовая организация и телефон; фото необязательно;
- `ACTIVE/ARCHIVED`, положительная optimistic revision и exact access provenance;
- control-gated domain API и запрет публичного массового изменения/физического удаления.

Migration `0010` исторически не создавала resident rows и не меняла M4/M5/occupancy. Последующий этап выполнен migration `0011_resident_subject_transition`:

- forward создаёт или переиспользует единственный internal `EMPLOYEE` wrapper для каждого прежнего subject Employee в M4/M5;
- `EmployeeAccess`, Role, PIN и фиктивная external provenance не создаются;
- `EmployeeAccommodationBinding` и `SettlementCohortMember` переходят на обязательный `resident` с `PROTECT`;
- direct subject-FK Employee удаляется, actor/audit FK Employee сохраняются;
- reverse восстанавливает Employee subject только для internal resident и останавливается fail-closed при наличии external binding/member, не удаляя и не переписывая такие строки.

Внешний resident после `0011` может входить в cohort и получать calendar binding. Минимальное безопасное read-only ядро M6 для MVP завершено без новой migration: оно читает APPROVED cohort, M4 evidence, official EquipmentAssignment/PersonnelPosition и физический фонд, не пишет persistence и возвращает controlled unresolved для неоднозначной или неподдержанной волны. UI создания внешней карточки, legacy preview integration, persistent RoomUseProfile/ResolverRule, saved preview, Apply, external occupancy и trainee adapter остаются отдельными последующими этапами. Текущий migration leaf остаётся `settlement.0011_resident_subject_transition`.

## 8. M6 — room profiles, явные категории и resolver rules

Статус: `MINIMAL MVP CORE COMPLETE / PERSISTENT CONFIG PARTIAL`. Публичная read-only функция `resolve_settlement_cohort(*, cohort_id)` возвращает immutable placements/unresolved, reason codes, provenance и deterministic fingerprint. Порядок внутренних волн: `CONFIRMED binding → EquipmentAssignment → PersonnelPosition → controlled unresolved`. Equipment route требует официальный effective assignment (`ACCEPTED`, role есть, shift отсутствует, применимый assigned/accepted/ended interval), active Equipment, единственный active equipment anchor, единственный effective `CONFIRMED` bed assignment и `CONFIRMED` CalendarSlot того же WatchPeriod. Неоднозначность не разрешается первой строкой; DAY/NIGHT не создаёт отдельную identity bed; равноправная конкуренция за одну bed возвращает `hard_rule_conflict`. Fingerprint включает assignment/equipment/anchor/bed-assignment/slot/bed relations.

Внешние комнаты допускаются в residual pool только при уже доказанной M4 внешней привязке, внутренние и внешние resident не смешиваются, а дефицит равноправных участников не разрешается PK/name/order. Migration `0012` не создана, потому persistent RoomUseProfile и SettlementResolverRule не реализованы. Protected/reserve/service, 2+1, EARLY/STANDARD/SPECIAL и trainee-specific routing без конфигурации остаются controlled `resolver_not_configured`; это не блокирует M7, где такие resident должны сохраняться в списке нерасселённых с причиной. Следующий milestone — M7 saved preview; Apply, occupancy writes и UI ещё не реализованы.

Additive модели/конфигурация:

- period room use profile;
- gender, early/standard/special;
- staff/external resident type и текстовая организация;
- reserve/protected/service;
- 2+1 orientation;
- `SettlementCategory` и `EmployeeSettlementCategoryAssignment` с permanent/temporary lifecycle;
- существующий структурированный статус стажировки либо отдельный последующий adapter; Vacancy, будущая должность и JSON-fallback не создаются;
- versioned non-equipment resolvers с раздельными `hard_constraints` и `soft_preferences`.

Начальная конфигурация покрывает утверждённые технические и функциональные группы, общий женский фонд, отдельных подрядчиков и protected. Фамилии, количество техники и номера комнат не зашиваются. До настройки категории возвращается `resolver_not_configured`.

## 9. M7 — saved preview

Создать:

- `AutoSettlementRun`;
- immutable `AutoSettlementRunRow`;
- `AutoSettlementRunConflict` для групповой потребности и дефицита;
- отдельный immutable `SettlementConflictDecision` с автором, основанием, сотрудниками и ссылкой на новый run/команду;
- source snapshot;
- input hash;
- rule version;
- `KEEP/SETTLE/SETTLE_NEW_BINDING/CONFLICT`;
- reason codes.

Group-first allocator не применяет частичный скрытый приоритет, если мест не хватает всей группе. Конфликт содержит потребность, доступно, дефицит и затронутых сотрудников и ждёт решения уполномоченного руководителя. Решение не изменяет исходный run и применяется только как вход нового расчёта или отдельной разрешённой команды.

Старый GET preview остаётся временно доступным как диагностический legacy path, но не получает Apply. После parity-проверки UI переключается на saved run.

## 10. M8 — transactional Apply

Добавить только после READY M2–M7:

- endpoint с `run_id`, confirmation и idempotency key;
- workflow `preview → confirmation → Apply AUTO baseline → MANUAL corrections → final` без штатного MANUAL-before-first-Apply;
- явное предупреждение перед повторным Apply, который может заменить AUTO/MANUAL только целевого WatchPeriod и обязан закрыть/supersede прежние строки без удаления истории;
- обязательную действующую control fencing revision;
- stable lock order `Lease → nonlocking full lock plan → все Employee PK → все EmployeeAccess PK с OF self → revalidation → PhysicalBed PK → PhysicalRoom PK → EmployeeBedOccupancy PK`; после первого Access-lock запрещены новые Employee-locks, а неполный plan завершает Apply fail-closed;
- re-read/input hash;
- полный COMMIT validator;
- atomic safe batch;
- audit/result links;
- replay того же idempotency result;
- stale/no-write contract.

Legacy preview никогда не является входом Apply.

Повторный Apply не затрагивает другие или завершённые WatchPeriod. Provenance каждого результата различает AUTO run и MANUAL actor/reason.

## 12. Обработка legacy assignment types

| Legacy type | Миграционная политика |
|---|---|
| `PERMANENT` occupancy | Сохранить как historical factual record; не считать binding без подтверждения |
| `TEMPORARY` | Сохранить factual interval; проверить обязательный конец и reason/provenance |
| `PROPOSED` | Проинвентаризировать отдельно; не переносить в run и не считать подтверждённым предложением автоматически |

Удаление legacy fields/types возможно только после полного чтения старых записей новым кодом, reconciliation и отдельного rollback-плана.

## 13. Стоп-условия

Миграция останавливается, если:

- найдены неразрешённые interval overlaps;
- Equipment pair нельзя восстановить однозначно;
- неизвестна календарная группа;
- нет официального источника для binding/cohort;
- отсутствуют обязательные актуальные кадровые или room-profile факты для включаемой resolver-волны;
- фактическое число/тип техники не сверены с реестром;
- dirty worktree пересекается с изменяемыми файлами;
- PostgreSQL-проверка недоступна;
- control lease/takeover допускает двух владельцев, старую revision или необъяснимый административный перехват;
- data migration предполагает постоянное решение за владельца продукта.
