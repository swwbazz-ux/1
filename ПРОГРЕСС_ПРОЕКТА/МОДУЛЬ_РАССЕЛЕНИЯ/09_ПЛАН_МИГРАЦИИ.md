# План миграции от текущей модели к целевой

Версия: 0.6
Проверенный HEAD перед текущей документационной актуализацией: `c52ae35f2a204556320541cfa989e4d2e71b2725`; migration leaves: `assignments.0007_equipment_assignment_provenance`, `settlement.0016_shift_scoped_apply_and_occupancy`
Статус: архитектурный план; production-операции запрещены без отдельного решения

## 1. Принципы

1. Миграции выполняются additively: сначала новые таблицы/поля, затем заполнение и сверка, только потом переключение readers/writers.
2. Существующие occupancies, anchors и assignments не преобразуются в постоянные bindings автоматически.
3. Неоднозначная строка попадает в reconciliation report и требует подтверждения.
4. Каждая schema/data migration получает отдельную задачу и отдельную проверку.
5. SQLite может использоваться для быстрой регрессии, но interval/concurrency готовность доказывается на PostgreSQL.
6. Production data migration, commit, push и deploy — разные операции и требуют отдельных разрешений.

### Исключительное управление

В проверенном baseline `902e3886` локально реализованы:

- schema `SettlementControlLease` и `SettlementControlEvent` с current-state lease, отдельными session hash, UUID `lease_token`, сохраняемой монотонной `fencing_revision` и application-level неизменяемым audit;
- migration `0007_settlement_control_lease_and_event` с bootstrap FREE singleton `scope='settlement'` без фиктивного владельца;
- внутренние ensure/acquire/heartbeat/release/expire, HMAC session binding, fencing validation и события `ACQUIRED`, `RELEASED`, `EXPIRED`;
- внутренний административный takeover с обязательной причиной, новым token/revision и событием `TAKEN_OVER`;
- SQLite/PostgreSQL schema, lifecycle, audit и concurrency tests; migration drift отсутствует.

Migration `0007` существует в репозитории и проверена только в изолированных тестовых средах. Её применение к production не выполнялось и этим документом не утверждается.

На том историческом этапе до расширения ручных writers и применения плана оставалось:

- связать control acquire с единственной открытой бизнес-сменой делопроизводителя (`EmployeeShift` + `WatchPeriod`); expiry lease не должен передавать бизнес-право второму сотруднику до закрытия этой смены;
- привести acquire/takeover и все кадровые writers к единому порядку `Lease, если участвует → все Employee по PK → все EmployeeAccess по PK`, исключив joined-row locks и повторно проверяя предварительно прочитанные данные;
- добавить общий write-boundary guard, который первым блокирует control row, проверяет session/token/revision, неблокирующим чтением строит полный lock plan, затем блокирует все `Employee` по PK, все `EmployeeAccess` по PK с `OF self`, повторно проверяет связи/активность/роли и только после этого переходит к `PhysicalBed` → `PhysicalRoom` → `EmployeeBedOccupancy` по PK;
- подключить gate к `settle`, `relocate`, `release` и будущему M8;
- добавить control HTTP endpoints/URLs, хранение credentials в пользовательской session и browser heartbeat;
- controlled 409 для старой/перехваченной сессии без частичной доменной записи;
- server-side read-only режим для остальных уполномоченных пользователей;
- расширение существующей карты v29 индикатором владельца, acquire/release, read-only banner и административным takeover без переписывания комнат, коек, поиска, счётчиков, DnD и guards;
- реализовать применение авторосселения только через общий gate после готовности остальных M2–M7.

В текущем HEAD control HTTP/session/UI, write gate, M8 и ручной сменный контур подключены. Отдельным follow-up остаётся ранее зафиксированное доказательство связи `acquire` с единственной открытой бизнес-сменой делопроизводителя; это не меняет статусы официальной смены жильца и двухдневного применения плана.

Точный timeout утверждается эксплуатационно до включения HTTP/browser lifecycle. Существующая migration не назначает владельца автоматически, не хранит history-поля в lease и не делает кадровый график техническим lock.

До первой блокировки `EmployeeAccess` gate обязан знать полный набор `Employee`: владельца lease/оператора, subject employee, отличный `settled_by`/actor и всех участников пакетного Apply. Порядок `Employee(A) → EmployeeAccess(A) → Employee(B)` запрещён; невозможность заранее построить полный набор завершает команду fail-closed. Предварительно прочитанный Access не является авторитетным до повторной проверки под блокировками, joined Employee/Role не расширяют lock set, а отдельный Role-lock при необходимости выполняется только после EmployeeAccess. OUP, login/activation, кадровые переводы и batch writers используют тот же кадровый префикс без Lease.

До внедрения DB-ограничения обязательна проверка существующих overlaps; иначе migration должна остановиться.

## 8. M6 — room profiles, явные категории и resolver rules

Статус: `MINIMAL MVP CORE COMPLETE / PERSISTENT CONFIG PARTIAL`. Публичная read-only функция `resolve_settlement_cohort(*, cohort_id)` возвращает immutable placements/unresolved, reason codes, provenance и deterministic fingerprint. Порядок внутренних волн: `CONFIRMED binding → EquipmentAssignment → PersonnelPosition → controlled unresolved`. Сменный контур реализован `0015`/`0016`; внешний UI ещё не реализован.

- gender, early/standard/special;

- reserve/protected/service;

## 10. M8 — транзакционное применение

Статус серверного контура и интерфейса: `COMPLETE`. Реализовано только для актуального `CONFIRMED` M7-плана:

- canonical domain API `apply_confirmed_settlement_preview(*, run_id, work_shift, control_context, confirm_replace_manual=False)`;
- отдельная атомарная и идемпотентная операция для ночной и дневной смены;
- явное предупреждение перед повторным Apply, который может заменить AUTO/MANUAL только целевого WatchPeriod и обязан закрыть/supersede прежние строки без удаления истории;
- обязательную действующую control fencing revision;
- stable lock order `Lease → nonlocking full lock plan → все Employee PK → все EmployeeAccess PK с OF self → все SettlementResident PK с OF self → revalidation → PhysicalBed PK → PhysicalRoom PK → EmployeeBedOccupancy PK`; external resident не добавляет фиктивный Employee/Access, после первого Access-lock запрещены новые Employee-locks, а неполный plan завершает Apply fail-closed;
- re-read/input hash;
- полный COMMIT validator;
- atomic safe batch;
- audit/result links;
- idempotent replay Application той же смены одного плана;
- stale/no-write contract.

Legacy preview никогда не является входом Apply.

Migration `settlement.0014_m8_apply_provenance` зависит от `settlement.0013_resident_occupancy_subject`, является schema-only и не выполняет backfill. Она добавляет immutable `SettlementPreviewApplication`/`SettlementPreviewApplicationItem` и nullable occupancy provenance. Reverse разрешён только до появления Application/provenance/replacement rows и иначе fail-closed.

Повторный Apply не затрагивает другие или завершённые WatchPeriod. Unchanged AUTO переиспользуется как `REUSED`; relocation, swap и unresolved заменяют только доказанный baseline текущего cohort/WatchPeriod. MANUAL заменяется только при `confirm_replace_manual=True`, без него возвращается controlled confirmation-required, а история сохраняется. Resolver включает replaceable baseline в fingerprint; изменение после DRAFT делает preview stale.

Миграция `settlement.0015_cohort_member_work_shift` добавляет смену и происхождение участника без угадывания legacy. Миграция `settlement.0016_shift_scoped_apply_and_occupancy` добавляет смену в Application и фактическое проживание, допускает отдельные Application одного run по ночной и дневной смене и блокирует небезопасный reverse после сменных данных. Старый endpoint применения всего плана возвращает controlled HTTP 409. Production migration/deploy этим документом не разрешаются.

## 10A. Переход к следующему заезду по сменам

Статус: официальный источник смены, смена M5–M7, двухдневное применение, две UI-команды, ручное сменное проживание, M9 и отдельный режим плановой карты — `COMPLETE` локально.

Реализованная схема хранит структурированную смену и происхождение участника, допускает ровно одну неизменяемую запись на `(run, смена)` и сохраняет `SettlementPreviewRun` в lifecycle `DRAFT → CONFIRMED → SUPERSEDED`. Отдельный статус «Активирован» не вводится. Migration `settlement.0017_m9_preview_corrections` добавила неизменяемую линейную историю точечных исправлений без переписывания исходных строк M7.

Применение обрабатывает только выбранную смену. Ночная команда доступна не раньше `WatchPeriod.starts_on - 1 день`, дневная — не раньше `WatchPeriod.starts_on`; досрочное применение запрещено сервером. Каждая команда атомарна, идемпотентна и не затрагивает другую смену. Действующий план рассчитывается как исходный утверждённый план плюс последняя допустимая точечная поправка своей линейной цепочки.

Плановое право не является occupancy. До применения соответствующей смены текущая occupancy не меняется. Физическая задержка прежнего resident не создаёт вторую occupancy и не сохраняет прежнее право после установленной даты. После применения дальнейшие изменения выполняются canonical ручными writers режима «Текущая вахта».

Для internal resident официальная дневная или ночная смена поступает только из единственного `deputy_published_plan` с точным `source_crew_plan_slot`; список табельщика задаёт состав и сверку. Для external resident смену указывает делопроизводитель с exact Access и основанием. Неоднозначность либо отсутствие блокируют операцию с состоянием «Требуется проверка».

Исторические строки не получают угаданную смену: они помечаются как legacy/unverified. Reconciliation исторических записей фактического проживания без смены остаётся `NEXT`.

## 11. M9 — ручные операции и точечные исправления

Статус: сменная идентичность фактических ручных операций и точечные исправления будущего плана — `COMPLETE` локально.

Реализовано:

- новое заселение только после применения соответствующей смены; период и смену определяет сервер;
- заселение принимает точного resident, переселение и освобождение — точную запись фактического проживания;
- переселение legacy-записи без смены запрещено, освобождение разрешено по точному PK;
- ручное происхождение и смена сохраняются, другая смена не затрагивается.
- плановое перемещение, исключение и возврат сохраняются отдельными неизменяемыми событиями M9; исходные строки утверждённого плана не меняются.

Следующие отдельные команды остаются `NEXT`:

- temporary occupancy override;
- permanent binding correction;
- release/early departure.

Legacy `relocate` сохраняется как UI-механика только после явного выбора смысла операции. Молчаливое изменение binding запрещено.

## 11A. T1–T3 — единый реестр заезда

Статус: T1.1–T1.3b — `COMPLETE` локально; T1.4, T2 и T3 — `NEXT`. Текущий migration leaf приложения `rotations` — `0004_arrival_roster_employee_pool`.

`rotations.0002_arrival_roster_versions` добавила закрытое хранение исходного файла и SHA-256, версии, исходные и нормализованные строки, предварительное сопоставление, кандидатов, вопросы и события. Существующим строкам не приписываются выдуманные кадровые или жилищные факты.

`rotations.0003_arrival_roster_manual_review` добавила защищённую текущую проекцию ручной проверки и решения вопросов с точным доступом табельщика и неизменяемым журналом. Исходный Excel и исходные строки не переписываются.

`rotations.0004_arrival_roster_employee_pool` добавила формирование версии из базы `Employee` и точные строки кадрового состава. Сотрудник сохраняется FK даже без `SettlementResident`; внешняя карточка допускается без фиктивного `Employee`, доступа, роли или принадлежности к вахте. Повторное формирование создаёт новую версию, а не изменяет прежнюю.

Миграции T1.1–T1.3b не создают `SettlementSource`, `SettlementRevision`, `SettlementCohort`, `Employee`, `EmployeeAccess` или `SettlementResident` и не меняют M4–M9 либо фактическое проживание.

T1.4 должен добавить окончательное утверждение и безопасную замену прежней подтверждённой версии с сохранением истории. Только после доказанного утверждения допускается создание `SettlementSource`/`SettlementRevision`. T2 передаёт общий список заместителю начальника участка; T3 передаёт готовый состав делопроизводителю и создаёт черновой `SettlementCohort`.

Передача в расчёт блокируется, пока версия не подтверждена, есть несопоставленные строки или критические конфликты, отсутствует обязательная опубликованная расстановка, не доказана официальная смена внутреннего жильца либо не подтверждены обязательные сведения внешнего жильца.

Следующие миграции должны останавливаться при недоказуемых данных и не восстанавливать смену из чисел 1/2, свободного текста, техники или времени. Существующие T1.1–T1.3b и M4–M9 строки не переписываются; связь с ними создаётся только через доказанные точные идентификаторы.

## 12. Обработка legacy assignment types

| Legacy type | Миграционная политика |
|---|---|
| `PERMANENT` occupancy | Сохранить как historical factual record; не считать binding без подтверждения |
| `TEMPORARY` | Сохранить factual interval; проверить обязательный конец и reason/provenance |
| `PROPOSED` | Проинвентаризировать отдельно; не переносить в run и не считать подтверждённым предложением автоматически |

Удаление legacy fields/types возможно только после полного чтения старых записей новым кодом, reconciliation и отдельного rollback-плана.

## 13. Стоп-условия

Миграция останавливается, если:

- найдены неразрешённые interval overlaps;
- Equipment pair нельзя восстановить однозначно;
- неизвестна календарная группа;
- нет официального источника для binding/cohort;
- отсутствуют обязательные актуальные кадровые или room-profile факты для включаемой resolver-волны;
- фактическое число/тип техники не сверены с реестром;
- dirty worktree пересекается с изменяемыми файлами;
- PostgreSQL-проверка недоступна;
- control lease/takeover допускает двух владельцев, старую revision или необъяснимый административный перехват;
- data migration предполагает постоянное решение за владельца продукта.
