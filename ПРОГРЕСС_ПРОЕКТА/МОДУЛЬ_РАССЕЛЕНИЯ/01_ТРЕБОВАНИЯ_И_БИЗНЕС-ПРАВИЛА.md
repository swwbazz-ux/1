# Требования и бизнес-правила

Версия: 0.5
Статус: нормативная основа разработки

## 1. Участники процесса

| Роль | Ответственность |
|---|---|
| Заместитель начальника участка | Публикует обычный производственный план, явно назначает резерв и подтверждает постоянный перевод сотрудника |
| Делопроизводитель | Получает исключительное управление settlement-контуром, ведёт карточки внешних жильцов, проверяет и фиксирует версию состава заезда, запускает preview, разбирает конфликты, подтверждает Apply и выполняет разрешённые ручные корректировки |
| Администратор | Наблюдает состояние управления; при необходимости явно перехватывает его с обязательной причиной и аудитом, не обходя доменные правила расселения |
| Владелец жилищной карты | Утверждает привязку жилищных мест к технике, функциям, категориям и защищённым зонам |
| ОУП/кадровый источник | Ведёт внутреннего `Employee` и его принадлежность к `WatchComposition`, даёт официальные ФИО, пол, реальную должность, подразделение и кадровый статус |
| Мастер/диспетчер/уполномоченный | Устанавливает действующий режим комнаты на период по утверждённому рабочему процессу |
| Руководитель/уполномоченный | Разрешает постоянные исключения, изменение постоянного жилищного закрепления и ручное решение дефицита мест |
| Система | Применяет правила, блокирует недоказанные решения и сохраняет трассировку |

### 1.1. Единственный активный управляющий расселением

1. В каждый момент право выполнять изменяющие settlement-команды принадлежит ровно одной активной управляющей сессии во всём модуле.
2. Обычный владелец управления обязан иметь действующий доступ `settlement_clerk`. Наличие роли, кадровой должности, рабочего графика или открытой страницы само по себе не создаёт право записи.
3. Право управления связано одновременно с `owner_access` → действующим `EmployeeAccess`, серверной сессией, отдельным непрогнозируемым `lease_token` и текущей `fencing_revision`. `owner_session_hash` идентифицирует серверную сессию, `lease_token` доказывает конкретное владение, а `fencing_revision` задаёт его монотонный порядок; эти значения не взаимозаменяемы. Второй браузер, устройство или отдельная сессия того же сотрудника не получает право записи автоматически.
4. Несколько вкладок одной серверной сессии могут видеть один lease, но их изменяющие запросы сериализуются сервером. Единственный пользователь не считается гарантией отсутствия параллельных HTTP-запросов.
5. Preview без записи и чтение карты доступны второму делопроизводителю и администратору без lease в режиме read-only. `settle`, `relocate`, `release`, постоянная коррекция и реализованный backend Apply требуют действующих `lease_token` и `fencing_revision`.
6. Lease приобретается, продлевается и освобождается атомарно в БД. При acquire создаётся новый непрогнозируемый UUID `lease_token`; явный release и expiry очищают `owner_access`, `owner_session_hash`, token и timestamps текущего владения, увеличивают `fencing_revision` и делают прежний token недействительным. Закрытие браузера или потеря сети не считаются доказанным освобождением; после expiry техническое управление восстанавливает владелец всё ещё открытой бизнес-смены, а административный перехват остаётся аварийным механизмом.
7. Администратор не становится вторым параллельным управляющим. Перехват с подтверждением и обязательной причиной одной транзакцией заменяет `owner_access`, session hash, token и timestamps текущего владения, увеличивает `fencing_revision` и сохраняет полную историю только в `SettlementControlEvent`.
8. После перехвата, release или expiry любой запрос со старым token либо revision отклоняется до доменной записи стабильной контролируемой ошибкой. Административная роль не отключает interval, transfer, sex, room-profile, binding и иные hard constraints.
9. Начало каждого изменяющего запроса сериализуется на singleton-записи управления до блокировок Employee, Bed, Room и Occupancy. Уже начатая транзакция завершается или откатывается раньше, чем перехват получает управление.
10. Точный heartbeat/timeout задаётся конфигурацией и принимается эксплуатационно до включения функции; он не зашивается в бизнес-алгоритм.

Карта v29 расширяется без переписывания существующего интерфейса. Сохраняются комнаты, койки, поиск, счётчики, DnD и действующие guards. Добавляются компактный индикатор текущего владельца, команды «Начать работу» и «Завершить работу», read-only banner для второго делопроизводителя, административная кнопка «Перехватить управление» с подтверждением и обязательным полем причины, а также уведомление прежнего владельца о потере управления. Любая settlement-запись из UI блокируется без действующих token и revision.

### 1.2. Бизнес-смена делопроизводителя и техническое управление

1. В системе две чередующиеся вахты, и в каждой работает свой делопроизводитель.
2. Одновременно открыта только одна бизнес-смена делопроизводителя. Второй делопроизводитель находится на межвахтовом отдыхе и не может открыть параллельную смену.
3. Следующий делопроизводитель начинает работу только после штатного закрытия предыдущей смены. Бизнес-право определяется открытым `EmployeeShift` и связанным `WatchPeriod`.
4. `SettlementControlLease` не заменяет бизнес-смену: это только техническая блокировка browser writers внутри допустимой смены.
5. Expiry lease не передаёт бизнес-право второму делопроизводителю, пока первая смена открыта. Владелец действующей смены может восстановить lease; takeover остаётся аварийной административной командой.
6. Проверка открытой смены/WatchPeriod при control acquire является обязательным follow-up. До отдельной реализации документация не считает её существующей в коде.

## 2. Физический фонд

1. Физическая комната и физическая койка существуют независимо от того, переданы ли они ООО «Коппер Рисорсез».
2. Все комнаты отображаются на карте.
3. Непереданные комнаты отображаются приглушённо и недоступны для автоматического и ручного заселения.
4. Делопроизводитель не изменяет статус передачи комнаты.
5. Архивный снимок фонда содержит 60 комнат и 348 коек, из них 47 комнат и 270 коек были переданы. Это не вечная константа и должно читаться из актуальных данных.
6. Стандартная комната содержит два физических блока A и B, по три койки: A1–A3 и B1–B3.
7. Физическая вместимость не может превышаться ни автоматической, ни ручной операцией.

## 3. Технические комнаты и тяжёлая техника

1. Одна единица тяжёлой техники получает логическую пару из двух атомарных жилищных мест.
2. Пара отображается физическими койками `An + Bn` в одной комнате.
3. Два сотрудника одной машины в одной месячной вахте занимают две разные физические койки этой пары.
4. A/B не обозначают DAY/NIGHT и не должны кодироваться как постоянная смена сотрудника.
5. Если сотрудники меняются DAY/NIGHT, их постоянные койки сохраняются.
6. Одна техническая комната содержит три пары техники.
7. Распределение текущих DAY/NIGHT внутри комнаты должно сохранять схему 2+1 либо её зеркало. Это проверяется для периода заезда, но не изменяет идентичность постоянной койки.
8. Если графики отдельных сотрудников делают схему 2+1 недоказуемой, автоматическое применение блокируется для затронутой комнаты.

## 4. Чередующиеся месячные вахты

1. `AccommodationAnchorCalendarSlot` — конкретный экземпляр `AccommodationAnchor + WatchComposition + WatchPeriod` с identity `(anchor_id, watch_period_id)`.
2. Включительные `valid_from/valid_to` точно равны `WatchPeriod.starts_on/ends_on`; composition slot обязан совпадать с composition периода. Несовпадение отклоняется fail-closed.
3. Сохранённые границы не переписываются. Последующее расхождение с WatchPeriod означает stale relation и запрещает подтверждение/коррекцию.
4. Две календарно чередующиеся группы могут использовать одну физическую койку только через конкретные непересекающиеся slots. Пересекающиеся подтверждённые slots одного места запрещены независимо от DAY/NIGHT или названия смены.
5. Для следующего WatchPeriod создаётся новый slot. Повторяемое долгосрочное правило относится к M5/M6.
6. В каждом календарном слоте атомарного места может быть не более одного постоянного `SettlementResident` на пересекающемся периоде действия закрепления.
7. Для внутреннего resident принадлежность к календарной группе проверяется по связанному `Employee`; для внешнего resident корпоративная `WatchComposition` не выдумывается. Совместное использование койки разрешается только по доказанному непересечению конкретных календарных slots.
8. Фактическое заселение всегда создаётся на конечный интервал конкретного заезда.

## 5. Постоянное закрепление и оперативная работа

1. Постоянная койка не определяется текущим оперативным назначением на технику.
2. Временная смена машины, комплекса, наставника, экипажа, DAY/NIGHT, ремонтной или резервной техники не изменяет постоянное жилищное закрепление.
3. Если постоянного жилищного закрепления ещё нет, обычный опубликованный `CrewPlan` и созданный из него `EquipmentAssignment` могут предложить исходную жилищную группу и место.
4. Делопроизводитель не утверждает отдельный «постоянный производственный план». При Apply он подтверждает первичное жилищное закрепление вместе с фактическим заселением; система сохраняет снимок производственного основания.
5. После создания жилищного закрепления оно имеет приоритет над всеми последующими `EquipmentAssignment`. Оперативное назначение не является командой переселения.
6. Постоянное изменение койки выполняется отдельной подтверждённой командой уполномоченного лица и сохраняет основание, автора и ревизию.
7. Временное переселение создаёт только ограниченное по времени фактическое исключение и не уничтожает постоянное закрепление.

## 6. Состав заезда

Общая identity потенциального и фактически проживающего жильца — `SettlementResident`. Для внутреннего resident authoritative source остаётся связанный `Employee`: из него берутся кадровые сведения, пол и принадлежность к `WatchComposition`. Для подрядчика, командированного или иного внешнего человека используется отдельная карточка без `Employee`; она не создаёт login, PIN, `Role`, `EmployeeAccess` или кадровые/производственные права и не получает выдуманную корпоративную `WatchComposition`. M4 binding, M5 cohort member и фактическая occupancy используют `SettlementResident` как subject: внешний resident может входить в cohort, получать calendar binding, быть заселён, переселён и освобождён через canonical server-side API. Минимальное безопасное read-only ядро M6, сохраняемый immutable preview M7 и backend M8 Apply реализованы. UI создания внешней карточки, UI ручного внешнего заселения, HTTP/UI preview-confirm-apply и trainee adapter ещё не реализованы.

Техническое имя `EmployeeBedOccupancy` временно сохраняется для совместимости, но прямого subject-FK на `Employee` в модели больше нет. Обязательный subject — `resident`; uniqueness, overlap и interval guards сравнивают `resident_id`. `settled_by` и другие actor/audit-поля остаются ссылками на корпоративный `Employee` и не меняют identity жильца.

Canonical write API фактического проживания:

- `settle_resident_on_bed`;
- `relocate_resident_to_bed`;
- `release_resident_from_bed`.

Employee-based функции разрешены только как совместимые адаптеры действующего внутреннего HTTP UI. Они обязаны находить уже существующий internal resident и не вправе скрыто создавать `SettlementResident`.

Пол является обязательным hard-rule фактом. Internal resident получает его только из `Employee.sex`, без дублирования в resident. External resident обязан иметь `external_sex=male/female`; неизвестный пол не обходит room guard. Несовместимое изменение `external_sex` при открытой occupancy отклоняется, а допустимое изменение входит в M6 fingerprint и делает ранее сохранённый M7 preview stale.

1. Авторосселение работает только для конкретного утверждённого состава заезда и конечного интервала `[arrival_at, departure_at)`.
2. Состав заезда должен включать всех ожидаемых жильцов, а не только внутренних сотрудников с назначением на технику.
3. Базовый состав собирается из официальных `WatchComposition`, `WatchPeriod` и подтверждённых откликов/решений о ротации; утверждённые продления и ручные изменения входят отдельными версионируемыми поправками.
4. Делопроизводитель проверяет и фиксирует жилищную версию состава, но не переписывает кадровую принадлежность к вахте.
5. Идентичность чередующейся месячной группы определяется записью `WatchComposition`, а не названием, датой, бригадой или графиком.
6. Для каждой строки состава обязательны:
   - authoritative resident subject;
   - время прибытия и выбытия;
   - календарная группа/вахта;
   - статус участия;
   - источник и версия утверждения.
7. Незаезды, продления, ранние выезды, командированные и дополнительные сотрудники фиксируются как изменения состава с новой версией.
8. `EquipmentAssignment` обогащает строку маршрутом техники, но не формирует полный состав заезда.

Для внутреннего resident без применимого подтверждённого binding M6 использует строгий порядок маршрутизации: `CONFIRMED binding → EquipmentAssignment → PersonnelPosition → controlled unresolved`. Equipment route использует только действующее назначение со статусом `ACCEPTED`, заполненной `role`, отсутствующей `shift`, `assigned_at` не позже начала `WatchPeriod`, `accepted_at` отсутствующим либо уже наступившим и `ended_at` отсутствующим либо ещё не наступившим. Цепочка должна однозначно доказать active Equipment, единственный active equipment anchor, единственный effective `CONFIRMED` AnchorBedAssignment, `CONFIRMED` CalendarSlot того же WatchPeriod и PhysicalBed. Множественность не разрешается первой строкой. DAY/NIGHT остаётся только provenance/compatibility-контекстом и не создаёт вторую identity физической койки.

## 7. Совместимость

Жёстко проверяются и никогда не нарушаются ради компактности:

- одна физическая койка — не более одного фактически проживающего сотрудника в пересекающийся интервал;
- один сотрудник — не более одной фактически занимаемой койки в пересекающийся интервал;
- мужчины и женщины расселяются раздельно;
- ранний и стандартный режимы не смешиваются в одной комнате на один период;
- сотрудники подрядчиков не смешиваются с сотрудниками компании без отдельного явного разрешения уполномоченного лица;
- защищённые комнаты и места не используются общим алгоритмом;
- превышение вместимости запрещено;
- неизвестный обязательный факт блокирует решение, а не заменяется предположением.

После жёстких проверок система ранжирует допустимые варианты. Она стремится сохранить постоянную койку, собрать вместе утверждённую жилищную группу, компактно занять фонд, разместить однотипную технику рядом и уменьшить одновременную нагрузку на комнату. Такие предпочтения не создают несуществующих коек и не разрешают нарушение жёстких правил.

## 8. Категории без тяжёлой техники

### 8.1. Общий принцип маршрутизации

Для нового сотрудника без постоянного закрепления применяется последовательность:

1. определить authoritative source: внутренний `Employee` либо внешняя карточка `SettlementResident`;
2. проверить обязательные структурированные факты; произвольный JSON не создаёт кадрового или организационного права;
3. определить пересечение допустимых фондов по полу, типу resident, организации внешнего жильца и protected-правам;
4. для стажёра использовать настоящую должность уже принятого `Employee`, но только после доказанного структурированного статуса стажировки;
5. применить явную жилищную категорию, например резерв; она имеет приоритет над временной работой на технике;
6. при отсутствии явной категории использовать опубликованное назначение на технику;
7. затем использовать официальную должность, службу и функциональную группу;
8. вернуть конфликт, если доказанного маршрута или допустимого фонда нет.

Существующее постоянное закрепление проверяется раньше этой последовательности и сохраняется при временных изменениях работы.

Каждое версионируемое resolver-правило определяет официальный признак, жилищную группу, допустимые места, жёсткие ограничения, порядок ранжирования, владельца и период действия. Если правило не настроено, результат — `CONFLICT/resolver_not_configured`; система не угадывает.

### 8.2. Явные категории и резерв

1. Резерв является отдельной жилищной категорией только после явного назначения заместителем начальника участка.
2. Назначение бывает постоянным или временным. Для временного назначения обязательна дата окончания.
3. Отсутствие назначения на технику само по себе не делает сотрудника резервистом.
4. Временная работа резервиста на технике не меняет его категорию и постоянную койку.
5. Постоянный перевод из резерва закрывает прежнее назначение, сохраняет историю и запускает отдельное изменение постоянного закрепления.
6. Категория не означает, что система держит пустой физический пул «на всякий случай»: места выделяются фактическому подтверждённому составу с учётом дефицита фонда.

### 8.3. Стажёры и постоянные помощники

1. Стажёр — временный статус сотрудника, а не отдельная жилищная категория.
2. Отдельный постоянный пул коек для стажёров не создаётся.
3. Стажёр уже является внутренним `Employee`, оформленным на настоящую должность; отдельные `Vacancy` и «будущая должность стажёра» не создаются.
4. M6 вправе применить trainee-routing только по существующему структурированному статусу стажировки. Если такого authoritative state нет, требуется отдельный adapter и resolver возвращает конфликт, а не читает произвольный JSON.
5. Учебная машина, наставник и временная смена не определяют постоянную койку; маршрутизация использует настоящую должность `Employee`.
6. «Помощник машиниста экскаватора» — постоянная должность. Такие сотрудники образуют функциональную жилищную группу и не привязываются к текущему экскаватору.

### 8.4. Технические группы

1. Всех технических сотрудников максимально группируют по официальному типу техники.
2. Одна единица тяжёлой техники занимает пару `An + Bn`; в стандартной технической комнате размещаются три единицы.
3. Одинаковые типы техники размещаются вместе и, по возможности, в соседних комнатах.
4. Неполная техническая группа не удерживает пустую пару: она может быть отдана другой совместимой технической группе.
5. Шесть бульдозеров должны занимать две комнаты по три единицы, если актуальный реестр подтверждает шесть действующих единиц.
6. Количество грейдеров и любой другой техники берётся из актуального реестра, а не зашивается в код. Ожидаемое количество грейдеров — две или три единицы — подлежит сверке перед настройкой.

### 8.5. Постоянные функциональные группы

- водители легковых автомобилей и «Газелей» составляют одну постоянную группу и размещаются вместе независимо от конкретной машины;
- водители вахтовок/автобусов образуют отдельную группу и не объединяются с водителями лёгкого транспорта;
- водитель тягача относится к механической службе и размещается вместе с механиками и другими сотрудниками этой службы;
- мужские сотрудники АСУ ГТК и охраны труда/ПБ/БДД составляют одну компактную совместимую группу; правило является версионируемым и пересматривается при изменении штата;
- мужские ИТР сначала группируются по службе, после чего совместимые службы могут делить комнату ради компактности;
- мужские диспетчеры, горные мастера и оперативное руководство образуют одну функциональную группу с учётом режима отдыха.

### 8.6. Женщины

1. Все женщины размещаются в женском фонде совместно независимо от технической или служебной группы; пол является жёстким правилом верхнего уровня.
2. Внутри женского фонда система по возможности учитывает службу и график.
3. Предпочтительный вариант для комнаты — две сотрудницы дневного графика и диспетчер ночного графика. Это улучшает использование фонда и уменьшает одновременное нахождение трёх человек в комнате.
4. Если дефицит не позволяет выполнить предпочтение, совместное проживание трёх сотрудниц с одинаковым временем отдыха допустимо. Это мягкое предпочтение, а не причина отказа.
5. Каждая сотрудница занимает отдельную физическую койку; совместное использование одной койки в одной месячной вахте запрещено.
6. DAY/NIGHT сотрудника не равны комнатным режимам EARLY/STANDARD. Предпочтение DAY/NIGHT применяется только внутри уже совместимого `RoomUseProfile`.

### 8.7. Защищённые комнаты, подрядчики и дефицит

1. Комнаты руководства и иные защищённые комнаты исключены из общего пула даже при дефиците. Изменение их назначения выполняется только отдельным уполномоченным решением.
2. Подрядчики и другие внешние жильцы представлены внешними `SettlementResident` с нормализованным текстовым полем организации, размещаются отдельно от внутренних сотрудников и получают остаточный приоритет. Внешние жильцы одной организации группируются как мягкое предпочтение; при нехватке иначе совместимого места допускается совместное проживание внешних жильцов разных организаций. Организация сравнивается как `trim` + case-insensitive exact match, без fuzzy matching и отдельного справочника работодателей. Внутренние и внешние жильцы в одной комнате не смешиваются.
3. Жилой фонд имеет фиксированную ограниченную вместимость. Алгоритм не резервирует пустые пулы для переменных категорий и стремится компактно использовать каждую разрешённую койку.
4. Если для подтверждённой группы не хватает подходящих мест, система показывает один групповой конфликт с величиной дефицита и затронутыми сотрудниками.
5. Система не применяет скрытый приоритет и не решает сама, кого оставить без места. Решение принимает уполномоченный руководитель и фиксирует основание.
6. Решение дефицита хранится отдельно от исходного run: выбранные руководителем сотрудники и способ решения явно записываются, после чего выполняется новый расчёт либо отдельная разрешённая ручная команда. Исходный конфликт не переписывается.

Конкретные должности, сотрудники и номера комнат задаются данными конфигурации, а не зашиваются в алгоритм.

## 9. Повторный запуск и ручные решения

1. Штатный workflow: `preview → подтверждение → Apply auto baseline → ручные корректировки → итог`.
2. MANUAL-before-first-Apply отсутствует: ручные исправления начинаются после создания auto baseline целевого WatchPeriod.
3. Допустимое существующее заселение целевого периода возвращается как `KEEP`; недопустимое — как `CONFLICT`, а не скрытый автоматический переезд.
4. Повторный Apply может заменить auto baseline и ручные корректировки только целевого WatchPeriod и требует явного предупреждения пользователя.
5. История не удаляется: предыдущие AUTO/MANUAL записи закрываются либо получают `superseded`; provenance хранит AUTO run или MANUAL actor/reason.
6. Другие и завершённые WatchPeriod повторным Apply не затрагиваются.
7. Постоянная ручная корректировка изменяет отдельное постоянное закрепление и требует повышенного подтверждения.
8. После окончания временного исключения следующее заселение снова использует постоянное закрепление.

## 10. Preview и Apply

1. Preview ничего не меняет в фактической занятости.
2. Реализованный M7 сохраняет результат M6 в `SettlementPreviewRun` и неизменяемых строках `SettlementPreviewPlacement`/`SettlementPreviewUnresolved` с resolver fingerprint, normalized fingerprint и source snapshot.
3. Жизненный цикл сохранённого preview: `DRAFT → CONFIRMED → SUPERSEDED`; на один `WatchPeriod` допускается не более одного `CONFIRMED` запуска.
4. Подтверждение принимает только exact server-side `SettlementControlWriteContext`, повторно запускает M6 и отклоняет stale либо конкурентно устаревший preview без частичной записи.
5. Нерасселённые residents сохраняются с точными reason codes; их наличие не запрещает подтверждение preview и предназначено для последующей ручной обработки.
6. M7 сам не пишет occupancy, не меняет M4/M5, resident, комнаты, койки или anchors; запись выполняет отдельный backend M8 Apply.
7. Реализованный canonical API `apply_confirmed_settlement_preview(*, run_id, control_context, confirm_replace_manual=False)` принимает только текущий актуальный `CONFIRMED` run, exact server-side control context, совпадающие M6/M7 fingerprints и неизменённые placement/unresolved rows.
8. Все заранее показанные безопасные строки должны применяться одним атомарным пакетом. Нерасселённые строки остаются для ручной работы.
9. Повторный Apply одного run идемпотентно возвращает существующий `SettlementPreviewApplication` и не создаёт дубликаты.
10. Первый Apply создаёт AUTO baseline целевого WatchPeriod; только после него доступны штатные MANUAL-корректировки.
11. Повторный Apply считает заменяемыми только AUTO/MANUAL occupancy resident текущего APPROVED cohort в его authoritative `[arrival_at, departure_at)` и том же WatchPeriod. Неизменившаяся AUTO occupancy получает действие `reused` без закрытия, новой строки и изменения исторических timestamps.
12. MANUAL correction текущего целевого периода заменяется только при `confirm_replace_manual=True`; без подтверждения возвращается controlled confirmation-required. Заменённые AUTO/MANUAL строки сохраняются в истории, а unrelated residents и другие/завершённые WatchPeriod остаются hard conflict и не изменяются.
13. Resolver включает весь replaceable baseline и его provenance в детерминированный fingerprint. Изменение baseline после DRAFT делает preview stale; DAY/NIGHT не создаёт отдельную identity PhysicalBed.

## 11. Аудит

Для каждого решения должны сохраняться:

- кто запустил расчёт и кто применил;
- дата и время;
- период заезда;
- версия состава;
- версия правил;
- использованные источники и ревизии;
- исходное и итоговое состояние;
- reason codes;
- ручное основание и комментарий, если применимо.
- решение руководителя по групповому дефициту и затронутые им сотрудники.

Удаление подтверждённых исторических решений не допускается обычным пользовательским процессом.
