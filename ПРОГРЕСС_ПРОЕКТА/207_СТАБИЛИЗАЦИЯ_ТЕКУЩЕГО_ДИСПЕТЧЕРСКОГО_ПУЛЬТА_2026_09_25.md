# Стабилизация текущего Диспетчерского пульта — 25.09.2026

## Цель

Сделать единой отправной точкой не старую feature-ветку, а фактически
работающий на `driverform.ru` Диспетчерский пульт, сохранить его поведение и
поэтапно разделить накопившиеся контуры без большого переписывания.

## Исправленный эксплуатационный дефект

После фонового fragment-refresh скрытое поле `next` могло получить
`?_operational_fragment=dispatcher`. Обычный POST завершения смены затем
перенаправлял основное окно на JSON-фрагмент — пользователь видел сырой JSON
вместо пульта.

Исправление состоит из двух защит:

1. форма всегда получает полный безопасный URL экрана без внутренних
   fragment-параметров;
2. сервер повторно очищает `next` и `Referer`, допускает только текущий host и
   сохраняет только пользовательские query-параметры.

Основной обнаруженный риск первого этапа: браузер Диспетчера загружал почти
половину JavaScript, предназначенного только для мобильного Горного мастера.
Этот код не исполнялся на desktop-экране, но увеличивал payload и делал любое
изменение одной роли опасным для другой.

## Выполненный этап 1

- Из `static/js/dispatcher-control-v1.js` удалена повторная мобильная ветка
  Горного мастера: mobile fragment-refresh, PWA update UI, touch/drag runtime и
  связанные недостижимые desktop-ветки.
- Канонический mobile runtime Горного мастера сохранён в условной ветке
  `mining_master_mobile_enabled` общего шаблона и не менялся.
- Desktop runtime уменьшен примерно вдвое: с `364 394` до `178 164`
  байт и с `6 610` до `3 317` строк.
- Оставшийся runtime размечен семью стабильными зонами: старт/смена, карточка
  техники, транспорт запросов, realtime reconciliation, карточка/тема,
  service worker/диагностика, desktop-доска/DnD.
- Публичный диагностический объект получил корректное имя
  `window.DispatcherSyncDebug`.
- Добавлен контрактный тест границы ролей: мобильные функции не должны снова
  попадать в desktop bundle, при этом обязаны оставаться в mobile-ветке.
- Версия оболочки Диспетчера подготовлена как
  `dispatcher-desktop-shell-v132`, чтобы будущая публикация не оставила у
  браузеров закэшированный `v131`.

## Проверка этапа 1

- `23/23` адресных Django-теста Диспетчера и системного push прошли;
  `manage.py check` завершился без замечаний.
- Все `87/87` профильных Node-тестов Диспетчера, fragment runtime,
  responsive-контрактов, звука, push и границы ролей прошли.
- В изолированной временной SQLite Browser QA прошёл реальный цикл
  `открыть смену -> получить fragment-refresh -> закрыть смену`.
  Версия доски обновилась с `8` до `9`, безопасный `next` остался
  `/dispatcher/control/`, закрытие вернуло `text/html`, а не JSON.
- На `1280 px` и `390 px` горизонтального overflow нет; итоговый журнал
  браузера пуст. Временные БД, сотрудник, доступ, журналы и QA-сервер удалены.
- Карточки техники, поиск и drag-and-drop на этом пустом Browser QA-наборе не
  воспроизводились; их действующие контракты покрыты профильными Node-тестами,
  а полный наполненный Browser QA остаётся обязательным release gate.
- Новый include формы смены явно добавлен в production-files manifest; все
  изменённые рабочие файлы текущего пакета теперь входят в будущий release.

## Карта дальнейшего разделения

Следующие этапы выполняются отдельными малыми commit с Browser QA после
каждого, без одновременного редизайна:

1. Вынести transport/offline queue в отдельный модуль, сохранив текущий ключ
   localStorage для восстановления уже поставленных в очередь действий.
2. Вынести realtime fragment reconciliation и зафиксировать его DOM-контракт
   отдельными тестами.
3. Разделить карточку техники и desktop board/DnD, оставив общий публичный
   bootstrap минимальным.
4. Разобрать CSS по функциональным секциям с visual-regression проверкой до
   удаления перекрывающих исторических правил.
5. Только после стабилизации frontend выделять dispatcher-обработчики из
   `trips/views.py`; перенос backend нельзя смешивать с изменением поведения.

## Обязательные release gates

- профильные Django-тесты Диспетчера и проверка `manage.py check`;
- все Node-контракты Диспетчера, fragment runtime и boundary ролей;
- Browser QA `1280×800` и `390×844`: открытие/закрытие смены, fragment-refresh,
  карточка техники, поиск, drag-and-drop, отсутствие overflow и ошибок консоли;
- проверка deployment manifest: каждый новый production-файл должен быть явно
  включён;
- публикация только отдельным разрешённым этапом через `VERIFY`, затем
  `DEPLOY` того же полного SHA с rollback-комплектом.
