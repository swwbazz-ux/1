# Регламент сквозного тестирования учетной системы

Дата утверждения: 23.07.2026.

Статус: основной нормативный документ для демонстрационных прогонов, регрессии, пилотных смен и подготовки решения о реальном запуске.

## 1. Назначение

Этот регламент определяет:

- как подготовить систему и тестовые данные;
- как пройти производственную цепочку минимум через две смены;
- какие роли, интерфейсы, состояния, отчеты и отрицательные сценарии проверить;
- как рассчитать ожидаемый результат до начала рейсов;
- какие доказательства собирать;
- как оформлять дефекты;
- как готовить рекомендации по исправлению;
- в каком виде выдавать итоговый отчет;
- по каким критериям принимать решение о готовности к реальному пилоту.

Главная цель тестирования — проверить не отдельные страницы, а единый поток:

`сотрудник -> доступ -> расстановка -> смена -> назначение -> погрузка -> разгрузка -> простой -> пересменка -> отчет -> Excel -> решение руководства`.

### 1.1. Краткий рабочий порядок

1. Заполнить паспорт прогона.
2. Зафиксировать исходные открытые состояния и создать резервную копию.
3. Выбрать существующие справочники и рассчитать ожидаемые итоги.
4. Создать сотрудников с единым маркером.
5. Пройти дневную смену, простой и отрицательные проверки.
6. Создать переходящий рейс и выполнить пересменку.
7. Пройти ночную смену и закрыть тестовые состояния.
8. Сверить экран, базу, отчеты и Excel.
9. Оформить каждый дефект и рекомендацию.
10. Выдать вердикт, инвентаризацию данных и статус local / commit / push / deploy.

Старые демо-коды, ветки, проценты готовности, конкретные подписи кнопок и прежний вывод об отсутствии P0/P1 не являются действующим нормативом.

## 3. Обязательные принципы

### 3.1. Использовать реальные справочники

Во время основного прогона запрещено придумывать:

- самосвалы и их вместимость;
- экскаваторы;
- породы и грузы;
- плотности;
- точки разгрузки;
- причины простоев;
- правила расчета объема.

Перед тестом выбираются существующие активные записи базы. Если нужной связи нет, шаг получает статус `BLOCKED`, а отсутствие справочного значения оформляется отдельным дефектом или вопросом к владельцу процесса.

### 3.2. Сервер является источником истины

Рабочие интерфейсы отправляют действия. Сервер сохраняет:

- смены;
- назначения;
- рейсы;
- простои;
- журналы;
- расчетные объемы и тоннаж.

Экран, база, отчет и Excel должны показывать один согласованный результат.

### 3.3. Минимум две смены

Полный прогон обязательно включает:

- дневную смену;
- ночную смену;
- передачу техники;
- хотя бы один переходящий рейс;
- проверку состояния до и после границы смен.

Односменный сценарий допускается только как короткая целевая перепроверка уже известного дефекта.

### 3.4. Пользовательский путь проверяется через пользовательский интерфейс

Прямой вызов серверного обработчика, ORM, SQL или административного сервиса допустим только:

- для диагностики;
- для продолжения исследования после подтвержденного блокера;
- для проверки серверного состояния;
- при явном указании этого в отчете.

Если пользователь не смог выполнить шаг через штатный интерфейс, шаг нельзя отмечать `PASS`, даже если серверный обход дал правильную запись.

### 3.5. Никаких скрытых исправлений исходного состояния

До начала прогона отдельно фиксируются:

- старые открытые смены;
- активные рейсы;
- открытые простои;
- незавершенные ремонты;
- действующие назначения;
- старые тестовые данные.

Нельзя молча закрывать или удалять их ради продолжения. Влияние старого состояния должно быть показано в отчете.

### 3.6. Каждый вывод должен иметь доказательство

Для подтверждения используются:

- снимок экрана;
- видео действия или жеста;
- точный URL;
- дата и время;
- HTTP-статус и ответ;
- журнал браузера или сервера;
- идентификатор записи;
- read-only запрос к базе;
- Excel-файл и координата ячейки;
- повторное воспроизведение.

Фразы «иногда не работает» или «кажется, неправильно» без воспроизводимых фактов имеют статус `OBSERVATION`, а не подтвержденного дефекта.

Артефакты одного прогона хранятся в отдельном каталоге с ID прогона. Рекомендуемый формат имени:

`<ID_прогона>_<номер_шага>_<роль>_<экран>_<статус>_<время>`.

Снимки и выгрузки с персональными данными не размещаются в публичных каталогах.

### 3.7. Тестовые данные должны легко находиться

Каждый прогон получает идентификатор:

`СКВОЗНОЙ_ГГГГММДД_RNN`

Пример:

`СКВОЗНОЙ_20260723_R01`

ФИО тестового сотрудника начинается с единого маркера:

`ТЕСТ_СКВОЗНОЙ_20260723_R01 Диспетчер День`

Один и тот же маркер по возможности указывается также в комментарии или табельном номере.

Постоянные PIN-коды, пароли, токены и иные секреты в документы и снимки экрана не включаются.

### 3.8. Production защищен от несанкционированного теста

Без отдельного прямого разрешения запрещено:

- создавать production-сотрудников;
- открывать production-смены и рейсы;
- менять production-справочники;
- выполнять сброс данных;
- менять `.env`;
- запускать миграции;
- выполнять deploy, `collectstatic` или restart сервисов.

На production по умолчанию разрешена только read-only проверка уже опубликованной версии.

## 4. Виды тестового прогона

| Вид | Назначение | Минимальный объем |
|---|---|---|
| Полный сквозной | Допуск к пилоту или проверка крупного релиза | Все основные роли, две смены, рейсы, простои, отчеты, Excel, права, мобильные устройства |
| Регрессионный | Перепроверка после исправлений P0/P1 | Исходные шаги дефекта и полный критический цикл двух смен |
| Целевой | Проверка одного интерфейса или отчета | Конкретный положительный, отрицательный и граничный сценарий |
| Мобильная приемка | Проверка реальных действий в карьере | Настоящий телефон, свайп, drag, удержание, фон, сеть, PWA |
| Сверка отчетов | Проверка учетных итогов | Контрольный расчет, база, экран, Excel, внешняя форма |

## 6. Минимальный состав ролей

### 6.1. Основной производственный прогон

| Роль | Количество | Зачем |
|---|---:|---|
| Системный администратор | 1 существующий доступ | Создание ОУП, доступы, контроль журналов |
| ОУП | 1 | Создание сотрудников и выдача доступов |
| Заместитель начальника участка | 1 | Дневная и ночная расстановка |
| Горный мастер | 2 | Пересменка |
| Диспетчер | 2 | Пересменка |
| Машинист экскаватора | 2 | Дневная и ночная смены |
| Водитель самосвала | 4 | Два самосвала в двух сменах |
| Механик | 1 | Механический простой |
| Руководитель | 1 | Read-only отчеты |

Минимум создается 14 маркированных сотрудников, если Системный администратор уже существует.

### 6.2. Дополнительный кадровый прогон

Если проверяемый релиз затрагивает перевахту, отдельно включаются:

- Табельщик;
- Начальник участка;
- сотрудник с доступом к `/my/rotation/`.

Этот контур проходит собственный цикл сбора, ответа, продления, решения, Excel и DOCX и не смешивается с производственными рейсами.

### 6.3. Другие модули

Корпоративный портал, публичная витрина, опросы, обращения, защищенные медиа и редакционные права проверяются отдельным сценарием, если они входят в изменяемый релиз. Успешный двухсменный производственный прогон не означает автоматический `PASS` этих контуров.

## 7. Подготовка окружения

### 7.1. Техническая проверка

1. Зафиксировать `git status`, текущую ветку и commit.
2. Подтвердить фактический Django-контур.
3. Создать резервную копию базы до любых изменений.
4. Запустить систему штатным способом.
5. Выполнить `manage.py check`.
6. Зафиксировать результат актуального автоматического набора тестов.
7. Проверить доступность ключевых маршрутов.
8. Открыть журналы браузера и сервера.
9. Проверить серверный и клиентский часовые пояса.
10. Проверить текущие PWA shell-версии и состояние кеша.

Успешный автоматический набор является самостоятельным доказательством, но не отменяет браузерный, ролевой, мобильный и бизнес-прогон.

### 7.2. Аудит исходного состояния

До создания сотрудников записать количество и идентификаторы:

- открытых смен;
- открытых и груженых рейсов;
- открытых простоев;
- активных ремонтов и аварий;
- ожидающих и принятых назначений;
- активных расстановок;
- отключенной техники и справочников.

Обнаруженная старая запись не удаляется автоматически. Если она мешает новому сотруднику работать, это самостоятельный результат теста.

### 7.3. Выбор реальных справочников

Выбрать и записать фактические ID и названия:

- одного активного экскаватора;
- минимум двух активных самосвалов;
- минимум двух пород с действующими расчетными правилами;
- минимум трех точек разгрузки;
- причин простоя Водителя, Машиниста и Механика;
- вместимости каждого выбранного самосвала по каждой выбранной породе;
- плотности каждой выбранной породы.

Если в базе меньше записей, сценарий сокращается только после фиксации ограничения.

### 7.4. Проверка маршрутов

Точные URL должны быть подтверждены перед каждым прогоном. Исторический документ не является доказательством существования маршрута в текущей версии.

## 8. Контрольный расчет до начала рейсов

До выполнения погрузки составить независимый контрольный расчет.

| Рейс | Самосвал | Экскаватор | Порода | Правило вместимости | Плотность | Назначенная разгрузка | Фактическая разгрузка | Смена погрузки | Смена разгрузки | Ожидаемые м3 | Ожидаемые т |
|---|---|---|---|---:|---:|---|---|---|---|---:|---:|
| 1 |  |  |  |  |  |  |  | день | день |  |  |
| 2 |  |  |  |  |  |  |  | день | день |  |  |
| 3 |  |  |  |  |  |  |  | день | ночь |  |  |
| 4 |  |  |  |  |  |  |  | ночь | ночь |  |  |

Тоннаж рассчитывается по действующему серверному правилу и округлению системы.

Отдельно вычислить ожидаемые итоги:

- общий объем, тоннаж и число рейсов;
- по смене погрузки;
- по смене разгрузки;
- по экскаватору;
- по самосвалу;
- по Водителю;
- по Машинисту;
- по породе;
- по фактической точке разгрузки;
- по переходящим рейсам;
- по простоям и их длительности.

Правила сменной атрибуции:

- выработка экскаватора относится к смене погрузки;
- выработка самосвала и Водителя относится к смене разгрузки;
- переходящий рейс хранит обе смены и не дублирует общий итог;
- назначенная и фактическая точки разгрузки хранятся раздельно;
- отмененные рейсы не попадают в фактическую выработку.

## 9. Основной двухсменный сценарий

Каждый шаг записывается в журнал выполнения из раздела 18.

### Этап A. Администратор и ОУП

1. Администратор создает маркированного сотрудника ОУП.
2. Администратор выдает первичный PIN.
3. ОУП входит по телефону и первичному PIN.
4. ОУП обязан установить новый постоянный PIN.
5. Проверить, что временный PIN больше не действует.
6. ОУП начинает рабочий период.
7. ОУП создает остальных маркированных сотрудников.
8. ОУП выдает каждому только требуемую роль.
9. Проверить журнал административных действий.

Обратить внимание:

- слабый, повторяющийся и несовпадающий PIN должен отклоняться;
- повторный доступ той же роли не должен появляться случайно;
- ФИО, должность, специализация, график и бригада должны проходить серверную валидацию;
- секретные значения после выдачи не попадают в отчет.

### Этап B. Активация ролей и изоляция сессий

1. Каждый сотрудник активирует доступ и меняет PIN.
2. Выполнить повторный вход постоянным PIN.
3. Проверить собственный стартовый экран.
4. Проверить прямой переход на чужой экран.
5. На общем устройстве выйти из одной роли и войти в другую.
6. Убедиться, что действие выполняется от имени текущего сотрудника.
7. Проверить независимость ролевых PWA и поддоменов.

### Этап C. Расстановка Заместителем начальника участка

1. Открыть требуемую производственную дату.
2. Создать дневную и ночную расстановку Водителей.
3. Создать дневную и ночную расстановку Машинистов экскаватора.
4. Проверить конфликты сотрудника и техники.
5. Опубликовать план Водителей.
6. Отдельно опубликовать план Машинистов.
7. Повторно открыть дату и проверить сохраненную ревизию.
8. Проверить, что сотрудники видят только назначенную технику и смену.

Обратить внимание:

- статус публикации должен однозначно относиться к конкретной роли;
- устаревший черновик не должен затирать новую версию;
- один сотрудник и одна техника не должны одновременно иметь конфликтующие назначения.

### Этап D. Начало первой смены

1. Дневные Горный мастер и Диспетчер начинают смену.
2. Проверить тип смены по серверному времени.
3. Дневные Водители начинают смены на двух самосвалах.
4. Дневной Машинист начинает смену на экскаваторе.
5. Ввести начальные показатели техники.
6. Горный мастер активирует экскаватор и задает контекст забоя.
7. Назначить оба самосвала под экскаватор.
8. Водители принимают назначения.
9. Проверить появление связки у всех затронутых ролей без ручной перезагрузки.

### Этап E. Дневные рейсы

Выполнить минимум два рейса.

Рейс 1:

1. Машинист выбирает первый самосвал.
2. Использует первую реальную породу.
3. Отправляет на первую точку разгрузки.
4. Водитель видит груженый рейс.
5. Водитель подтверждает разгрузку.

Рейс 2:

1. Машинист загружает второй самосвал.
2. Назначает первую точку разгрузки.
3. Водитель меняет фактическую точку на вторую существующую точку.
4. Водитель завершает рейс.
5. Проверить раздельное хранение назначенной и фактической точки.

После каждого действия проверить:

- состояние у Машиниста;
- состояние у Водителя;
- состояние у Горного мастера;
- состояние у Диспетчера;
- отсутствие дубля рейса;
- серверный журнал и ID записи.

### Этап F. Простой и отрицательные блокировки

1. Открыть для второго самосвала реальный простой Водителя.
2. Проверить изменение состояния у Водителя, Машиниста, Горного мастера, Диспетчера и Механика.
3. Попытаться погрузить самосвал в активном простое.
4. Попытаться закрыть смену при активном простое.
5. Открыть или классифицировать механический простой через Механика.
6. Закрыть простой штатным способом.
7. Проверить продолжение работы после закрытия.
8. Проверить простой в отчетах и журнале смены.

Запрещенная операция должна:

- дать понятное сообщение;
- не создать частичную запись;
- не изменить счетчики;
- не вызвать ошибку `500`.

### Этап G. Переходящий рейс

Текущий сервер запрещает закрыть смену Водителя и передать занятый самосвал, пока на нем уже существует активный рейс. Поэтому штатная последовательность пересменки проверяется так:

1. Завершить текущие рейсы первого самосвала дневного Водителя.
2. Закрыть дневную смену этого Водителя и передать показатели техники.
3. Открыть ночную смену нового Водителя на том же самосвале.
4. Оставить дневную смену Машиниста, Горного мастера и Диспетчера открытой.
5. Дневной Машинист загружает самосвал, которым уже управляет ночной Водитель.
6. Рейс остается в состоянии ожидания разгрузки и получает дневную смену погрузки.
7. Зафиксировать его видимость у дневных ролей и ночного Водителя.
8. Закрыть оставшиеся дневные смены по их штатным правилам.
9. Открыть ночные смены Машиниста, Горного мастера и Диспетчера.
10. Проверить, что новый Диспетчер и Горный мастер видят тот же активный рейс.
11. Ночной Водитель завершает разгрузку.
12. Проверить:
   - дневную смену погрузки;
   - ночную смену разгрузки;
   - признак переходящего рейса;
   - единственный общий учет рейса.

Переходящий рейс, невидимый любой новой оперативной роли, является P1.

Отдельным отрицательным шагом проверить, что попытка закрыть смену Водителя при уже активном рейсе отклоняется понятным сообщением и не меняет данные.

### Этап H. Ночной рейс

1. Ночной Машинист использует вторую реальную породу.
2. Назначает третью существующую точку разгрузки.
3. Ночной Водитель завершает рейс.
4. Сверить объем и тоннаж со вторым правилом справочника.
5. Закрыть ночные смены.
6. Закрыть рабочий период ОУП.

### Этап I. Финальное состояние

Проверить:

- открытые тестовые смены: `0`;
- открытые тестовые рейсы: `0`;
- открытые тестовые простои: `0`;
- незавершенные назначения и ремонты;
- состояние техники после смен;
- наличие всех журналов действий.

Если объект намеренно оставлен открытым для отдельного теста, это явно указывается в отчете.

## 11. Негативные и граничные сценарии

### 11.1. Авторизация

- неверный PIN;
- слабый новый PIN;
- новый PIN совпадает с временным;
- заблокированный или деактивированный доступ;
- уволенный сотрудник;
- старая вкладка после logout или блокировки;
- прямой доступ к чужому приложению.

### 11.2. Расстановка

- один сотрудник на двух машинах;
- одна техника в двух конфликтующих слотах;
- неверная специализация;
- отключенная техника;
- устаревшая версия черновика;
- повторная публикация;
- публикация только одной роли.

### 11.3. Начало смены

- нет опубликованного назначения;
- техника уже занята;
- смена сотрудника уже открыта;
- обязательные показатели пусты;
- показатели имеют недопустимое значение;
- в базе осталась старая смена другого сотрудника.

### 11.4. Рейс

- у Водителя или Машиниста нет смены;
- экскаватор не активен;
- отсутствует порода или точка;
- самосвал в простое, ремонте или аварии;
- у самосвала уже есть открытый рейс;
- повторная погрузка;
- повторная разгрузка;
- изменение завершенного рейса;
- отмененный рейс попадает в отчет.

### 11.5. Простои

- несовместимая с ролью или техникой причина;
- второй открытый простой;
- закрытие уже закрытого простоя;
- одновременное действие Водителя и Механика;
- переходящий между сменами простой;
- попытка закрыть смену при запрещающем простое.

### 11.6. Справочники

- отключенная запись больше не предлагается в новой операции;
- исторический рейс с отключенной записью продолжает отображаться;
- отсутствующая плотность или правило не превращаются в вымышленный ноль без объяснения;
- изменение справочника не переписывает историю незаметно.

## 12. Идемпотентность, повторные действия и конкуренция

В изолированной тестовой среде проверить:

- двойной тап по погрузке;
- двойное подтверждение разгрузки;
- повторное открытие и закрытие смены;
- повторное открытие и закрытие простоя;
- обновление страницы после POST;
- потерю ответа после успешной записи и повтор после восстановления сети;
- одинаковый `client_action_id`;
- новый `client_action_id` для уже невозможного перехода;
- два браузера, одновременно назначающие одну технику;
- два пользователя, одновременно открывающие смену, рейс или простой.

Критерий:

- создается не более одного учетного объекта;
- повтор получает безопасный результат или понятный конфликт;
- нет ошибки `500`;
- журналы и счетчики не дублируются;
- интерфейсы сходятся к одному серверному состоянию.

Конкурентные мутации на production без отдельного разрешения не выполняются.

## 13. Проверка времени и пересменки

### 13.1. Подтвержденный временной контракт

Владелец проекта подтвердил 23.07.2026:

- рабочая и отчетная временная зона участка — `Asia/Vladivostok`;
- дневная смена — с `07:00:00` до `18:59:59`;
- ночная смена — с `19:00:00` до `06:59:59` следующих календарных суток;
- производственная дата ночной смены — календарная дата ее начала в зоне `Asia/Vladivostok`;
- часовой пояс устройства пользователя не меняет тип смены, производственную дату и атрибуцию событий.

Работа владельца проекта из Самарской области во время межвахты является обычным удаленным доступом. `Europe/Samara` используется только для локального отображения системного времени устройства и не является бизнес-часовым поясом учетной системы.

Обязательно зафиксировать:

- серверный часовой пояс;
- часовой пояс каждого устройства;
- правила определения производственных суток;
- границы дневной и ночной смены для всех ролей.

Проверить:

1. минуту до границы смены;
2. точную границу;
3. минуту после границы;
4. одинаковую подпись смены во всех интерфейсах;
5. одинаковый `shift_type` в базе;
6. переходящий рейс;
7. переходящий простой;
8. служебное восстановление зависшей смены;
9. дату и смену во всех отчетах.

Клиент не должен самостоятельно определять смену иначе, чем сервер.

Для виртуального прогона без ожидания реальной границы времени допускается только контролируемый источник времени или тестовая фикстура в изолированной среде. Изменять системные часы рабочего компьютера или production-сервера ради теста запрещено. Способ моделирования времени обязательно указывается в отчете.

## 15. Проверка прав доступа

Полный набор ниже выполняется только в локальной или специально выделенной тестовой среде. В режиме `Production read-only` запрещены прямые POST, подбор ID, блокировка, увольнение и другие мутации. Production-проверка использует заранее подготовленную разрешенную сессию, выполняет только GET и фиксирует недоступные пункты как `NOT RUN`.

Для каждой роли:

1. Собственный экран открывается.
2. Чужой экран недоступен.
3. Прямой POST на чужой обработчик отклоняется.
4. Подстановка ID чужого объекта не меняет данные.
5. После logout, блокировки или увольнения старая вкладка теряет доступ.
6. Ролевой поддомен не открывает соседнее приложение.
7. Руководитель не получает изменяющих действий.

Минимальные перекрестные пары:

- Водитель -> Админка;
- Водитель -> Руководство;
- Руководитель -> Админка;
- ОУП -> Системная админка;
- Заместитель -> Диспетчер;
- Диспетчер -> Заместитель;
- Машинист -> Водитель;
- Механик -> Руководство.

Редирект без изменения данных считается штатным отказом только после проверки целевого адреса и базы.

## 16. Мобильность, PWA и realtime

### 16.1. Размеры экранов

Минимально проверить:

- телефон около `390 x 844`;
- телефон около `462 x 794`;
- планшет около `768 px`;
- desktop около `1280 x 720`;
- широкий desktop около `1440 x 900`.

### 16.2. Геометрия и доступность

Для каждого критического экрана проверить:

- отсутствие общего горизонтального переполнения;
- осознанный горизонтальный скролл таблицы внутри контейнера;
- ненулевую ширину полей;
- видимость текущего сотрудника, техники и смены;
- длинные ФИО и номера техники;
- размер интерактивных элементов не менее `44 px` на мобильном;
- фокус клавиатуры;
- сообщения об ошибках рядом с действием;
- безопасные зоны экрана;
- отсутствие перекрытия нижней навигацией.

Свайп, перетаскивание и длительное удержание должны иметь понятную альтернативу. Критические жесты отдельно проверяются на реальном Android-устройстве.

### 16.3. PWA

Проверить:

- manifest, `start_url`, scope и orientation;
- актуальную иконку и название роли;
- текущую shell-версию;
- первое открытие;
- установку;
- обновление service worker;
- старую вкладку и старый кеш;
- возврат из background;
- повторный вход;
- отсутствие перехода в соседнее ролевое приложение.

### 16.4. Realtime и сеть

В двух или более вкладках проверить, что без ручного reload появляются:

- назначение;
- принятие назначения;
- погрузка;
- разгрузка;
- простой;
- закрытие простоя;
- смена контекста экскаватора;
- служебное действие Диспетчера.

При разрыве связи:

- пользователь видит честный статус;
- действие не выглядит выполненным до подтверждения сервера;
- восстановление не создает дубль;
- экран возвращается к серверному состоянию.

### 16.5. Производительность и рабочий темп

Без выдумывания неутвержденных нормативов измерить:

- время входа;
- время открытия рабочего экрана;
- время подтверждения смены, назначения, погрузки и разгрузки;
- задержку появления события у другой роли;
- время формирования каждого отчета и Excel;
- поведение при медленной и нестабильной сети.

В отчете указываются фактические значения, число повторов и устройство. Если согласованный норматив отсутствует, результат получает статус `OBSERVATION`, а не произвольный `FAIL`.

## 17. Статусы шага

| Статус | Значение |
|---|---|
| `PASS` | Штатный пользовательский путь полностью дал ожидаемый результат |
| `FAIL` | Получен воспроизводимый дефект |
| `BLOCKED` | Шаг нельзя выполнить из-за другого дефекта или отсутствующих данных |
| `NOT RUN` | Шаг не выполнялся |
| `OBSERVATION` | Есть замечание или риск, но дефект еще не доказан |

Служебный обход не превращает `FAIL` или `BLOCKED` в `PASS`.

## 23. Решение о готовности

### `GO`

Допускается, только если:

- критический цикл двух смен пройден через штатные интерфейсы;
- открытых P0 и P1 нет;
- переходящий рейс виден всем новым сменным ролям;
- контрольные суммы экрана, базы, отчетов и Excel совпали;
- повторные действия не создают дублей;
- права ролей выдержаны;
- нет значимых ошибок браузера и сервера;
- реальные мобильные действия приняты на целевых устройствах;
- все тестовые данные инвентаризированы.

### `CONDITIONAL GO`

Допускается только если:

- нет открытых P0 и P1;
- остались только P2/P3 или ограничения, принятые владельцем с письменным обоснованием;
- существует безопасный обход, доступный обычным сотрудникам;
- определены ответственный и срок устранения;
- данные и отчетность не искажаются.

### `NO-GO`

Обязателен, если:

- есть открытый P0 или P1;
- основной шаг выполнен только служебным обходом;
- отчет искажает производственные итоги;
- переходящие события теряются;
- роль не может начать или завершить работу;
- есть обход прав;
- данные дублируются, теряются или не могут быть восстановлены.

### Немедленная остановка прогона

Прекратить новые мутации, сохранить доказательства и уведомить владельца, если обнаружены:

- потеря или повреждение данных;
- обход прав;
- изменение настоящих данных за пределами тестового маркера;
- неконтролируемое массовое создание дублей;
- попадание локального теста в production;
- невозможность определить, какие записи созданы тестом;
- отсутствие пригодной резервной копии перед опасным продолжением.

После остановки разрешены только read-only диагностика и согласованные действия по восстановлению.

## 24. Критерии закрытия дефекта

Дефект можно закрыть, только если:

- исправление находится в указанной версии или commit;
- исходные шаги больше не воспроизводят проблему;
- ожидаемый результат достигнут через штатный интерфейс;
- проверены положительный, отрицательный и граничный сценарии;
- проверены все затронутые роли;
- экран, база, отчет и Excel совпали;
- нет новых ошибок браузера и сервера;
- мобильный дефект проверен на целевой ширине и реальном устройстве;
- сменный дефект проверен на границе смен и переходящем рейсе;
- автоматические тесты успешны;
- приложены доказательства «до» и «после»;
- служебный обход больше не требуется.

После исправления P0/P1 повторяется полный критический прогон дневной и ночной смен.

Решение «не исправлять» не закрывает дефект. Оно оформляется как принятый риск с ответственным, причиной и сроком пересмотра.

## 27. Допуск к повторному тесту после исправлений

Повторный тест после передачи дефектов является отдельным прогоном. Он не начинается автоматически после сообщения «исправлено».

### 27.1. Обязательные входные документы

Перед любыми новыми тестовыми мутациями тестовый чат обязан прочитать:

1. Исходный отчет `73_СКВОЗНОЙ_ТЕСТ_ДВУХ_СМЕН_23_07_2026.md`.
2. Реестр передачи `75_ПЕРЕДАЧА_ДЕФЕКТОВ_И_РЕКОМЕНДАЦИЙ_НА_ИСПРАВЛЕНИЕ.md`.
3. Полностью заполненный чатом исправлений файл `76_ОТЧЕТ_ОБ_ИСПРАВЛЕНИЯХ_ШАБЛОН.md`.
4. Актуальный `git status`, ветку, commit и перечень локальных изменений.

Если файл `76_...` отсутствует, остался шаблоном, имеет статус `ЧЕРНОВИК` или не описывает точную проверяемую версию, повторный прогон получает статус `BLOCKED`. Разрешена только read-only проверка состояния и запрос недостающих сведений.

### 27.2. Условия допуска

Полный повторный прогон разрешен, если:

- статус `76_...` равен `ГОТОВО К ПОВТОРНОМУ ТЕСТУ`;
- все `QA-P1-*` отмечены как `ГОТОВО К ПЕРЕПРОВЕРКЕ`;
- для временного дефекта подтверждены владельцем серверная зона, обе границы смен и правило производственной даты;
- заполнен статус каждого ID из документа `75_...`;
- каждый неготовый P2 имеет владельца, безопасный обход, срок и письменное принятие риска;
- `QA-RISK-001` имеет результаты конкурентных тестов либо явное решение владельца по непроверенному риску;
- указана точная ветка и commit либо полный отпечаток локального состояния, если commit не был разрешен;
- текущий код совпадает с версией из отчета;
- перечислены все измененные файлы;
- профильные тесты и полный набор имеют фактические результаты;
- нет скрытой или неразрешенной миграции;
- перечислены непроверенные пункты и остаточные риски;
- указано, затрагивались ли production, commit, push и deploy.

Для локального состояния без commit полный отпечаток включает `git status --short`, все измененные и untracked-файлы рабочего контура, SHA-256 их итогового содержимого и полный diff или patch. Один `git diff --stat` точное состояние не доказывает.

Несовпадение проверяемого кода с отчетом не разрешается трактовать как «почти та же версия». Нужно вернуть документ чату исправлений либо обновить его под фактическое состояние.

### 27.3. Порядок повторной проверки

1. Зафиксировать новый паспорт прогона и новую резервную копию.
2. Использовать новый маркер вида `ТЕСТПОВТОР<ГГГГММДД><СУФФИКС>`.
3. Не изменять и не переименовывать сотрудников маркера `ТЕСТДВЕСМЕНЫ20260723`.
4. Сначала повторить точные шаги каждого P1 из документа `75_...`.
5. Для каждого результата присвоить один статус:
   - `FIXED` — исходная ошибка устранена;
   - `NOT FIXED` — исходная ошибка воспроизводится полностью или частично;
   - `REGRESSION` — прежний шаг исправлен, но сломан ранее рабочий результат;
   - `NEW` — обнаружен новый независимый дефект;
   - `NOT RUN` — проверка не выполнена с обязательной причиной.
6. Если целевые проверки P1 успешны, пройти полный двухсменный сценарий раздела 9.
7. Присвоить наблюдаемый результат каждому P1, P2 и риску из документа `75_...`; отсутствие проверки одного ID отмечать как `NOT RUN` с причиной.
8. Повторить контрольные, отрицательные, временные, ролевые, отчетные, мобильные, PWA и realtime-проверки, связанные с измененными файлами.
9. Сравнить новый контрольный оракул между базой, экраном, отчетами и Excel.
10. Сравнить реестр нового прогона с документом `73_...`: закрытые, незакрытые, регрессионные и новые дефекты.
11. Подготовить новый самостоятельный отчет. Старый отчет `73_...` не переписывать.

Если любой P1 получает `NOT FIXED`, полный прогон можно остановить после сохранения достаточных доказательств и выдать `NO-GO`. Если продолжение безопасно и нужно для поиска регрессий, решение о продолжении явно записывается в паспорт.

### 27.4. Проверка отчета об исправлениях

Тестовый чат не принимает как доказательство:

- только описание измененного кода;
- фразу «тесты проходят» без команды и количества;
- скриншот без версии и роли;
- прямой POST вместо штатного интерфейса;
- локальную проверку UI без проверки фактического PWA-ресурса;
- исправление экрана без сверки базы и Excel;
- статус `ГОТОВО К ПЕРЕПРОВЕРКЕ`, если остался служебный обход.

Если реальный результат отличается от документа `76_...`, приоритет имеет наблюдаемый результат повторного теста. Расхождение оформляется как `NOT FIXED`, `REGRESSION` или `NEW`.

### 27.5. Состояние данных после повторного прогона

Тестовые данные первого и повторного прогонов сохраняются раздельно до подготовки итогового сравнения. Очистка выполняется только после:

- сохранения обоих отчетов;
- инвентаризации всех зависимых записей;
- проверки резервной копии;
- отдельного разрешения пользователя.

## 28. Критерий завершения тестового прогона

Прогон считается завершенным, когда:

- выполнены все запланированные шаги или каждому невыполненному шагу присвоен статус;
- для каждого `FAIL` создана карточка дефекта;
- контрольные итоги сверены;
- отчет и Excel проверены;
- права и мобильные экраны проверены в заявленном объеме;
- указаны все обходы и ограничения;
- тестовые данные инвентаризированы;
- подготовлен итоговый вердикт;
- явно указаны local / commit / push / deploy / production;
- локальный сервер штатно остановлен.
