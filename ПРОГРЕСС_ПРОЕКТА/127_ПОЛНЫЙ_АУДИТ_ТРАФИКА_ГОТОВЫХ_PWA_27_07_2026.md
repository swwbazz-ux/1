# Полный аудит трафика готовых PWA

Дата: 27.07.2026  
Статус: **АУДИТ ЗАВЕРШЁН / ПОДТВЕРЖДЁН РИСК / НУЖЕН PRODUCTION-LIKE SOAK**

## 1. Итог

Готовые PWA функционально работают. Аудит подтвердил несколько источников
лишнего обмена, но не выполнял 12-часовой production-like soak и поэтому
не объявляет систему непригодной к полной смене.

При составе недельного QA-прогона:

- 53 Водителя;
- 8 Машинистов экскаватора;
- по одному Системному администратору, ОУП, Заместителю начальника
  горного участка, Диспетчеру, Горному мастеру и Руководителю;
- всего 67 одновременно открытых рабочих приложений;
- из них 65 приложений запускают realtime-опрос;

получены две разные оценки на одну 12-часовую смену:

| Уровень оценки | Объём |
|---|---:|
| Постоянный секундный polling 65 открытых клиентов | **3,788 ГиБ** |
| Дополнительная сценарная оценка широкого обновления HTML | 5,065 ГиБ |
| Сценарный итог polling + широкое обновление HTML | **8,852 ГиБ** |
| Сценарный исходящий трафик сервера | **6,878 ГиБ** |

Итог рассчитан из точных байтов до округления отдельных строк таблицы,
поэтому сумма отображённых `3,788 + 5,065` отличается на `0,001 ГиБ`.

Если широкое распространение событий сохранится во всех 14 сменах,
сценарная недельная оценка составит:

- **123,9 ГиБ** суммарного обмена;
- **96,3 ГиБ** исходящего трафика сервера.

Это не замер production-HAR всей реальной смены. Постоянный polling
рассчитан непосредственно из текущего секундного контракта. Вторая часть
является нагрузочным сценарием, построенным из:

- фактических тел и HTTP-заголовков авторизованных запросов восьми PWA;
- реального состава техники и сотрудников недельной QA-БД;
- фактической частоты событий этой недели;
- фактической production-компрессии и production-протокола HTTP/1.1.

Сценарий не включает TLS/TCP-накладные расходы, все запросы подробностей
событий, часть проверок достижений, пассивные обновления Горного мастера и
запросы проверки service worker. Одновременно он предполагает широкую
релевантность каждой секунды изменения для перечисленных PWA. Поэтому
`8,852 ГиБ` — ориентир нагрузочного сценария, а не доказанный нижний
предел фактической смены.

## 2. Границы аудита

Полный авторизованный аудит выполнен для восьми готовых ролей первой волны:

1. Системный администратор;
2. ОУП;
3. Заместитель начальника горного участка;
4. Диспетчер;
5. Горный мастер;
6. Машинист экскаватора;
7. Водитель;
8. Руководитель.

В Django также существуют установочные PWA-оболочки Табельщика,
Начальника участка и Механика. Они не включены в расчёт рабочей смены,
потому что их функциональные контуры не входят в готовое ядро. Для них
проверены только публичные manifest/service worker и объём оболочки.

Делопроизводитель и Охрана труда пока не имеют подтверждённых RoleApp,
manifest и service worker и поэтому не объявляются готовыми PWA.

## 4. Методика

Использованы четыре независимых слоя измерения:

1. Django HTTP-аудитор создал отдельные авторизованные сессии восьми ролей,
   загрузил рабочие экраны, все связанные ресурсы, контрольную
   безусловную повторную загрузку, условную загрузку с validators и серию
   realtime-запросов.
2. Локальный измерительный reverse proxy зафиксировал реальные запросы
   восьми одновременно открытых PWA без сохранения содержимого и
   реквизитов авторизации.
3. PostgreSQL `pg_stat_user_tables` и `CaptureQueriesContext` измерили
   записи сессий и SQL-нагрузку одного неизменившегося realtime-опроса.
4. Публичный read-only production-аудит проверил gzip, cache headers,
   manifest/service worker и транспорт nginx.

Воспроизводящие инструменты:

- `СИСТЕМА_MVP/backend/tools/full_pwa_traffic_audit.py`;

- `realtime-client.js` получает новый секундный параметр на каждом

network-first-загрузку. Фактическую долю стабильных ресурсов из browser
cache следует отдельно подтвердить после исправления release-URL.

Production-проверка дала тот же результат:

- `app.css` с первым новым query — `200`, 106 135 Б gzip;
- `app.css` со вторым новым query — `200`, ещё 106 135 Б gzip;
- тот же URL с `If-Modified-Since` — `304`, тело 0 Б.

Минимум 111 581 Б сжатых общих CSS/JS получает новый URL и повторно
запрашивается при каждой навигации.

## 6. Фоновый realtime-опрос

Фактический контракт:

- запрос `/realtime/state/?after=<version>&include_events=0`;
- период — 1 000 мс;
- отдельного облегчённого ответа для неизменившегося состояния нет;
- скрытая вкладка не останавливает основной realtime-опрос;
- ОУП и Заместитель начальника участка realtime не запускают;
- остальные шесть типов готовых PWA запускают его.

В реальном браузерном отрезке продолжительностью 29,029 секунды
зафиксировано:

| PWA | Realtime | Прочие GET |
|---|---:|---:|
| Руководитель | 30 | 0 |
| Водитель | 30 | 2 проверки достижения |
| Машинист | 29 | 2 проверки достижения + 1 SW |
| Системный администратор | 29 | 0 |
| Диспетчер | 29 | 0 |
| Горный мастер | 29 | 0 |
| **Итого** | **176** | **5** |

Отдельный 15-секундный отрезок подтвердил ровно по 15 realtime-запросов
каждого из шести типов PWA.

Средний сжатый JSON-ответ составляет всего 261–276 Б, но HTTP/1.1
заголовки значительно больше:

- заголовок запроса — 752–785 Б;
- общий заголовок ответа — около 290 Б;
- личная сессия дополнительно получает `Set-Cookie`.

Для 65 realtime-клиентов за 12 часов:

- 2 808 000 запросов;
- 2 119 780 800 Б заголовков запросов;
- 1 208 952 000 Б заголовков ответов;
- 738 374 400 Б сжатых JSON-тел;
- всего **4 067 107 200 Б / 3,788 ГиБ**.

То есть полезный JSON составляет меньше пятой части этого обмена.

## 7. SQL и перезапись личной сессии

Один неизменившийся realtime-запрос выполняет:

- общая сессия — 7 `SELECT`;
- личная сессия — 7 `SELECT`, `BEGIN`, `UPDATE django_session`, `COMMIT`;
- всего 10 SQL-операторов для личной сессии.

Причина записи подтверждена в
`users/middleware.py`: `PersonalSessionRenewalMiddleware` вызывает
`request.session.set_expiry(...)` после каждого ответа личной сессии.

Контроль `pg_stat_user_tables`:

- 20 realtime-запросов личной сессии — ровно 20 дополнительных
  `UPDATE django_session`;
- 20 запросов общей сессии — 0 дополнительных обновлений.

При 63 личных и двух общих realtime-сессиях расчёт на 12 часов:

- 27 820 800 SQL-операторов;
- 19 656 000 `SELECT`;
- 2 721 600 обновлений `django_session`.

Даже если Администратор и Руководитель используют общий компьютер,
61 мобильная личная сессия Водителей и Машинистов создаст 2 635 200
обновлений сессий за смену.

Дополнительно каждый realtime-запрос активной роли вызывает
`reconcile_due_haul_assignments()`. Одна и та же серверная сверка
повторяется каждым клиентом раз в секунду.

## 8. Сценарная оценка усиления трафика производственными событиями

В недельной QA-БД:

- 80 341 `OperationalStateEvent`;
- 59 364 события `trip_changed`;
- 28 563 разные секунды, в которых менялась глобальная версия;
- от 2 015 до 2 067, в среднем 2 040 таких секунд на 12-часовую смену.

Точный half-open диапазон `20.07.2026 07:00 → 27.07.2026 07:00`
Владивостока, SQL и все 14 строк сохранены в
`АРТЕФАКТЫ_127_ТРАФИК/event_frequency.json`.

Текущие клиенты реагируют не только коротким JSON:

- Водитель при изменении глобальной версии получает весь актуальный HTML;
- Машинист, Диспетчер и Горный мастер получают подробности событий, а
  затем полный HTML при событиях, признанных релевантными;
- глобальный `trip_changed` широко распространяется между клиентами;
- Системный администратор-наблюдатель перезагружает страницу целиком;
- Руководитель продолжает polling, но применяет обновление вручную.

Не все секунды изменения обязаны быть релевантны каждому PWA: Машинист,
Диспетчер и Горный мастер применяют клиентские фильтры, а близкие события
могут объединяться. Поэтому таблица ниже показывает сценарий широкого
распространения при 2 040 циклах, а не фактически измеренный расход:

|---|---:|---:|---:|
| 53 Водителя | 108 120 | 22,707 ГиБ | 3,986 ГиБ |
| 8 Машинистов | 16 320 | 3,016 ГиБ | 0,546 ГиБ |
| Диспетчер | 2 040 | 1,635 ГиБ | 0,128 ГиБ |
| Горный мастер | 2 040 | 1,739 ГиБ | 0,135 ГиБ |

Это показывает потенциально главный источник исходящего трафика и
обосновывает адресный замер релевантности по каждой роли. Число
`5,065 ГиБ` нельзя трактовать как гарантированный минимум.

## 9. Вторичные источники

### 9.1 Горный мастер

В видимой мобильной вкладке выполняется дополнительное полное получение
HTML каждые 10 секунд независимо от событий. Верхняя оценка чистого
простоя — ещё около 0,286 ГиБ за смену.

### 9.2 Достижения

Водитель и Машинист:

- проверяют текущее достижение через 1,2 секунды после открытия;
- повторяют GET каждые 20 секунд в видимой вкладке;
- повторяют проверку после полного обновления рабочего экрана.

Для 61 мобильного рабочего места это не менее 131 760 запросов за смену.
При вызове после каждого из 2 040 событий возможно ещё до 124 440
запросов. Тело ответа мало, но сохраняются HTTP-заголовки, cookies и
обновление личной сессии.

### 9.3 Проверка версии service worker

Машинист и Горный мастер запрашивают полный service worker раз в минуту:

- Машинист — 1 357 Б gzip;
- Горный мастер — 1 764 Б gzip.

Для восьми Машинистов и одного Горного мастера это около 8,66 МиБ за
смену только на проверку двух небольших строк версии.

### 9.4 Статические ресурсы

- Общий `app.css`: 836 634 Б без gzip, 106 135 Б gzip.
- Суммарный precache всех 11 установочных оболочек: около 3,65 МиБ.
- Три CSS Машиниста: 343 366 Б без gzip, 35 566 Б gzip.
- Найдено 96 повторяющихся CSS-селекторов в контуре Машиниста.
- Десять PNG техники занимают 598 682 Б.
- Lossless WebP занимает 416 940 Б, потенциальное сокращение 30,4%.
- WebP quality 85 даёт около 159 766 Б, но требует отдельной визуальной
  приёмки.
- В 11 PWA пары иконок `512` и `maskable` побайтово одинаковы; суммарное
  потенциально дублируемое содержимое — 171 434 Б.

Эти размеры не являются главным риском по сравнению с realtime, но их
следует оптимизировать после серверного обмена.

## 10. Production-транспорт

Read-only проверка production:

- nginx `1.24.0`;
- gzip включён, уровень 6, минимальный размер 256 Б;
- JSON, CSS, JavaScript, manifest и SVG сжимаются;
- static получает `Cache-Control: max-age=2592000`;
- HTTPS virtual host использует `listen 443 ssl`;
- HTTP/2 не включён.

Все `16/16` публичных запросов manifest/service worker восьми готовых PWA
вернули `200` и gzip; все `8/8` service worker содержат ожидаемый
`pwa-contract-v1` и свою shell-версию.

Отсутствие HTTP/2 особенно заметно при секундных коротких запросах:
HTTP/1.1 не сжимает повторяющиеся заголовки HPACK и не мультиплексирует их
в одном соединении. Включение HTTP/2 полезно, но само по себе не устраняет
миллионы ненужных запросов.

## 11. Карточки оптимизации

### QA-TRAFFIC-P1-001 — секундный глобальный polling

**Факт:** 65 клиентов создают 2 808 000 realtime-запросов за смену,
3,788 ГиБ обмена и миллионы SQL-запросов даже без изменений.

**Требуется:**

- не опрашивать сервер раз в секунду скрытой или неактивной вкладкой;
- ввести разные интервалы для рабочих и наблюдательных ролей;
- возвращать минимальный неизменившийся ответ;
- после первичной оптимизации решить, нужен ли SSE/WebSocket, а не
  внедрять новый транспорт без повторного замера.

**Критерий:** фоновые запросы и SQL должны сократиться не менее чем на
80%, при этом изменение рабочего состояния должно доходить до активного
Водителя/Машиниста не позднее согласованного эксплуатационного окна.

### QA-TRAFFIC-P1-002 — глобальные события загружают целые экраны

**Факт:** релевантные события запускают загрузку полного HTML, а глобальные
события могут широко распространяться. При сценарии, где все 2 040
секунд изменения релевантны перечисленным клиентам, это 130 560 HTML GET
и 5,065 ГиБ сжатых ответов за смену.

**Требуется:**

- фильтровать события на сервере по роли, сотруднику, Самосвалу,
  Экскаватору и комплексу;
- не загружать полный HTML при нерелевантном событии;
- для релевантного события передавать дельту либо узкий фрагмент;
- исключить дубли событий одного бизнес-действия.

**Критерий:** нерелевантное событие не вызывает ни подробный events GET,
ни HTML GET; релевантный рейс обновляет только связанные экраны.

### QA-TRAFFIC-P1-003 — личная сессия записывается на каждом GET

**Факт:** 20 из 20 личных poll дали `UPDATE django_session`; до 2 721 600
обновлений за смену.

**Требуется:**

- сохранить годовую личную авторизацию;
- обновлять срок сессии редко и контролируемо, а не после каждого ответа;
- не отправлять новый `Set-Cookie` на неизменившийся realtime GET.

**Критерий:** серия из 100 read-only realtime-запросов даёт 0 обновлений
`django_session`, при этом регрессии личного и общего устройства проходят.

### QA-TRAFFIC-P1-004 — нестабильные release-URL мешают кэшированию

**Факт:** `app.css` и `realtime-client.js` получают новый секундный URL при
каждом формировании страницы. Два разных production-URL передали полное
тело; при стабильном URL validators работают, а `62/62` контрольных
запросов вернули `304`.

**Требуется:**

- заменить текущую секунду в URL на стабильную release-версию либо
  content hash;
- кэшировать неизменяемую versioned static как cache-first/immutable;
- оставить HTML и рабочие API network-first;
- не создавать новый cache key при каждой навигации.

**Критерий:** повторная загрузка той же версии передаёт не более 20%
тела холодной загрузки и не создаёт новые timestamp-URL.

### QA-TRAFFIC-P1-005 — производственная сверка выполняется каждым клиентом

**Факт:** каждый poll вызывает `reconcile_due_haul_assignments()` и
выполняет 7 `SELECT` ещё до полезного действия.

**Требуется:**

- вынести сверку в один серверный периодический процесс либо
  дедуплицировать её общим временным lock/throttle;
- отделить дешёвую проверку версии от тяжёлой доменной сверки;
- сократить SQL неизменившегося состояния.

**Критерий:** рост числа клиентов не умножает частоту одной и той же
сверки; неизменившийся poll не выполняет запись и использует минимальное
число запросов.

### QA-TRAFFIC-P2-001 — пассивная полная загрузка Горного мастера

Убрать безусловный полный HTML GET каждые 10 секунд. Обновлять только
нужные элементы по релевантным событиям.

### QA-TRAFFIC-P2-002 — отдельный частый опрос достижений

Не запускать проверку после каждого общего realtime-изменения.
Использовать событие достижения, увеличенный интервал либо backoff.

### QA-TRAFFIC-P2-003 — полная загрузка service worker для проверки версии

Использовать уже передаваемый `role_shell_version`, условный запрос с
ETag/Last-Modified либо небольшой version endpoint. Увеличить интервал.

### QA-TRAFFIC-P2-004 — HTTP/2 не включён

После отдельного инфраструктурного разрешения включить HTTP/2 с планом
отката и проверить все PWA. Это уменьшит накладные расходы заголовков, но
не заменяет исправления P1.

### QA-TRAFFIC-P3-001 — статические изображения, иконки и CSS

После P1/P2:

- перевести изображения техники в WebP после визуальной проверки;
- устранить безопасно подтверждённые дубли иконок;
- удалить неиспользуемый и повторяющийся CSS;
- вынести стабильный большой inline-код в versioned static.

## 12. Рекомендуемая очередность

1. Исправить перезапись личной сессии `QA-TRAFFIC-P1-003`.
2. Устранить глобальные полные HTML-обновления `P1-002`.
3. Облегчить и адаптировать realtime `P1-001`.

## 13. Обязательная повторная проверка

После исправлений:

1. Повторить этот же аудит на той же недельной QA-БД.
2. Сравнить каждый показатель с данным документом.
3. Прогнать 12-часовой или ускоренный эквивалентный профиль 65 клиентов.
4. Убедиться, что:
   - нет `UPDATE django_session` на read-only polling;
   - скрытые и неактивные PWA не продолжают секундный polling;
   - нерелевантные события не загружают HTML;
   - повторная static-загрузка использует кэш;
   - отчёты и рейсы функционально не изменились.
5. Выполнить ступени `15 → 30 → 45 → 65` клиентов на
   production-like nginx + gunicorn + PostgreSQL.
6. Повторить реальный Android-тест Водителя, Машиниста и Горного мастера
   на корпоративной сети с записью переданных байтов.

Целевой ориентир первой оптимизации:

- сократить подтверждённую polling-оценку `3,788 ГиБ/смену` минимум на
  80%;
- адресным event-перехватом заменить сценарные `5,065 ГиБ` фактическим
  показателем и затем сократить полные HTML GET минимум на 80%;
- сохранить согласованную актуальность рабочих экранов.

## 15. Вердикт

**Готовые PWA пригодны для ограниченного пилота. Готовность сетевого
обмена к постоянной полной смене из 65 realtime-клиентов остаётся
непроверенной до production-like soak.**

Блокеров корректности рейсов этим аудитом не обнаружено. Обнаружен
подтверждённый масштабный риск производительности, трафика и нагрузки на
PostgreSQL. Карточки P1 имеют высокий приоритет до расширения пилота;
окончательный GO/NO-GO должен опираться на повторный измерительный прогон
и soak, а не только на сценарную экстраполяцию.

Результат аудита и инструменты находятся только локально. Commit, push,
deploy и изменения production не выполнялись. Тестовые вкладки закрыты,
локальные Django, измерительный proxy и PostgreSQL остановлены; порты
`8000`, `8001` и `55432` свободны.
