Дата: 10.09.2026. Ветка: `codex/mm-perf-audit-2026-09-09` (worktree `C:\mm-audit`),
поверх аудита v163. Shell поднят до `mining-master-mobile-shell-v164`, общая статика —
`ready-core-traffic-v133` (на бою на момент разбора — v132, shell v162).
Production не менялся, deploy не выполнялся.

## 1. Сбой: 500 и белый экран при «Начать смену»

Снято с подключённого по USB телефона пользователя (Redmi 22011119UY, боевой WebAPK
`mining-master.driverform.ru`). Адрес белой страницы с «Server Error (500)»:

```
/mining-master/assignments/?_operational_fragment=mining_master&_operational_version=0
```

Это адрес **фонового обновления**, а не экрана. В форме кнопки на телефоне он и лежал:
`shift_form_action` собирается из `request.get_full_path()` (`assignments/views.py`),
а фрагмент доски сервер рендерит тем же view с этим query-string — адрес запекается в
форму, и следующая же замена доски делает POST старта смены «на фрагмент».

**Первопричина (найдена по боевым журналам и базе, только чтение, 10.09 вечером):**

- Адрес — не причина. 500 повторился три раза (09:10:29, 09:54:15, 09:54:25 МСК), все три
  раза с телефона пользователя, тело ответа 145 байт — стандартная страница Django. В
  `journalctl -u accounting-mvp` трассировки **нет ни одной**: в `LOGGING` проекта заведён
  только логгер CSRF, а стандартный обработчик Django пишет ошибки запросов в консоль
  только при `DEBUG=True`. На бою 500 до сих пор были невидимы.
- В базе: сотрудник 394 (у него активированы все 12 ролей) в 09:07:16–09:10:57 и
  09:44:34–10:07:32 держал открытую смену **диспетчера** (с компьютера). Все три 500
  попадают внутрь этих окон; в 10:13:49, когда диспетчерская смена была закрыта, смена
  мастера открылась. Код мастера (`get_shift_state`) видит только смены мастера, а в
  базе стоит ограничение `unique_open_shift_per_employee` (одна открытая смена на
  сотрудника во всех контурах) → `EmployeeShift.objects.create` падает с `IntegrityError`,
  которую `handle_shift_action` не ловит (ловит только `ValidationError`) → 500.
- Воспроизведено локально на боевой версии кода `360e8f31`: открыл сотруднику смену
  диспетчера, POST `start_shift` → `IntegrityError: UNIQUE constraint failed:
  shifts_employeeshift.employee_id` на обоих адресах. У диспетчера тот же случай уже
  обработан (`open_dispatcher_shift` в `trips/dispatcher_header.py`) — мастер отставал.
- Осиротевших NOT NULL столбцов в `shifts_employeeshift` нет; `shifts` мигрирована до 0018.

**Правки:**

- `assignments/views.py` `handle_shift_action`: перед созданием смены — проверка любой
  открытой смены сотрудника (`select_for_update`), сообщение «У вас уже открыта смена
  «Горный диспетчер». Завершите её перед началом смены Горного мастера.» (те же ярлыки
  `WORKPLACE_ROLE_LABELS`, что у диспетчера); страховка — `IntegrityError` → понятное
  сообщение вместо 500. Тест `test_mining_master_start_is_refused_while_other_role_shift_is_open`.
- `config/settings.py`: логгер `django.request` уровня ERROR в консоль — трассировки 500
  теперь попадают в `journalctl` и при `DEBUG=False`.
- `shift_form_action = request.path` — форма всегда бьёт в чистый адрес экрана (адрес
  фрагмента в форме — отдельный дефект, найденный по пути; не причина 500).

**Не баг, но ловушка:** у кнопок смены `data-confirm-delay="10"` — короткое нажатие
открывает окно подтверждения, где кнопка «ОК» разблокируется через 10 секунд; удержание
самой кнопки ничего не делает. Пользователь ожидал удержание, как у водителя и
экскаваторщика. Механику смены не менял (предметное решение), см. «что дальше».

## 2. «Все карточки перемешаны, через пару секунд расставляются»

Механизм подтверждён кодом service worker и содержимым его кэша на телефоне:
`networkFirst` для навигации соревнует сеть с таймером **2,5 секунды**; страница на
бою — 1,18 МБ (11 комплексов), на карьерном LTE она за это время не успевает, и на экран
выходит **доска из кэша** (последняя увиденная расстановка). Через пару секунд фоновая
сверка (`_operational_version=0`) подменяет её свежей — это и есть «перемешка». На
стенде при обычной навигации геометрия и порядок после 500 мс не меняются вовсе.

**Правки (по решению пользователя — не ждать, а показывать стандартную плашку):**

- SW: быстрый старт сохранён (2,5 с), без сети кэш отдаётся сразу, без ожидания.
- Экран: при старте показывается стандартная плашка `app-sync-overlay` («Загружаем
  пульт», кружок) и снимается, когда доска подтверждена актуальной: по первому ответу
  realtime, полученному **после** старта страницы (realtime при инициализации публикует
  «связь есть» с временем успеха предыдущей страницы — такое событие игнорируется), с
  тиком 80 мс на разбор версии; если сервер знает версию новее отрисованной —
  ожидается завершение подмены доски (`mm-mobile-board-refresh-done`, шлётся всегда,
  и при успехе, и при отказе). Без сети — снимается сразу; страховка — 8 секунд.

Проверено на телефоне: сценарий «изменений нет» — показ 356 мс, снятие 472 мс по
первому ответу сервера. Сценарий «доска устарела» на стенде честно **не воспроизведён**:
при эмуляции сети через DevTools realtime перестаёт опрашивать, а без эмуляции окно между
отдачей страницы и первым опросом ~300 мс; остаётся проверка кодом и страховка 8 с.
Подтвердить утром на бою при первом открытии.

## 3. Кнопка «Выйти»

Как у водителя и экскаваторщика — тем же модулем `mobile-shift-unified-v1.js`
(`MobileShiftHold`, удержание 2 с). Стоит в одну строку с «Начать/Завершить смену» во
вкладке «Отчёты» (`.mm-mobile-shift-actions`): короткое нажатие — подсказка
«Удерживайте кнопку, чтобы выйти», удержание — «Держите» → «Выходим» → `/logout/`.
Проверено настоящим касанием на телефоне (`adb input motionevent`).
