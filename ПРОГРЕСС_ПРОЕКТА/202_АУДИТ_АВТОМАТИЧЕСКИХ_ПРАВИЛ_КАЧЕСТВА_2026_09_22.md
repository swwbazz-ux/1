## 2. Главный вывод

Вводить глобальный строгий formatter/linter сейчас нельзя: он создаст большой
механический diff и начнёт конфликтовать с параллельной разработкой Водителя и
Экскаваторщика. Профессиональный путь для текущего состояния — ratchet:

1. сначала убрать уже объявленные GitHub инфраструктурные deprecation;
2. затем проверять новый файл целиком, а существующий — только по новым строкам;
3. типы вводить по явному allowlist новых и выделенных доменных сервисов;
4. coverage сначала измерить без порога и только потом закреплять baseline;
5. security сначала включить в режиме отчёта, затем блокировать новые
   `high/critical`, не маскируя старые риски общим исключением.

## 3. GitHub Actions: срочный долг

## 4. Formatter, linter, типы и размер

### 4.1. Чего сейчас нет

В repository отсутствуют `pyproject.toml`, Ruff/Black/isort/flake8/pylint,
mypy/pyright, `.pre-commit-config.yaml`, `.editorconfig`, ESLint/Prettier/stylelint
и воспроизводимый dev/quality requirements-файл. CI выполняет Django check,
migration guard и тесты, но не выполняет format/lint/type/file-size gates.

### 4.2. Измеренный Python baseline

Production-срез без migrations/tests/tools:

- `214` файлов и `2 885` функций;
- все файлы успешно разбираются Python AST;
- return-аннотация есть у `144` функций (`5,0%`);
- полностью аннотированы `119` функций (`4,1%`);
- `372` функции имеют не менее `50` строк, `140` — не менее `100`,
  `37` — не менее `200`, `6` — не менее `500`;
- крупнейшие функции: `build_dispatcher_dashboard_context` — `1 579` строк,
  `excavator_work_view` — `1 263`, `resolve_settlement_cohort` — `904`,
  `driver_shift_view` — `622`;
- в отслеживаемом production Python нет хвостовых пробелов и начальных tab,
  `tabnanny` проходит;
- уже существуют `78` `# noqa` и `6` `type: ignore`.

Whole-project mypy или полное автоформатирование сейчас дадут преимущественно
исторический шум, а не защиту нового кода.

### 4.3. Измеренный JavaScript baseline

- `52` production JS-файла и около `30 000` строк;
- `dispatcher-control-v1.js` — `6 696` строк;
- `driver-shift-v1.js` — `2 535`;
- `settlement-clerk.js` — `2 263`;
- `1 089` обращений `window.*` находятся в `39` production-файлах.

Запрещать весь `window.*` нельзя. Сначала нужен manifest существующих публичных
application globals; только новое имя вне allowlist должно блокировать PR.

### 4.4. Принятый ratchet-дизайн

Первый Python-пакет должен добавить закреплённые quality dependencies,
`pyproject.toml`, repository-owned wrapper и его тесты. Wrapper обязан:

- получать точный base SHA и добавленные строки из Git diff;
- в существующем файле блокировать только нарушение на добавленной строке;
- новый Python-файл проверять целиком;
- `ruff format --check` сначала применять только к новым файлам;
- исключить migrations, generated/vendor и исторические QA artifacts;
- размер нового production-файла более `500` строк и новой функции более `100`
  строк сначала показывать предупреждением, затем включить блокировку после
  проверки ложных срабатываний.

Включение выполняется двумя PR:

- `2A`: non-blocking режим и реальные отчёты;
- `2B`: после подтверждения стабильности добавить job в Required quality gate.

Реализация `2A` закрепляет Ruff `0.16.8` версией и SHA-256. Отдельный job
публикует summary, warning-аннотации и JSON artifact, но намеренно не входит в
агрегатор `Required quality gate`. Находки возвращают успешный код report-only;
невозможность построить достоверный отчёт возвращает код `2` и не маскируется.
Wrapper проверяется существующим обязательным discovery тестов `tools`.

Типы вводятся через `.github/ci/typecheck-targets.txt`: сначала новые и уже
хорошо типизированные доменные сервисы. Большие legacy `views.py` не включаются
целиком до их отдельного безопасного разделения.

## 5. Coverage

`coverage.py`, `.coveragerc`, XML/JSON report и сохранённый baseline сейчас
отсутствуют. Поэтому назначать процент из предположения запрещено.

Безопасная последовательность:

1. добавить report-only сбор Python coverage к полному PostgreSQL nightly;
2. сохранять machine-readable report как artifact;
3. получить минимум три сопоставимых запуска одного и того же состава;
4. только после измерения согласовать начальный floor;
5. затем запретить снижение baseline и отдельно повышать покрытие изменяемых
   доменных сервисов.

Не следует сразу объединять coverage всех PR matrix jobs: сначала надо доказать
корректное объединение путей и отсутствие потери данных между runner.

## 6. Security baseline

### 6.1. Что уже защищено

- repository публичный;
- GitHub secret scanning включён;
- secret scanning push protection включён;
- прямой API-контроль показал `0` открытых и `0` закрытых secret alerts;
- Python runtime requirements используют точные версии;
- npm использует lock-файл;
- GitHub Actions закреплены полными SHA.

### 6.2. Чего не хватает

- Dependabot vulnerability alerts и security updates выключены;
- CodeQL default setup имеет состояние `not-configured`, хотя repository
  поддерживает анализ Actions, Python и JavaScript/TypeScript;
- нет `pip-audit`, SAST, Gradle dependency scan и policy для advisory ignore;
- Gradle wrapper не содержит `distributionSha256Sum`;
- Django `check --deploy` не является CI-gate.

`npm audit --omit=dev` сейчас показывает `0` production-уязвимостей. Полный
dev-аудит показывает `3 moderate`, все в цепочке `@capacitor/cli` → `xcode` →
`uuid`; это build tooling, не runtime приложения. Ручной override `uuid` не
вводится, пока upstream Capacitor сохраняет эту зависимость.

Локальный `manage.py check --deploy` с безопасными CI-переменными дал только
`security.W004` об отсутствующем HSTS. HSTS нельзя включать механически в рамках
этого этапа: это долговременная production-настройка и требует отдельной
проверки HTTPS/proxy/rollback.

### 6.3. Безопасный security ratchet

1. Отдельным разрешённым settings-шагом включить Dependabot alerts и CodeQL
   default setup; сначала только получить и классифицировать baseline.
2. В CI добавить report-only `pip-audit` и полный npm audit.
3. После классификации блокировать новые `high/critical`; существующее исключение
   допускается только по advisory ID, с причиной, владельцем и сроком.
4. `npm audit --omit=dev --audit-level=high` можно сделать блокирующим раньше:
   текущий production baseline равен нулю.
5. Django deploy-check и Gradle warnings пока публиковать как diagnostics, не
   ослабляя рабочие production-настройки ради зелёного CI.
