# Задание: аудит и исправление ложной потери связи в полевых приложениях

## 1. Цель

Проверить весь фактический контур определения связи с сервером у Машиниста экскаватора и Водителя: Django/WebView, общий realtime-клиент, role-specific fragment refresh, Android foreground heartbeat, offline outbox, service worker и индикаторы.

Не считать, что механика отсутствует. Она частично есть; нужно доказать, как именно она работает в текущем live/release коде, найти расхождения между слоями и исправить подтверждённые дефекты.

Основной результат: один отменённый, зависший или кратковременно неудачный HTTP/realtime-запрос не должен объявлять механику полную потерю связи. При реальном offline рабочие действия должны сохраняться и синхронизироваться без дублей.

## 4. Что уже есть в production и почему этого недостаточно

По живому `static/js/realtime-client.js` на 15.09.2026:

- есть `realtimeConsecutiveFailures`, `realtimeLastSuccessAt`, `realtimePollInFlight`, `AbortController` и `realtimePollGeneration`;
- есть защита владения ответом через generation;
- есть состояния `ok`, `weak`, `lost` в `document.body.dataset.connectionState`;
- есть pause/wake для `visibilitychange`, `focus/blur`, `pageshow/pagehide`, `resume`, `native-connectivity-resume`, `online/offline`;
- есть foreground reconciliation и role-specific fragment refresh;
- для Водителя есть `data-connection-indicator`, который визуально различает `weak/lost`;
- по Android-коду в release-ветках есть `ConnectivityForegroundService`: две ошибки до объявления потери, exponential backoff, `NetworkCallback`, `START_STICKY` и сброс после успеха.

При этом нужно проверить и либо опровергнуть, либо исправить следующие риски:

1. `pollOperationalState({force: true})` показывает offline уже после первой ошибки из-за условия `realtimeConsecutiveFailures >= 2 || options.force`.
2. `inspectRealtimeWatchdog()` публикует disconnected после одного `poll_stuck`, `silent_timeout` или `initial_timeout`.
3. У экскаваторщика не найден такой же role-specific `data-connection-indicator`, как у Водителя. Общая нижняя плашка имеет фиксированный текст `Связь с сервером потеряна`, поэтому даже `weak` может выглядеть как полная потеря.
4. WebView realtime и Android foreground heartbeat принимают решение о связи независимо; успех native heartbeat может не снять ложный WebView-индикатор.
5. Нужно доказать, что все плановые abort по generation являются нейтральными и не попадают в счётчик ошибок, `ClientErrorReport`, offline-озвучивание или долгоживущий stale-класс.
6. Нужно проверить, не создают ли `focus + pageshow + resume + native-connectivity-resume + interaction` ненужные force poll/abort при одном физическом возврате приложения.
7. `client-error-report.js` регистрирует resource error для `/excavator/work/`; нужно установить конкретный DOM target и отличить поломку ресурса от плановой навигации/отмены.

## 5. Границы и источник правды

1. Сначала выполнить read-only аудит production, актуальной release-ветки и Android-исходников.
2. Production не является Git-клоном. Снять SHA-256 live-файлов и сравнить с кандидатами, а не доверять `DEPLOYED_COMMIT` или названию ветки.
3. Текущий грязный worktree и папки `tmp/` не считать baseline. Выбрать чистый worktree от фактической рабочей ветки/коммита и наложить необходимые live overlays только после сверки.
4. Не принимать код Android из случайной `tmp/`-копии за актуальный. Найти release-коммит, из которого собраны `excavator 0.1.26` и `driver 0.1.28`, и сверить versionCode/versionName с опубликованным APK-контрактом.
5. Не трогать доменную логику рейсов, смен, назначений, планов, простоев и отчётов, если нет прямого доказанного дефекта.
6. Не делать миграции и не менять БД для этого фикса.
7. Не рестартовать production во время диагностики.
8. Код, тесты, commit и push разрешены этим заданием после доказания дефекта. Production deploy, `collectstatic`, nginx/systemd, замена APK и установка на физические телефоны — только после отдельного прямого разрешения пользователя.

## 7. Целевой контракт связи

Реализовать единую машину состояний или доказать, что уже имеющаяся реализация эквивалентна:

- `unknown` — страница только открылась, результата ещё нет;
- `ok` — есть свежий успешный server response;
- `reconnecting/weak` — есть единичная ошибка или короткая тишина, идёт повторная попытка;
- `lost` — есть подтверждённая серия ошибок или превышен порог тишины;
- `recovering` — сервер уже ответил, но server truth/outbox/DOM ещё не применены;
- `ok` после завершения сверки.

Минимальные правила:

1. Плановый abort из-за generation, pause, background или замены запроса — нейтральный, не увеличивает failure counter.
2. Одна ошибка не показывает `Связь потеряна`; допустим ненавязчивый `Переподключение…`.
3. `lost` допустим не раньше трёх последовательных неплановых ошибок или 10–15 секунд без единого успешного канала. Точный порог обосновать тестами и трафиком.
4. `navigator.onLine=false` — сигнал отсутствия сети, но не доказательство падения production.
5. Первый успешный realtime/heartbeat немедленно сбрасывает failure counter и снимает `lost`.
6. Если есть pending outbox или server version, ещё не применённая к DOM, показывать `Восстанавливаем данные`, а не ложное `ok`.
7. На каждую роль в один момент допустим один владелец WebView poll и один владелец fragment refresh. Wake-причины коалесцируются, а не порождают шторм.
8. Android heartbeat и WebView не должны противоречить друг другу. Нужен явный bridge-контракт или обоснованное разделение: transport alive, WebView synchronized, outbox applied.
9. Восстановление связи не должно перезагружать весь экран, сбрасывать вкладку/скролл/ввод или создавать дубли действий.

Минимум для события связи:

## 9. Обязательные тесы

### 9.1. JavaScript

1. Один timeout/network error: `ok -> weak`, но не `lost`.
2. Вторая попытка успешна: `weak -> ok`, failure count сброшен, нет долгой плашки/озвучивания.
3. Три последовательные неудачи или порог тишины: `lost`.
4. Первый успех после `lost`: `recovering`, server-truth reconciliation, затем `ok`.
5. Intentional `AbortError` при superseded generation: не меняет connection state и failure count.
6. Timeout-abort текущего владельца классифируется как неудача, но не как planned abort.
7. Поздний `.catch/.finally` старой generation не сбрасывает controller/in-flight нового poll.
8. Один набор `focus/pageshow/resume/native resume` создаёт один poll/reconciliation.
9. Background pause не показывает `lost`; foreground resume всегда выполняет сверку.
10. Индикаторы Водителя и Экскаваторщика показывают одинаковую семантику `ok/weak/lost/recovering`.
11. Озвучивание потери не запускается на `weak`; восстановление озвучивается только если ранее был реальный `lost`.

### 9.2. Android

1. Один HTTP exception не объявляет полную потерю.
2. Порог и backoff согласованы с WebView-контрактом.
3. `onLost()` не оставляет ложный lost, если другая default network уже доступна.
4. `onAvailable()` и успешный heartbeat сбрасывают lost и побуждают WebView reconciliation.
5. Background/foreground, task removal, погашение экрана и переключение Wi-Fi/mobile не порождают дубли heartbeat-циклов.
6. Offline outbox не теряется и повтор одного client action остаётся идемпотентным.

### 9.3. Browser/Django

- целевые Django-тесты контрактов realtime/heartbeat/offline sync;
- JavaScript runtime tests общего realtime-клиента и обеих ролей;
- Browser QA Водителя и Экскаваторщика на mobile viewport;
- принудительные timeout, abort, offline/online, background/resume и invalid response;
- проверка, что нет дублирующихся poll/fragment refresh, DOM-цикла, сброса ввода, вкладки и скролла;
- `manage.py check`, `git diff --check`, целевые tests, `makemigrations --check --dry-run`.

Физическая APK-приёмка не заменяется Browser QA. Она должна включать: открытый экран, 30–60 секунд в фоне, погашение/включение экрана, краткий airplane mode, Wi-Fi ↔ mobile, зону неустойчивой связи и возврат без ручного перезапуска.

## 10. Критерии приёмки

1. Один неудачный или отменённый запрос не показывает механику `Связь с сервером потеряна`.
2. Плановый abort не считается сбоем и не порождает ложный голосовой сигнал.
3. Реальная потеря связи определяется по серии ошибок/времени, показывается одинобразно в обеих ролях и не маскируется.
4. Первый успех снимает lost; server truth и outbox применяются до окончательного `ok`.
5. Нет двух параллельных WebView poll и двух role fragment refresh.
6. Нет request storm, refresh-loop, накопления `499`, новых 5xx и JavaScript exception.
7. Действия в offline outbox не теряются и не дублируются.
8. Состояние рейса, кнопки, точка разгрузки и карточка экскаваторщика восстанавливаются из server truth без ручного перезапуска.
9. Водитель и Экскаваторщик имеют одинаковую семантику индикатора и не требуют от механика технических действий.
10. Физическая Android-приёмка пройдена отдельно для `excavator` и `driver`.
