## 2. Воспроизведение и подтверждённые причины

### 2.1. QA-WEEK-P1-001

До исправления в изолированной недельной PostgreSQL QA-базе:

- `Окисленная` и `Рыхлая` оставались активными;
- для них отсутствовали правила кубатуры;
- у задействованных моделей отсутствовал резервный `body_volume_m3`;
- существовало `4` активных сочетания `модель × порода` и `106` сочетаний
  `самосвал × порода` без разрешённой кубатуры;
- штатный POST погрузки создавал рейс с `volume_m3=NULL` и `tonnage=NULL`.

Причина в коде: обе рабочие точки создания рейса сходились в
`create_loaded_waiting_unload_trip()`, но общий helper создавал рейс с пустыми
измерениями и откладывал расчёт до разгрузки. Проверки разрешённой кубатуры перед
`Trip.objects.create()` не было.

### 2.2. QA-WEEK-P2-001

Исходный подтверждённый baseline документа 124:

```text
реальный HTTP:       8,596 с
Django Client:       8,365 с
SQL-журнал:          достиг лимита 9000
зафиксировано:       8973 запроса после среза журнала
сумма времени SQL:   1,159 с
```

Причины подтверждены по коду:

- `management_dashboard_context()` трижды загружал и полностью рассчитывал
  сменную аналитику для `Все / День / Ночь`;
- `Equipment.__str__()` вызывал N+1 из-за незагруженных
  `truck__equipment_type` и `excavator__equipment_type`;
- страница материализовывала полную историю завершённых рейсов;
- семидневные планы запрашивались отдельно для каждой даты;
- недельные рейсы создавали множество связанных Django model instances, хотя
  витрине требовалась только ограниченная проекция полей.

## 3. Исправление QA-WEEK-P1-001

### 3.1. Серверный guard

В `trips/trip_creation.py` создан единый расчёт:

1. `TruckCapacityRule`;
2. резервный `EquipmentModel.body_volume_m3`;
3. тоннаж из найденного объёма и плотности породы.

До создания рейса общий helper теперь требует полный результат:

- неизвестная кубатура отклоняется сообщением
  `Для выбранных модели самосвала и породы не настроена кубатура.`;
- неизвестная плотность отклоняется сообщением
  `Для выбранной породы не настроена плотность.`;
- разрешённая погрузка сразу сохраняет `volume_m3` и `tonnage`.

Защита применяется к обоим рабочим POST-путям:

```text
POST /excavator/truck-loaded/
POST /excavator/work/
```

Для JSON-пути возвращается доменный HTTP `409` с кодом
`trip_measurements_unresolved`. До ошибки не создаются:

- `Trip`;
- `TripClientAction`;
- изменение рабочего контекста Машиниста;
- закрытие простоя.

Legacy-путь возвращает ошибку формы HTTP `400`; транзакция откатывается.

### 3.2. Совместимость с актуальными справочниками при разгрузке

Принятый ранее контракт не отменён:

- незавершённый рейс при разгрузке пересчитывает измерения по актуальным
  справочникам;
- если актуальный полный расчёт недоступен, сохраняется уже записанный snapshot;
- завершённый рейс не пересчитывается и остаётся исторически неизменным.

## 4. Исправление QA-WEEK-P2-001

Выполнены следующие изменения:

1. QuerySet погрузки и разгрузки загружает
   `truck__equipment_type` и `excavator__equipment_type`.
2. Источники сменной аналитики загружаются один раз.
3. Карточка `Все` строит полную аналитику.
4. Карточки `День` и `Ночь` используют тот же source и считают только totals.

8. Планы семи дней загружаются пакетно:
   один запрос snapshot-смен и один агрегатный запрос `ShiftPlan`.
9. Приоритет snapshot над исходным `ShiftPlan` сохранён.
10. Страница и Excel используют один эквивалентный context.
