## Сохранённое событие

`OfflineFieldEvent.input_envelope` содержит версию конверта, точную JSON-копию
исходного события, нормализованный снимок до привязки локальных ссылок и
фактические `actor_id/access_id/role_code/device_id`. В снимке остаются исходные
IDs смены, техники и рейса, клиентские заявления об авторе/доступе, исходное
время, clock hints, эффективное время и первое `received_at`.

Повтор совпавшего события восстанавливает именно этот снимок. Он не пересчитывает
операционное время по следующему HTTP-запросу и не заменяет автора. Связи
`shift/equipment/trip/downtime_event` заполняются только после применения;
непроверенный или отсутствующий FK не может помешать сохранить квитанцию.
Старый fingerprint оставлен совместимым с уже выпущенными клиентами.

Конверт дополнительно защищён checksum и проверкой структуры. Повреждённая
сохранённая запись получает `saved_envelope_invalid`/conflict, не меняет сам
снимок и не прерывает соседние события HTTP-пакета или прохода worker.

Старые квитанции не содержат полного исходного события. Пустой конверт не
восстанавливается из результирующих FK. Совпавшая явная повторная отправка
телефона может сохранить `source=legacy_resubmission`, однако исходные
top-level clock hints до обновления недоказуемы. Поэтому **автономный повтор
старых квитанций, включая такой обратный снимок, исключён**. Для них сохранён
прежний явный повтор клиента. Неизменяемость полного первого конверта относится
к новым квитанциям с `source=first_receipt`.

## Автоматическое продолжение

После принятия родителя сервер в той же транзакции просматривает до 250 RETRY
квитанций исходного сотрудника/доступа/роли/устройства по `sequence` и применяет
до 50 связанных потомков. Проверяются явные зависимости и локальные ссылки
смены, рейса, простоя, свободного ковша. Принятый ребёнок может открыть следующего
потомка в этом проходе. Рекурсии нет; каждую выбранную квитанцию посещают один раз.
Появление родителя обходит задержку только связанных потомков.

Каждое применение использует прежние доменные проверки, idempotency keys и
savepoint. Ошибка одного события откатывает его доменные изменения и намерения
уведомлений, сохраняя RETRY; следующие независимые события проходят. Для RETRY
есть счётчик и `next_retry_at` с ограниченной задержкой. Пропущенные из-за лимита
или временного сбоя события подбирает команда:

```bash
python manage.py process_offline_retries --once --limit 50
python manage.py process_offline_retries --loop --interval 5 --limit 50
```

Worker применяет событие только через исходный активный `EmployeeAccess` и
исходную роль/сотрудника. Отозванный доступ оставляет событие в RETRY с задержкой;
другой сеанс или новый доступ не дают ему чужую авторизацию.

В PostgreSQL перед событием берётся транзакционный advisory lock потока
`actor/role/device` (совпадает с областью уникальности sequence), затем ключ
события и строка квитанции. Worker соблюдает тот же порядок. Принятые квитанции
читаются без `FOR UPDATE`: чужая зависимость отвергается по владельцу и порядку
без взаимного захвата двух потоков. Отдельная аренда для DB-only replay не нужна.

## Уведомление и доставка

`NotificationIntent` хранит уникальный ключ эффекта, неизменяемый JSON-снимок
текста/получателя/роли/версии и связь один-к-одному с существующим
`PushNotification`. Всё создаётся вместе с доменным действием. Нельзя потерять
уведомление из-за исчезнувшего `transaction.on_commit` callback.

Ключ включает исходное действие или ревизию, вид эффекта и сотрудника. Для
операционного события — его версия и ID; для offline-погрузки — исходный
event ID; для применения назначения — ID, время сохранённого перехода,
экскаватор и вид эффекта. Два законных изменения не сливаются только потому,
что относятся к одному рейсу или назначению. Получатели ролевого уведомления
фиксируются в исходной транзакции, текст не пересчитывается при доставке.

`NotificationDelivery` создаётся для каждого зафиксированного endpoint/token:
уникальность `(intent, channel, target_id)`, fingerprint получателя/роли/ключей
подписки, следующая попытка, lease token/срок, счётчик, результат и короткая
ошибка без секретов. Worker:

1. Короткой транзакцией забирает доступную запись с `SKIP LOCKED`, аренда 120 с.
2. Вне **всех** транзакций проверяет текущего владельца и fingerprint подписки.
3. Отправляет пустой Web Push или native wake с устойчивым `effect_id` и
   сохранённой версией; HTTP timeout ограничен.
4. Записывает результат только при совпадении lease token. Поздний ответ старого
   worker не может затереть результат новой попытки. Временная ошибка или
   отсутствие конфигурации получают задержку; мёртвый или изменённый target
   завершается. Успешные endpoints повторно не отправляются.

```bash
python manage.py process_notification_outbox --once --limit 50
python manage.py process_notification_outbox --loop --interval 5 --limit 50
```

Вызов notification worker под внешним `transaction.atomic` явно запрещён.
Фоновый HTTP не запускается из доменных запросов. **Для фактических внешних
push после будущей выкладки нужен запущенный worker**; его установка/запуск
остаются отдельным разрешаемым этапом. До запуска текст и доставка сохраняются
в БД. HTTP после сбоя между send и ack допускает повтор того же wake; это не
гарантия «один звук на телефоне». Текст в серверной очереди остаётся один.

## Схема и проверки

Одна добавочная миграция `core.0004_durable_offline_replay_and_notifications`:
три поля квитанции, индекс RETRY и две таблицы с индексом/ограничением
уникальности. Нет удаления/переписывания старых данных и миграции исторических
событий в выдуманные полные конверты. Перед будущим откатом к старой версии кода
нужно остановить workers; новую схему безопаснее оставить до отдельного решения
о сохранности накопленных квитанций/доставок, не удалять таблицы вслепую.

Новые тесты: `core.test_offline_durable_replay` и
`core.test_notification_outbox`. SQLite проверяет время, конверт, автоматическую
цепочку, лимиты/backoff, отзыв доступа, границу legacy, откат эффекта/намерения,
один текст, смену владельца подписки, истечение аренды и crash send→ack.
PostgreSQL-тесты используют два независимых `pg_backend_pid`: worker против
HTTP-дубля, родитель против retry ребёнка, взаимные чужие зависимости с барьером
при уже захваченных строках; конкурентные enqueue/claim и невидимость
незакоммиченного намерения другому worker.

postgres не запускается от root); PostgreSQL gate должен пройти в CI на
окончательном commit. Непройденный локально PG не считается проверенным.

Результат подготовлен для локального commit и последующей интеграции оркестратором.
Push, merge, deploy, production-миграция и запуск workers в production не выполнялись.
