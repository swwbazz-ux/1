## 3. Реализовать читающий сервис

Предлагаемый вход — конкретный `trip_id`; при необходимости явный внутренний контекст вызова. Сервис не аутентифицирует caller и не выдаёт заключение о праве выполнить новую команду. Переданный trusted-флаг не превращает недоказанную запись в доказанную: результат отражает найденное происхождение и пробелы. Контроль доступа к будущему endpoint и реальное подтверждение UI-наблюдения остаются отдельной границей подключения; новый permission-check в этом шаге не нужен.

Результат:

1. Исходные свидетельства с происхождением: модель/PK, ID/тип события, автор/роль/смена, заявленное и серверное время, payload, receipt/status/result. Legacy-поля сохраняются отдельным снимком, без изменения их значений.
2. Нормализованные входы ядра только в той части, где основания положительно установлены. Синтетический ключ ссылки допустим как внутренний `source_reference`, но не выдаётся за существовавший event_id погрузки. Неизвестное не заполняется выдуманным автором/событием/временем.
3. Полнота и точные причины неполноты: отсутствие исходного события, неизвестное происхождение actual, отсутствие before/after, непроверенное наблюдение, неполная связь замещения. Конец queryset не означает `history_complete=True`. Предъявленное, принятое, no_change и действительно изменившее маршрут действие различаются.
4. Lifecycle и его свидетельства. COMPLETED/CANCELLED достаточно исключить новую оперативную команду по старому рейсу, но COMPLETED без соответствующего подтверждения не называется физической разгрузкой водителя. Таймерный UNCONTROLLED не создаёт разгрузку. Пустая FK при возможном Y не оживляет X: неизвестная история остаётся неизвестной, без выбора по PK или порядку получения.
5. Отдельный результат происхождения/контекста автора. Автор погрузки, автор маршрутного действия, сменщик и автор административной коррекции не подменяют друг друга. Полученный из старого обработчика receipt не становится доказательством нового контракта UI-наблюдения.

Не превращать все принятые offline receipts в полную причинную историю R1. В старых direct-путях части сведений нет, а нового события перенаправления машиниста ещё нет. Для legacy ожидаем честный incomplete и отсутствие нового notification key. Существующее отображение приложения остаётся прежним, потому что адаптер к нему не подключён.

Чтение не вызывает reconcile, мутирующие GET-построители, bump_operational_state, save/update, закрытие резервов или смен. Если данные собраны несколькими SELECT, описать границу согласованности: `transaction.atomic()` при обычном READ COMMITTED сама по себе не доказывает единый снимок. Без соответствующей проверки не заявлять согласованность при конкурентной записи.

## 4. Адресная приёмка на настоящих Django-моделях

Только изолированная test DB. SQLite допустима для функциональной проверки чтения; не выдавать её за PostgreSQL-конкурентность. Production/постоянные данные не читать и не менять.

| Сценарий | Проверяемый результат |
|---|---|
| Погрузка через существующую фабрику | P1 и автор сохранены; заполненный actual без разгрузки не порождает DriverEvent |
| Принятое изменение точки водителя через реальный путь | Настоящий ID, точка, автор и оба времени извлечены; старый depends_on/expected point не считается доказательством P28-В2 |
| Accepted с no_change, retry, conflict, несовместимый повтор | Различимы предъявление и эффект; конверты остаются свидетельствами, не ложными применёнными маршрутами |
| Несовместимый ID: исходный receipt рейса Y, предъявленный конверт рейса X, отдельный Z | Свидетельство конфликта извлечено для обоих X/Y, Z не меняется. Выборка не ограничивается `existing_event__trip_id`: принадлежность предъявленного конверта устанавливается отдельно из submitted_event и доступного контекста, без привязки к текущему рейсу самосвала |
| Direct-действие с одним TripClientAction и legacy actual | Неполнота не скрывается и значения не восстанавливаются из отсутствующего payload |
| Реальная административная коррекция завершённого рейса | Автор коррекции не становится водителем; нет выдуманного нового маршрута/озвучки |
| Технический X без Y; X с положительно доказанным Y; X с возможным Y без FK | Нет фиктивной разгрузки и оживления старого рейса. Доказанное замещение и unknown разделены |
| CANCELLED, подтверждённая разгрузка, служебное COMPLETED | Нет ключа новой команды; основания завершения различимы |
| Смена автора/сменщик, чужой экскаватор, закрытая исходная смена | Сохраняется контекст каждой записи; новые полномочия не вводятся |
| Повтор чтения и иной порядок выдачи свидетельств | Одинаковая нормализация при одинаковых данных; ноль изменений Trip, receipts, резервов, operational version/events |

Создание входных фикстур может писать в test DB; сам вызов адаптера — только чтение. Отделить настоящие вызовы существующих обработчиков от вручную созданных legacy-строк и обозначить их в отчёте. Зафиксировать отсутствие DML/побочных вызовов во время чтения, а не только одинаковую выбранную точку. Проверить отсутствие рабочего hook/побочных эффектов импорта. Повторить принятые pure-Python проверки при переносе ядра; не менять их бизнес-ожидания.
