## 5. Блокирующие дефекты P1

### QA-P1-001. Переходящий рейс исчезает у новой смены

**Затронутые роли:** Диспетчер, Горный мастер, Водитель.

**Производственный риск:** новая оперативная смена считает загруженный самосвал просто назначенным и не видит, что он должен завершить разгрузку. Это создает риск повторного назначения, неверной команды и потери контроля над грузом.

**Как воспроизвести:**

1. Выполнить этап G документа `74_...`.
2. Дневной Машинист загружает самосвал, на котором уже открыта смена ночного Водителя.
3. Не разгружать рейс.
4. Закрыть оставшиеся дневные смены Диспетчера, Горного мастера и Машиниста.
5. Открыть ночные смены этих ролей.
6. Открыть рабочие экраны нового Диспетчера и Горного мастера.

**Ожидается:** обе роли видят тот же рейс, тот же самосвал и состояние «На разгрузку».

**Фактически:** Водитель видит рейс, а новый Диспетчер и Горный мастер видят только активное назначение без открытого рейса.

**Подтвержденная причина:**

Оперативный запрос получает открытые рейсы, а затем отбрасывает записи, созданные раньше открытия текущей диспетчерской смены. Состояние самосвала вычисляется уже из урезанного списка. Горный мастер повторно использует тот же диспетчерский render-контур.

**Места в коде:**

- `СИСТЕМА_MVP/backend/trips/views.py:4020-4029` — временной фильтр открытых рейсов;
- `СИСТЕМА_MVP/backend/trips/views.py:1315-1319` и `1375-1390` — вычисление состояния из отфильтрованного списка;
- `СИСТЕМА_MVP/backend/trips/views.py:1271-1279` — отдельный сменный срез статистики;
- `СИСТЕМА_MVP/backend/trips/views.py:1416-1417` — расчет активного объема, который нельзя случайно приписать новой смене;
- `СИСТЕМА_MVP/backend/assignments/views.py:989-996` — повторное использование экрана Горным мастером.

**Рекомендация:**

- разделить оперативный список открытых рейсов и сменные KPI;
- оперативный список строить по всем статусам `OPEN_TRIP_STATUSES` без ограничения временем открытия текущей смены;
- сменную статистику продолжать рассчитывать по правилам атрибуции конкретной смены;
- не использовать расширенный оперативный список для автоматического начисления объема новой смене;
- сохранить один ID рейса во всех ролях и не создавать копию при пересменке.

**Автоматические тесты:**

- в `trips/tests.py` рядом с `DispatcherGarageCurrentStateTests`: рейс с `created_at < dispatcher_shift.opened_at` виден как открытый, но не входит в KPI новой смены;
- в `assignments/tests.py` в `MiningMasterAssignmentsViewTests`: тот же рейс виден Горному мастеру как «На разгрузку»;
- после завершения разгрузки рейс исчезает из открытых у обеих ролей;
- погрузка относится к старой смене, разгрузка — к новой, общий рейс учитывается один раз.

**Критерии приемки:**

- новый Диспетчер и Горный мастер видят переходящий рейс без reload и служебного обхода;
- состояние, самосвал и ID совпадают у трех ролей;
- завершение Водителем обновляет остальные экраны;
- новая смена не получает чужой объем погрузки;
- экран, база и отчеты не создают дубль.

### QA-P1-002. Транспортный отчет удваивает рейсы и объем

**Затронутые роли:** Диспетчер, Руководитель.

**Производственный риск:** официальный отчет показывает вдвое больший объем и количество рейсов.

**Контрольный пример:**

- факт: `4 рейса / 198 м3`;
- день: `2 рейса / 94 м3`;
- ночь: `2 рейса / 104 м3`;
- ошибочный общий результат: `8 рейсов / 396 м3`.

**Ожидается:** каждая строка смены содержит только рейсы своей смены разгрузки, сумма строк равна числу уникальных рейсов.

**Фактически:** суточный итог самосвала повторяется в дневной и ночной строках; экран и Excel ошибаются одинаково.

**Подтвержденная причина:**

Рейсы сначала группируются только по `truck_id`. Затем один и тот же суточный итог самосвала присваивается каждой его смене, после чего общий итог снова суммирует эти повторенные строки.

**Места в коде:**

- `СИСТЕМА_MVP/backend/reports/views.py:640` — группировка по самосвалу;
- `СИСТЕМА_MVP/backend/reports/views.py:673` — присвоение общего итога каждой смене;
- `СИСТЕМА_MVP/backend/reports/views.py:721` — повторное суммирование строк;
- `СИСТЕМА_MVP/backend/reports/views.py:829` — Excel использует тот же ошибочный контекст;
- `СИСТЕМА_MVP/backend/users/tests.py:2904` — существующий тест не покрывает две смены и `unloading_shift`.

**Рекомендация:**

- группировать завершенные рейсы по точному `unloading_shift_id`;
- фильтр `День / Ночь` применять к `unloading_shift__shift_type`;
- строку смены связывать со статистикой по `shift.id`;
- старые рейсы без `unloading_shift` не распределять по всем сменам: выводить отдельную явно подписанную строку «Смена не определена» либо применить согласованное историческое правило;
- экран и Excel строить из одного исправленного набора.

**Автоматические тесты:**

- один самосвал, дневная и ночная смены;
- два рейса разгружены днем и два ночью;
- переходящий рейс попадает в смену разгрузки;
- фильтры `Все / День / Ночь` дают `4 / 2 / 2`;
- сумма строк равна числу уникальных рейсов;
- Excel совпадает с экраном.

**Критерии приемки:**

- общий итог `4 / 198`;
- день `2 / 94`;
- ночь `2 / 104`;
- ни один ID рейса не суммируется дважды;
- экран, Excel и запрос к базе совпадают.

**Автоматические тесты:**

**Критерии приемки:**

- тупика нет;
- молчаливого автоматического закрытия нет;
- пользователь видит, что произошло;
- сохраняются причина, исполнитель и время;
- новая смена открывается штатным UI.

## 7. Риск QA-RISK-001. Конкурентные действия

Первый прогон не воспроизвел дубль, но не доказал устойчивость всех операций при одновременном действии двух клиентов.

Проверить минимум:

- два Диспетчера одновременно начинают смену;
- Диспетчер и Горный мастер одновременно назначают один самосвал;
- две роли одновременно открывают или закрывают один простой;
- повторный запрос после потери ответа;
- одинаковый и новый `client_action_id`;
- две вкладки одновременно завершают один рейс.

**Ожидается:** одна доменная запись, понятный `409` или ошибка валидации второму клиенту, отсутствие `500`, дубля и частичного состояния.

Если тест падает, оформить отдельные дефекты. Если требуется новое ограничение базы или миграция, не выполнять ее без отдельного разрешения.

## 11. Правило передачи обратно в тестовый чат
