## 2. QA-CHAOS-P2-001-R3 — безопасный выход из старого read-only-экрана

### 2.1. Воспроизведение до исправления

Сначала была добавлена исполняемая JavaScript-регрессия, которая извлекает настоящий `openConfirmDialog` и настоящий обработчик клика по ссылкам непосредственно из `templates/base.html`.

До изменения production-шаблона новый тест воспроизводимо показал:

```text
role_active=false
→ клик по обычной ссылке /logout/
→ event.preventDefault()
→ openConfirmDialog() возвращается из-за read-only
→ URL остаётся /mining-master/assignments/
```

В первом тестовом прогоне итог был `4 PASS / 2 FAIL`. Одно из двух падений относилось именно к заблокированному logout.

### 2.2. Подтверждённая причина

Общий обработчик ссылок в `templates/base.html`:

1. распознавал `/logout/` как действие с подтверждением;
2. заранее вызывал `event.preventDefault()`;
3. передавал действие в `openConfirmDialog()`;
4. `openConfirmDialog()` корректно запрещал открытие изменяющего подтверждения на неактивной роли и возвращался;
5. переход уже был отменён, поэтому безопасный серверный `/logout/` не вызывался.

Серверный middleware уже разрешал `/logout/`, а `logout_view()` корректно очищал только текущую host-only-сессию. Источник дефекта находился в общем клиентском обработчике ссылки.

### 2.3. Исправление

В `templates/base.html` добавлена узкая ветка только для точного `href="/logout/"` при текущем read-only:

- стандартное событие ссылки перехватывается;
- выполняется прямой переход `window.location.href = link.href`;
- общий confirm для этого безопасного выхода не открывается.

Поведение активной роли не менялось: обычный logout активной роли по-прежнему использует существующее подтверждение.

Запрет изменяющих действий не ослаблялся:

- изменяющие ссылки с `data-confirm` при read-only не получают выполняемое действие;
- POST-формы остаются заблокированными клиентским read-only-барьером;
- серверный middleware продолжает отклонять unsafe-запросы неактивной роли;
- готовое изменяющее подтверждение по-прежнему обезвреживается при live-потере роли.

### 2.4. Регрессионное покрытие

Исполняемая JS-регрессия проверяет три ветки настоящего production-обработчика:

1. read-only + обычный `/logout/` — выполняется переход;
2. read-only + изменяющая ссылка с confirm — переход и действие не выполняются;
3. активная роль + `/logout/` — сохраняется прежний confirm.

Добавлен Django-тест `ActiveRoleSwitchRegressionTests.test_old_inactive_host_can_logout_safely`:

- Водитель входит в своём role-origin;
- тот же сотрудник активирует Диспетчера в другом role-origin;
- старая сессия Водителя становится неактивной;
- GET `/logout/` старой сессии возвращает redirect на login;
- старая host-only-сессия очищается;
- сессия Диспетчера остаётся действующей.

## 3. QA-REG-P2-001 — отсутствующий resetHold()

### 3.1. Воспроизведение до исправления

Сначала добавлен исполняемый интеграционный тест настоящего обработчика формы Водителя.

Тест:

- извлекает из `templates/users/driver_shift.html` настоящий `createDriverRoleHoldGuard`;
- извлекает настоящий production-блок привязки формы закрытия смены;
- создаёт форму в состоянии `shift_action=close`;
- запускает настоящий guard и продвигает fake RAF до ненулевого progress;
- отправляет событие `input` настоящему production-listener.

До исправления тест завершался:

```text
ReferenceError: resetHold is not defined
```

Это было второе падение первого прогона `4 PASS / 2 FAIL`.

### 3.2. Подтверждённая причина

После прежнего рефакторинга локальная функция `resetHold()` была удалена, а жизненным циклом удержания стал управлять `shiftCloseHoldGuard`.

В production-обработчике изменения показаний сохранился один устаревший вызов:

```javascript
resetHold();
```

Обычный UI-путь через кнопку `Изменить показания` сначала переводил action в `review`, поэтому дефект не возникал в прежнем ручном Browser QA. Но событие `input` при состоянии `close` выполняло отсутствующий идентификатор и давало реальный `ReferenceError`.

### 3.3. Исправление

Устаревший вызов заменён на:

```javascript
shiftCloseHoldGuard.cancel();
```

Использован именно `cancel()`, потому что он выполняет принудительный полный reset текущего guard:

- отменяет timeout и RAF;
- возвращает progress в `0%`;
- снимает `is-holding` и `is-pending`;
- возвращает `driverShiftConfirmed=false`.

После события `input` форма возвращается к проверяемому состоянию:

```text
shift_action=review
driverShiftDirty=true
driverShiftConfirmed=false
review hidden
inputs visible
progress=0%
таймеры/RAF отсутствуют
```

Во всём шаблоне Водителя вызовов отсутствующего `resetHold()` больше нет: `0`.

### 9.3. Независимый Browser QA QA-REG-P2-001

Использовать отдельную тестовую базу, зарегистрированного Водителя с назначенным самосвалом и открытой сменой.
