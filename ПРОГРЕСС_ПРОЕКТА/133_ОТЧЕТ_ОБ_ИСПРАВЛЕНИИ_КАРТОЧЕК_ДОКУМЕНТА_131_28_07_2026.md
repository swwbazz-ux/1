## 3. QA-TRAFFIC-P1-002-R2-R1

### 3.1. Подтверждённая причина

После потери фокуса прежний
`isDriverOperationalRefreshUnsafe()` больше не защищал форму открытия смены:

- проверялся активный элемент;
- проверялась форма закрытия смены;
- форма начальных показаний не имела устойчивых признаков `dirty`,
  `validation error` и `pending submit`.

Поэтому связанное realtime-событие могло заменить весь
`[data-driver-shell]` узким JSON-фрагментом и стереть введённые, но ещё не
сохранённые показания.

### 3.2. Исправление

В форме открытия смены Водителя добавлены:

- baseline начальных значений;
- `data-driver-shift-opening-dirty`;
- `data-driver-shift-opening-pending`;
- запрет fragment replace при изменённых показаниях, серверных ошибках или
  незавершённой отправке;
- пробуждение отложенного realtime-обновления после явного `form.reset()` или
  возврата к baseline.

### 3.3. Исполняемая регрессия

Новый тест исполняет production-функции шаблона и проверяет:

```text
321 / 654 / 987
→ blur
→ связанное realtime-событие
→ fragment request count = 0
→ replace count = 0
→ значения = 321 / 654 / 987
```

Дополнительно проверены:

- блокировка при `.errorlist`;
- блокировка при pending submit;
- применение отложенной версии после reset.

### 3.4. Живой Browser QA

## 4. QA-TRAFFIC-P1-002-R2-R2

### 4.1. Подтверждённая причина

После fragment-refresh Диспетчера заменялась `.dispatcher-board`, но замкнутая
runtime-переменная `dispatcherShiftOpen` продолжала хранить значение,
полученное при первой загрузке страницы.

В результате DOM мог показывать новое состояние смены, а обработчики действий
продолжали использовать старое.

### 4.2. Исправление

Корень `.dispatcher-board` теперь содержит серверный признак:

```text
data-dispatcher-shift-open="true|false"
```

Перед `replaceWith()` и повторным binding вызывается
`syncDispatcherShiftRuntime(freshBoard)`.

Порядок стал явным:

```text
parse fragment
→ sync runtime shift state
→ replace board
→ bind interactions
```

### 4.3. Исполняемая регрессия

Новый production-JavaScript harness проверяет:

- `closed → open`: drop-handlers привязаны, DnD POST выполняется один раз;
- `open → closed`: drag/drop заблокирован, mutation `fetch count = 0`;
- синхронизация runtime выполняется до замены DOM и повторного binding.

### 4.4. Живой Browser QA

В изолированной PostgreSQL QA-базе временно создана смена Диспетчера
`EmployeeShift id=885`.

Фактически без ручного reload:

|---|---:|---|---|---|
| исходно закрыто | `83556` | `false` | да | нет |
| `closed → open` | `83557` | `true` | нет | да |
| `open → closed` | `83558` | `false` | да | нет |

Сетевой запрет закрытого DnD с `fetch count = 0` подтверждён исполняемой
JavaScript-регрессией.

## 5. QA-TRAFFIC-P2-002-R1-R1

### 5.1. Подтверждённая причина

`_personal_access_event()` считал совпадение `employee_id` достаточным до
проверки роли события. Поэтому `personnel_assignment_changed` для роли
Водителя мог считаться релевантным активному доступу Машиниста того же
сотрудника.

### 5.2. Исправление

Для `personnel_assignment_changed` совпадение сотрудника теперь не отменяет
роль-селективность:

- если событие содержит `role_code`;
- активная worker-роль должна совпасть с ролью события.

Личные `access_changed` для того же сотрудника не сужены этим правилом и
сохранили прежний контракт.

### 5.3. Регрессия

Добавлен тест:

```text
crew-plan role_code = driver
employee_id совпадает
active role = excavator_operator
event_is_relevant = false
```

Отдельный существующий сценарий подтверждает, что личный `access_changed`
другой роли того же сотрудника по-прежнему доставляется.

## 6. QA-TRAFFIC-P2-002-R1-R2

### 6.1. Подтверждённая причина

Publisher корректно передавал изменённые `employee_ids`, но одновременно
передавал общую технику. Неизменённый сотрудник противоположной смены на той
же технике получал событие через общий fallback по `equipment_ids`.

### 6.2. Исправление

Для `personnel_assignment_changed` с
`payload.action == "crew_plan_published"` объявленный `employee_id` /
`employee_ids` является авторитетной областью получателей.

После проверки роли:

- изменённый сотрудник получает событие;
- неизменённый сотрудник другой смены не получает его;
- fallback по общей технике для такого crew-plan события не выполняется.

Остальные типы событий и обычная equipment-область не менялись.

### 6.3. Регрессия

Добавлен точный сценарий:

```text
изменены employee_ids: day worker A, day worker B
неизменённый worker: night worker C
equipment_id у всех общий
worker C relevant = false
```
