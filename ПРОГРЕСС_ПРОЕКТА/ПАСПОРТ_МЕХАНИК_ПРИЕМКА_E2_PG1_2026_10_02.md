# E2-PG1 — приёмка и передача координатору

Дата: 02.10.2026. Астра.

## Решение

E2-PG1 принят. Назначенная адресная приёмка E2 завершена на test-only SHA bd6358337d316f3097902657314531eb0f5885f9 поверх runtime-кандидата 60994c919498ca12323d25e4bc0605f8f00efdec. Дополнительная итерация исправления E2 не назначается.

Это готовность к подготовке интеграции, не разрешение PR/merge/VERIFY/deploy. Производственная установка и полный офлайн-контур не приняты этим документом.

## Проверенные свидетельства

Источник: docs 8a4c4d40d5cf1449ae56802d2bee70857f3b3c59, [отчёт](ПАСПОРТ_МЕХАНИК_ДОКАЗАТЕЛЬНЫЙ_ОТЧЕТ_E2_PG1_2026_10_02.md), [пакет](ПАКЕТ_E2_PG1_2026_10_02/README.md).

Астра прочитала commit, родителя, patch, TransactionTestCase и helper отправки, RUN_COMMANDS, stderr, source-sha, DB identity, exit и stop logs. Собственного повторного запуска PostgreSQL не было.

- Commit меняет только core/test_offline_sync.py: +119 строк; родитель точно 60994c91…; runtime не изменён.
- Django identity: connection_vendor=postgresql, version_num=160015. Stderr подтверждает создание и уничтожение test_accounting_e2_pg1.
- Все десять перечисленных тестов имеют ok; Ran 10 tests in 6.323s / OK, без skipped. Exit log содержит EXIT_CODE=0 (файл представлен с признаками UTF-16, это не новый UTF-8 raw).
- Временный RuntimeError ребёнка — тестовая инъекция; соответствующий тест заканчивается ok.
- Два новых теста используют TransactionTestCase, ThreadPoolExecutor, Barrier перед POST, отдельный Client и thread-local connection. SQLite приводит к skip, но в представленном прогоне skip отсутствует.
- Проверки утверждают один receipt/action/trip для повторов корня; для root/child — итог после контрольных повторов, исходные времена/sequence/depends_on/payload и маркеры восстановления, отмену своим временем ребёнка.
- Общий барьер подтверждает конкурентный старт запросов, но не доказывает каждый возможный порядок захвата DB locks. Нет трассировки ожиданий блокировок или исчерпывающего перебора расписаний. Для назначенного узкого gate это достаточный результат; не объявлять доказательство отсутствия всех гонок.
- Stop log: PG_STOP_EXIT_CODE=0. По отчёту кластер слушал localhost, production не использовался. Это результаты автора, не независимое обследование его машины.
- Хеш wheel фиксирует заявленный бинарный артефакт, но не является аудитом его поставщика. Бинарники в production не предлагаются.

## Что принято и что остаётся

Принято в совокупности E2/R1/R2/PG1: снятие cooldown для обычного самосвала и ТЕСТ-1, соответствующие карточки/сервер/QA, адресное восстановление старого отказа и сохранённых потомков с теми же ID/временем, сохранность происхождения через RETRY, PostgreSQL gate.

Сохраняются границы:
- физический APK/Xiaomi NOT_RUN;
- новый браузерный прогон на R2/PG1 NOT_RUN; тестовый PG-коммит не меняет приложение;
- R1 browser доказывает очередь/доставку после устранения зависания, а не startup при продолжающем silent listener;
- startup остаётся OFF-C1, здесь не исправлялся;
- известный Driver baseline не объявляется зелёным;
- при изменении release-основы успешные тесты исходного кандидата не заменяют проверки итогового интеграционного SHA.

## Следующий шаг — координатор, не новая разработка Кодекса

Передать координатору точный bd635833… и эту приёмку. Сверить актуальную release-основу, очередь выпуска и использование Excavator v264, пересечения с OFF-C1. Подготовить конкретный состав включения и проверки итогового SHA, а также короткую приёмку установленного приложения: обычный самосвал после разгрузки доступен сразу онлайн и без сети; после reconnect нет дубля.

Не переносить ветку целиком поверх свежих файлов и не считать v264 автоматически свободной. Не выпускать E2 под видом исправленной полной автономности.

Кодексу дополнительной работы по E2 сейчас нет. После подготовки координатор возвращает план включения и оставшиеся проверки; фактическое слияние/VERIFY/deploy требует отдельного разрешения владельца. Астра изменила только документационную ветку.
