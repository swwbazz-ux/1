## 1. Итог

На exact candidate `b5781132a7885546c32cb4e45735d78001b4f674` один обычный `QA-DRIVER-T-01` прошёл непрерывную цепочку:

1. машинист реальным drag создаёт X;
2. водитель реальным удержанием создаёт `driver.trip.unloaded`, отдельные receipt/action и завершает именно X;
3. серверная проекция машиниста возвращает ту же карточку в `assigned / canLoad=1` без cooldown;
4. менее чем через 10 минут реальный drag создаёт ровно один Y.

Цепочка выполнена трижды: online, offline→restart→reconnect и при потере уже принятого ответа. Во всех случаях один Driver unload завершил предшествующий Trip; Y создал один `OfflineFieldEvent`, один `TripClientAction` и один Trip. Q2 сохранил исходные `event_id`, `occurred_at` и `sequence` через закрытие/запуск приложения. Q3 завершился `deduplicated` с прежними receipt/trip ID без второго эффекта.

### Q1: проекция экрана

После принятого Driver unload server version стал 97 и содержал `trip_changed` для Trip 1. Автоматический foreground reconcile, без ручного reload, показал ту же карточку:

```text
openTripId=""; equipmentState="assigned"; canLoad="1";
block=""; draggable=true; visible=true
```

После этого Y создан через 76.086 s от server acceptance разгрузки. Карточка не имела cooldown-затемнения или отсчёта.

### Q2: offline, закрытие и запуск приложения

После принятого Driver unload и видимой доступной карточки удалён только test `adb reverse`. Физический drag создал локальное событие `4c426d…` в `07:41:32.661Z`; до reconnect сервер имел 0 receipt / 0 action. До и после force-stop/start durable queue содержала те же event ID, tap time и sequence 3. После возврата reverse сервер создал ровно 1/1/1, pending очистился, а `Trip.loaded_at` сохранил `07:41:32.661Z` с источником `excavator_device`.

### Q3: принятый ответ потерян

Django принял `8de21c…` и вернул proxy HTTP 200/accepted. Proxy полностью дочитал ответ и уничтожил downstream до headers. TLS bridge преобразовал upstream `socket hang up` в HTTP 502 телефону; следующие десять попыток намеренно получали HTTP 503. После restart сохранился тот же envelope. Разрешённый повтор вернул `deduplicated` с `trip_id=4`, `event_receipt_id=7`; DB-снимки до и после повтора побайтно совпадают (`8505B304BA3AA20F7D0B38A266FAD97F4524001C4F959D905B4A386EEE3DDE43`).

Это проверка потери принятого ответа с 502/503, не молчащего порта.

## 6. Время

У всех Driver unload и у online Q1/Q3 load receipt сохраняет исходное время жеста. Из-за `device_clock_adjusted=true` operational `completed_at`/`loaded_at` для этих online-событий берётся из `server_receipt`. У offline Q2 `Trip.loaded_at` равен исходному tap time и имеет источник `excavator_device`.

Client timestamps и proxy/DB timestamps относятся к разным часам. В отчёте они не сортируются как одна временная шкала без поправки.

## 9. Границы и следующий выпускной шаг

- Это изолированный установленный QA на одном Android-устройстве, не общий RuStore QA и не production.
- Q2 подтверждает cached-shell restart при hard connection refusal. Известный OFF-C1 запуск при продолжающем молчать listener этим не принят и не переносился.
- Наличие receipt, изменение БД и обновление экрана проверены раздельно.
- PR №149 остаётся draft; merge, production VERIFY и deploy не выполнялись.

После адресной приёмки Астрой Координатору нужно ещё раз сверить свежий release/очередь/резерв `Excavator v264`, затем решать merge PR №149. Перед merge при новом release кандидат следует обновить и повторить CI exact head. Откат не требует миграции: в кандидате их нет; достаточно revert интеграционного изменения и возврата предыдущего shell marker/статики штатным защищённым каналом.
