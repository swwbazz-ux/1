## 6. Остаточные дефекты

### 6.1. QA-TRAFFIC-P2-002-R2-R2 — routine connected=true превращает recovery в polling

#### Фактическое поведение

`achievement_prize.html` вызывает `recoverAchievementCheck()` на любое
событие:

```text
operational-state-connection
detail.connected === true
```

`realtime-client.js` публикует `connected=true` после каждого успешного
realtime poll, а не только после перехода из offline в online.

После первоначального GET и трёх ограниченных повторов
`failedAchievementCheck` остаётся сохранённым. Каждый очередной обычный
успешный realtime poll:

1. снова переносит ошибку в `pendingAchievementCheck`;
2. сбрасывает попытку восстановления;
3. планирует новый GET через debounce;
4. при следующем realtime poll повторяет цикл.

#### Независимое воспроизведение

На настоящем `achievement-prize-runtime`:

```text
после первоначального исчерпания: 4 GET
после трёх обычных connected=true: 7 GET
ожидалось: 4 GET
```

Диагностический тест:

```text
DIAGNOSTIC repeated connected=true after exhaustion must not become polling
tests 20
pass 19
fail 1
actual 7
expected 4
```

#### Влияние

В здоровом режиме лишнего трафика нет. При недоступном achievement
endpoint и здоровом realtime ограниченный retry превращается примерно в
один GET на каждый пятисекундный poll каждого активного приложения.

#### Требуемое исправление

- реагировать только на фактический переход `false → true`;
- допустим явный `reconnected=true` от общего realtime-клиента;
- первое и каждое обычное `connected=true` без предыдущего
  `connected=false` не должно вооружать исчерпанную ошибку;
- один реальный reconnect может запустить ровно один новый ограниченный
  цикл;
- если новый цикл снова исчерпан, последующие routine `connected=true`
  не должны создавать GET и не должны сокращать backoff.

#### Обязательная регрессия

1. Довести qualifying GET до `1 + 3` ошибок.
2. Передать несколько обычных `connected=true`.
3. Подтвердить неизменные `4 GET`.
4. Передать `connected=false`, затем `connected=true`.
5. Подтвердить ровно один новый recovery-цикл.
6. Снова исчерпать его.
7. Передать несколько обычных `connected=true`.
8. Подтвердить отсутствие новых GET.

### 6.2. QA-TRAFFIC-P2-003-R2-R2 — waiting worker снимает блокировку непроверенного controller

#### Фактическое поведение

После `controllerchange` общий guard правильно:

- увеличивает generation;
- ставит `controllerVersionPending=true`;
- очищает `state.serviceWorker`;
- переводит экран в `ready=false / locked=true`;
- запрашивает версию текущего controller.

Но `isExpectedVersionWorker()` той же generation также принимает:

- `registration.active`;
- `registration.waiting`;
- `registration.installing`.

Если controller не ответил, а matching waiting worker ответил, payload
waiting worker передаётся в `acceptServiceWorkerVersion()`. Экран
ошибочно возвращается в `ready=true / locked=false`, хотя версия
фактического controller остаётся неизвестной.

#### Независимое воспроизведение

```text
до controllerchange:
ready=true, locked=false

после controllerchange без ответа controller:
ready=false, locked=true

после matching ответа waiting worker:
ready=true, locked=false

ожидалось:
ready=false, locked=true
```

Диагностическое утверждение:

```text
AssertionError:
waiting worker must not unlock an unverified controller
actual:   {ready: true,  locked: false}
expected: {ready: false, locked: true}
```

#### Влияние

На коротком переходном интервале изменяющие действия могут снова стать
доступны до проверки фактически управляющего страницей service worker.

#### Требуемое исправление

- пока `controllerVersionPending=true`, принимать version payload только
  от точного `navigator.serviceWorker.controller`;
- ответ `active`, `waiting` или `installing`, который не является точным
  controller, не должен менять `state.serviceWorker`, `ready`, `locked`
  или reload-state;
- только ответ точного controller может снять
  `controllerVersionPending`;
- после ответа matching controller экран штатно разблокируется;
- после mismatch controller остаётся действующий однократный безопасный
  recovery/reload-контракт.

#### Обязательная регрессия

```text
controllerchange
+ новый controller не отвечает
+ waiting worker той же generation отвечает matching-версией
= ready=false / locked=true
```

Дополнительно проверить:

- поздний matching controller после этого разблокирует экран;
- поздний mismatch controller не разблокирует экран;
- два ответа waiting worker не меняют состояние;
- reload loop не появляется.

### 6.3. QA-TRAFFIC-P2-003-R3-R2 — поздний старый sync воскрешает update badge

#### Фактическое поведение

Затронуты:

- `templates/trips/excavator_work.html`;
- `templates/trips/dispatcher_control.html`.

Последовательность:

1. старый `syncContractState()` или
   `syncMiningMasterPwaContractState()` запускает асинхронный
   `getCurrentVersion()`;
2. другая вкладка активирует новый worker;
3. `controllerchange` правильно очищает ссылку на waiting worker,
   закрывает modal и скрывает badge;
4. новый sync подтверждает актуальную версию;
5. запоздавший ответ старого active worker приходит последним;
6. старый `.then()` снова вызывает `setIndicator(true, ...)` и сохраняет
   ложное обновление.

#### Независимое воспроизведение

На настоящих production-IIFE двух ролей:

```text
штатные тесты: 6 PASS
добавленные out-of-order сценарии: 2 FAIL
```

Оба падения:

```text
AssertionError: late old sync must not resurrect badge
actual badge.hidden: false
expected: true
```

#### Влияние

Рабочие действия не блокируются и повторный `SKIP_WAITING` не
отправляется, но пользователь снова видит ложное предложение обновить
уже обновлённое приложение. Stale-запись может сохраниться в
`localStorage` до следующей проверки или reload.

#### Требуемое исправление

Для обеих ролей:

- завести отдельную generation для каждого запуска sync;
- перед асинхронным запросом сохранить точные ссылки на controller,
  registration и active worker;
- перед любым изменением modal, badge, visible version или
  `localStorage` проверить:
  - generation всё ещё актуальна;
  - controller не сменился;
  - registration/active worker остаются теми же;
- stale `.then()` и stale `.catch()` должны завершаться без UI/storage
  mutation;
- существующая защита waiting-inspection и запрет повторного
  `SKIP_WAITING` должны сохраниться.

#### Обязательные регрессии

Отдельно для Машиниста и Горного мастера:

1. старый active worker получает `GET_VERSION`, но ответ задерживается;
2. активируется новый worker;
3. новый sync отвечает первым и скрывает modal/badge;
4. старый worker отвечает последним;
5. modal/badge остаются скрыты;
6. stale version не записывается в `localStorage`;
7. `SKIP_WAITING=0`.
