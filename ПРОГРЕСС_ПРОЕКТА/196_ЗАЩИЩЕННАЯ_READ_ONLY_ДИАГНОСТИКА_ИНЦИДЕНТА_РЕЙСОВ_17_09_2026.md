## Статус

Подготовлен локальный протокол диагностики production через штатный GitHub Actions-канал. На момент записи:

- база данных, рейсы и зависшие состояния не изменялись;
- очистка очередей и восстановление данных не выполнялись;

Следующая изменяющая операция — `update_receiver` — требует отдельного точного разрешения владельца.

## Новое фактическое уточнение инцидента

Диспетчер сообщил, что у целевой техники рейсы визуально «сбросились» в коротком интервале, но в почасовом отчёте данные за этот же период присутствуют.

Это не доказывает полноту всех рейсов, однако делает удаление самих записей маловероятным. Основная рабочая гипотеза — расхождение оперативной проекции/счётчика диспетчера с сохранёнными `Trip`, а не потеря истории.

Точные идентификатор техники и UTC-границы фокусного окна/смены являются production-параметрами. Они хранятся вне публичного Git и будут переданы только через защищённый workflow event после разрешённого обновления receiver.

## Почему существующий канал не подходил

- `verify_data` проверяет только пакет и не читает production-БД.
- `apply_data` устанавливает присланный Python и запускает его `--dry-run` до резервной копии БД; транзакция не защищена `READ ONLY`, отсутствуют диагностические лимиты, stdout попадает в открытый Actions log.
- Репозиторий публичный, поэтому реальные выгрузки рейсов, сотрудников и диагностический plaintext нельзя помещать в commit, workflow env, log или обычный artifact.

## Подготовленный контракт `diagnose`

- Разрешена только фиксированная операция `trip_accounting_incident_v1`.
- Пакет не содержит Python, SQL, файлов данных, команд или путей.
- Допустимы только идентификатор техники, две строгие UTC-границы и лимит до 500 строк; окно не более 24 часов.
- Запрос хранится в установленном receiver и запускается от непривилегированного пользователя приложения.
- PostgreSQL-запрос выполняется с `PGOPTIONS default_transaction_read_only=on` внутри единого `transaction.atomic()`-снимка; первый SQL — `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`, затем проверяются оба режима.
- Установлены `statement_timeout=12s`, `lock_timeout=2s` и общий process timeout 45 секунд.
- Секции и поля ответа проходят точный server-side allowlist. ФИО, табельные номера, PIN, телефоны, cookies, токены, URL/query, request body, stack и произвольные payload запрещены.
- В диагностику входят рейсы, смены, назначения, свободный ковш, простои, offline receipts/конфликты, административные конфликты, handoff, относящиеся к объектам realtime-события/версии, application sessions и хэши сообщений клиентских ошибок.
- Ответ ограничен по строкам и размеру. Receiver валидирует и шифрует отчёт на production; GitHub runner получает только CMS-DER в безопасном JSON-конверте и загружает `.cms` на один день. Диагностический plaintext на runner не попадает.
- В открытом логе остаются только код фиксированной операции, число строк, признак усечения и SHA-256 шифротекста.
- Workflow отклоняет `update_receiver` и `diagnose` вне канонической ветки `codex/github-production-deploy-20260916`; все используемые GitHub Actions закреплены полными commit SHA. До запуска этих режимов дополнительно обязательны внешняя Environment branch policy и защита самой control-ветки: одной проверки внутри изменяемого YAML недостаточно.

## Подтверждённые кодом дефекты, которые нельзя смешивать с данными инцидента

1. «Нужна сверка · 11» выводит общий размер локальной очереди, хотя режим включается при наличии хотя бы одного `conflict/invalid/auth_required`; число 11 не означает 11 конфликтов.
2. Терминальные `conflict/invalid` остаются в outbox без штатного экрана разбора и могут висеть бессрочно.
3. Свободный ковш может ошибочно считать рейс управляемым при открытой смене водителя, даже когда водительское приложение отсутствует/офлайн; такой рейс способен остаться «На разгрузку».
4. Устаревший офлайн-каталог позволяет повторно принять тот же самосвал до свежего server fragment, после чего сервер создаёт `open_trip_exists`.
5. Каталог допускает самосвал с блокирующим простоем, а free-bucket обработка простоев расходится с обычной погрузкой.
6. После смены точки разгрузки фактическая точка сохраняется и realtime маршрутизируется, но основной экран экскаваторщика раскладывает бейдж сначала по `assigned_dump_point`, поэтому визуально оставляет его у исходной точки.

Эти дефекты требуют отдельных регрессионных исправлений, но конкретную причину полевых симптомов нельзя объявлять доказанной без production-сверки.

## Безопасная последовательность продолжения

1. Зафиксировать и отправить feature-commit.
2. Выполнить не изменяющий production режим `verify_receiver` и получить `VERIFY_OK`.
3. Остановиться и получить отдельное точное разрешение на защиту control-ветки/Environment и `update_receiver` для полного SHA.
4. После разрешения включить внешнюю policy, fast-forward канонической control-ветки тем же SHA, выполнить `update_receiver`, проверить установленный receiver.
5. Запустить две зашифрованные read-only диагностики целевой техники: согласованное фокусное окно и вся смена; точные параметры не фиксировать в публичном Git.
6. Расшифровать локально, сопоставить `Trip`, отчётный интервал, версии оперативного состояния, offline receipts и client sessions.
7. Только после доказательства причины готовить кодовый фикс и отдельный план очистки. Не удалять рейсы и receipts, не создавать дубли.
