# Границы локальной Git-фиксации ready-core

Дата: 27.07.2026  
Основание: разрешение владельца проекта провести Git-scope аудит и создать
локальный commit.  
Push и deploy: **НЕ РАЗРЕШЕНЫ**.

## 1. Итог аудита

Проверенный пакет ready-core можно зафиксировать одним локальным commit после
индексации только по точному allowlist.

Исходное состояние перед фиксацией:

- ветка: `codex/new-public-site-ux-prototype`;
- HEAD: `e75922ce7d26c1b9cf4335d8c1af67064a40d440`;
- `origin/main`: `5f959e48ad7e753c38da8d755137d1c4bad77b72`;
- удалённый GitHub-репозиторий публичный;
- staged-файлов до аудита не было.

Ветка исторически содержит изменения публичного сайта. Это не меняет состав
локального commit, но перед будущим push владелец должен отдельно решить, на
какой ветке публиковать ready-core.

## 2. Точный состав commit

В commit входят:

1. `81` файл Django ready-core:
   - `52` изменённых отслеживаемых файла;
   - `6` новых production-файлов;
   - `23` новых regression/test-файла.
2. `59` Markdown-документов:
   - `9` изменённых документов прогресса;
   - все `49` документов QA-цепочки `73–121`;
   - этот документ 122.
3. Два безопасных машинных результата:
   - `АРТЕФАКТЫ_83_R04/R04_РЕЗУЛЬТАТ.json`;
   - `АРТЕФАКТЫ_87_R05/87_R05_РЕЗУЛЬТАТ.json`.

Всего по allowlist: `142` файла.

Все `81` backend-файл входят как единый связный пакет: новые production-файлы
уже импортируются изменённым кодом, а новые тесты воспроизводят заявленный
набор `705` тестов. Применять только `git add -u`, `git add .` или
`git add -A` запрещено.

Защитный запрет для Механика также входит в пакет, поскольку он предотвращает
несанкционированное закрытие простоя Самосвала. Это не означает готовность
рабочего места Механика и не расширяет границы пилота на эту роль.

## 3. Что намеренно не входит

Из commit исключаются и сохраняются локально без удаления:

- весь `SITE_PROTOTYPE`: `96` файлов, `29 226 308` байт;
- папка `Шрифты`: `3` файла, `113 894` байта;
- `10` QA-скриншотов из `АРТЕФАКТЫ_83_R04` и
  `АРТЕФАКТЫ_87_R05`: `436 819` байт.

Скриншоты не включаются в историю публичного репозитория, поскольку один из
них содержит имя и фотографию реального сотрудника, а остальные показывают
внутренние обозначения техники и производственные показатели. Они остаются
локальными доказательствами и могут быть опубликованы только после отдельного
обезличивания.

Также не входят:

- `db.sqlite3`;
- `private_media`;
- `.env`;
- файлы миграций;
- production-конфигурация и deploy-материалы;
- локальный переносимый PostgreSQL и временные данные.

## 5. Основание готовности к фиксации

Финальная независимая приёмка документа 121 зафиксировала:

- SQLite: `705/705 OK`, PostgreSQL-only `31` штатно пропущен;
- PostgreSQL 16.14: `705/705 OK`, skipped `0`;
- `manage.py check`: PASS;
- `makemigrations --check --dry-run`: изменений нет;
- AST-аудит: `41` test-файл, `RETURN_BLOCK_FINDINGS=0`;
- `git diff --check`: PASS;
- рабочая SQLite и `private_media` не изменены;
- локальные серверы и PostgreSQL остановлены.

После документальной санитарной правки production-код не менялся. Перед
commit нужно повторить staged-аудит, `git diff --cached --check` для
backend, Markdown-aware проверку документов, `manage.py check`, контроль
миграций и JavaScript-регрессии. Для Markdown допустимы ровно два пробела
в конце строки как штатный hard line break; прочие хвостовые пробелы
запрещены.

## 6. Разрешённое действие

Разрешено:

- проиндексировать только `142` файла allowlist;
- создать один локальный commit с сообщением
  `feat: зафиксировать проверенное производственное ядро`.

Не разрешено:

- push;
- deploy;
- изменение production;
- применение миграций;
- изменение рабочей базы или `.env`.

Хэш commit указывается в итоговом сообщении после успешной фиксации, а не в
этом документе, чтобы не создавать циклическую зависимость содержимого commit
от его собственного идентификатора.
