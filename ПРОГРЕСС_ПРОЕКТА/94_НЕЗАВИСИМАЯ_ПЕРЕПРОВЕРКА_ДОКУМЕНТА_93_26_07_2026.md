## 6. Воспроизведенный остаточный дефект

### QA-CHAOS-P2-001-R1. Открытое окно подтверждения остается активным после live-переключения роли

Приоритет: `P2`, потому что серверный уровень продолжает защищать данные  
Статус: `BROWSER REPRODUCED / CODE CONFIRMED`

Точный сценарий:

1. Горный мастер входит в активную смену.
2. Нажимает `Завершить смену`.
3. Открывается общее окно подтверждения.
4. После десятисекундной задержки кнопка `Завершить смену` становится активной.
5. В другой role-origin тот же сотрудник входит Диспетчером.
6. Старая PWA Горного мастера без reload получает:
   - `role_active=false`;
   - `data-role-readonly=true`;
   - баннер `Роль неактивна — доступен только просмотр`.
7. Основная кнопка завершения смены на экране блокируется.
8. Уже открытое окно подтверждения остается открытым.
9. Кнопка подтверждения внутри окна остается активной:

```text
modalHidden=false
acceptDisabled=false
acceptText="Завершить смену"
```

Причина:

- кнопки общего окна подтверждения находятся вне исходной POST-формы;
- `[data-confirm-accept]` не входит в `CONTROL_SELECTOR`;
- при live-переходе в read-only не очищается `pendingConfirmAction`;
- обработчик активной кнопки все равно вызывает сохраненное действие.

Серверный middleware должен остановить запись, но утвержденное требование звучит как «старый экран только для просмотра без возможности действий». Поэтому оставлять активную кнопку нельзя.

Требуется:

1. при переходе в read-only немедленно закрыть активное окно подтверждения либо очистить его действие и отключить подтверждение;
2. очистить таймер задержки и `pendingConfirmAction`;
3. не блокировать безопасные `Отмена` и `Закрыть`;
4. добавить исполняемый JS-тест:
   `confirm открыт и готов → active-role-state-changed(false) → действие очищено, confirm недоступен`;
5. повторить Browser QA без reload.

Основные доказательства:

- `templates/base.html:215-243`;
- `templates/base.html:408-465`;
- `static/js/role-readonly.js:11-27`;
- фактический Browser QA на `/mining-master/assignments/`.

### QA-CHAOS-P2-001-R2. Уже начатые удержания Водителя не сбрасываются при смене роли

Приоритет: `P2`, потому что сеть защищена клиентским и серверным барьерами  
Статус: `CODE CONFIRMED`

Найдено два варианта:

1. Удержание завершения смены:
   - `requestAnimationFrame` продолжает работать после деактивации;
   - выставляется `driverShiftConfirmed=true`;
   - вызывается `form.requestSubmit`.
2. Удержание разгрузки:
   - таймер продолжает работать;
   - кнопка переходит в локальное состояние `is-pending`;
   - подпись меняется на `ОТПРАВКА`;
   - вызывается `form.submit`.

Изменяющий запрос не должен пройти, но старая PWA может показать ложное локальное состояние `confirmed/pending`.

Требуется:

1. подписать оба механизма удержания на `active-role-state-changed`;
2. при `active=false` отменить timer и animation frame;
3. сбросить progress, `is-holding`, `is-pending`, `driverShiftConfirmed` и `holdComplete`;
4. повторно проверять `window.isAppRoleReadonly()` внутри завершающего callback до любого изменения локального состояния;
5. добавить тест переключения роли посреди удержания, а не только жеста, начатого уже после деактивации.

Основные доказательства:

- `templates/users/driver_shift.html:3452-3478`;
- `templates/users/driver_shift.html:4205-4245`.
