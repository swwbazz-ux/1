## 1. Цель, исходники и граница

После [приёмки P28-I2-R2](ПАСПОРТ_МЕХАНИК_ПРИЕМКА_P28_I2_R2_2026_09_29.md) переходим от чтения неполной старой истории к сохранению новых исходных свидетельств. Журнал нужен, чтобы дальнейшее перенаправление конкретного рейса, в том числе после исчезновения карточки через пять минут, опиралось на сохранённые действия и их причинные связи.

Проверенная основа: release `5721c045d665f5811fc8d343d7374575f386af66`, кандидат `bdecc7eb9c528e40a4891201e1bae4682dc309e1`, docs `c55b5affd46223089261f8da90727abec46c62e8`. R2 исправляет чтение конфликтов; отдельный полный журнал и подтверждение показанного UI-контекста от этого не появляются. Адаптер обоснованно сохраняет `history_complete=False`.

Источники проекта: `core/models.py` (OfflineFieldEvent/Conflict), `trips/models.py` (Trip, TripClientAction, DispatcherActionLog), принятые ядро/адаптер и [P28-R2, редакция 3](ПАСПОРТ_МЕХАНИК_КОНТРАКТ_P28_R2_2026_09_28.md). Код текущих функций не считается автоматически утверждённой нормой.

Ближайшая предполагаемая область реализации после рецензии: **неподключённый внутренний сервис хранения и чтения**, квитанция и преобразование доказанного набора для неизменённого ядра R1. Состав новых моделей/миграций будет определён отдельным заданием. Сейчас не меняются рабочие handlers, телефоны/очереди, экраны, озвучка, отчёт 188, существующие Trip-поля или production. Массовый backfill и новый глобальный протокол авторизации/часов не входят.

## 2. Пять гарантий проекта

### Ж1. Неизменяемое происхождение погрузки

Положительно подтверждённая исходная погрузка хранится отдельно: стабильная идентичность события/рейса, исходная точка, автор, экскаватор, контекст смены, время и источник доказательств. Последующее направление, разгрузка, отмена, замещение и административная коррекция — отдельные свидетельства с собственным авторством. Поздняя повторная отметка не становится исходным автором погрузки.

Копия изменяемого `Trip.dump_point` не доказывает исходную точку. Для legacy сохраняются доступные источники и неизвестность, без искусственного происхождения. Будущая запись исходного события при создании реального рейса должна быть атомарна с этим созданием; пока действующий путь не подключён, такая гарантия для приложения не объявляется реализованной.

### Ж2. Автор, доставщик и точная принадлежность

Неизменный исходный конверт сохраняет заявленные сведения. Проверенный автор, контекст полномочия и основание проверки хранятся отдельно от доставившей сессии. Новый доставщик не становится автором старого действия. Хеш сам по себе не доказывает ни автора, ни право.

Локальная ссылка разрешается только через доказанную область `(автор, устройство, local_trip_id)` погрузки. Неизвестная или неоднозначная ссылка не заменяется «текущим/последним рейсом». Право сменщика по P28-В1 опирается на контекст того же экскаватора при действии, при сохранённом авторе исходной погрузки.

Этот этап не придумывает аутентификацию после выхода из приложения: внутренний сервис принимает проверяемое основание от доверенного вызывающего кода; неподтверждённый claim сохраняет такой статус. Клиентское поле `trusted=true` основанием не является. Если для будущего рабочего входа свидетельства нет, это явно остаётся границей интеграции.

### Ж3. Показанный контекст отдельно от очереди

Сохраняются идентичность направления/маршрутных событий, показанных рабочим интерфейсом при создании распоряжения, локальные зависимости и основание подтверждения этого контекста. **Наблюдение здесь означает показанный контекст действия, а не доказательство того, куда смотрел человек.**

Получение снимка в фоне, `depends_on`, совпадение значения точки или глобальная версия сами по себе не подтверждают показ нужного направления. При отсутствии клиентского пути журнал хранит заявление и его доказательный статус, не повышает их до подтверждённого показа. Неизвестный предок не означает независимости.

Принятые P28-В2/В3 сохраняются: наблюдённое последующее указание машиниста может изменить текущее направление; для конкретной доказанно независимой пары водитель/машинист действует направление водителя. Новых победителей независимых событий одной роли/нескольких устройств этот проект не вводит.

### Ж4. Сохранение отдельно от применения

Полный конверт с версией формата, ID и отпечатком сохраняется неизменным. Квитанция «сохранён» подтверждает durable commit именно этого ID/содержимого. Точный повтор не создаёт второе событие. Несовместимый повтор сохраняется целиком отдельно, не заменяет оригинал и диагностируется для всех доказанно затронутых рейсов; независимый рейс не меняется.

Разрешение ссылок, подтверждение оснований, результат вычислителя и операционный эффект — отдельные записи/результаты с входными ID и версией расчёта. Их изменение не переписывает исходный конверт. Недостающая погрузка, предок или справочная ссылка не стирают принятую запись. Сбой после commit должен позволять возобновить связывание/расчёт без нового нажатия сотрудника.

В неподключённом этапе восстановимость проверяется служебным повторным вызовом в изолированном тесте; постоянный исполнитель и доказательство автономного восстановления без открытого пульта относятся к будущей интеграции и не объявляются уже готовыми.

Разгрузка, техническое закрытие, замещение, отмена и административная коррекция имеют разные основания. Коррекция хранит автора, причину и доступные before/after и не превращается в событие водителя. История уже разгруженного/замещённого X не создаёт оперативную команду возвращаться и не изменяет следующий Y. Технический UNCONTROLLED не является доказанной физической разгрузкой.

### Ж5. Честная область полноты

Наличие новой таблицы или одного нового конверта не устанавливает `history_complete=true`. Нужны обозначенная область протокола/среза, доказанное происхождение, покрытие участвующих путей записи и отсутствие известных недостающих или неподтверждённых причинных ссылок. Основание полноты должно быть доступно читателю для проверки; это не свободный клиентский флаг.

Смешанная legacy-история и отсутствие доказанного показанного контекста остаются явной неполнотой. Полнота относится к доступному срезу и обозначенным источникам, а не к обещанию, что на отключённых телефонах больше нет событий. Новая доставка даёт новый расчёт с новым набором оснований, сохраняя прежние конверты и аудит.

Граница полноты и `policy_unresolved` — внутренний контракт. Она не разрешает показывать работникам техническую очередь разбора или требовать повторного ввода. Рабочий экран будет подключаться отдельным заданием с проверкой ГП-0.

## 3. Шесть проверочных сценариев для рецензии

| № | Вход | Требуемая гарантия |
|---|---|---|
| Ж-С1 | Погрузка P1 → направление P2 → выбор водителя P3 → административная коррекция | Исходные P1/автор неизменны. Коррекция со своим автором и основанием не становится водительским направлением. Не вводится новый приоритет коррекции. |
| Ж-С2 | Два конкурентных одинаковых конверта; затем тот же ID с другой точкой/автором/рейсом | Один оригинал, отдельный полный конфликт, диагностируются X/Y, Z неизменен. Конкурентную часть будущего хранилища проверять на PostgreSQL, двумя соединениями. |
| Ж-С3 | Направление до появления погрузки/локальной привязки; одинаковый L у другого автора/устройства; доставка другой сессией | Запись сохраняется, автор не меняется. Связь только по доказанной области; неоднозначность не выбирает произвольный рейс. Сменщик того же экскаватора сохраняет собственное авторство по В1. |
| Ж-С4 | D:P2 → наблюдавший D машинист O:P3 с отстающими часами; отдельно независимая D/O; отдельно только фоновый снимок/depends_on | В2 даёт P3 при обоих порядках доставки; В3 для независимой пары даёт P2. Фоновое получение/зависимость не доказывают наблюдение. Неутверждённая пара одной роли остаётся без нового победителя. |
| Ж-С5 | Commit → потеря ответа/сбой до расчёта → повтор; затем появляется недостающая ссылка; X уже разгружен/замещён | Событие сохранено один раз, расчёт восстановим. Поздняя история X не создаёт оперативную команду и не меняет Y. |
| Ж-С6 | Новый конверт рядом с legacy/direct без полного payload либо без показанного контекста; позднее приходит предок | Полнота не выдумывается. Пересчитывается производный результат, исходники неизменны; техническое закрытие не становится физической разгрузкой. |

Это сценарии проекта, не отчёт о пройденных тестах I3. Приёмка I2-R2 не является их выполнением.
