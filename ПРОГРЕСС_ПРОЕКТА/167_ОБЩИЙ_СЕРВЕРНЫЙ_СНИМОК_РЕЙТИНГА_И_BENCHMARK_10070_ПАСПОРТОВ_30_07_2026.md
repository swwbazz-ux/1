# Общий серверный снимок рейтинга и benchmark 10 070 паспортов 30.07.2026

## Результат этапа

Завершён серверный контур, который отделяет тяжёлый расчёт
рейтинга Водителей от пользовательского HTTP-запроса.

Теперь для каждой канонической группы

`участок × период рейтинга × состав вахты × дневная/ночная смена`

хранится одна текущая готовая строка. Фоновая команда пересчитывает её раз
в пять минут, а desktop/TV-экран, портал и будущие мобильные приложения
читают уже опубликованный результат.

Старый диагностический HTTP-пересчёт рейтинга по одному `WatchPeriod`
выведен из эксплуатации и возвращает `410`. Формула и паспорта смен больше
не читаются этим HTTP-маршрутом.

Рабочий рейтинг остаётся выключенным и неофициальным:

- `PORTAL_WORKING_DRIVER_RATING_ENABLED=false`;
- `official=false`;
- `official_rating_eligible=false`;
- `м³·км` и `т·км` имеют вес `0`;
- блок рабочего времени остаётся нейтральным;
- синтетический benchmark не калибрует реальные KPI и не разрешает
  премирование.

Production, рабочая SQLite, `.env` и действующие feature flags этим этапом
не изменялись. Миграция `reports.0009` подготовлена в отдельной ветке, но в
production не применялась.

## Серверный контракт

Модель `DriverRatingPeriodMaterializedSnapshot` хранит:

- техническую область участка;
- период рейтинга;
- утверждённый состав вахты;
- дневную или ночную смену;
- версию формулы и версию JSON-контракта;
- готовый JSON рейтинга;
- fingerprints области, источников, сменных баллов, JSON и состава;
- сотрудников группы и время их последних закрытых смен;
- номер ревизии и время публикации;
- время последней успешной проверки и последней попытки;
- состояние и краткую внутреннюю ошибку фонового обновления.

Уникальность строки задаётся по
`scope_code + rating_period + watch_composition + shift_type`.

Публикация выполняется атомарно. PostgreSQL advisory lock не допускает два
одновременных расчёта одной группы. После получения блокировки сервис
сам открывает верхнеуровневую транзакцию `REPEATABLE READ`, повторно читает
в ней период рейтинга и состав вахты, затем в том же снимке базы определяет
активную область сотрудников, исторических участников группы и время их
последних закрытых смен, считает KPI и публикует результат. Вызов из уже
открытой PostgreSQL-транзакции отклоняется, а не ослабляет изоляцию.

Предварительный проход management-команды используется только для
перечисления групп, которые нужно обработать. Готовые employee ID и
`latest_closed_at` из этого прохода в публикацию не передаются. Поэтому
закрытие новой смены между перечислением групп и началом расчёта не может
смешать старый состав с новыми KPI: изменение целиком попадёт либо в
текущую ревизию, либо в следующий пятиминутный цикл.

Если исходные данные не изменились:

- ревизия не увеличивается;
- `published_at` не меняется;
- большой JSON и метаданные состава не переписываются;
- обновляется только heartbeat успешной проверки.

Если расчёт завершился ошибкой:

- последний совместимый результат сохраняется;
- большой JSON не переписывается;
- фиксируются время, код и счётчик ошибки;
- клиент до мягкой границы получает последний результат с предупреждением;
- внутренняя ошибка пользователю не раскрывается.

## Интервалы готовности

- плановый фоновой цикл — `300` секунд;
- мягкая задержка — после `600` секунд;
- жёсткое скрытие устаревшего результата — после `1 800` секунд.

До `600` секунд результат имеет состояние `fresh`. После мягкой границы
или неуспешной последней попытки он имеет состояние `delayed`. После
жёсткой границы результат не показывается до успешного пересчёта.

Пятиминутный systemd timer и service подготовлены в отдельной ветке. Service имеет
`TimeoutStartSec=600`, пониженный приоритет `Nice=10` и строгую маску
файлов. Устанавливать timer разрешено только после отдельного deploy,
применения миграции, ручной проверки и сохранения выключенных feature
flags.

## Защита области и целостности

- HTTP-reader проверяет совпадение версии формулы, схемы и scope
  fingerprint.
- Payload и метаданные выбора группы имеют отдельные fingerprints.
- KPI, membership и `latest_closed_at` формируются по одному MVCC-снимку
  PostgreSQL.
- Повреждённый JSON, malformed-список сотрудников, чужой состав или новая
  область закрывают выдачу, а не вызывают HTTP `500`.
- Портальный поиск группы читает только компактные поля membership, не
  загружает payload всех групп и не сканирует таблицу паспортов.
- После выбора группы читается одна готовая строка с payload.
- Ручной `--site-code`, не совпадающий с `PORTAL_SITE_CODE` сервера,
  отклоняется до чтения сотрудников.
- API сохраняет ролевой, участковый и приватный доступ, а также
  `Cache-Control: private, no-store`.
