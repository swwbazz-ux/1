# Карта шаблона Диспетчерского пульта

Дата: 26.09.2026.

Рабочий файл:
`СИСТЕМА_MVP/backend/templates/trips/dispatcher_control.html`.

Назначение документа: перед дальнейшим разделением большого шаблона зафиксировать,
какому рабочему месту принадлежит каждый блок, какие DOM-атрибуты уже являются
контрактами JavaScript и какие функции обязаны повторно инициализироваться после
realtime fragment. Номера строк относятся к локальному состоянию шаблона после
четырёх template include; текущий счётчик строк — `6902`. После следующих структурных
изменений номера должны обновляться.

## Главный вывод

Текущий файл — это не один экран. В нём физически совмещены:

1. desktop-пульт Диспетчера;
2. мобильный пульт Горного мастера;
3. общая серверная разметка доски и карточки техники;
4. небольшие ветки масштабирования;
5. большой старый inline runtime Горного мастера;
6. уже разделённый внешний runtime desktop-Диспетчера.

Поэтому блок `707–6893` нельзя считать «оставшимся JavaScript Диспетчера» и
переносить в `dispatcher-control-v1.js`: он находится внутри
`{% if mining_master_mobile_enabled %}` и принадлежит прежде всего мобильному
Горному мастеру. Desktop-Диспетчер на текущем контуре загружает шесть внешних
модулей в строках `6895–6900`.

## Карта серверной HTML-разметки

### Оболочка и параметры runtime — строки `41–64`

Элемент `<main>` передаёт клиенту:

- URL перемещения экскаватора и назначения самосвала;
- шаблоны URL detail-карточки и закрытия простоя;
- static prefix и service-worker scope;
- тип клиента, role code и shell version.

Корневой `.dispatcher-board` передаёт состояние смены, собственную смену,
`operational_state_version` и `server_now`. Это входные данные
`dispatcher-control-v1.js`, `dispatcher-transport-v1.js` и
`dispatcher-realtime-v1.js`; переименование этих атрибутов без одновременного
изменения модулей запрещено.

### Основная доска — `trips/includes/dispatcher_board.html`, строки `2–144`

- `3–5` — общий include `includes/dispatcher_header.html`.
- `7–29` — гараж экскаваторов.
- `31–122` — активные производственные комплексы.
- `124–143` — гараж самосвалов.

Основной шаблон содержит только строку подключения include. Файл начинаетcя с
`{% load static %}`, потому что подключаемая разметка сама использует static-tag.

Ключевые DOM-контракты доски:

- `data-dispatcher-drag` и `data-dispatcher-drop` — drag-and-drop;
- `data-equipment-card-id`, `data-equipment-id`, `data-equipment-name` — адресация
  плитки и открытие detail-карточки;
- `data-equipment-state` — семантическое состояние техники;
- `data-haul-assignment-state-id` — optimistic concurrency назначения;
- `data-zone-id`, `data-assigned-zone`, `data-placement-zone` — топология доски;
- `data-plan-*` — отображение плана, циклов и заполнения;
- `data-dispatcher-free-bucket-expires-at` — локальное окончание маркера свободного
  ковша.

Realtime-модуль ожидает три именованных региона и стабильные ключи:

- `.dispatcher-excavators` → `.dispatcher-equipment-tile` по `equipmentId`;
- `.dispatcher-zone-grid` → `.dispatcher-complex-card[data-zone-id]` по `zoneId`;
- `.dispatcher-trucks` → `.dispatcher-truck-tile[data-equipment-id]` по
  `equipmentId`.

### Мобильный Горный мастер — строки `66–568`

- `67–152` — домашний экран с комплексами и нижней навигацией;
- `154–207` — гараж экскаваторов;
- `209–260` — гараж самосвалов;
- `262–412` — отчёт и действие со сменой;
- `414–465` — отдельные экраны набора состава каждого комплекса;
- `467–516` — модальное выполнение плана смены;

Все `data-mm-*` — контракт мобильного Горного мастера. Их нельзя переименовывать в
рамках задачи desktop-Диспетчера. Особенно чувствительны `data-mm-mobile-fill-*`,

### Служебные списки — `trips/includes/dispatcher_service_lists.html`, строки `1–243`

Секция сейчас скрыта, но содержит реальные формы и источники данных:

## Что происходит после realtime fragment

### Desktop-Диспетчер

`dispatcher-realtime-v1.js`:

1. получает и разбирает только `.dispatcher-board`;
2. пытается точечно согласовать три keyed-региона;
3. при неполном контракте заменяет всю `.dispatcher-board`;
4. повторно вызывает `dispatcherBoard.bindInteractions()`;
5. повторно вызывает общие `initAppConfirmForms`, `initSharedShiftLogin`,
   `initDispatcherThemeControls`, `initDispatcherRadialClocks`;
6. восстанавливает выбранную/открытую карточку и scroll state;
7. запускает integrity/layout и обновляет индикатор связи.

Следовательно, новый интерактивный блок внутри доски обязан либо входить в
`bindInteractions`, либо иметь отдельный идемпотентный rebind callback в realtime.

### Мобильный Горный мастер

`refreshMobileBoardFromServer` заменяет целиком `.mm-mobile-shell`, затем вызывает
`bindMiningMasterMobileScreens()`, восстанавливает выбранный экран и прокрутку и
обновляет PWA-индикатор. Глобальные listeners защищены флагом
`window.__mmMobileGlobalHandlersBound`; общий `ResizeObserver` перед повторным bind
отключается и подписывается на новые DOM-узлы. Это обязательный контракт, иначе после
каждого fragment будут накапливаться обработчики.

## Безопасный порядок дальнейшего разделения

1. Сначала выделять только HTML includes без изменения классов, атрибутов, порядка и
   JavaScript.
2. Каждый новый include в том же локальном commit должен быть добавлен в
   `.github/deploy/production-files.txt` и защищён release-тестом. Иначе будущая
   manifest-scoped публикация установит основной шаблон без подключаемого файла.
3. Push invite, основная доска, служебные списки и detail-карточка уже вынесены.
   Остаток HTML относится к мобильной оболочке Горного мастера и не должен входить
   в чисто dispatcher-рефакторинг.
4. Мобильную оболочку Горного мастера `66–568` выносить отдельным role-owned include,
   не смешивая с изменениями desktop-Диспетчера.
5. Малые scaler-блоки `580–700` анализировать отдельно от HTML includes; совпадение
   текста ещё не доказывает одинаковое поведение canvas и shell.
6. Перед внешним `.js` для блока `707–6893` сначала создать явный bootstrap config и
   boundary-тест отсутствия Django syntax в будущем модуле.
7. После каждого include или JS-модуля запускать адресные Node tests, полный backend
   JS-набор и Browser QA. Редизайн и новые функции на этих commit не добавлять.
