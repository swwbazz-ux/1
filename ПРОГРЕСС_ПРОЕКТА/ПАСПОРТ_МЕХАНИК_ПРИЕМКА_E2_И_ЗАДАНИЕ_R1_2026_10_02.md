## E2-R1-C1 — сервер не восстанавливает сохранённых детей корня (блокирует приёмку)
Трасса с нормальными часами и собственными actor/access/device:
1. r: excavator.trip.loaded сохранён как CONFLICT/post_unload_cooldown.
2. c: зависимое допустимое событие машиниста, например отмена этой погрузки по её local_trip_id, уже попало на сервер и сохранено как CONFLICT/dependency_rejected. Такое состояние допускает _dependency_state.
3. После обновления client restore помечает r и c pending, поскольку recursively распространяет recoverable на depends_on.
4. r повторно принят.
5. c отправлен с прежним event_id, но process_one_offline_event вычисляет dependency_chain_is_ready только для Driver. Для Excavator существующий dependency_rejected допускается только при собственной/родительской ошибке часов. При нормальных часах recoverable_removed_refusal=false (это не корневая loaded+cooldown), и сервер возвращает прежний _stored_result без обработки c.
Итог: root восстановлен, серверный ребёнок остаётся conflict. Нынешний новый Node-тест проверяет только корень и mock accepted, Django-тест — тоже один корень. Они не закрывают эту трассу.

Минимальная цель:
- адресно восстановить доказанную собственную цепочку снятого отказа, включая уже сохранённые dependency_rejected и client-only зависимые записи;
- сохранённый исходный конверт/время каждого ребёнка не подменяются временем приёма или родителя; существующее clock-исправление отдельно от допуска;
- все зависимости должны пройти проверку автора/access/role/device/порядка и готовности; depends_on не передаёт права или объектные ссылки;
- обосновать как сервер распознаёт связь с восстановленным root, в том числе после того, как у root уже cleared error_code. Не расширять все CONFLICT по одному признаку зависимости;
- не переоткрывать ACCEPTED/no_effect, не менять массово старые receipts; повторы не создают вторых эффектов.

Адресные Django+Node тесты: r→c→g с normal clocks; root восстановлен/ответ потерян/удалён из клиентской очереди; restart между root и c; ребёнок раньше восстановления root остаётся повторяемым; собственный результат после связи. Отдельно ребёнок с уже сохранённым серверным отказом и client-only cascade. Отрицательные: чужой actor/device, неподходящий root/код, одна непринятая дополнительная зависимость, подмена envelope; ранее ACCEPTED остаётся неизменным. Если конкретный event type требует несуществующий объект, ожидается его предметный retry, а не выдуманный success.

## E2-R1-C2 — выполнить заявленный сетевой сценарий, уточнить доказательства
В raw/browser-qa-observations.json weak_signal — latency 1800 ms и ограничения 32/16 KiB/s. Это полезная медленная сеть, **но не принимающий и молчащий порт из задания E2**. Выполнить этот отдельный сценарий: карточка/реальный путь жеста → немедленная долговечная запись без ожидания HTTP → restart при недоставленном Y → восстановление сети → один Y с доказанным исходным событием. Исходный прогон с ограничением скорости сохранить под точным названием.

Жест в опубликованном прогоне синтетический PointerEvent через Runtime.evaluate. Приёмка реального UI-пути требует браузерного pointer/touch input через обработчики страницы, не непосредственного вызова функции. Физический APK-жест остаётся NOT_RUN до отдельной проверки. Если стенд не позволяет — оставить эту строку NOT_RUN и вернуть координатору точный SHA, не объявлять физическую приёмку.

Опубликованные времена:
- online X.completed 22:56:11.066705Z → Y.loaded 22:59:36.071932Z: примерно 205 с, т.е. внутри старого окна, но не «немедленно»; нулевую границу подтверждает адресный unit test, не этот browser run;
- weak_signal event 23:02:44.392Z → Y.loaded 23:02:44.484669Z: разница 92.669 ms. Сохранить это расхождение явно и указать server path/time_source, не заявлять точное равенство. Не переписывать время в доказательствах и не расширять E2 до общей реформы времени.
По новому прогону сохранить команды/методику подготовки изолированной БД, наблюдаемые ID/receipt/loaded_at и первичные журналы; одна вручную составленная JSON-сводка не заменяет воспроизводимость.
