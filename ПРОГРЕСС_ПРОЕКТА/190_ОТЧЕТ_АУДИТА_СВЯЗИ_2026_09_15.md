## 2. Доказанные дефекты и предел вывода об инциденте

На точном live realtime-файле воспроизводятся девять регрессий. Основные причины ложной потери связи: forced poll отменяет действующий запрос; плановая отмена или одна ошибка могут переводить UI в offline; параллельные wake/watchdog учитывают один сбой повторно; Android и WebView имеют расходящиеся сведения о связи.

В обоих интерфейсах подтверждена преждевременная запись серверной версии после подтверждения действия до применения нового DOM. При потере fragment-ответа следующий poll мог видеть уже известную версию, и рабочий экран оставался старым. Отдельный regression test на live-шаблонах фиксирует преждевременный переход версии 100→101.

В `core/offline_sync.py` подтверждён неполный адресный payload `truck_loaded`: отсутствовали сведения об управляющей водительской смене/участии и разгрузке, уже присутствующие в online-контракте. До исправления три новых серверных теста давали восемь failed assertions. Исправлены только поля payload из сохранённого Trip; правила создания/завершения рейса и схема БД не менялись.

Это доказательства дефектов в переданном коде. Полная цепочка именно инцидента К‑1 НЕ доказана: нет соответствующих production-журналов запросов, устройства и синхронной временной шкалы. Данные тестового Xiaomi из пакета не считаются логами телефона К‑1.

## 3. Что изменено

### Общая связь и сверка данных

- Состояния `unknown / ok / weak / lost / recovering`, единые подписи и цвет индикаторов. Пустая очередь означает «Все действия отправлены», но сама по себе не доказывает связь.
- Для активного полевого интерфейса lost возникает после трёх ошибок без свежего успешного дополнительного канала либо 15 секунд без подтверждённого успешного транспорта. Время нахождения в фоне исключено из watchdog. Первая ошибка — weak.
- Успех адресного realtime, проверенного fragment, авторизованного native heartbeat или WebView heartbeat снимает lost. До применения ожидающего DOM и завершения outbox остаётся recovering.
- У poll один владелец и generation; forced wake использует текущий запрос. Плановые отмены нейтральны, timeout учитывается один раз, события focus/resume/pageshow/online объединяются. Ошибки повторяются с ограниченной задержкой, без бесконечного роста параллельных запросов.
- Версии обнаруженного, применённого и ожидающего состояния разделены. ACK сохраняет идентификаторы и инициирует сверку; applied version обновляется после валидного DOM и инициализации элементов.
- Независимая сверка рабочего fragment раз в 20 секунд; повторы после ошибки 2/4/8/15 секунд. Занятый интерфейс откладывает замену, но не снимает pending.
- Сохраняются вкладка, прокрутка и ввод; ответ старого поколения не заменяет новый экран. Дополнительный таймер сверки Экскаваторщика удалён, владелец общий.
- Fragment отвергает redirect/login HTML, неверный MIME, повреждённый контракт, неподходящую корневую область и устаревшую/некорректную версию.

### Android и WebView

- Native heartbeat имеет одного планировщика, различает сетевую ошибку, timeout, авторизацию, таймаут чтения cookie и локальную ошибку после успешного ответа. Потеря старой default network лишь запускает пробу новой.
- После ошибки старого маршрута смена сети вызывает одну ускоренную пробу; успешный ответ сохраняет обычный интервал.
- Отрицательные, дробные, бесконечные и небезопасные числовые версии native JSON отвергаются до объявления успеха. Foreground-уведомление о повторе фонового канала не объявляет общую потерю связи при работающем WebView.
- Служба передаёт WebView свежие санитизированные сведения об успешном HTTP. Старые APK без нового контракта сохраняют прежнюю работу bridge.
- WebView presence heartbeat сохраняет частоту 30 секунд, ограничивает запрос 8 секундами, не разгоняется от focus. Успехом считается только актуальный авторизованный HTTP 204 без redirect; поздние ответы отменённого поколения нейтральны.
- Голосовой сигнал потери произносится один раз за эпизод lost, восстановление — при окончательном ok. Штатные weak/recovering не порождают повторную озвучку.

### Диагностика и offline-ресурсы

- Диагностика ограничена по частоте и объёму, сохраняет причину, owner/generation, состояния, счётчики и времена. Query, cookie, token/PIN, содержимое рейсов и полные ответы не отправляются.
- Обычные здоровые циклы сверки не расходуют лимит диагностических отправок; остаются в ограниченном буфере. Реальные эпизоды weak/lost и их восстановление сохраняют бюджет.
- Версии шаблонов, registry, service worker и тестов согласованы. Оба field worker кешируют с v180 новые/изменённые realtime, indicators, heartbeat, native bridge, telemetry и общую CSS.
- Изменения внешнего дизайна кнопок, бизнес-логики свободного ковша и модели рейса в задачу не добавлялись.

Для следующей попытки нужно явное подтверждение пользователя на публикацию этих двух подготовленных commits в указанном репозитории. Нельзя публиковать весь Git snapshot поверх production: базовый снимок частичный. Перед будущей публикацией потребуется повторно сверить актуальные live-хеши, собрать release-ветку с сохранением всех более новых серверных правок и применять только проверенный targeted diff. Чтобы закрыть приёмку, требуется актуальный `СИСТЕМА_MVP/backend/shifts/services.py` с production либо полный совместимый backend snapshot. Затем повторить штатные Django gates без ограниченной URLconf. Нужен разрешённый тестовый origin для Browser QA. После согласования установки проверить обе роли на физических телефонах и подписать release APK в доверенном окружении. Подробные сценарии: `ПРИЕМКА_190.md` в пакете передачи.
