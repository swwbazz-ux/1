## 0. Зачем это всё

Пользователь попросил привести код в порядок: убрать мёртвое, разложить гигантские шаблоны по частям, **чтобы потом добавлять новые функции и экраны, не дописывая в общую кучу**. Порядок работ он задал сам: сначала довести один экран до конца, потом так же, по очереди, остальные.

Водителя довели. Дальше — экскаваторщик, горный мастер, диспетчер.

**Главное правило всей этой работы:** ни одна правка не должна менять поведение. Это перекладывание кода, а не его улучшение. Если по дороге нашёлся баг — чинить ОТДЕЛЬНЫМ коммитом, не смешивая с перекладыванием.

## 2. ЧТО НЕЛЬЗЯ ЛОМАТЬ (читать до первой правки)

### 2.1. Не возвращать стили и код внутрь шаблона
Новый блок `<style>` или `<script>` с кодом в `driver_shift.html` добавлять нельзя. Правка стилей — в `driver-shift-v1.css`, правка поведения — в соответствующий `driver-shift-*.js`.

### 2.2. Новая функция = новый файл
Так уже устроены готовые узлы: `driver-free-bucket-v1.js`, `driver-downtime-drum-v1.js`, `driver-offline-outbox-v2.js`, `mobile-dial-actions-v1.js`. Новый файл надо:
1. подключить в шаблоне (в правильном месте по порядку загрузки),
2. добавить его имя в `DRIVER_SCREEN_SCRIPTS` в `static/js/tests/driver-screen-source.js`,
3. добавить его имя в `DRIVER_SCREEN_SCRIPTS` в `users/tests.py`,
4. добавить путь в `.github/deploy/production-files.txt`.

Пропустишь пункт 4 — файл физически не доедет на бой, экран откроется без него.

### 2.3. Порядок подключения файлов критичен
Внутри одного файла функции видны с любого места (подъём объявлений). **Между файлами — нет.** Код, выполняемый СРАЗУ при загрузке, не должен обращаться к тому, что определено в следующем файле.

Это стережёт `static/js/tests/driver-screen-load-order.test.js`: он грузит части по очереди в песочнице с заглушками браузера и падает, если такая связь появилась. **Не удалять и не «чинить» его заглушками — он ловит реальный класс поломок.**

### 2.4. В статике не работают django-вставки
`{{ ... }}` и `{% ... %}` в `.js`/`.css` не обрабатываются — это обычные файлы. Значение с сервера передаётся через data-атрибут на `<main data-driver-shell ...>` и читается из `shell.dataset`.

Так уже сделано для двух случаев:
- версия оболочки — `data-driver-pwa-version`,
- область service worker — `data-driver-sw-scope` (добавлен при выносе).

### 2.5. Проверки читают ВСЕ файлы экрана как один источник
- **js-тесты:** `driverScreenSource()` из `static/js/tests/driver-screen-source.js` — склеивает шаблон + CSS + все скрипты.
- **python-тесты:** помощники `driver_stylesheet()` и `driver_script()` в `users/tests.py`.
- **тесты Android-приложения:** `mobile/capacitor-shell/tests/driver-voice-wiring.test.mjs` и `profile-contract.test.mjs` — у них свой список файлов, он тоже требует обновления.

Новую проверку стиля или кода писать через эти помощники, а НЕ через `assertContains(response, ...)`: в HTML-ответе этих строк больше нет.

**Ловушка, которая уже случилась:** я починил разделение и прогнал свои тесты — всё зелёное. А CI упал на `mobile/capacitor-shell/tests/`, о существовании которых я не знал. Перед выкладкой прогонять `node --test mobile/capacitor-shell/tests/*.test.mjs` тоже.

### 2.6. Версию оболочки поднимать при ЛЮБОЙ правке экрана
`DRIVER_SHELL_VERSION` в `users/views.py` **и** `shell_version` в `users/role_apps.py` — оба места, иначе рассинхрон. Плюс строки версии в тестах:
- `static/js/tests/driver-offline-template-contract.test.js`
- `static/js/tests/driver-service-worker-cache-runtime.test.js`
- `users/tests.py`, `users/test_role_apps.py`

Проще всего: `grep -rl "driver-mobile-shell-vNNN" --include=*.py --include=*.js .` и заменить во всех найденных.

Не поднимешь версию — у полусотни телефонов в поле останется старый экран из кэша, и «правка не работает» будет ложной.

### 2.7. nginx отдаёт `staticfiles/`, а не `static/`
Раньше стили и код ехали внутри HTML и доезжали всегда. Теперь это отдельные файлы. **После выкладки обязательно проверить, что они реально на бою:**

```
curl -s "https://driverform.ru/static/css/driver-shift-v1.css" | head -3
curl -s "https://driverform.ru/static/js/driver-shift-v1.js" | head -3
```

Пустой ответ = файл не доехал, у водителей голый HTML. (Приёмник деплоя сам делает `collectstatic`, так что при штатной выкладке всё в порядке — но проверять после каждой.)

## 3. Как делать такую разборку. Пошаговый рецепт

Проверено на водителе от начала до конца. Повторять для каждого следующего экрана.

### Шаг 0. Бэкап
```
git tag backup/before-<экран>-split-YYYYMMDD
git push origin backup/before-<экран>-split-YYYYMMDD
git archive --format=zip -o C:/gh-backup/before-<экран>-split-YYYYMMDD.zip HEAD
```

### Шаг 1. Разведка — ДО любой правки
Главный вопрос: **сколько django-вставок внутри встроенных блоков.** Они определяют, возможен ли вынос вообще.

```
f=templates/<путь>/<экран>.html
grep -n -E "<style|</style>|<script|</script>" $f          # границы блоков
sed -n '<начало>,<конец>p' $f | grep -c -E "\{\{|\{%"      # сколько вставок
```

У водителя было: в CSS — 0, в JS — 2. Это и сделало вынос безопасным.

Если вставок десятки — сначала переводить их на data-атрибуты отдельным коммитом, и только потом выносить.

### Шаг 2. Кто читает этот шаблон текстом
```
grep -rln "<экран>.html" --include="*.test.js" --include="*.test.mjs" --include="*.py" . | grep -v .venv
```

У водителя таких оказалось **19 js-тестов + 2 python-файла + 2 теста Android-приложения**. Все они ищут код текстовым поиском внутри HTML и сломаются при выносе. Список надо иметь ДО начала, а не узнавать от CI.

### Шаг 3. Вынести CSS (если есть)
Отдельным коммитом. Ссылку `<link>` поставить **ровно на место** прежнего блока — иначе поедет порядок каскада.

### Шаг 4. Перевести django-вставки в коде на data-атрибуты
Отдельным коммитом, до выноса JS. После этого проверить, что вставок в блоке не осталось.

### Шаг 5. Вынести JS одним куском
Тег `<script src=...>` — на место прежнего блока и **без `defer`**: иначе изменится порядок выполнения относительно остальных скриптов.

### Шаг 6. Разложить по темам
Резать **подряд**, по существующим маркерам разделов. Не переставлять куски местами. После — `node --check` каждого файла.

### Шаг 7. Завести сторожевой тест порядка загрузки
По образцу `static/js/tests/driver-screen-load-order.test.js`.

### Шаг 8. Починить тесты из шага 2
Перевести их на общий источник (по образцу `driver-screen-source.js`), а не править регулярки по одной.

### Шаг 9. Поднять версию оболочки (см. 2.6) и обновить `production-files.txt`

### Шаг 10. Проверка — самое важное

**Нельзя считать «у меня всё зелёное».** В проекте ~18 тестов в `users` падают давно и не по нашей вине, плюс часть тестов зависит от времени суток. Сравнивать надо **списки падений**, а не их количество, и снимать оба замера **в одно время**.

```
# копия исходного состояния — путь ОБЯЗАТЕЛЬНО короткий, иначе "Filename too long"
git worktree add --detach C:/tmp-baseline HEAD
mkdir -p C:/tmp-baseline/СИСТЕМА_MVP/backend/media    # иначе тесты не стартуют (check E001)

# оба прогона запускать одновременно
cd C:/tmp-baseline/СИСТЕМА_MVP/backend && python manage.py test users core trips assignments shifts -v 0 > /tmp/base.txt 2>&1
cd <рабочая копия>/СИСТЕМА_MVP/backend && python manage.py test users core trips assignments shifts -v 0 > /tmp/after.txt 2>&1

grep -aE "^(FAIL|ERROR):" /tmp/base.txt  | sort -u > /tmp/b.txt
grep -aE "^(FAIL|ERROR):" /tmp/after.txt | sort -u > /tmp/a.txt
comm -13 /tmp/b.txt /tmp/a.txt      # ПОЯВИЛОСЬ — должно быть пусто
comm -23 /tmp/b.txt /tmp/a.txt      # ИСЧЕЗЛО

git worktree remove --force C:/tmp-baseline
```

Плюс отдельно:
```
node --test "static/js/tests/*.test.js"
cd mobile/capacitor-shell && node --test tests/*.test.mjs
```

**Известные «плавающие» тесты** (падают/проходят сами по себе в зависимости от времени суток и порядка запуска, НЕ регрессия): `trips.test_manual_loading`, `trips.test_chaos_p06_p08_p11_legacy`, `trips.test_excavator_hourly_report`, `core.test_free_bucket_sync`. Если такой тест появился в «ПОЯВИЛОСЬ» — прогнать его отдельно в обоих деревьях, прежде чем считать поломкой.

**Проверка, что новый тест вообще что-то ловит:** временно откатить свою правку, убедиться, что тест падает, вернуть правку. Я делал так для каждого нового теста — дважды это спасло от теста-пустышки.

## 4. Как выкладывать на бой

Прямой SSH запрещён с 17.09.2026. Только через GitHub Actions.

### Порядок
1. Своя ветка **от текущей вершины** `codex/github-production-deploy-20260916`.
2. PR в неё. Прямой push в релизную ветку отклоняется (protected branch).
3. Дождаться CI. **CI падает всегда** — те самые ~18 старых падений в `users`. Сверять список с эталоном, а не ждать зелёного.
4. Слияние — **только `--squash`**. Обычный merge запрещён (нужна линейная история), rebase не проходит из-за merge-коммита внутри истории ветки.
5. `verify` → проверить успех → `deploy`.

```
SHA=$(git rev-parse origin/codex/github-production-deploy-20260916)
gh workflow run production-deploy.yml --ref codex/github-production-deploy-20260916 \
  -f mode=verify -f expected_commit=$SHA -f confirmation=VERIFY
# дождаться success, затем:
gh workflow run production-deploy.yml --ref codex/github-production-deploy-20260916 \
  -f mode=deploy -f expected_commit=$SHA -f confirmation=DEPLOY
```

### Ловушки выкладки

**Squash ломает следующую ветку.** После squash-слияния твоя ветка содержит исходный коммит, дублирующий уже влитое → следующий PR из той же ветки будет `CONFLICTING`, и GitHub **вообще не запустит CI** (выглядит как «проверка висит»). Лечение: новая ветка от свежей вершины + `cherry-pick` только нужного коммита.

**Миграции в `production-files.txt` ломают обычную выкладку.** Пока в списке лежит хоть один файл миграции, ЛЮБОЙ режим кроме `verify_migrations`/`deploy_migrations` падает с «database migrations require a separately approved release». **После успешной выкладки с миграциями — убирать их из списка**, иначе следующий релиз спотыкается на пустом месте. Я это уже почистил 19.09.2026.

**Режим с миграциями** (`deploy_migrations`) делает бэкап кода и полный дамп PostgreSQL — он безопаснее, но дольше. Обычный `deploy` — только код.

**Точка отката** печатается в логе: `RELEASE_OK ... backup=/srv/accounting-mvp/backups/code/github-...`. Записывать её в отчёт пользователю.

### 5.2. Горный мастер и диспетчер — вместе, и в последнюю очередь
**Внимание: у них ОДИН общий шаблон** `templates/trips/dispatcher_control.html` (7479 строк). Роль переключается флагом `mining_master_mobile_enabled` (15 упоминаний в шаблоне).

## 6. Чему меня научил этот день (не повторять мои ошибки)

1. **Я чинил симптом в одном экране вместо общего определения.** Заявку на свободный ковш читают три экрана. Я починил запрос экрана водителя — и получил от пользователя: «на пульте и у экскаваторщика всё ещё висит». Правильно было сразу класть правило в общий фильтр `active_free_bucket_acceptance_filter()`. **Перед правкой ищи, кто ещё читает эти данные:** `grep -rn "<Модель>.objects" --include=*.py . | grep -v test`.

2. **«У меня зелёное» ≠ «ничего не сломано».** Тесты Android-приложения в `mobile/capacitor-shell/` я нашёл только когда CI упал. Список читателей шаблона собирать ДО работы.

3. **Первая версия правила почти всегда слишком узкая.** Моё «право привязано к смене водителя» уронило случай, где заявку заводит сам машинист и смены водителя нет вовсе. Спасла сверка со списком падений, а не счётчик.

4. **Не объявлять проблему косметической, не проверив.** Я сказал пользователю «спешки нет» про застрявший свободный ковш — а он ответил, что машинист из-за этого **не может отгрузить самосвал**. Это блокировало реальную работу. Если не уверен в последствиях — спроси, а не предполагай.

5. **Не сваливать на пользователя ручные шаги.** Он не программист. Я трижды за день просил его нажать кнопку на GitHub, один раз — на странице, где он даже не был залогинен. Правильно: довести самому; если технически заблокировано — сказать прямо и коротко, с одним конкретным действием, а не с инструкцией на десять шагов.

6. **Проверять живое поведение, а не только код.** Нативное Android-приложение отлаживать нечем (`run-as` и devtools недоступны — релизная сборка), но работает: `adb shell uiautomator dump` даёт настоящее дерево экрана. Важная ловушка: элементы с атрибутом `hidden` в дамп **не попадают вовсе** — «элемента нет» и «элемент скрыт» по дампу неразличимы. Я на этом потерял час, решив, что кнопки нет в разметке.
