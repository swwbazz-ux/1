## 2. Собственная сверка кода

Прочитан `СИСТЕМА_MVP/backend/core/offline_sync.py` на обоих SHA. Для release: восстановление ковша 1236–1289 и 1425–1447; зависимости и повторный приём 3017–3194. Для PR №106: обработчик погрузки 1969–2084, зависимости и helper 4170–4269, повторный приём 4290–4344. Номера относятся только к указанным SHA.

| Случай | Release | PR №106 до согласования |
|---|---|---|
| Водитель, `driver.trip.loaded` + `free_bucket_not_available` | Повтор разрешён; CANCELLED восстанавливается при отсутствии другого открытого права; REQUESTED может быть принят отметкой водителя | Такого разрешения в helper и соответствующего восстановления/self-accept в обработчике нет |
| Водитель, `dependency_rejected` | Повтор после принятия всех зависимостей; проверяются actor/access/role/device и меньший sequence | Helper допускает этот код без данных условий |
| Машинист, `dependency_rejected` | Проверяется собственный сдвиг часов либо часовой предок | Helper допускает этот код безусловно |
| `device_clock_ahead` | Восстановление для обеих полевых ролей при доказанном исходном сдвиге | Тот же отдельный часовой допуск |
| Остальные доменные отказы | Не становятся повторяемыми только из-за ГП-0 | Есть дополнительные event/code-пары helper, включая dependency_owner_mismatch/order_invalid; их основания нужно перечислить отдельно |

Существенные границы:

1. **Допуск к повтору не означает принятия факта или подмены времени.** Release для восстановленного зависимого события машиниста использует первое received_at даже при нормальных часах самого ребёнка; PR №106 в таком случае оставляет occurred_at ребёнка. Это отдельное различие поведения. Сохранность исходного времени и выбор эффективного времени не смешиваются.
2. `_dependency_state` в release проверяет отсутствие, принадлежность, порядок и статус зависимостей; в PR эти обстоятельства в основном логируются с продолжением обработки по собственным предметным ссылкам события. Старый receipt с доменным отказом и новый несовместимый конверт — разные случаи. Наличие ветви в PR не делает её утверждённой паспортом.
3. Проверка actor/access/role/device/fingerprint исходного event ID выполняется **до** повторного приёма. `event_id_reused` не превращается в разрешение повторно применить чужой или изменённый конверт. Уже ACCEPTED, включая no_effect, остаётся дедуплицированным.
4. Восстановление CANCELLED в release не различает TTL и другие причины отмены. Если есть другое REQUESTED/ACCEPTED/USED-право, старое не восстанавливается. Это описание действующего кода, не новая норма отказа; обход этих условий нельзя прятать в объединение списков.

## 3. Клиентский контрпример и границы проверки

Водительский startup на release начинает восстановление с часового конфликта или пары `driver.trip.loaded/free_bucket_not_available`, затем включает зависимые конфликты из той же обнаруженной цепочки. Сервер также допускает повтор ребёнка, если родители уже приняты.

Адресный Node probe выполнил настоящий `driver-offline-outbox-v2.js` release `5721c045`, с MOCK-транспортом: родитель уже принят и удалён из очереди, его event-identity/server-map сохранены; ребёнок остаётся conflict/dependency_rejected. После нового initialize отправок нет, ребёнок остаётся conflict. Это подтверждает пробел клиентского восстановления данного сохранённого состояния. Backend-трасса, получение такого состояния в реальной смене, DOM, WebView, телефон и production этим probe не проверены.

[Воспроизводимый probe и сырые результаты](ДОКАЗАТЕЛЬСТВА_S106_C1_2026_09_29/README.md).

Из этой проверки **не следует** разрешение повторять все конфликты безусловно. Нужны условия, проверка неизменности, отсутствие немедленного бесконечного цикла и сохранение записи при неизвестном результате. Уже удалённые очисткой исходники нельзя обещать восстановить; startup выполняет своё восстановление перед обычной очисткой terminal-записей старше 24 часов.
