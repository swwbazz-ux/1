# Доказательство: старт простоя при несовпадении серверной гружёности

Дата проверки: **28.09.2026**.

Связанные механики: `M-DOWN-1`, `M-QUEUE-1`, `M-REFUSE-1`.

## 1. Сценарий

Телефон Водителя уже надёжно записал в очередь событие
`driver.downtime.started` с причиной «Ожидание разгрузки». При доставке сервер
не находит у самосвала открытого гружёного рейса. Сравниваются два неизменяемых
среза кода:

- PR #106: `5181350683e176c3151299f6f1228e11ad0ee938`;
- release: `fd749e8ae89e524e2f2f1dc787073e112e15462c`.

Это воспроизведение не меняет приложение, данные production, PR #106 или
релизную ветку.

## 2. Статус стендового прогона

**PostgreSQL: `NOT_RUN`.** На рабочей машине не найден доступный изолированный
PostgreSQL-стенд: отсутствуют исполняемые `psql`/`pg_isready`, служба или
слушатель PostgreSQL, Docker/Podman и установленный WSL-дистрибутив. Запускать
миграции или подключаться к production вместо изолированного стенда запрещено.

Поэтому ниже приведено точное статическое прохождение ветвей и ожидаемая запись
в БД/логах. Оно **не является** результатом PostgreSQL-приёмки.

## 3. Сравнение кода

| Срез | Ветка обработчика | Статус события по коду | Доменная запись | Запись расхождения |
|---|---|---|---|---|
| PR #106 `5181350683e176c3151299f6f1228e11ad0ee938` | `core/offline_sync.py:_process_downtime`, строки `3863–3997`; при `loaded_trip_required` вызывается `_conflict()` на `3932–3938` | `conflict`, `error_code=loaded_trip_required`, `retryable=false` | Новый `DowntimeEvent` не создаётся | Нет: до `_log_discrepancy()` эта ветка не доходит |
| release `fd749e8ae89e524e2f2f1dc787073e112e15462c` | `core/offline_sync.py:_process_downtime`, строки `2604–2741`; конфликт на `2675–2681` только логируется, затем обработка продолжается | `accepted`, без error code | Создаётся `DowntimeEvent`; ответ содержит `server_ids.downtime_event_id`, `shift_id` и operational `version` | Только `logger.warning` из `_log_discrepancy()` |

В обоих срезах `_log_discrepancy()` не пишет отдельную модель или таблицу:
PR — `core/offline_sync.py:46–56`, release — `:36–46`. Формат записи — обычный
warning приложения вида `offline_sync: accepted despite discrepancy ...`.
Следовательно, требуемая «запись расхождения» в release существует только в
серверном журнале процесса; структурированного ряда расхождения в PostgreSQL
нет.

## 4. Ожидаемые receipts по статическому контракту

Общий контракт результата задают `_result()` и `_stored_result()`:

- PR #106: `core/offline_sync.py:1557–1581`;
- release: `core/offline_sync.py:779–803`.

Для PR #106 ожидается `OfflineFieldEvent.status=conflict`,
`error_code=loaded_trip_required`, `result_payload.server_received_at`; связи с
новым простоем нет.

Для release ожидается `OfflineFieldEvent.status=accepted`, пустой `error_code`,
`result_payload.server_ids` с ID созданного простоя и смены,
`server_received_at` и `version`. Receipt и доменная запись одного события
сохраняются транзакционно в `process_one_offline_event()`; это не делает весь
batch одной транзакцией.

## 5. Что ещё требуется подтвердить

   сохранить фактические строки `OfflineFieldEvent`, `DowntimeEvent` и log.
2. На Xiaomi подтвердить, что установленный Driver APK действительно доставляет
   кнопку простоя через outbox, а не через legacy direct POST.
3. Решить отдельно, нужен ли структурированный внутренний журнал расхождений.
   В этой работе поле `load_learned_late`, `applied_sequence` или иная новая
   реализация не вводились.
