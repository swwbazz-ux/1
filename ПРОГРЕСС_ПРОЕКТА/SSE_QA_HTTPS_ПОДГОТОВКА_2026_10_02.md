# SSE-QA: подготовка HTTPS и первого короткого включения

Дата: 02.10.2026.

## Подтверждено публично

- `sse-qa.driverform.ru` имеет A `77.91.93.47`; это тот же публичный IPv4, что
  у `driverform.ru`. AAAA и CNAME не обнаружены.
- TCP/443 доступен, но сервер предъявляет сертификат `driverform.ru`, в SAN
  которого нет `sse-qa.driverform.ru`. HTTPS hostname validation не проходит.
- HTTP и HTTPS для QA hostname отвечают `400` от nginx, то есть выделенный
  публичный QA-vhost не подтверждён.
- Один ранний запрос с рабочего Windows-компьютера показал `92.50.235.178`.
  Контрольный запрос в `2026-10-02T00:04:15Z` и пять повторов сразу после него
  показали `77.41.146.126`, то есть текущий результат совпал с установленным
  allow CIDR `77.41.146.126/32`. Причина раннего расхождения не установлена;
  влияние VPN/proxy доступными средствами не подтверждено и не исключено.

## Неизвестно без защищённой проверки сервера

- фактические версии и состояние Certbot и `certbot.timer`;
- наличие/целостность отдельной lineage
  `/etc/letsencrypt/live/sse-qa.driverform.ru`;
- конфликт `server_name sse-qa.driverform.ru` в активной конфигурации nginx;
- наличие безопасной существующей Certbot account registration.

Для этих фактов подготовлен read-only `inspect_sse_qa_https`, который не запускает
и не останавливает QA-службы и не пишет файлы.

## Локальная дельта

Отдельный фиксированный контроллер публикует внешнему receiver только `inspect`
и `prepare`; внутренние `renew-pre`, `renew-post`, `renew-deploy` доступны
только как фиксированные Certbot lineage hooks.
`prepare` допускает один canonical IPv4 `/32`, проверяет выключенное состояние
QA, DNS, Certbot/timer и отсутствие nginx-конфликта, затем использует отдельный
постоянный пустой owned webroot и временный HTTP-only ACME-vhost. QA upstream,
Basic Auth bypass и произвольные server
paths/commands отсутствуют. Перед каждым reload общего nginx выполняется
`nginx -t`. Продление обслуживает `certbot.timer`: `pre` hook временно создаёт
HTTP-only challenge, `post` удаляет его, `deploy` принимает только точную
QA-lineage и перезагружает nginx. Механизм не зависит от enabled/disabled QA и
не открывает QA upstream.

После независимого ревью первая HTTPS-дельта отклонена. Локально исправлены:
раздельные pins основного и HTTPS-контроллера; fail-closed разбор nginx с
кавычками/переносами; доказуемое владение ACME и lineage; SIGTERM rollback с
75-секундным бюджетом; работоспособный HTTP-01 renewal. До нового ревью,
CI/CodeQL и отдельного разрешения публикация и серверные операции запрещены.

R2-ревью выявило два оставшихся дефекта, исправленных в новом локальном
кандидате: промежуточный webroot теперь имеет собственный случайный marker и
может быть безопасно удалён до появления hook; renewal-конфиг разбирается по
действующим секциям/ключам и поддерживает проверенные варианты `renew_hook` и
`deploy_hook`. Комментарии, конфликтующие значения, чужой webroot и подмена
marker отклоняются. Диагностика внешних команд больше не выводит их произвольный
stdout. Windows-набор проходит; два настоящих SIGTERM-теста остаются NOT_RUN до
изолированного Linux CI. Это не разрешает публикацию или серверный prepare.

Независимая Linux-проверка R3 затем подтвердила 38/38 controller и 11/11
protocol, включая оба настоящих SIGTERM-теста. Единственный найденный после
этого parser-дефект исправлен локально: `webroot_path` принимает точный путь и
его одноэлементную ConfigObj-сериализацию с завершающей запятой, но не принимает
пустые, многозначные, чужие или неоднозначные списки. Новый серверный этап всё
ещё требует публикации точного кандидата и обычных CI/CodeQL.

Для публикации принятого кандидата обычный PR quality gate дополнен только
тремя standalone contract-командами: baseline release protocol, HTTPS
controller и HTTPS protocol. Job не получает серверные секреты и не вызывает
production workflow, receiver или server prepare.

Принятые source C2, runtime и основной SSE-QA controller не меняются.

## Будущий короткий этап после отдельного разрешения

1. Опубликовать точную control-дельту и дождаться обязательных CI/CodeQL.
2. Обновить receiver защищённым каналом, сохранив точные предыдущие байты.
3. Повторить `api.ipify.org` на рабочем Windows-компьютере. Продолжать только
   если результат равен заранее разрешённому `77.41.146.126`; иначе остановка
   без изменения allow CIDR.
4. Выполнить один read-only `inspect_sse_qa_https`; при любом неизвестном или
   отрицательном gate остановиться.
5. Выполнить один
   `prepare_sse_qa_https`. Это включает общий `nginx reload`, но не deploy и не
   restart production-приложения.
6. Выполнить `enable_sse_qa`, штатный внутренний `smoke_sse_qa`, затем внешнюю
   HTTPS-проверку Driver и Excavator из согласованной сети: Basic Auth, два
   логина, максимум два SSE-клиента, одно синтетическое событие, только нужные
   получатели, без повторного показа/озвучки.
7. Всегда завершить `disable_sse_qa`; при отказе — немедленный disable и
   сохранение диагностики. Отдельно подтвердить внешний HTTPS, поскольку
   внутренний smoke этого не доказывает.

Нагрузка 80–96 клиентов, Firebase, APK, Doze и батарея в этап не входят.
