## 3. Остаточные дефекты

### 3.1. QA-TRAFFIC-P2-002-R2-R1 — нет восстановления по фактическому reconnect приложения

Статус:

```text
FAIL
```

`templates/includes/achievement_prize.html` слушает `online`,
`visibilitychange` и `navigator.connection.change`, но не слушает
фактическое событие приложения `operational-state-connection`, которое
публикует `static/js/realtime-client.js`.

Сценарий:

1. qualifying achievements GET и три ограниченных retry исчерпаны во
   время недоступности Django;
2. интернет устройства не отключался, поэтому `online` не возникает;
3. Django/realtime восстановился и сообщил
   `operational-state-connection` с `connected=true`;
4. pending achievement не повторяется до следующего рейса, переключения
   видимости или перезагрузки.

Независимый диагностический runtime:

```text
до reconnect: 4 GET
после operational-state-connection: фактически 4
ожидалось: 5
```

Требуется:

- слушать `operational-state-connection`;
- реагировать только на `detail.connected === true`;
- объединять его с существующими pending/in-flight;
- не возвращать периодический polling;
- добавить исполняемую регрессию восстановления после исчерпанного
  error/backoff при постоянно видимой вкладке.

### 3.2. QA-TRAFFIC-P2-002-R3 — назначенный Экскаватор ошибочно считается открытой сменой

Статус:

```text
FAIL
```

В `templates/includes/achievement_prize.html` exact-match использует:

```text
eoCurrentExcavatorId || eoShiftExcavatorId
```

Но `eoShiftExcavatorId` содержит также технику из действующего назначения
до открытия смены. Поэтому read-only/ожидающий Машинист с назначенным
экскаватором получает лишний achievements GET на завершение рейса этого
экскаватора. Backend не выдаёт чужой приз, но выполняются лишний HTTP GET
и расчёты БД.

Независимый диагностический runtime:

```text
eoCurrentExcavatorId = ""
eoShiftExcavatorId = "31"
matching trip_unloaded excavator_id = 31
achievements GET: фактически 1
ожидалось: 0
```

Требуется:

- exact и truncated achievement match выполнять только при реально
  открытой смене Машиниста;
- назначение техники до открытия смены не должно считаться активной
  сменой;
- добавить регрессии exact/truncated для назначенной техники без
  открытой смены.

### 3.3. QA-TRAFFIC-P2-003-R2-R1 — controllerchange оставляет непроверенный controller в ready

Статус:

```text
FAIL
```

В `templates/base.html` обработчик `controllerchange`:

1. увеличивает generation;
2. отправляет асинхронный `GET_VERSION` новому controller;
3. не сбрасывает прежний `state.serviceWorker`;
4. сразу вызывает `reloadOnceForExpectedContract()`.

Если прежний worker был `ready`, функция видит старое готовое состояние и
снимает `controllerReloadPending` до ответа нового controller. В итоге:

- до ответа нового worker изменения разрешены под непроверенным
  controller;
- при несовпадающем позднем ответе экран блокируется, но pending reload
  уже потерян;
- при отсутствии ответа экран может неограниченно оставаться ready по
  версии прежнего worker.

Штатный тест не видит гонку, потому что replacement worker отвечает через
MessageChannel синхронно.

Независимый асинхронный runtime с новым controller без ответа:

```text
ожидалось: ready=false, locked=true
фактически: ready=true, locked=false
```

Требуется:

- при `controllerchange` немедленно перестать считать версию прежнего
  worker версией нового controller;
- не снимать `controllerReloadPending` до проверки текущего controller;
- до ответа держать mutations в безопасном состоянии;
- несовпадающий ответ должен дать не более одного безопасного reload;
- отсутствие ответа не должно оставлять старый ready;
- отдельно проверить незавершённое действие: без reload во время работы
  и с восстановлением после её завершения.

### 3.4. QA-TRAFFIC-P2-003-R3-R1 — stale modal не закрывается после активации worker

Статус:

```text
FAIL
```

Машинист и Горный мастер правильно не отправляют повторный
`SKIP_WAITING`, если показанный worker уже стал active/controller. Но
обработчик contract/controller-события не очищает сохранённую ссылку и не
закрывает уже открытое окно обновления.

Сценарий:

```text
waiting modal показан
→ другая вкладка активировала worker
→ controllerchange
→ stale modal остаётся видимым
→ нажатие пользователя лишь закрывает бесполезное окно
```

Две независимые регрессии дали:

```text
Excavator modal.hidden: фактически false, ожидалось true
Mining Master modal.hidden: фактически false, ожидалось true
```

Требуется при потере `registration.waiting === shownWorker`:

- инвалидировать inspection generation;
- очистить ссылку на worker;
- автоматически закрыть modal;
- скрыть/пересчитать badge;
- сохранить `0` повторных `SKIP_WAITING`.

### 3.5. QA-TRAFFIC-P2-003-R1-R1 — обязательный совместный runtime-тест не реализован

Статус:

```text
TEST CONTRACT FAIL
```

Документ 140 требовал исполнять настоящий общий
`AppPwaContractGuard` вместе с настоящими role-runtime. Текущие тесты:

- отдельно исполняют настоящий общий guard;
- отдельно исполняют role-runtime с ручным stub
  `AppPwaContractGuard`;
- либо проверяют строки production-исходника.

Поэтому не доказан полный путь:

```text
automatic update уже pending
→ пользователь нажал настоящую кнопку роли
→ общий guard присоединил ручной путь
→ registration.update() ровно один
→ UI получил корректный результат
```

Требуется совместный runtime-тест настоящего `base.html` guard и
настоящего обработчика роли, включая успешный путь и повтор после ошибки.
