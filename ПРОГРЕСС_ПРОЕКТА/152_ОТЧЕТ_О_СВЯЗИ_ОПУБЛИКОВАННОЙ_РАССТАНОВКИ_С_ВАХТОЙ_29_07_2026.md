# Отчёт о связи опубликованной расстановки с вахтой

Дата: 29.07.2026
Статус: **ЛОКАЛЬНО ПРОВЕРЕНО / ГОТОВО К COMMIT И PUSH ПОСЛЕ РАЗРЕШЕНИЯ**

## 1. Цель

Локально реализовать недостающую техническую связь для теневого рейтинга
Водителей самосвалов, не меняя утверждённый производственный процесс:

1. ОУП вводит сотрудника и выдаёт ему действующий доступ.
2. Заместитель начальника участка закрепляет сотрудника за техникой и
   дневной либо ночной сменой.
3. Заместитель публикует расстановку.
4. Водитель открывает смену по действующему назначению.
5. Открытая смена получает снимок вахтового периода только при однозначном
   подтверждении всех исходных фактов.

Делопроизводитель продолжает контролировать расселение, но сведения о жилье
не определяют производственную вахту и не участвуют в расчёте связи.
Табельщик и Руководитель не создают, не подтверждают и не изменяют связь
смены с вахтой. Рейтинговый модуль остаётся только потребителем фактов.

## 2. Фактический разрыв до исправления

Поле `EmployeeShift.watch_period` уже существовало, но ни один рабочий путь
открытия смены его не заполнял.

Одного `EquipmentAssignment` недостаточно как доказательства расстановки:
действующее назначение может быть создано не только публикацией плана
Заместителя, но и из административной карточки сотрудника.

Надёжный доступный источник без изменения моделей:

- `CrewPlan` со статусом `published`;
- точный `CrewPlanSlot`;
- совпадение производственной даты, роли, сотрудника, техники и типа смены;
- дата публикации не позднее открытия смены;
- опубликовавший сотрудник активен и имеет действующий активированный
  доступ Заместителя, существовавший до публикации;
- ровно один активный `WatchPeriod`, покрывающий производственную дату.

Модель `WatchPeriod` допускает отсутствие периодов и несколько активных
пересекающихся периодов. Поэтому выбирать первый, последний либо наиболее
новый период запрещено.

## 3. Реализованный контракт

В `shifts/services.py` добавлено серверное определение вахты при открытии
смены Водителя.

Алгоритм:

1. Проверяется допустимый тип смены.
2. Тип назначенной смены сверяется с фактической сменой по единому
   производственному времени `Asia/Vladivostok`, границы `07:00/19:00`.
3. Определяется производственная дата открытия.
4. Ищется точный слот опубликованной расстановки Заместителя:
   `дата + роль driver + сотрудник + самосвал + day/night`.
5. Публикация должна фактически существовать до открытия смены, а её автор
   должен оставаться активным сотрудником с активной ролью и активированным
   доступом Заместителя.
6. На PostgreSQL неблокирующе фиксируется снимок справочника периодов.
7. Ищутся активные вахтовые периоды, покрывающие эту дату.
8. Ссылка записывается в `EmployeeShift.watch_period` только при ровно одном
   результате.
9. При отсутствии доказательства либо неоднозначности смена открывается
   штатно с `watch_period=NULL`; производственная работа не блокируется, а
   рейтинг продолжает работать fail-closed.

PostgreSQL использует `SHARE MODE NOWAIT` внутри восстанавливаемого
savepoint:

- если изменение справочника уже держит конфликтующую блокировку, попытка
  немедленно завершается, внешняя транзакция остаётся рабочей и смена
  открывается без связи;
- если снимок получен первым, конкурентное изменение справочника дожидается
  завершения короткой транзакции открытия смены;
- несколько Водителей могут одновременно получать совместимые
  `SHARE`-снимки.

`opened_at` и `watch_period` записываются одним снимком внутри существующей
транзакции открытия смены. Исторические смены не перепривязываются.

Изменение ограничено Водителем самосвала. Машинист, Диспетчер, Горный мастер,
ОУП, Табельщик, Делопроизводитель и Руководитель не включены в новый
записывающий путь.

## 4. Пограничные случаи

### 4.1. Ночная смена после полуночи

Ночная смена, открытая после полуночи, относится к производственной дате
начала ночи. Например, `10.08.2026 01:00` Владивостока относится к
производственной дате `09.08.2026`. Опубликованный ночной слот и вахта за
эту дату связываются штатно.

### 4.2. Ранний дневной комплекс

Система пока не хранит отдельный структурный признак раннего комплекса.
Открытие дневного назначения около `06:00` конфликтует с общим серверным
контрактом, который в это время считает активной ночную смену предыдущих
производственных суток.

Контур рейтинга не угадывает такой случай: смена открывается и продолжает
полный рабочий цикл, но `watch_period` остаётся пустым. Для включения ранних
комплексов в будущий официальный рейтинг сначала нужен отдельный
утверждённый структурный признак или расписание раннего комплекса.

### 4.3. Пересекающиеся периоды

Если одну дату покрывают два активных `WatchPeriod`, связь не создаётся.
Смена не блокируется.

### 4.4. Назначение без опубликованного плана

Ручное административное назначение либо иное действующее назначение без
точного опубликованного `CrewPlanSlot` не считается доказательством вахты.

### 4.5. Повтор клиентского действия

Повтор того же `client_action_id` возвращает уже созданную смену и сохраняет
её исходный снимок вахты, даже если справочник периода позднее изменился.

## 6. Регрессии

Добавлены пятнадцать исполняемых проверок:

1. опубликованная расстановка связывает смену с единственным периодом;
2. назначение без опубликованного плана не создаёт связь;
3. два подходящих периода не выбираются автоматически;
4. неактивный период не используется;
5. закрытая связанная смена видна в теневой сводке и остаётся неофициальной;
6. раннее дневное назначение без структурного признака не угадывается;
7. граница двух вахт около `06:00` остаётся безопасной;
8. ночной сменщик после полуночи получает период по производственной дате;
9. повтор одного клиентского действия сохраняет исходный снимок;
10. публикация сотрудником без доступа Заместителя не принимается;
11. неактивный, неактивированный, заблокированный или деактивированный
    доступ, неактивная роль и неактивный сотрудник не принимаются;
12. публикация после момента открытия не действует задним числом;
13. опубликованный слот другого сотрудника не связывает смену;
14. конкурентная вставка периода после снимка ждёт завершения открытия;
15. уже выполняющееся изменение периода не задерживает Водителя и приводит
    к безопасному `watch_period=NULL`.

## 8. Что это даёт

После будущей публикации новые стандартные водительские смены смогут
накапливать структурно связанную историю для калибровки KPI. Рейтинг по-
прежнему:

- не начисляет баллы;
- не присваивает места;
- не формирует официальную первую пятёрку;
- не меняет рабочие данные из read-only отчёта;
- всегда возвращает `official_rating_eligible=false`.

## 9. Что ещё требуется

1. После отдельного разрешения создать commit из проверенного Git-allowlist
   и выполнить push.
2. После отдельного разрешения выполнить rollback-ready deploy.
3. Внести в production точные уже утверждённые `WatchPeriod` только по
   фактическим датам и названиям, полученным от владельца процесса.
4. Накопить минимум одну полноценную связанную водительскую вахту.
5. Лишь после этого калибровать нормализацию и веса KPI.

До выполнения пунктов 3–4 отсутствие `WatchPeriod` не мешает сотрудникам
работать, но штатно удерживает данные от официального рейтинга.
