## Решение

E2-R2-C1 закрыт в проверенных границах. Новая итерация исправления механики сейчас не требуется. Удаление десятиминутного cooldown и уже принятые части E2/R1 сохраняются. E2 готов к следующему адресному PostgreSQL gate; это не разрешение интеграции или выпуска.

Рецензия основана на чтении точного commit (три файла, +366/-10), новых тестов и опубликованных raw. Астра не выполняла собственный Django/Node/браузерный прогон. Числа ниже относятся к прогонам автора.

## Почему замечание закрыто

- _removed_refusal_retry_provenance читает серверный result_payload, проверяет статус RETRY, причину, original_code, роль, тип корня и множество ID. Клиентский конверт не создаёт marker.
- Проверка same_identity выполняется до восстановления. Для потомка сервер заново вычисляет реальные корни зависимостей и сравнивает их с сохранёнными.
- Обработчики предметного RETRY, concurrent_state_retry и temporary_server_error сохраняют marker через _removed_refusal_retry_payload.
- После успешного повтора сохраняются окончательные conflict_recovery/dependency_recovery; принятие не создаёт новое событие.
- Тест корня дважды вводит TimeoutError, затем отдельно повторяет корень/ребёнка/внука; проверяет дедупликацию, исходные поля и по одному receipt/action.
- Тест ребёнка вводит RuntimeError в доменную операцию; другой временно убирает trip-ссылку и получает два trip_reference_pending. После восстановления цепочки проходят.
- Отдельный Node-тест восстанавливает сохранённого внука после удаления принятого ребёнка из очереди. Транспорт в нём mock; он не заменяет серверную регрессию.
- Изменённый payload и чужой device не повреждают сохранённое основание. Это не утверждение исчерпывающего покрытия всех комбинаций авторов/прав.

Сверены окончания raw: Django 293/293 OK, Node 48/48, mobile 44/44, operational fragment 10/10, users Ran 610 / OK (skipped=3). Stack trace инъекций отказа не является падением suite. В журналах PowerShell есть RemoteException и повреждённые кириллические строки; английские итоги читаемы. Нормализовать или переписывать исходные журналы не требуется.

## Границы

- PostgreSQL и физический APK/Xiaomi NOT_RUN.
- Новый browser run R2 NOT_RUN. Production JS/оболочка в R2 не менялись.
- Прежний R1 подтверждает очередь, сохранность через restart и доставку после устранения зависания. Старт при продолжающемся silent listener не подтверждён, относится к OFF-C1. Этот дефект не закрыт приёмкой E2.
- Driver baseline из E2/R1 не пересматривается и не выдаётся за зелёный полный Node suite.
- Приёмка относится к точному candidate SHA. Иной интеграционный SHA требует проверки после объединения.

## Единственное следующее поручение Кодексу — E2-PG1

Цель: проверить транзакции/блокировки именно E2, без новой бизнес-логики и без переноса OFF/S106.

1. На изолированной PostgreSQL test DB выполнить адресные E2/R1/R2 регрессии снятого cooldown, корня, ребёнка/внука через RETRY и dedup. Зафиксировать точный source SHA, PostgreSQL version, connection.vendor=postgresql и имя отдельной test DB. Production/permanent DB не использовать.
2. Два отдельных соединения одновременно повторяют один старый cooldown-root: один производственный эффект и один receipt/action; временный конкурентный исход допустим только с успешным последующим повтором того же ID.
3. Отдельные соединения доставляют корень и сохранённого потомка с перекрытием: после повторов оба приняты, собственные времена сохранены, цепочка/marker не потеряны; нет зависания без конечного результата. Не выдавать последовательный TestCase за concurrency.
4. Сохранить отрицательные identity/envelope/dependency проверки. Новые тесты допустимы в отдельной кандидатной ветке; runtime-код не менять без найденного контрпримера и отчёта.
5. Можно использовать доступный изолированный тестовый контур/существующий CI без production-операций. Если это требует запрещённого сейчас PR или недоступной инфраструктуры — сообщить конкретный блокер и готовую команду, не имитировать PostgreSQL SQLite-прогоном.
6. Вернуть raw stdout/stderr, exit code, числа PASS/SKIP и SHA. Широкий nightly и повторное сравнение Driver baseline не требуются. Не скрывать пропуски concurrency.

PR, merge, VERIFY и deploy этим поручением не разрешены. Версии оболочек не занимать и не менять. OFF-C1-R1, Driver и общие ветки кода не затрагивать. После PG gate координатор сверяет актуальный release, очередь выпуска и совместимость версии v264; решение о выпуске остаётся отдельным.
