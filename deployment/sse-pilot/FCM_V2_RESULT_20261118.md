# Итог сравнения обычного и срочного FCM

18.11.2026, Самара. Тестовый USB-телефон75292cdf0603, контекст Экскаваторщика№99/ТЕСТ-1. Рабочие действия, рейсы и смены не создавались и не закрывались, CAT-9/№10 не изменялись. Сравнивали транспорт тестовыми сигналами kind=fcm_latency_probe, которые вызывают штатную сверку и отдельное тестовое уведомление. Это не приёмка нового режима для всех видов рабочих событий.

## Вывод

В этой серии новый режим **не сократил задержку**. Все3 срочных сообщения действительно вызвали onNotificationReceived (transport=urgent_v2), автоматический возврат к legacy исключён. Все3 обычных сообщения вызвали onMessageReceived. По3 сообщения на режим недостаточно для статистической гарантии; редкая задержка6–12секунд в итоговой серии не воспроизвелась.

Межсистемные интервалы не следует считать абсолютной миллисекундной точностью: getSentTime и телефон используют разные часы. Близость этапов позволяет сравнить порядок величин, но изменение в сотни миллисекунд по шести сообщениям не доказывает устойчивую разницу режимов.

Окна ресурсов начинаются примерно через8–12секунд после первого принятого сообщения и заканчиваются после третьего; включают два последних сообщения. Это уменьшает влияние первоначальной инициализации. Окна не равны по продолжительности, GMS UID обслуживает и другую фоновую работу, размер актуального ответа сервера меняется. Поэтому снижение суммы UID не объявляется гарантией меньшего расхода нового режима. Отдельно GMS в этом опыте передал на530байт больше; это наблюдение, а не изолированный замер каждого пакета FCM.

JSON POST отправителя в Google:327байт legacy и669байт V2 (+342байта на сообщение). Это размер серверного HTTP payload, а не прямой размер пакета на телефоне. В V2 добавляется fallback-уведомление. Утверждать полное отсутствие дополнительного трафика нельзя.

Прокси CPU из batterystats UID: приложение4168мс против3202мс, GMS323мс против762мс, суммы4491мс против3964мс. На CPU также влияют разные ответы сервера и прочий фон. Значения не являются измерением энергии. Реальный расход аккумулятора при физическом USB-питании не измерен; dumpsys battery unplug только имитирует отключение питания для Doze и не отключает кабель. Критерий «быстрее без роста батареи/трафика» этим опытом **не подтверждён**.

## Изоляция, уведомления и контроль доставки

Водитель временно force-stop без удаления данных/закрытия смены. Перед каждым этапом подтверждены принудительный deep IDLE и Asleep. Исключение только основного Экскаваторщика из Doze временно снято; min_time_to_alarm временно0 из-за близкого будильника. Данные/интервалы отправки одинаковы:3 сообщения каждые25секунд. Никакого учащения heartbeat или постоянного wake lock не добавлено.

SDK26.1.0-eap01 взят по официальной ссылке Google, подключён только флагом -PfcmUrgentPilot. Обычная сборка оставлена на прежнем SDK/сервисе. Подпись/package/versionCode47 сохранены. Новый обработчик возвращает NotificationResponse с тем же тестовым каналом, заголовком и звуком, что legacy. NotificationRecord для V2: id1299, tag=fcm-urgent-pilot, channel=fcm_urgent_pilot_v2, importance4, isNoisy=true. Это проверка системного тестового уведомления, а не голосовой фразы конкретного назначения комплекса.

Отправитель работает через защищённый production environment GitHub Actions, owner-only, точный SHA и подтверждение; ключ не извлекался. Получатель ограничен хэшем токена USB-приложения. Сам токен передан AES-GCM/RSA-OAEP конвертом, открытым в Git/inputs/файлах не сохранялся. Сервер, receiver, БД, collectstatic, systemd и обычная рассылка не менялись и не перезапускались.

Первый запуск из feature-ветки отклонён штатной защитой environment до исполнения. Использована уже разрешённая t-031-release-candidate, правила защиты не менялись. Запуски: validate_only44170796422 (HTTP200, без доставки), итоговый legacy44173533945, итоговый urgent44173837954. Все итоговые sender jobs завершились success. Фактический код отправителя df7c5490683959f725392ccee17ccd269a3ef31e.

Две ранние попытки измерения исключены из сравнения: ошибка передачи ключа уведомления shell и отсутствие detail в dumpsys netstats. Настройки/публичный APK восстанавливались после каждой попытки; живой второй sender был отменён в finally, первый успел завершиться. Затем сборщик проверен отдельно на публичном APK и повторён полноценный опыт. Артефакты прежних попыток сохранены в attempt1/attempt2, не смешаны с итоговыми JSON.
