# Рабочий SSE. Подготовка инфраструктуры и откат

База прикладного кандидата `4eb356906fe86c457c4b20a75463a8871842b15d`.
Каталог готовит приложения и зависимости. Штатная установка должна
исполняться отдельным режимом защищённого приёмника. Шаблоны служб
требуют подтверждённых пользователей и групп из topology-проверки.

WSGI и ASGI используют модуль `config.settings_sse_production` и один
Redis-канал. Общий файл окружения содержит модуль настроек и URL Redis.
Отдельный файл окружения WSGI содержит флаг, который включает объявления SSE
и публикацию после коммита журнала. ASGI включает поток через свой unit.
Если маршрут потока ошибочно попадёт в WSGI, обработчик вернёт отключённый статус.
При пустом
Redis URL поток проверяет журнал периодически. Для приёмки доставки
без ожидания такого опроса проверить Redis publish/subscribe.

## Проверки перед применением

- Уточнить SHA кода production и сравнить действующие отпечатки Nginx
  и WSGI с проверенным планом. Проверить include, правила доступа,
  владельцев каталогов, Redis ACL и совместимость версии Python.
- Установить закреплённые wheels по SHA-256 в отдельный каталог,
  не засоряя действующую виртуальную среду. Без сети на сервере,
  из проверенного пакета, с `--no-index --require-hashes`.
- Проверить модули Django и systemd unit до активации, вызвать
  `nginx -t`. Для выставленного ASGI локальный запрос через Unix-сокет
  должен вернуть `401 authentication_required` на маршруте потока,
  а обычный путь — `404 sse_endpoint_only`.
- Сохранить с правами root образ исходного файла сайта, drop-in,
  unit-файлов, конфигурации приложения, доступа к зависимостям и
  список исходных состояний служб. Зафиксировать SHA до и после каждого
  управляемого изменения. Смены, их назначения и база данными релиза
  не являются. Миграций нет.

## Порядок включения и отката

1. Подготовить ASGI и сверку без перевода клиента на SSE. Проверить
   подключение к Redis и здоровый WSGI. Лимит ASGI ограничивает
   одновременные запросы. Nginx проксирует лишь точный путь потока.
2. Применить проверенную конфигурацию Nginx с точным маршрутом,
   проверить HTTPS и только затем включить флаг в оболочке WSGI.
   Обычные HTTP-запросы продолжают обслуживаться через WSGI.
3. При ошибке вернуть WSGI на опрос. Восстановить файлы Nginx из
   резервной копии после сверки текущих SHA и применить через
   `nginx -t` и reload. Вернуть прежний WSGI drop-in, восстановить
   исходные состояния unit-файлов и проверить ответ сайтов,
   прежний HTTP polling и отключённый маршрут SSE. Откат не трогает
   журнал событий и открытые смены.
4. В производственной приёмке использовать только экскаватор №99 и
   самосвал №1. Доказательство берётся из реальной погрузки,
   подходящего события в потоке водителя и обновления его экрана.
   Состояние, обнаруженное только через опрос, не засчитывать.
