## 1. Зафиксировать доставку именно принятого кандидата

В `github-actions/source-overlay/.github/workflows/production-deploy.yml` checkout использует `github.sha`; затем требуется совпадение `HEAD` с `expected_commit`. Для SSE-QA дополнительно требуется ветка `codex/github-production-deploy-20260916`. Пакет берётся из `deployment/sse-qa-install` того же checkout.

При этом `PLAN.md` предлагает перенести на control-ветку только четыре control-файла, а QA-пакет получить из отдельного `fb81480a…`. Отдельного источника для этого кандидата в workflow нет.

Следствия:

- control-ветка + `expected_commit=fb81480a…` не проходит проверку HEAD;
- candidate-ветка + `expected_commit=fb81480a…` не проходит ограничение ветки;
- control-ветка + её новый SHA не доказывает доставку пакета из `fb81480a…`.

**Доработка:** подготовить один конкретный защищённый путь, который сохраняет control SHA и отдельно фиксирует источник QA-пакета. Использовать проверенный, заданный в коде SHA/артефакт либо включённое и побайтно сверенное дерево кандидата. Не возвращать пользовательский произвольный checkout SHA и не ослаблять существующие branch/confirmation/CodeQL gates.

В evidence раздельно фиксировать control SHA, candidate SHA, controller/runtime/package hashes. Показать точные параметры будущего dispatch и локальную проверку, что выбран именно принятый источник; подмена или mismatch должны завершаться отказом. Изменять рабочую бизнес-логику приложения ради этой задачи не требуется.

## 2. Сделать начальный preflight действительно read-only и строгим

Сейчас `verify_sse_qa` совмещает две разные операции:

- без `INSTALLATION_MARKER` — предварительную проверку;
- при найденном marker — проверку установленного QA через `sse-qa-verify.service`.

Receiver выбирает второй путь автоматически. В controller `_verify_real_runtime()` при выключенном QA временно запускает PostgreSQL и Redis. Следовательно, общее разрешение на «read-only verify» не гарантирует отсутствия запусков служб, если на хосте обнаружится существующая установка. Сам отчёт пока не подтверждает отсутствие её объектов.

Кроме того, `verify_installation()` вызывает `preflight(..., installed_ok=True)` даже при отсутствии marker. Этот флаг пропускает конфликты пользователя/кластера и допускает ownership journal. Затем отсутствие marker позволяет вернуть `not_installed_preflight_only`. В `preflight()` также не проверяется exit code `pg_lsclusters`: ошибка запроса может выглядеть как отсутствие кластера.

Это проверено безопасными вызовами реальных функций с подменёнными внешними операциями, без запуска системных команд и служб:

| Сценарий | Фактический результат текущего кода |
| --- | --- |
| Receiver verify без marker | Нет запуска slice/transient service |
| Тот же verify с marker | Выбран запуск slice и `sse-qa-verify.service` |
| Строгий preflight, пользователь уже существует | Отказ |
| `verify_installation`, тот же существующий пользователь, marker отсутствует | PASS `not_installed_preflight_only` |
| `pg_lsclusters` возвращает exit 2 и пустой stdout | Preflight проходит |
| `id` возвращает exit 2 | Preflight проходит |

Дополнительно воспроизведён PASS начального verify при одновременно существующих пользователе `sseqa` и кластере `16/sseqa`. Сам `real_install()` повторно вызывает строгий preflight, поэтому это ложное подтверждение готовности, а не доказанная перезапись чужой установки.

**Доработка:** выделить однозначный начальный режим проверки без изменения состояния QA. При существующей или частичной установке, конфликте либо неизвестном результате проверки он должен остановиться; автоматически переходить к live-verify нельзя. Реализовать это минимальной правкой канала/предпроверки, сохранив принятый install/rollback lifecycle.

Проверка должна различать «объект отсутствует» и «проверить не удалось». Нельзя выдавать полный preflight PASS при неуспешном запросе списка кластеров или при пропущенных конфликтах.

Адресно проверить безопасными локальными mocks:

1. Чистый хост — начальная проверка проходит без запуска или остановки QA-служб.
2. Существующий marker, полный или частичный ownership journal — начальная проверка отказывает без live-verify.
3. Конфликт пользователя/кластера — отказ; ошибка запроса состояния — отказ, а не «свободно».
4. В начальном режиме не вызываются install/enable, `systemd-run` для QA, запуск slice/PG/Redis, nginx reload или автоматическое удаление найденных объектов.

В плане разделить реально проверяемое до установки и проверяемое во время установки. Наличие CLI, cgroup controllers и `/dev/loop-control` ещё не доказывает применённые лимиты, успешный mount или runtime isolation. Сменный пик, event-loop и nginx-маршруты не следует объявлять проверенными операцией, которая их не измеряет. Это уточнение границ проверки, а не требование нового суточного или нагрузочного прогона.

Также исправить обещание независимого zero-residue scan внутри install/remove: такой scan подтверждён в disposable harness, но отдельно не вызывается текущим receiver после этих операций. Для будущего серверного этапа указать фактический способ проверки результата; переносить disposable fault/cancel cycle на рабочий сервер нельзя. Заявленную проверку конфликта группы `sseqa` тоже следует либо реализовать в начальной предпроверке, либо явно отметить как ещё не выполненную.

## Что сделать сейчас

Выполнить только эти локальные доработки, адресные проверки и проверки затронутого release-протокола. Вернуть один компактный пакет: точный diff, необходимые исходники, фактические логи, обновлённые `PLAN.md` и `PERMISSION_REQUEST.md`, manifest и SHA-256.

В запросе следующего разрешения оставить только конкретную последовательность: публикация проверенного control patch → `verify_receiver/update_receiver` точного SHA → однократный строго read-only начальный preflight → остановка с отчётом. Условное автоматическое разрешение `install_sse_qa`, сейчас включённое в основной текст `PERMISSION_REQUEST.md`, убрать. Решение об установке выключенного QA принять по фактическому результату preflight.

Лимиты будущего QA сохраняются: 1 CPU, 2 GiB RAM, 6 GiB образа, отдельный PostgreSQL с максимумом 16 подключений; первая установка заканчивается `enabled=false clients=0`.

Сейчас не выполнять commit/push/merge, обновление receiver, новый dispatch, установку QA, DNS/TLS/nginx-изменения или нагрузку. Повторять принятый disposable Linux-цикл без изменения его кода либо нового конкретного риска не требуется. Покупки, APK/Firebase и массовое внедрение SSE в эту задачу не входят.

В рамках данного ревью выполнялись только локальные проверки предоставленных файлов; рабочий сервер не изменялся.
