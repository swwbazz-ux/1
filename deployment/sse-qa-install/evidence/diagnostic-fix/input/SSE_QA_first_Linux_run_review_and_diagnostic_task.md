## Подтверждённая причина потери диагностики

В `source/linux_disposable_cycle.sh`:

1. `wait_install_checkpoint()`, строки 150–168, продолжает ждать до 300 секунд при завершившемся с ошибкой unit и не использует уже возможный exit marker.
2. Ошибка вызова на строке 375 при `set -e` переводит выполнение в EXIT trap. До `collect_install_result()` на строке 379 управление не доходит.
3. `on_exit()` сразу вызывает cleanup. Строки 348–350 сбрасывают failed state и удаляют `.exit`/`.invocation`, не сохранив журнал и первичный статус в evidence.

Поведение воспроизведено на настоящих Bash-функциях с подставными systemctl и временем: искусственный wrapper exit 23 превращается в harness exit 1, journal collector не вызывается, exit/InvocationID удаляются. Реальные службы не запускались.

Есть ещё один участок той же проблемы диагностики: `source/sse_qa_ctl.py`, строки 90–95, использует `capture_output=True`. При `CalledProcessError` дочерний stderr остаётся в объекте исключения, но не включается в стандартный текст ошибки. Это также воспроизведено. Простого экспорта systemd journal может оказаться недостаточно, чтобы увидеть причину ошибки дочерней команды.

## Задание Codex: локально исправить сохранение диагностики

Выполнить одну ограниченную доработку аварийного пути. Бизнес-логику SSE и ранее принятые механизмы установки/изоляции R4 не перерабатывать; первопричину этого отказа не угадывать.

1. Сохранять label, InvocationID и время попытки сразу в evidence вне удаляемого QA-каталога. Не оставлять единственную копию идентификатора в `/run/sse-qa-cycle`.
2. При подтверждённом раннем завершении installer прекращать ожидание checkpoint. Учитывать асинхронный старт: краткое начальное состояние до запуска процесса не считать отказом. Различать terminal failure, exit marker, timeout и отсутствие доступного статуса.
3. На аварийном выходе **до reset-failed и удаления файлов** сохранять journal точного invocation, имеющийся wrapper exit и безопасные systemd-поля: `ActiveState`, `SubState`, `Result`, `ExecMainCode`, `ExecMainStatus`, `MainPID`, `InvocationID`. Сохранять последнюю наблюдаемую phase отдельно от статуса checkpoint.
4. Для живого процесса при timeout снять диагностику до остановки, затем финальный результат после остановки, пока unit ещё не сброшен. Сбор должен иметь ограниченное время и не мешать обязательному cleanup. Отсутствие InvocationID/exit marker или ошибка journal export должны оставлять понятную запись, а не новый безымянный отказ.
5. В диагностике дочерних команд сохранять фиксированный идентификатор шага, exit/timeout и ограниченный, очищенный от секретов stderr/stdout. Обрабатывать также ошибки до создания ownership. Не выводить сырой SQL, `input_text`, environment или аргументы с credentials. Сохранить действующие маски и проверку evidence перед публикацией.
6. Первичная ошибка, ошибка сбора диагностики и результат cleanup должны быть отдельными полями. Успешная очистка не превращает FAIL в PASS, а сбой диагностики не должен отменять cleanup.

Адресно проверить ранний отказ до checkpoint, timeout живого процесса, отсутствие exit marker, ошибку экспорта journal и stderr с искусственным секретом. Проверять фактический порядок «сохранение → cleanup», сохранение исходного exit code и отсутствие секрета в публикуемых данных. Достаточно безопасных локальных тестов; production для воспроизведения не использовать.

Вернуть **один пакет** с точечным diff, изменёнными исходниками, адресными результатами и SHA-256. В кратком ответе разделить: «сохранение диагностики исправлено» и «первопричина первого installer FAIL пока неизвестна». Это разные утверждения.

На этом этапе подготовить локальную доработку. Публикация и второй disposable dispatch этим заданием не разрешаются: единственный разрешённый пробный запуск уже использован. После проверки конкретной правки можно согласовать один повтор на новом candidate SHA с обычными обязательными checks. Рабочий сервер, существующий QA, receiver, DNS, Firebase, покупки и нагрузка 80–96 клиентов остаются вне этапа.
