## Причина повторного отказа

`evidence/extracted/cycle/install-attempts/normal-install/journal-pre-cleanup.log` содержит:

```text
SSE_QA_FAIL wheelhouse contains non-CPython-3.12 artifacts
```

В `scripts/sse_qa_ctl.py`, функция `validate_wheelhouse()`, строки 732–737, проверяется только фрагмент `-cpNNN-`: всё, кроме `cp312`, отклоняется. ABI и платформа при этом не учитываются.

Единственный файл фактического wheelhouse, попавший под этот запрет:

```text
cryptography-50.0.1-cp311-abi3-manylinux_2_34_x86_64.whl
```

`cp311-abi3` допускает использование стабильного ABI на подходящем CPython 3.12; также должна подходить платформа. В данном run тот же wheel уже успешно установлен в Python 3.12 test venv — это прямо видно в `raw/test-venv-install.log`.

Независимый безопасный тест настоящей функции воспроизвёл ошибочное отклонение. Он также показал обратную ошибку того же правила: имена с `cp312`, но Windows или ARM64, принимаются для целевого Linux x86_64. Поэтому исправлять нужно полную проверку совместимости, а не добавлять исключение для одного имени `cryptography`.

В этом run отказ произошёл до создания ownership и ресурсов установки: `validate_wheelhouse()` вызывается на строке 979, до создания состояния на строках 989–991. До проверки работоспособности PostgreSQL/Redis/ASGI выполнение не дошло.

## Задание Codex: одна локальная правка validator

1. Работать от опубликованного candidate `0d733461d569003fe6fcab4d61b57c38df77bdef`. Исправить проверку wheelhouse; принятую диагностику, бизнес-логику SSE и механизмы изоляции не перерабатывать.
2. Сохранить проверки состава manifest, дубликатов и SHA-256. Заменить regex по `cpNNN` проверкой полного набора compatibility tags. Предпочтительный механизм — `packaging.utils.parse_wheel_filename()` и пересечение с `packaging.tags.sys_tags()` целевого интерпретатора. Проверять Python, ABI и платформу, включая составные теги.
3. Источником фактической совместимости должен быть целевой `/usr/bin/python3.12` на Linux, а не Windows-машина разработчика. В переносимых unit-тестах использовать явно заданный набор целевых тегов.
4. Учесть порядок запуска: validator работает **до создания application venv**. Обеспечить доступность используемой библиотеки проверки в этом окружении; не полагаться на зависимости test venv или будущего application venv. Не добавлять сетевой `pip install` внутрь установщика. При недоступности проверки завершаться с понятной диагностикой, без разрешающего fallback.
5. Проверить таблицу ниже настоящей функцией с корректными тестовыми manifest. Сохранить полезную ошибку: безопасное имя отклонённого wheel и причину отказа. Не выводить секреты.
6. Вернуть **один локальный ZIP**: точечный diff, изменённые исходники, тесты, raw-логи, объяснение доступности зависимости до venv и SHA-256. Указать, какие проверки выполнены локально, а какие требуют будущего Linux-прогона.

| Случай для целевого CPython 3.12 / Linux x86_64 | Ожидание |
| --- | --- |
| Точное имя проблемного `cryptography … cp311-abi3-manylinux_2_34_x86_64`, при совместимой glibc | ACCEPT |
| Обычный `cp312-cp312` с подходящей платформой | ACCEPT |
| `py3-none-any`, составной `py2.py3-none-any` | ACCEPT |
| `cp311-cp311`, `cp313-abi3` | REJECT |
| Windows/macOS, чужая архитектура, несовместимое требование glibc | REJECT |
| Некорректное имя, повреждённый manifest, несовпадение SHA-256 | REJECT |
| Зависимость проверки недоступна до application venv | Понятный отказ, без пропуска проверки |

Не менять версии Python или `cryptography` ради обхода ошибочного правила и не ослаблять проверки целостности. Достаточно исправления валидатора и необходимого обеспечения его зависимости; отдельную систему управления пакетами строить не требуется.

**На этом этапе — локальная правка и проверяемый пакет.** Единственный разрешённый повтор уже использован. Commit/push, новый dispatch, merge, deploy, production, существующий QA, receiver, SSH, DNS, Firebase, покупки и нагрузка 80–96 клиентов этим заданием не разрешаются.
