**Остаток 1 — неверный путь cgroup блокирует реальный Linux-запуск.**

Файлы: `scripts/sse_qa_ctl.py:358, 368, 384`; `scripts/linux_disposable_cycle.sh:44`; `tests/test_package_contract.py:75, 83, 88`. Аналогичное предположение есть в проверке cgroup receiver около строки 2475.

В systemd дефис в имени slice задаёт вложенность. Для выбранного имени пути имеют вид:

```text
sse-qa.slice                  → /sse.slice/sse-qa.slice
sse-qa-install.service внутри → /sse.slice/sse-qa.slice/sse-qa-install.service
```

Код и Bash-сценарий ожидают `/sse-qa.slice`, а тестовые заглушки повторяют это ошибочное ожидание. Точные функции R3 с корректными значениями systemd воспроизвели:

```text
correct_parent_path: QA slice resource property mismatch: ControlGroup
correct_child_path: unit cgroup membership mismatch: sse-qa-install.service
```

Поэтому подготовленный disposable cycle остановится на `assert_slice_limits` до запуска installer. Через receiver контроллер также отвергнет корректное размещение.

Первичный источник: [systemd v255, systemd.slice.xml, строки 30–37](https://github.com/systemd/systemd/blob/v255/man/systemd.slice.xml); отображение имён в cgroup также описано в [официальной документации systemd](https://systemd.io/CGROUP_DELEGATION/).

Исправить единообразно controller, receiver, Bash и тесты. Предпочтительно получать фактический путь slice из `ControlGroup` и проверять дочернее размещение по этому пути, сохраняя проверку ожидаемой slice и точных лимитов. Не ослаблять проверку до наличия подстроки. Добавить независимый тест с настоящей иерархией `/sse.slice/sse-qa.slice`, включая отказ для процесса вне неё.

**Остаток 2 — проверки при enable обходят общий бюджет QA.**

Файлы: `github-actions/source-overlay/deployment/server/accounting_github_deploy_receiver.py:2465–2471`; `scripts/sse_qa_ctl.py:1020–1047, 457–460`.

Receiver помещает в ограниченную slice install, smoke и отдельный installed verify. Но `real_enable()` дважды напрямую вызывает `verify_installation()`. Та запускает Django-команду обычным subprocess. Путь enable не обёрнут в QA scope, поэтому эти процессы остаются вне общего бюджета, в том числе когда QA-службы уже запущены.

Провести обе внутренние проверки enable через тот же ограниченный механизм либо ограничить весь подходящий QA-процесс enable. Сам production receiver должен остаться в своей группе. Добавить поведенческий тест именно enable-пути: обе Django-проверки выполняются внутри общего бюджета, включая повторную проверку после старта служб и обработку ошибки.
