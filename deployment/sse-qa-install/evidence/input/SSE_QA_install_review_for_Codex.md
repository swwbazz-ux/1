# SSE-QA install: исправления до серверной установки

Проверен архив `SSE-QA-install-20260927.zip`, SHA-256:

`2F76E9CE0E4A21AF0B1CAF27EDA5B49CD0E35AB2045FEEE27487B3F2832A06D2`

**Вывод: архитектура отдельного QA на существующем сервере подходит для продолжения работы, но этот установочный пакет пока не готов к установке. Требуются исправления ниже. Покупка нового сервера или домена не нужна для выполнения этого задания.**

## Что независимо подтверждено

- SHA архива, runtime, source overlay и control-channel patch совпали с заявленными.
- Self-check подтвердил 46 индексируемых файлов; пакетные тесты повторены: **10/10 PASS**. Заявленный release-protocol 37/37 отдельно не повторялся.
- 53/53 файлов производного R3 overlay совпали с ранее проверенным R3. Замена ASGI entrypoint на instrumentation-overlay явная; все три instrumentation-файла совпадают с runtime. Полная пересборка baseline f99 здесь не выполнялась.
- Постоянные QA-службы отнесены к отдельной slice; PostgreSQL, Redis и upstreams отделены от production. Конфигурация nginx предусматривает Basic Auth, CIDR и предел двух SSE-подключений.
- Проверенные опасные ZIP-пути и ссылки отклоняются; операции передаются controller фиксированными аргументами.
- Приложение, установщик и серверные probes не запускались. Выполнялись чтение, unit/mock-тесты, временный render и отдельная статическая проверка systemd без запуска службы.

Все пути ниже относительны корню пакета; номера строк относятся к полученной версии.

## QA-1. Исправить проверки до и после установки

`scripts/sse_qa_ctl.py:209–231,473–485` вызывает `systemd-analyze verify` до создания venv. Проверяемые unit-файлы уже ссылаются на `/srv/sse-qa/venv/bin/uvicorn`, `gunicorn` и `python`. На чистом сервере этих executable ещё нет, а verify проверяет их существование и исполнимость.

Независимый минимальный пример unit с отсутствующим executable дал exit 1 и `is not executable: No such file or directory`. Служба не запускалась. Такое поведение также описано в [официальной документации systemd](https://github.com/systemd/systemd/blob/v255/man/systemd-analyze.xml).

Разделить проверку подготовленных конфигураций до установки и проверку фактического runtime после его создания. Нельзя просто игнорировать ошибки verify: предустановочная проверка должна корректно работать на чистой машине и сохранять проверку остальных зависимостей.

`verify_installation():182–206` сейчас проверяет пять файлов и несколько подстрок. Она **не подтверждает** фактический mount source, применённые cgroup-лимиты, SQL role/connection limits, Redis ACL, synthetic fixture и даже значение `SSE_PILOT_ENABLED=false`, обещанные документацией. Реализовать эти проверки с учётом фазы: установленный выключенный стенд и включённый стенд требуют разных проверок.

Также проверить соответствие Python/ABI: workflow собирает wheelhouse под Python 3.12, а installer использует произвольный host `python3`. Наличие команды не доказывает совместимость; версия целевого Python в переданном infra-отчёте не установлена.

## QA-2. Исправить два конкретных отказа запуска и бизнес-сценария

**Redis ACL недоступен сервису.** `sse_qa_ctl.py:281` создаёт `/etc/sse-qa/redis.acl` с mode `0600`, строка 319 назначает владельца `root:sseqa`, а Redis работает как `sseqa:sseqa`. Установка прервётся при старте Redis на строке 355. Локальный render подтвердил отсутствие группового чтения.

Исправить на подходящие права, например `root:sseqa 0640`, и проверить чтение от имени сервисной учётной записи, не раскрывая содержимое ACL.

**Synthetic seed создаёт несовместимый тип техники.** `app-overlay/users/management/commands/seed_sse_qa.py:66–67` создаёт `Экскаватор SSE QA`, тогда как runtime `backend/trips/views.py:4324–4336` ищет точное имя `Экскаватор`. Рабочий экран не находит открытую смену; downtime-сценарий возвращает 409. AST/ORM-stub воспроизведение: тип seed → `None`; канонический тип → смена найдена.

Использовать канонические типы техники, оставив QA-маркировку в номерах и аккаунтах. Проверить штатный вход двух ролей, наличие смен/техники и создание/доставку синтетического рейса. Одного heartbeat для приёмки недостаточно.

## QA-3. Сделать восстановление после ошибки и отмены работоспособным

`real_install():293–365` не имеет cleanup по фазам. Пользователь, image и units появляются **до** marker. В mock-прогоне ошибка `mkfs.ext4` оставила созданный image без marker; затем `real_remove()` отказался с `owned installation marker missing`. После поздних ошибок могут остаться запущенные PG/Redis: штатный stop есть только в конце успешного пути.

Receiver запускает controller с `timeout=900` (`github-actions/source-overlay/deployment/server/accounting_github_deploy_receiver.py:2323–2326`), но не управляет всем деревом дочерних процессов. Его подкоманды не имеют собственных таймаутов. Убийство непосредственного controller не гарантирует прекращения pip/миграции или уже запущенных systemd jobs.

Нужны: учёт созданных ресурсов с первой мутации, очистка по достигнутой фазе, управляемое завершение и ожидание потомков, остановка запущенных QA units, сохранение диагностируемого состояния при неудаче cleanup. Проверять доступные предпосылки runtime/wheelhouse до первой мутации. Не перемещать production receiver целиком в ограниченную QA-группу.

Добавить fault-injection проверки до marker, после старта PG/Redis и при timeout/cancel. Повторное выключение и удаление должны безопасно обрабатывать частичную установку.

## QA-4. Согласовать проверки принадлежности с записью и удалением

Список конфликтов в `sse_qa_ctl.py:153–159` не охватывает все WSGI/ASGI/reconcile/target/mount/drop-in/logrotate-файлы. Установка затем копирует их поверх существующих (`304–321`). В независимом временном root чужой `sse-qa-wsgi.service` не помешал preflight вернуть PASS.

`real_remove():427–444` удаляет cluster и файлы по именам, не проверяя обещанные фактические PG data directory, loop mount source и принадлежность каждого объекта. Один общий marker недостаточен.

Исправить через единый полный перечень создаваемых объектов: reject любого конфликта до записи, фиксация принадлежности, проверки реальных путей/ссылок/mount/cluster перед удалением. Чужой или изменённый неожиданный объект должен останавливать соответствующую опасную операцию. Проверить сохранность посторонних объектов и частично созданной установки.

## QA-5. Убрать сборку зависимостей из аварийного выключения

`github-actions/source-overlay/.github/workflows/production-deploy.yml:311–324` выполняет `pip download` и пересборку всего ZIP для **любого** `*sse_qa`, включая `disable_sse_qa` и `remove_sse_qa`. При недоступности package index команда выключения вообще не достигнет receiver.

Для управления установленным стендом нужен небольшой фиксированный пакет управления либо уже установленный проверенный controller. Выключение не должно зависеть от PyPI, разрешения зависимостей или пересборки runtime. Проверить выключение при недоступном индексе и частичной установке; сохранить защищённый канал и фиксированный контракт команд.

Отсутствие wheelhouse в переданном ZIP само по себе не считается отдельной ошибкой: его формирует workflow. Но конкретный Linux wheelhouse и его хеши должны быть зафиксированы и проверены как часть фактического установочного артефакта.

## QA-6. Обеспечить заявленные ресурсные границы

`venv`, `pip`, `pg_createcluster/initdb`, migrations, seed и collectstatic выполняются непосредственно из receiver (`sse_qa_ctl.py:337–363`), вне `sse-qa.slice`. Поэтому ограничение 1 CPU/2 GiB и заявленный резерв для maintenance эти фазы не охватывают. Запускать ресурсоёмкие фазы в отдельном ограниченном QA scope/service; проверить фактическую принадлежность процессов.

6 GiB image ограничивает файлы внутри `/srv/sse-qa`, но не весь дисковый след QA: nginx наследует общие журналы, а stdout/stderr служб уходят в journald вне image. Имеющийся logrotate этого не ограничивает. Выделить и ограничить QA-журналы без изменения глобальных правил production, либо явно задать отдельный ограниченный бюджет и честно описать область гарантии.

Относительный `IOWeight` не превращать в обещание полной изоляции физического диска; текущая документация правильно признаёт это ограничение.

## Следующее поручение и граница приёмки

Исправить QA-1–QA-6 локально, сохранив исходную архитектуру и предел первого этапа 1–2 клиента. Вернуть **один обновлённый проверяемый пакет** с SHA-256, исходниками, адресными регрессионными тестами и логами.

Для установщика нужны проверки поведения, а не только наличия строк в конфигурациях. До установки на рабочий сервер провести цикл `preflight → install → verify → enable → бизнес-проверка 1–2 клиентов → disable → remove` в одноразовой Linux-среде без доступа к production, а также проверки ошибок и отмены. Если такая среда пока недоступна, подготовить этот интеграционный тест и явно указать, что он не выполнен; не подменять его unit/mock PASS.

Локальные действия не требуют нового сервера или домена. Commit/push, обновление receiver, установка, DNS/TLS и любые изменения существующего сервера этим заданием не разрешаются. Нагрузку 80–96 клиентов, Firebase и Android сюда не добавлять.

Неблокирующее замечание для будущего отчёта: sampler работает на нужном ASGI loop, но его summarizer считает весь накопленный файл. Для критериев по двум пятиминутным окнам понадобятся границы запуска/окна и проверка свежести; не выдавать общий percentile файла за percentile отдельного окна.
