**1. Linux-имя mount unit искажается, из-за чего проверка конфликтов пропускает чужой файл, а verify не принимает свой.**

Файл: `scripts/sse_qa_ctl.py`, строки 52, 175–179, 418–422, 620–625, 680–684.

`SYSTEMD_SOURCE_TARGETS` правильно содержит имя с буквальным обратным слешем:

```text
/etc/systemd/system/srv-sse\x2dqa.mount
```

Но `rooted()` заменяет обратный слеш на `/` и проверяет другой путь:

```text
/etc/systemd/system/srv-sse/x2dqa.mount
```

При этом `_copy_owned()` пишет настоящий Linux-путь напрямую. В независимом тесте файл с правильным буквальным именем создавался без использования `rooted()`. Получено:

```text
preflight_passed_with_foreign_mount = true
exact_hash_owned_file_guard = false
```

Следствия: существующий mount unit может быть перезаписан; установленный unit не проходит проверку хеша по ошибочному пути; cleanup пропускает настоящий файл как отсутствующий.

Исправить представление POSIX-путей с сохранением буквального `\`. Добавить тест полного пути conflict → copy → verify → remove, где ожидаемое имя создаётся независимо от проверяемого helper. Нынешний тест конфликтов создаёт объект тем же ошибочным helper и потому не обнаруживает дефект.

**3. Cleanup удаляет PostgreSQL до проверки принадлежности файловой системы.**

Файл: `scripts/sse_qa_ctl.py`, строки 660–676.

Сначала выполняется `pg_dropcluster --stop 16 sseqa`, и лишь затем проверяется mount/backing file. Если регистрация PostgreSQL содержит ожидаемый путь `/srv/sse-qa/postgres/data`, но в `/srv/sse-qa` смонтирована чужая файловая система, проверка PG-пути проходит. Удаление данных уже запрошено до обнаружения чужого mount.

Изолированное воспроизведение с `_postgres_cluster_status()="match"`, `_mount_status()="mismatch"`:

```text
systemctl stop ...
pg_dropcluster --stop 16 sseqa
QaError: cleanup stopped safely: QA mount source mismatch
```

Все команды в этом воспроизведении — mocks; реальные данные не удалялись. Порядок вызовов подтверждает дефект.

Сделать cleanup двухфазным: сначала проверить принадлежность mount/backing file, регистрации и data directory PostgreSQL, управляющих файлов; затем выполнять разрешённые удаления. При mismatch не вызывать `pg_dropcluster`, удаление файлов или другие разрушительные операции на сомнительном ресурсе. Перед удалением повторно проверять критичные условия. Добавить тесты чужого mount и изменённых объектов, проверяющие отсутствие разрушительных вызовов.

**4. Успешное выключение объявляется без подтверждения; частичный запуск при verify также может остаться работающим.**

Файлы: `scripts/sse_qa_ctl.py:345–349, 384–386, 921–930`; `github-actions/source-overlay/deployment/server/accounting_github_deploy_receiver.py:2354–2372`.

В `real_disable()` результат `systemctl stop` игнорируется. Воспроизведение с return code 1 всё равно записало `complete_disabled` и выдало:

```text
SSE_QA_DISABLE_OK data_preserved=true complete=true
```

При таймауте установки receiver игнорирует отказ `systemctl stop sse-qa-install.service` и сообщает `was terminated`. Если сама команда stop зависает до своего таймаута, выполнение выходит до `killpg`. Завершение клиента `systemd-run` не подтверждает завершение отдельного systemd unit установки.

Кроме того, `_verify_real_runtime(False)` стартует PG/Redis до входа в `try/finally`. При частичном старте с ошибкой остановка из `finally` не выполняется.

Нужен проверяемый протокол остановки: учитывать отказ и таймаут, проверять фактическое состояние фиксированных QA units, завершать и дожидаться управляющего процесса в гарантированном cleanup. Если остановка не подтверждена — сохранять журнал и возвращать явную ошибку, без `DISABLE_OK`, `complete_disabled` и обещания `terminated`. Частичный старт dependencies должен попадать под cleanup. Добавить адресные тесты этих трёх веток отказа.

Уточнить документацию: установленный `verify_sse_qa` временно запускает PG/Redis и выполняет Django-команду. Он не является полностью read-only операцией, хотя preinstall-проверка может оставаться таковой.

**5. Общий бюджет 1 CPU / 2 GiB ещё не охватывает установку и вспомогательные процессы.**

Файлы: receiver, строки 2336–2346; `scripts/sse_qa_ctl.py:327–337, 377–380, 809–832, 959–962`; `RESOURCE_LIMITS.md`.

Installer получил собственные лимиты, но его `systemd-run` не задаёт `Slice=sse-qa.slice`. Во время migrations/seed одновременно работают PG и Redis в другой, QA slice. Поэтому два независимых бюджета складываются. Только для этой фазы конфигурация допускает до 140% одного CPU и 2.875 GiB RAM: installer 100%/2 GiB + PG 35%/768 MiB + Redis 5%/128 MiB. Это расчёт допускаемых лимитов, а не измеренное потребление.

Django-команды installed verify и business smoke также запускаются напрямую через receiver, без включения в общий QA-бюджет. Заявленный резерв QA slice на maintenance их не ограничивает.

Дополнительно live verify принимает любую конечную CPU quota: значение `8s` вместо ожидаемого одного CPU прошло проверку `cgroup_limits_applied` в изолированном тесте.

Обеспечить общий родительский бюджет для QA и её тяжёлых install/verify/smoke-процессов, сохранив receiver в его существующей группе. Проверять фактическую принадлежность cgroup и точные CPU/RAM/swap/tasks ограничения. Выбранный способ должен учитывать создание и удаление slice во время установки/отката. Добавить тест одновременной работы installer + PG/Redis и проверку отказа при неправильной CPU quota. Перенос постоянных QA-логов внутрь image можно считать закрытым.
