## Причина cancel FAIL

В `deployment/sse-qa-install/scripts/sse_qa_ctl.py`:

- строки 1254–1257 устанавливают обработчик SIGTERM, выбрасывающий `QaCancelled("install cancelled")`;
- строки 1350–1355 выполняют `cleanup_owned_installation()` при ошибке установки;
- прежний обработчик восстанавливается только в `finally`, строка 1357, после rollback.

В журнале cancel после достижения `dependencies_started` записано:

```text
SSE_QA_FAIL install failed (QaCancelled); cleanup incomplete: install cancelled
```

Сочетание точного исходника и сообщения подтверждает второе исключение отмены внутри rollback. Источник повторной доставки SIGTERM на уровне systemd/wrapper отдельно не трассировался; приписывать его конкретному механизму без дополнительных данных не нужно.

Независимый безопасный опыт выполнил настоящие `real_install()` и `cleanup_owned_installation()` с заменёнными системными командами и временными путями. Сигналы отправлялись только собственному временному Python-процессу:

| Опыт | Результат |
| --- | --- |
| Один SIGTERM во время установки | Исходный `QaCancelled` сохранён; cleanup дошёл до конца; временное состояние удалено |
| Второй SIGTERM внутри cleanup | Точно воспроизведено сообщение `cleanup incomplete: install cancelled`; cleanup оборвался; временное состояние осталось |

В обоих случаях прежний обработчик затем восстановлен. Реальные useradd/systemctl/installer-службы в опыте не запускались.


Здесь cleanup 0 относится к последующей аварийной очистке, а общий FAIL сохраняет провал cancel.

Есть связанная ошибка протокола cancel: `linux_disposable_cycle.sh:571–577` заранее записывает `cleanup_exit=0` и `CANCEL_MARKER_OK`, ещё **до** собственного zero-residue. Проверка строки `install cancelled` также принимает сообщение `cleanup incomplete: install cancelled`. Поэтому per-attempt `cleanup-result.txt` и ранний marker сейчас не доказывают успешного rollback. Последующий scan правильно остановил весь workflow.

## Задание Codex — локальная правка cancel

Работать от candidate `3aea8335998636740636b315f8acc62f61182588`. Принятые порты, wheel-validator, cleanup проверки состояния systemd, бизнес-SSE и normal/fault-сценарии сохранить.

1. **Сделать отмену идемпотентной.** Первый SIGTERM должен инициировать отмену установки. После начала отмены/rollback повторные SIGTERM не должны выбрасывать новое исключение внутрь cleanup или запускать rollback заново. Защитить переход к rollback, сохраняя исходную причину отказа; это относится и к rollback после обычной ошибки установки.
2. Сохранить ownership-проверки, ограничение времени и штатную остановку группы процессов. Не превращать отменённую установку в успех. Ошибки самой очистки должны оставаться видимыми отдельно от исходной причины. Прежний обработчик корректно восстанавливать на всех путях завершения.
3. **Подтверждать завершение собственного rollback.** Ввести однозначный безопасный результат/маркер успешного rollback, выдаваемый только после фактического завершения cleanup. Одной подстроки `install cancelled` для приёмки недостаточно.
4. В cancel-ветке harness сохранять результат rollback и собственного zero-residue **до** записи успешного cleanup/cancel marker и сброса контекста попытки. При незавершённом rollback или остатках фиксировать отказ. Последующая emergency cleanup должна оставаться отдельным результатом и не перезаписывать исходный cancel FAIL.
5. Сохранить общие `primary_exit`, diagnostic, per-attempt cleanup, emergency cleanup и финальный zero-residue раздельно. Не полагаться только на успешный `systemctl stop` или `Result=success` как на доказательство законченного отката.

Адресные проверки без реальной инфраструктуры:

- один SIGTERM инициирует отмену, cleanup завершается один раз;
- второй и последующие SIGTERM при уже начавшемся rollback не прерывают его, исходная отмена сохраняется;
- SIGTERM во время rollback после обычной ошибки не заменяет первоначальную причину;
- настоящая ошибка cleanup остаётся ошибкой, успешный rollback marker отсутствует;
- harness не пишет PASS при `cleanup incomplete`, неуспешном собственном zero-residue или отсутствии подтверждения rollback; отдельная emergency очистка не меняет первоначальный результат.

Сигнальные проверки выполнять в собственном дочернем процессе, с временными путями и подставными host-командами. Момент второго сигнала синхронизировать с подтверждённым входом в cleanup, без случайных задержек. Локальный опыт не объявлять полным Linux/systemd gate: собственный zero-residue после cancel без аварийного второго прохода должен быть подтверждён будущим отдельно согласованным disposable-прогоном.
