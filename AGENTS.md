# Инструкция для Codex по этому проекту

Эта папка является рабочей папкой проекта учетной системы.

Проект — учетная система Copper Resources.

Текущая фактическая архитектура — Django MVP. Основной код находится в `СИСТЕМА_MVP/backend`.

PWA-контуры находятся внутри Django и реализованы через `templates`, `static`, `views`, service worker и manifest. Отдельный Node frontend-пакет в текущей структуре проекта не считается рабочим контуром, пока он не найден и не подтвержден фактически.

Нельзя выдумывать несуществующие папки, модули, сервисы и frontend-приложения. Перед любой задачей нужно определить фактический рабочий контур, маршрут/экран и конкретные связанные файлы.

При мелких UI-задачах нельзя анализировать весь проект и нельзя расширять задачу на соседние контуры без прямого указания пользователя.

Production, база данных, `.env`, миграции, deploy, collectstatic, nginx и systemd нельзя трогать без прямого разрешения пользователя.

## Профили рабочих чатов

Если пользователь указал профиль чата, Codex должен использовать `CODEX_CHAT_ROUTING.md` и соответствующий раздел как рабочую рамку.

## Быстрый режим для мелких UI-правок

Если пользователь пишет "быстро", "мелкая правка", "поменять кнопку", "поправить интерфейс", "переставить блок" или похожую формулировку для одного экрана, Codex обязан использовать `FAST_UI_MODE.md`.

Быстрый режим применяется только к задачам типа A. Для него нужно определить рабочий контур, использовать `PROJECT_MAP.md`, не анализировать весь проект, не читать все документы `ПРОГРЕСС_ПРОЕКТА`, если задача явно локальная и понятная, и работать только с конкретным `template`/`static`/`view` нужного контура.

Для задач типа A `FAST_UI_MODE.md` имеет приоритет над общим правилом обязательного чтения всех крупных документов прогресса. Если задача явно локальная: поменять кнопку, изменить текст, поправить отступ, переставить блок, скрыть или показать элемент, поправить один экран, изменить порядок карточек или элементов, Codex не должен читать весь `ПРОГРЕСС_ПРОЕКТА`.

Для такой задачи достаточно открыть:

- `PROJECT_MAP.md`;
- `FAST_UI_MODE.md`;
- `СИСТЕМА_MVP/backend/AGENTS.md`;
- конкретные файлы рабочего контура.

## Финальный отчет по месту результата

При любой задаче Codex должен в финальном отчете явно указать:

- изменения остались только локальными или уже опубликованы;
- был ли сделан commit;
- был ли выполнен push;
- был ли выполнен deploy;
- где пользователь должен проверять результат.

## Защита от регрессий при работе в нескольких чатах

Каждый параллельный чат, который меняет код, должен работать в отдельной Git-ветке и отдельном worktree. Нельзя переносить целиком файлы из устаревшей ветки поверх актуальных файлов другого чата.

Перед объединением и публикацией изменений нужно создать итоговую release-ветку от фактического commit, указанного на production в `DEPLOYED_COMMIT`, и только затем переносить в неё отдельные проверенные commits. Deploy напрямую из функциональной ветки отдельного чата запрещён.

После объединения всех веток проверки выполняются повторно именно на итоговом release commit. Успешные проверки в исходных ветках не заменяют итоговую проверку.

Для мобильной озвучки критическими файлами считаются:

- `СИСТЕМА_MVP/backend/templates/users/driver_shift.html`;
- `СИСТЕМА_MVP/backend/templates/trips/excavator_work.html`;
- `СИСТЕМА_MVP/backend/static/js/mobile-operational-sounds-v1.js`;
- `mobile/capacitor-shell/android/app/src/main/java/ru/copperresources/mobile/`;
- `mobile/capacitor-shell/profiles/driver/res/raw/`;
- `mobile/capacitor-shell/profiles/excavator/res/raw/`.

Если итоговое изменение затрагивает любой из этих файлов либо мобильный интерфейс Водителя или Экскаваторщика, перед commit, push и deploy обязательны:

```powershell
Set-Location mobile/capacitor-shell
npm test
Set-Location ../../СИСТЕМА_MVP/backend
node --test static/js/tests/operational-fragment-runtime.test.js
& 'C:\Users\swwba\Desktop\Проект учетная система\ПОЕКТ\СИСТЕМА_MVP\.venv\Scripts\python.exe' manage.py test users
```

Тест `mobile/capacitor-shell/tests/driver-voice-wiring.test.mjs` является блокирующим контрактом. Если он не проходит, публиковать изменения нельзя: это означает, что водительские голосовые вызовы удалены или заменены старой звуковой логикой.

## Типы задач

### A — мелкая UI-правка

Работать только с конкретным `template`, связанным `static`-файлом и при необходимости с конкретным `view`, который отдает этот экран.

Для типа A запрещено трогать модели, миграции, базу данных, production, deploy, настройки инфраструктуры и соседние рабочие контуры.

Если задача типа A попадает под быстрый режим, использовать `FAST_UI_MODE.md` и не расширять ее до архитектурного анализа.

### B — логика одного рабочего контура

Сначала определить контур: водитель, машинист экскаватора, горный мастер, диспетчер, админка или отчеты. Менять только файлы этого контура и ближайшие серверные обработчики, если они действительно участвуют в задаче.

### C — backend/domain-логика

Перед изменениями найти доменные модели, сервисные правила, формы, обработчики и тесты, которые реально участвуют в процессе. Не смешивать доменную правку с визуальным редизайном.

### D — PWA/service worker/realtime

Сначала определить конкретный manifest, service worker, shell-версию и realtime-контракт. Не менять другие PWA-контуры по аналогии без отдельной проверки.

### E — инфраструктура/production

Любые изменения production, deploy, nginx, systemd, collectstatic, `.env`, базы данных и миграций требуют прямого разрешения пользователя и отдельного плана отката.

## Обязательное начало каждой новой сессии

Перед тем как отвечать на содержательные вопросы по проекту или продолжать работу, Codex должен открыть и прочитать:

1. `ПРОГРЕСС_ПРОЕКТА/00_ИНДЕКС.md`
2. `ПРОГРЕСС_ПРОЕКТА/01_ТЕКУЩЕЕ_СОСТОЯНИЕ.md`
3. При необходимости: `ПРОГРЕСС_ПРОЕКТА/02_ЖУРНАЛ_РЕШЕНИЙ.md`
4. При необходимости: `ПРОГРЕСС_ПРОЕКТА/04_БЛИЖАЙШИЕ_ЗАДАЧИ.md`

Если пользователь просит продолжить проект, планирование, архитектуру, производственный контур, отчеты, интерфейсы или базу данных, сначала восстановить контекст из этих файлов.

## Обязательное обновление прогресса

После каждого важного шага Codex должен сам обновлять файлы прогресса.

Важным шагом считается:

- принято новое архитектурное решение;
- изменился план работ;
- создан новый документ;
- уточнен состав MVP;
- описан новый модуль;
- изменились роли, отчеты, справочники или схема данных;
- появились новые вопросы без ответа;
- пользователь дал важное уточнение по процессу.

Для мелких UI-правок типа A не создавать новые progress-документы и не обновлять большие файлы прогресса, если не принято архитектурное решение, не изменился состав MVP, роли, схема данных, production/deploy или важный рабочий процесс.

Для обычной мелкой правки достаточно commit message, короткого финального отчета и явного указания, где находится результат: локально, в commit, после push или после deploy.

## Какие файлы обновлять

### `01_ТЕКУЩЕЕ_СОСТОЯНИЕ.md`

Обновлять, если изменилась общая картина проекта, текущий этап или главный фокус.

### `02_ЖУРНАЛ_РЕШЕНИЙ.md`

Обновлять, если принято важное решение. Записывать дату, решение и короткое объяснение.

### `04_БЛИЖАЙШИЕ_ЗАДАЧИ.md`

Обновлять, если поменялся ближайший план, добавились задачи или часть задач выполнена.

### Новые документы

Если тема становится большой, создавать отдельный документ в `ПРОГРЕСС_ПРОЕКТА`, например:

- `05_ПРОИЗВОДСТВЕННЫЙ_КОНТУР.md`
- `06_ОТЧЕТЫ.md`
- `07_СПРАВОЧНИКИ.md`
- `08_ИНТЕРФЕЙСЫ.md`
- `09_БАЗА_ДАННЫХ.md`
- `10_ВОПРОСЫ_БЕЗ_ОТВЕТА.md`

## Правило языка

Не держать важный смысл только в чате.

Если информация важна для продолжения проекта, она должна быть записана в файлы папки `ПРОГРЕСС_ПРОЕКТА`.
