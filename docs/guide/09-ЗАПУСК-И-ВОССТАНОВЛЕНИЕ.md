## 2. Локальный запуск (владелец)

- `START_SERVER_MVP.ps1`: находит `*_MVP/backend` (`:4-12`); берёт Python из
  `СИСТЕМА_MVP\.venv\Scripts\python.exe`, при наличии — из
  `codex-runtimes` (`:13-19`, `:40`); **выполняет `manage.py migrate`**
  (`:50-57`); запускает `runserver 127.0.0.1:8000 --noreload` с
  авто-перезапуском (`:64-67`); остановка — `STOP_SERVER_MVP.ps1` или маркер
  `.server-stop` (`:44-48`).
- Адрес по умолчанию: `http://127.0.0.1:8000/`.
- **Н:** в текущем клоне каталога `СИСТЕМА_MVP/.venv` нет; без runtime скрипт
  завершится «Python was not found» (`:26-31`). Окружение создаёт владелец.
- Ручной вариант владельца — `manage.py check` и адресные `manage.py test <app>`
  (backend `AGENTS.md:41-51`); в командном режиме это минимум для CI и
  владельца, а не право роли. Локально `copper-backend` и `copper-qa` запускают
  только фиксированный `run-trip-correction-tests.ps1` (два теста на
  изолированной PostgreSQL); полный набор L1–L4 выполняет CI по `pull_request`
  (`.github/workflows/django.yml:3-9`, `:85-227`).

## 4. APK

- Release-APK собирается только в CI: `npm ci`, `npm test`,
  `npm run android:release:<profile>`, `apksigner verify`, сверка сертификата
  (`production-deploy.yml:323-382`).
- `publish_apk` требует роста `versionCode` (`:384-400`) и сверяет манифест и
  SHA-256 (`:925-944`).
- QA-сборки side-by-side (`…driver.qa`, `…excavator.qa`) — ручной workflow
  `qa-mobile-probe.yml:3-13`, `:140-172`.
- Локальная release-сборка невозможна без секретов: подпись требует внешний
  файл через `COPPER_RELEASE_KEYSTORE_PROPERTIES`
  (`mobile/capacitor-shell/android/app/build.gradle:45-90`).
- Манифест обновления `*-update.json` формирует сборка
  (`mobile/capacitor-shell/scripts/build-android.mjs:56-95`).

Push в ветку команды `agent-team/bootstrap-20261109` quality gate **не
запускает** — её нет в списке веток `push` (`:5-8`). При этом у `pull_request`
фильтра веток нет (`:4`), поэтому PR из ветки команды гейт запускает.
Практический вывод: доказательство на своём commit получают через PR, а не
через push. Ручной запуск ночного прогона проверяет зашитую каноническую ветку
(`nightly-quality.yml:32-35`), а не выбранную.

## 6. Резерв и восстановление

- Перед заменой файлов приёмник создаёт
  `backups/code/github-<stamp>-<sha12>-<mode>-before`
  (`receiver:36`, `:3709-3711`).
- Итог успешного деплоя: `RELEASE_OK mode=… commit=… files=… backup=…`
  (`:5025`) — этот путь сохраняется в отчёте о выпуске
  (`DEPLOYMENT_WORKFLOW.md:116-128`).
- Для миграций/данных — `database.dump` (custom), `database.sha256`,
  `pg_restore --list` (`receiver:3755-3761`). Обычный `deploy` дамп не делает.
- Снимок `D:/CopperRestore/2026-11-08-laptop` — резерв ноутбука от 08.11.2026
  (215 958 файлов, 14,8 ГБ; `state/DOCUMENTATION-STATUS.md:40`). Только чтение
  и сверка, не база.

## 7. Откат

- **Автоматический:** при ошибке проверок, `collectstatic`, `nginx -t` или
  готовности приёмник восстанавливает код сам
  (`deployment/GITHUB_PRODUCTION_DEPLOY.md:21`).
- **Ручной:** режим `rollback` с `ROLLBACK` и точным каталогом `github-…-before`:
  файлы, при наличии `database.dump` — и база, затем статика и проверка
  (`GITHUB_PRODUCTION_DEPLOY.md:215-217`; `build_release.py:331-335`).
- **Откат приёмника** — отдельная процедура через revert и `update_receiver`
  (`GITHUB_PRODUCTION_DEPLOY.md:204-213`).
- **APK:** публикация без роста `versionCode` запрещена; «откат вниз» —
  отдельное решение владельца.

## 8. Release SHA и production

- HEAD `63dc191e` взят из документов; `git log`/`rev-parse` роли запрещены.
- `DEPLOYED_COMMIT` — маркер на сервере; в клоне его нет. Production не
  Git-клон: обновление идёт пакетом через приёмник
  (`DEPLOYMENT_WORKFLOW.md:50`).
- Ветка команды не release; часть режимов закреплена за
  `codex/github-production-deploy-20260916` (`production-deploy.yml:137-139`).
- Поэтому соответствие «release-ветка = production» из клона **не проверяемо**.
  Нужны серверные доказательства: `RELEASE_OK` последнего деплоя,
  `DEPLOYED_COMMIT`, какая ветка каноническая.
