## 6. Резерв и восстановление

- Перед заменой файлов приёмник создаёт
  `backups/code/github-<stamp>-<sha12>-<mode>-before`
  (`receiver:36`, `:3709-3711`).
- Итог успешного деплоя: `RELEASE_OK mode=… commit=… files=… backup=…`
  (`:5025`) — этот путь сохраняется в отчёте о выпуске
  (`DEPLOYMENT_WORKFLOW.md:116-128`).
- Для миграций/данных — `database.dump` (custom), `database.sha256`,
  `pg_restore --list` (`receiver:3755-3761`). Обычный `deploy` дамп не делает.
- Снимок `D:/CopperRestore/2026-11-08-laptop` — резерв ноутбука от 08.11.2026
  (215 958 файлов, 14,8 ГБ; `state/DOCUMENTATION-STATUS.md:40`). Только чтение
  и сверка, не база.

## 7. Откат

- **Автоматический:** при ошибке проверок, `collectstatic`, `nginx -t` или
  готовности приёмник восстанавливает код сам
  (`deployment/GITHUB_PRODUCTION_DEPLOY.md:21`).
- **Ручной:** режим `rollback` с `ROLLBACK` и точным каталогом `github-…-before`:
  файлы, при наличии `database.dump` — и база, затем статика и проверка
  (`GITHUB_PRODUCTION_DEPLOY.md:215-217`; `build_release.py:331-335`).
- **Откат приёмника** — отдельная процедура через revert и `update_receiver`
  (`GITHUB_PRODUCTION_DEPLOY.md:204-213`).
- **APK:** публикация без роста `versionCode` запрещена; «откат вниз» —
  отдельное решение владельца.

## 8. Release SHA и production

- HEAD `63dc191e` взят из документов; release SHA из истории клона не
  выводится — чтение Git такого доказательства не даёт.
- `DEPLOYED_COMMIT` — маркер на сервере; в клоне его нет. Production не
  Git-клон: обновление идёт пакетом через приёмник
  (`DEPLOYMENT_WORKFLOW.md:50`).
- Ветка команды не release; часть режимов закреплена за
  `codex/github-production-deploy-20260916` (`production-deploy.yml:137-139`).
- Поэтому соответствие «release-ветка = production» из клона **не проверяемо**.
  Нужны серверные доказательства: `RELEASE_OK` последнего деплоя,
  `DEPLOYED_COMMIT`, какая ветка каноническая.
