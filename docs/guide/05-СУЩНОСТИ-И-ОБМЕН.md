## 2. Обмен 1: оперативное состояние (server → устройство)

- Версия — одна строка `key='production'`; писатель один,
  `bump_operational_state` под `select_for_update`, версия и событие в одной
  транзакции (`core/models.py:167-207`).
- Push — только `transaction.on_commit` и только диспетчеру
  (`core/models.py:200-206`; `core/dispatcher_push.py`).
- Чтение — `GET /realtime/state/` (`core/urls.py:8`): дельта по
  `version__gt after`, лимит 50/200, скан ≤ 1000, признак `events_truncated`
  (`core/views.py:207-260`).
- Типы событий: 14 производственных + 3 доступа (`core/realtime.py:7-27`).
- **Не доходят ни до кого** 4 типа: `master_field_changed`,
  `shift_handover_closed`, `employee_access_forced_logout`,
  `employee_shift_admin_service_closed` (`core/realtime.py:7-40`). Это факт
  кода; «задумано так или недоделано» — вопрос (`EVENTS.md:23-40`).
- Клиент — опрос, не SSE: водитель/экскаваторщик 2 с, пульт/мастер 5 с,
  наблюдатель 15 с (`templates/base.html:2645-2664`; `EVENTS.md:101-114`).

## 4. Обмен 3: планшет горного мастера

`master-field/1` — `GET|POST /mining-master/tablet/field-sync/`

`master-field/2` — подпись P-256, регистрация `master.device.p256`, лимит

`assignments/field_sync.py:578-620`, `:651-673`). Клиент `master-field/2` в
репозитории **отсутствует** (T-005, T-006) — контракт есть, реализации нет.

## 5. Границы, которые нельзя смешивать

1. Realtime-опрос **не отправляет** действия — только читает состояние.
2. Офлайн-очередь **не доставляет** состояние обратно — только квитанции.
3. Push — не замена обмену: только исходящее уведомление диспетчеру.
4. Квитанция ≠ событие состояния: квитанция подтверждает приём, состояние
   приходит следующим опросом.
5. `master-field/2` ≠ `format_version 1`: разные протоколы, разные лимиты
   зависимостей (64 против 32).
