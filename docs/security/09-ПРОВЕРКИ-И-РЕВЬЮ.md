- Раздел: `docs/security/`, документ 9 из 9. Дата: 2026-11-12.
- Основание: минимальные проверки `SEC-BASELINE.md` §«Минимальные проверки»;

## 1. Десять минимальных проверок

| # | Проверка | Уровень | Что доказывает | Как | Кто |
|---|---|---|---|---|---|
| 1 | Чужой объект: `shift_id`/`trip_id`/`access_id`/вложение под ролью водителя, мастера, делопроизводителя | L2 + L5 | объектные проверки, а не только UI | подставить чужой ID в отчёт, корректировку, выгрузку, квитанцию; ожидаемо 403/404, не 200 | QA / backend |
| 2 | SSE snapshot/replay без чужих событий | L2 + L5 (только если SSE включён) | snapshot по текущим правам, `Last-Event-ID` — не право | в изолированном контуре: подключиться, сменить роль/технику, запросить replay; ожидаемо только разрешённые события | realtime + QA |
| 3 | Отзыв сессии и время закрытия доступа | L2 + стенд | старая cookie после блокировки/разблокировки; `force_end` ≤60 с | вход → сохранить cookie → блокировка → разблокировка → повтор запроса; контроль с `force_end`; замер времени | backend + QA |
| 4 | Старые офлайн-команды после отзыва и повтор без дубля | L2 PostgreSQL | идемпотентность и отказ после отзыва | повтор пакета с тем же `event_id`/payload; тот же `event_id` с другим payload; старый пакет после блокировки; сверка числа строк | backend + QA |
| 5 | Смена аккаунта не открывает чужой кэш/очередь | L5 + L6 | разделение по `accessId`, очистка при выходе | выход → вход другим сотрудником; проверить IndexedDB/localStorage/prefs/cookie; ожидаемо чужого нет | Android + владелец |
| 6 | Нет секретов и лишних ПДн в APK/Git/логах/URL/push/backup телефона | L6 + чтение | отсутствие PIN/токенов/PII в артефактах | `strings`/`apktool` по release и debug; `git grep` (только чтение); access-log nginx на `?observe=`; текст push на экране блокировки; `allowBackup` в APK | release + Android |
| 7 | Release-клиент не принимает недействительный сертификат | L6 | проверка TLS в WebView и нативном HTTP | стенд с самоподписанным/корпоративным CA; ожидаемо отказ; отдельно `http://` — блок cleartext | Android + владелец |

| 9 | Защита входа/восстановления/MFA | L2 + стенд | лимит ролевого входа, отсутствие перебора | 20 неудачных входов подряд по одному телефону с одного и с разных IP; замер задержки/блока; проверка журнала отказов; MFA для `/admin/` | backend + QA |
| 10 | Восстановление backup, история изменений, конфликты | L2 + инфраструктура | восстановимость и целостность | `pg_restore` в изолированную БД и сверка строк; проверка read-only журналов; разрешение конфликта планшета и терминального конфликта поля | data + QA |

Дополнительно к #4/#10 — **K-1**: на копии БД вызвать
`POST /system-admin/reset-shift-test-data/` с офлайн-квитанциями и без них.
Клиентское модальное подтверждение уже есть; проверяется именно **серверная**
проверка/подтверждающий ввод и область. Ожидаемо либо `ProtectedError` с понятной
ошибкой, либо удаление только в заданной области. Считать строки до/после и
проверить, что `OperationalStateVersion.version` не «замирает» при пустых
событиях.

## 2. Что можно и что нельзя

Можно:

- запускать адресные проверки по профилю роли: `manage.py check`,
  `manage.py test <app>` (группы PostgreSQL), `python -m pytest/unittest`,
  `node --test`, `npm test`; читать Git (`status`, `diff`, `log`, `show`,
  `rev-parse`, `ls-files`);
- писать рабочие файлы проверок в `D:/CopperAgentTeam/pilot/state/tmp/`;
- фиксировать «не проверено» с причиной.

Нельзя:

- выдавать SQLite-прогон за доказательство блокировок, гонок, частичных
  индексов и advisory-lock (`guide/08` §2);
- выдавать чтение кода (L0) за проверку; имя теста без вывода и версии — не
  доказательство;
- использовать debug-сборку APK как доказательство поведения приложения;
- запускать `migrate`, `collectstatic`, deploy, `runserver` в командном режиме;
- подключаться к рабочей БД или production; выводить секреты, токены, PIN и
  адреса инфраструктуры в отчёт;
- ослаблять или удалять существующие тесты, помечать падающий сценарий `skip`;
- обходить отказ прав другим инструментом или агентом.

Обязательное условие доказательства: версия (полный SHA или явная пометка
«версия из документов») + команда + вывод + число тестов/строк.

## 3. Включение в review

### 3.1. Для любого изменения доступа, API, хранения или Android

В описании изменения (паспорт/карточка) обязательны пять пунктов SEC-37:

1. какие данные затрагиваются и где хранятся (сервер, телефон, кэш);
2. какие права и объектная область проверяются, что при чужом объекте;
3. что уходит на устройство и в выгрузки;
4. какие внешние передачи (push, Firebase, файлы) появляются;
5. какие злоупотребления рассмотрены и чем ограничены.

Без этих пунктов изменение не принимается — это процессное требование, не
«галочка».

### 3.2. Чек-лист reviewer

1. Три статуса разделены: требование, реализация, проверка; код не выдан за
   решение владельца.
2. Есть `файл:строка` и версия; «тест существует» не равно «тест проходит».
3. Для новых/изменённых прав есть тест «чужой объект → 403/404»; матрица
   обновлена.
4. Миграции, настройки, `.env`, deploy и `mobile/**` не изменены вне карточки и
   разрешения.
5. В диффе нет секретов, PIN, токенов и личных данных в логах/URL.
6. Лимиты и отказы описаны; новое поле не расширяет передачу на устройство без
   необходимости.
7. Если затронут SSE — есть доказательства snapshot/replay/revoke или явное
   «не включаем».
8. Если затронут Android — приложены результаты по APK/устройству или честное
   «не проверено».
9. `git status --short` и `git diff` подтверждают границы; untracked проверены
   отдельно.
10. Автор не принимает свою работу; PASS без доказательств не ставится.

### 3.3. Блокирующие пункты

- утечка PIN/секрета, обход авторизации, встроенный секрет в APK,
  несанкционированное изменение данных — блокируют выпуск до исправления или
  формального ограничения риска (SEC-39);
- критический пункт без владельца, срока и проверки не может быть закрыт
  «документально»;
- расхождение «код разрешает больше, чем документ» (manager, планшет, сессии)
  требует решения владельца, а не молчаливого закрепления.

### 3.4. Для документационной задачи

Проверка — `guide/08` §6: существование ссылок, сверка `файл:строка`,
разделение статусов, границы diff, отсутствие ложных прогонов, локальность
изменений. «Файл создан» и «все разделы есть» доказательством не считаются.
