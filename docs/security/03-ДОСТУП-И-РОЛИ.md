## 1.1. Сессии и отзыв

| Факт | Значение | Доказательство |
|---|---|---|
| Личная сессия ролевого приложения | **365 дней**, продлевается автоматически | `config/settings.py:170-172`; `users/session_device.py:14-27`, `:42-49`; `users/middleware.py:152-194` |
| Повторный вход в тот же доступ | гасит прежнюю сессию того же доступа | `users/active_role.py:268-270` |
| Вход в другую роль | первую сессию **не** гасит (несколько ролей = несколько сессий) | `users/active_role.py:117-121` |
| Неактивная роль | изменяющие запросы → 409, чтение разрешено | `users/middleware.py:230-251` |
| Настоящий отзыв | `force_end_access_sessions`: удаляет сессии, двигает поколение, шлёт событие; только админ и с причиной | `users/live_monitor.py:664-692`; `users/live_monitor_views.py:389-428` |
| Блокировка/деактивация | меняют `status`/`is_active`, но **не вызывают** `force_end` | `users/views.py:3740-3749` |
| Разблокировка | возвращает `ACTIVATED`/`is_active=True`, **не меняя** `last_login_at` → прежняя cookie снова действует до года | `users/views.py:3750-3766` |
| `deputy`-контур | не требует `status=ACTIVATED` и не сверяет поколение сессии | `assignments/deputy_views.py:322-338` |
| Выход | только `session.flush()` текущей сессии; сервер кэш устройства не чистит | `users/views.py:1849-1851` |

Следствие: «≤60 с» для отзыва обеспечено только ручным `force_end`; блокировка и
разблокировка оставляют украденную cookie рабочей. Прогоном не проверялось —
сценарий в `security/09` §1.

## 4. Расхождения, которые нельзя потерять

1. **`manager` пишет на пульте (R-2).** Чтение по роли, но 4 мутирующие команды
   проходят при **чужой** открытой смене диспетчера; текст отчёта называет
   руководителя «только просмотр» (`templates/reports/dispatcher_shift_report.html:277-279`).
   Документа, разрешающего запись, не найдено — Q-01/C4.
2. **«Своя смена» на пульте не требуется.** `get_active_dispatcher_shift` берёт
   первую открытую чужую смену для не-диспетчера
   (`trips/dispatcher_header.py:73-82`).
3. **Мастер с планшета закрывает чужую смену (R-3/C10).** Право в документах не
   найдено, поведение закреплено тестом (`trips/test_tablet_control.py:226`).
4. **Несколько ролей = независимые сессии (R-1).** Решение 24.07.2026 говорит
   «одна активная роль», код реализует отдельные сессии
   (`users/active_role.py:117-121`; `guide/03` §2).
5. **Портал — общая читаемая поверхность.** Любой активированный доступ с
   телефоном и PIN входит в портал; сотрудник видит каталог активных сотрудников
   и фото при наличии портальной сессии (`portal/views.py:946-949`).
6. **Две админ-поверхности.** Ролевой `/system-admin/` (свой guard) и Django
   `/admin/` (отдельные auth-пользователи, свои права, без MFA и без
   `AdminActionLog`) — `config/urls.py:34`; `users/admin.py:171-229`.
7. **`reset-shift-test-data` (K-1).** Один POST удаляет производственные факты.
   Подтверждение в интерфейсе **есть**, но только клиентское: модальное окно с
   задержкой 3 с (`templates/users/system_admin_dashboard.html:115-120`;
   `templates/base.html:2260-2289`); прямой POST под сессией админа (с CSRF)
   удаляет всё. Нет серверной проверки/подтверждающего ввода, области, QA-флага
   и проверки истории. При наличии офлайн-квитанций удаление падает
   `ProtectedError` (`core/models.py:89-96`), то есть «или потеря данных, или
   500» — в зависимости от данных. Поведение закреплено тестом
   (`users/tests.py:855-934`).
8. **Аварийное закрытие смены администратором.** Отдельное решение владельца от
   11.11.2026 (не SEC-требование): причина обязательна, видны имя и причина.
   Реализация частичная: причина через `control` не запрашивается, `closed_by`
   указывает на водителя (`guide/03` §3).
9. **PIN — и секрет, и идентификатор.** 6 цифр без лимита ролевого входа
   (`users/views.py:1422-1449`); PIN пишется в журнал (`users/views.py:3332-3341`,
   `:3574`) и ищется в Django-admin (`users/admin.py:174`); первичный код
   генерируется уникальным по всей таблице (`users/views.py:846-850`) — то есть
   почти глобальный идентификатор человека. На экране журнала PIN виден
   (`templates/users/system_admin_logs.html:131-135`).
10. **Сессия и отзыв.** 365 дней (`config/settings.py:170-172`); блокировка не
    отзывает (`users/views.py:3740-3749`), разблокировка возвращает старую cookie
    (`:3750-3766`); `deputy` не сверяет статус и поколение
    (`assignments/deputy_views.py:322-338`); `reclaim-session` возвращает сессию
    без PIN (`users/views.py:1682-1724`).
11. **Выгрузки без следа и кэша-запрета.** Ни лимита объёма/частоты, ни записи
    факта, ни `Cache-Control: no-store` (`users/views.py:4013-4119`, `:916-924`);
    выгрузка доступов PIN не содержит — это смягчает риск (`:4054-4063`).

## 5. Что не проверено

1. Фактические ответы 403/409/302/401 в браузере и на устройстве — не
   наблюдались.
2. Полная инвентаризация guard'ов по всем вьюхам не выполнялась; матрица
   опирается на `guide/03`, `T-018-backend-1.md` §2 и выборочное чтение. Перечень
   точек — не доказательство полноты.
3. Права в production не сверялись (release SHA нет).
4. Что именно удаляет `reset-shift-test-data` на реальных данных и сколько строк
   — не запускалось (см. `security/09` §1).
5. Тесты «чужой объект → отказ» для каждой роли отсутствуют; существование
   отдельных тестов не означает покрытия матрицы.
6. Поведение старой cookie после «блокировка → разблокировка» выведено из кода,
   но не воспроизведено; 409/403 не наблюдались.
