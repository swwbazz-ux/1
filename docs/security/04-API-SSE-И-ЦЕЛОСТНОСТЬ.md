## 2. Проверка объекта (IDOR) и область

Что проверяется по коду:

- полевые экраны фильтруют по `employee=access.employee` + открытая смена —
  `trips/views.py:4366`, `:4381`, `:4396`, `:4633`, `:4739`, `:6350`;
  `users/views.py:6099-6253`;
- корректировка отчёта требует роль и вхождение рейса в выбранную смену —
  `reports/views.py:3548-3564`, `:4857-4872`;
- пульт повторно проверяет «свежий» доступ и поколение под блокировкой —
  `trips/dispatcher_guards.py:90-136`;
- офлайн-событие проверяет принадлежность смены сотруднику и технике —
  `core/offline_sync.py:1084-1106`.

Чего нет:

1. Единой модели прав: наборы кодов ролей литеральны (`reports/views.py:415`;
   `trips/dispatcher_guards.py:100-102`). Расширение прав ничем не затруднено и
   не требует теста процедурно.
2. `deputy_access_from_request` фильтрует `BLOCKED`/`DEACTIVATED`, но **не
   требует** `status=ACTIVATED` и **не сверяет поколение сессии**
   (`assignments/deputy_views.py:322-338`): доступ в `not_activated` или старая
   сессия продолжают открывать расстановку.
3. Разделения по участку нет: `PORTAL_EMPLOYEE_SCOPE_PROVIDER = ''`
   (`config/settings.py:395-398`).
4. Полной инвентаризации «вьюха → проверка» не было. Список выше — выборочные
   точки, а не доказательство полноты. Тестов «чужой `shift_id`/`trip_id`/
   `access_id` → 403/404» по всем ролям нет — сценарий в `security/09` §1.

## 4. SSE: отделить продукт от изолированного контура

**В основном checkout SSE нет.** Точка входа — только WSGI
(`config/wsgi.py:16`); `config/asgi.py` — стандартная заглушка; в `core/` нет
`sse.py`, `snapshot.py`, `sse_wakeup.py`, `voice_state.py`; маршруты — только
опрос и офлайн (`core/urls.py:6-9`). Redis мобильному клиенту не выдаётся:
обращений к Redis в `core/views.py` нет.

| Артефакт | Где | Что это значит |
|---|---|---|
| SSE-ядро (`core/sse.py`, `snapshot.py`, `sse_wakeup.py`), `test_sse_pilot.py` | ветка T-016 `t-016-sse-live-stand`, tip `eb1b5bad` по документам | **не слито и не отправлено**; продуктовой гарантии нет |
| 23 файла SSE-переноса, `tools/sse_pilot/**` | `state/tmp/sse-work-20261112` (копия без `.git`) | не продукт |
| Примеры инфраструктуры `deployment/sse-pilot/*.example` | там же | примеры, не установленная конфигурация |
| Локальный стенд (PostgreSQL/Redis/uvicorn, loopback) | `state/handoffs/SSE-STAND-20261112.md` | одноразовый стенд, в checkout не входит |

Поэтому SEC-22 в продукте **не применимо** до решения включать SSE; SEC-21
обеспечена по чтению кода только для опроса (проверка не выполнялась). Если SSE
будет включаться, до выпуска проверить:

1. snapshot строится по **текущим** правам, а не по сохранённым;
2. `Last-Event-ID` — не право: replay отдаёт только разрешённые события;
3. отзыв доступа закрывает уже открытый поток (цель ≤60 с) — не измерялось;
4. переподключение требует действующей сессии;
5. Redis и служебные каналы недоступны мобильному клиенту (loopback/ACL);
6. утечка событий при смене роли/техники и при `force_end`.

Ни один из шести пунктов не проверен: контур изолирован, прогонов не было.

## 6. Конкуренция и целостность

| Механизм | Факт | Доказательство |
|---|---|---|
| Версия состояния | одна строка `OperationalState(key='production')`, единственный писатель под `select_for_update`, версия и событие в одной транзакции | `core/models.py:5-44`, `:167-207` |
| Идемпотентность офлайна | `event_id` unique + `(actor, role_code, device_id, sequence)` unique + advisory-lock из `core.db_locks` + fingerprint | `core/models.py:64`, `:117-122`; `core/offline_sync.py:14`, `:3773-3798` |
| Повтор с другим содержимым | конфликт-запись, не дубль | `core/models.py:132-164` |
| Планшет | FIFO по `sequence`, `conflict.resolve` обходит FIFO | `assignments/field_sync.py:578-620`, `:651-673` |
| Авторство | `AdminActionLog`, `DispatcherActionLog`, `ShiftReadingCorrection`, `AdminActionLog` в Django-admin read-only | `users/models.py:798-826`; `trips/models.py:318-326`; `users/admin.py:209-229` |
| Таймауты БД | `statement_timeout`/`lock_timeout` в production-настройках **не заданы** | `config/settings.py:197-215`; только в тестах `settlement/test_control.py:2737-2738` |
| Ручная блокировка таблицы | `LOCK TABLE … SHARE MODE NOWAIT` под внутренними именами | `shifts/services.py:560` |

Риски целостности:

1. **Дедлок/долгая блокировка** на глобальной строке состояния и `LOCK TABLE` без
   таймаутов (T-11/R-9). Проверять только на PostgreSQL, SQLite это не покажет.
2. **Массовый сброс** `reset-shift-test-data` удаляет события/рейсы/простои/
   журналы. Клиентское подтверждение есть (модальное, задержка 3 с;
   `templates/users/system_admin_dashboard.html:115-120`,
   `templates/base.html:2260-2289`), но серверной проверки/ввода, области и
   QA-флага нет; при наличии офлайн-квитанций падает `ProtectedError`
   (`users/views.py:1964-1998`; `core/models.py:89-96`) — «или потеря истории,
   или 500».
3. **Неполное авторство:** автор закрытия простоя не сохраняется
   (`downtimes/models.py:70-107`); `AdminConflict` без автора
   (`users/models.py:828-853`); тип `report_source_correction` отсутствует в enum.
4. **Порядок задаёт телефон:** `occurred_at` «в прошлом» не переписывается
   (`core/offline_sync.py:970-971`), хотя при явном расхождении время заменяется
   серверным (`:979-994`). Это осознанное решение, но означает, что порядок в
   отчёте может отличаться от серверного.

## 7. Что не проверено

- Ни одного HTTP-кода, ни одной гонки: 401/403/409/413 не наблюдались.
- PostgreSQL: `select_for_update`, advisory-lock, уникальные индексы, дедлоки —
  не воспроизводились; SQLite доказательством не считается (`guide/08` §2).
- Браузер, устройство, IndexedDB, WebView, трафик и нагрузка.
- Production-nginx (`limit_req`, `client_max_body_size`, закрытие `/media/`),
  `.env`, фактические журналы.
- SSE-сценарии snapshot/replay/revoke не выполнялись: контур не слит.
